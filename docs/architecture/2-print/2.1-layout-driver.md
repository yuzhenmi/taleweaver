# 2.1 — `layout-driver/` and `nav/`

These two `@taleweaver/print` modules are the **print backend** half of the
core↔backend decouple. Core's editor reducer is geometry-free (see
[`1-core/1.5-editor.md`](../1-core/1.5-editor.md)): it owns the document edit
and records WHAT changed, but runs no render/cascade/layout pass and holds no
layout tree, and has no geometric-navigation actions. This backend owns both
sides of that seam — the **layout-driver** rebuilds the geometry from core's
state, and the **NavIntent resolver** turns a navigation keystroke into the
geometry-free `EditorAction` core should run. The controller composes them; the
layout-driver (`createLayoutDriver` / `LayoutConfig` / `LayoutDriver`) is also on
the `@taleweaver/print` package barrel so a host can build a layout tree from a
core `State` directly, while the NavIntent resolver stays controller-internal.

## The seam

```
keystroke ─► key-handler ─► KeyResult = EditorAction | NavIntent
                                 │
              ┌──────────────────┴───────────────────┐
              │ NavIntent                             │ EditorAction
              ▼                                       │
   nav.resolveNavIntent(intent, editorState,         │
       layoutTree, measurer, componentRegistry)      │
              │  reads geometry, returns              │
              ▼                                       │
        SET_SELECTION / DELETE_RANGE ─────────────────┤
                                                      ▼
                                  host dispatch ─► core.reduceEditor
                                                      │
                                                      ▼
                            new EditorState (.state, .lastDirtyIds)
                                                      │
                                                      ▼
              layout-driver.rebuild(state, containerWidth, lastDirtyIds)
                                                      │
                                                      ▼
                                       LayoutBox | VirtualLayoutTree
                                  (painted, and queried for cursor geometry)
```

So core never touches geometry: every keystroke flows *out* to the backend for
its geometric meaning (NavIntent) or stays a pure document action, and the
resulting state flows *back* to the backend for layout (layout-driver). The
geometry queries (`resolvePixelPosition`, `resolvePositionFromPixel`,
`computeSelectionRects`, `moveToLine`, `moveToLineBoundary`) are `@taleweaver/print`
functions the backend calls against the DRIVER-built tree.

## `layout-driver/`

`createLayoutDriver(layoutConfig: LayoutConfig): LayoutDriver` returns an object
whose single method `rebuild(state, containerWidth, lastDirtyIds)` runs one
render → cascade → layout cycle and returns the `LayoutBox | VirtualLayoutTree`.
It is a relocation of the render→cascade→layout pipeline that used to live inside
core's `rebuildTrees` / `createEditorStateFromState`.

```ts
interface LayoutConfig {
  readonly measurer: TextShaper | TextMeasurer;
  readonly hyphenator?: Hyphenator;
  readonly pageConfig?: PageConfig;
  readonly componentRegistry: ComponentRegistry;
  readonly attrRegistry: AttrRegistry;
}

interface LayoutDriver {
  rebuild(
    state: State,
    containerWidth: number,
    lastDirtyIds: ReadonlySet<BlockId> | null,
  ): LayoutBox | VirtualLayoutTree;
}
```

`LayoutConfig` is where the print-mechanics capabilities `measurer` /
`hyphenator` live — they LEFT core's `EditorConfig` in the decouple, so core's
reducer never sees them. `pageConfig` / `componentRegistry` / `attrRegistry`
ALSO remain on core's `EditorConfig` (the reducer's editing ops consult them) and
appear here because the render/cascade/layout passes the driver runs are
parameterized by them; the host supplies the SAME instances to both configs.

**Incremental reuse via retained trees.** The driver RETAINS the prior cycle's
six trees as closure state: the render output, the main / template-body /
embed-body cascaded trees, and the layout tree. When `rebuild` is called with a
non-null `lastDirtyIds` AND a prior cycle exists, each stage runs its incremental
variant (`render` with prev/dirtyIds, `cascadePassIncremental`,
`cascadeTemplateContents` / `cascadeEmbedContents` with prev maps,
`layoutTreeIncremental` with prev cascaded + prev layout), reusing unchanged
subtrees by reference. `lastDirtyIds === null` means a FULL rebuild (the initial
build, or a container-width resize) — it still reuses the prior cascaded tree as
the layout `prev` when one exists, matching the legacy full-build-from-cascade.

**FN-6.4 restart-per-page numbering second pass.** When the document footnote
policy is restart-per-page AND the doc has footnotes AND the layout is the
virtualized tree (the only path that surfaces `footnoteAnchorPages`), the driver
recomputes the per-page-correct footnote numbers from the layout's anchor→page
map and re-renders only the changed marker host blocks, looping until the page
assignment converges (capped, with graceful degradation on a glyph-width-coupled
limit cycle). Every other case is a no-op returning the first cycle's result. The
loop reuses `renderCascadeLayout` with a `footnoteNumbersOverride`, so the
feedback pass is just another incremental cycle.

## `nav/` — the NavIntent resolver

The seven `NavIntent` variants are EXACTLY the geometric editor handlers lifted
out of core:

```ts
type NavIntent =
  | { type: "MOVE_CURSOR"; direction: "forward" | "backward" }
  | { type: "EXPAND_SELECTION"; direction: "forward" | "backward" }
  | { type: "MOVE_LINE"; direction: "up" | "down" }
  | { type: "EXPAND_LINE"; direction: "up" | "down" }
  | { type: "MOVE_LINE_BOUNDARY"; boundary: "start" | "end" }
  | { type: "EXPAND_LINE_BOUNDARY"; boundary: "start" | "end" }
  | { type: "DELETE_LINE" };

function resolveNavIntent(
  intent: NavIntent,
  editor: EditorState,
  layoutTree: LayoutBox | VirtualLayoutTree,
  measurer: TextShaper | TextMeasurer,
  componentRegistry: ComponentRegistry,
): EditorAction | null;
```

`resolveNavIntent` reads the driver-built `layoutTree` + `measurer` (the
geometry) and applies the same rules the lifted handlers did — reusing core's
pure `cursor/` primitives (`moveToLine`, `moveToLineBoundary`,
`resolveLineForPosition`, `buildLineBidiView`, `moveVisually`,
`buildBlockGraphemeStepper`, `moveByCharacter`, `expandSelection`) plus the
barrel-exported `seedAnchorAffinity` from `editor/`. It RETURNS the geometry-free
`EditorAction` core should dispatch:

- move / expand intents → a `SET_SELECTION` threading the resolved
  `caretAffinity` / `anchorAffinity` / `targetX` (these are the only path that
  carries those — `SET_SELECTION` is core's sole action that manages them);
- `DELETE_LINE` → a `DELETE_RANGE` carrying the resolved line span (or the
  selection span for a non-collapsed delete);
- `null` for a no-op (a line move off the document edge, a defensive null line,
  an object-nav at a boundary, a degenerate line-delete) — matching each lifted
  handler's `return editor;` short-circuit.

**Object selection** is handled here too: `resolveNavIntent` consults
`isObjectSelection` (via the threaded `componentRegistry`) and resolves an arrow
on a selected atomic-leaf to a `SET_SELECTION` beside the object
(`objectMoveSelection`), or `DELETE_LINE` on one to `null`.

Behavior is byte-for-byte identical to the pre-decouple core handlers — the only
difference is the indirection: read `layoutTree` / `measurer` parameters instead
of `editor.layoutTree` / `config.measurer`, and RETURN a dispatched action
instead of mutating `EditorState`.

## `key-handler` integration

`mapKeyEvent(event, ctx?) → KeyResult | null` returns
`KeyResult = EditorAction | NavIntent`: the geometric keys (Arrow / Home / End /
Cmd-Backspace) map to a `NavIntent`, every other key to a core `EditorAction`.
The `isNavIntent(result): result is NavIntent` guard discriminates the two; the
controller routes a `NavIntent` through `resolveNavIntent` (dispatching its
returned action, if any) and an `EditorAction` straight to dispatch. See
[`2.8-editor-controller.md`](./2.8-editor-controller.md).
