# 2.2.1 — Block Formatting Context (BFC)

The BFC lays out an element whose `display` is `block`-like (`block`,
`flow-root`, the document root, `inline-block`'s inner content). It
arranges children vertically along the block axis and emits a `BlockBox`.

## Responsibilities

- **Stack children along the block axis.** Walk children in document
  order; place each at the next available block offset, advancing by the
  child's logical `blockSize` (not the physical `height`). The BFC reads no
  physical coordinate, so the same algorithm is correct under every writing
  mode — the writing mode lives entirely in each box factory's
  logical→physical mapping (plus the `vertical-rl` physicalize pass; see
  [`overview.md`](./overview.md#logical-axis-discipline-and-the-vertical-rl-physicalize-pass)).
  For `horizontal-tb` this is top-to-bottom; for the vertical modes the
  block axis runs horizontally.

- **Margin collapsing.** Adjacent block siblings collapse their
  block-axis margins (top of one with bottom of the prior). Empty blocks
  collapse with both surroundings. Parent/first-child collapsing applies
  when the parent has no top boundary (no padding, no border).

- **Inline-axis margins.** An in-flow block child honors its
  `marginInlineStart` / `marginInlineEnd`: it is positioned at logical
  inline offset `paddingInlineStart + marginInlineStart` and its content
  width is reduced by both inline margins (the child resolves into the
  narrowed space; its descendants stay child-relative). Inline-axis margins
  do NOT collapse (only the block axis does). This is what `INDENT`/`OUTDENT`
  drives. The offset is logical, so `logicalToPhysical` mirrors it under RTL
  (an inline-start margin sits on the physical right). List markers shift
  with the indented content so they stay glued to the item.

- **Floats.** When a child's `float` is `inline-start` or `inline-end`,
  ask the BFC's `FloatEnvironment` to place it. The float doesn't
  advance the block offset; it shapes the available width at subsequent
  block offsets where lines and other content flow around it. When a
  child has `clear` set, query the float environment for clearance and
  shift the block offset down accordingly. **Images participate via this same
  mechanic:** the `image` component bakes a logical `float` onto the image
  ElementBox from its `wrap` attr (the component-set seam — see
  [`1.2-render.md`](../../1-core/1.2-render.md) "Image wrap"), so a wrapped image is a
  document-root float sibling and the following paragraph's text narrows around
  it with no image-specific layout code. A non-wrapped (`break`) image carries no
  `float` and stays in the block flow.

  A float's **box geometry agrees with its float-exclusion region**: when the
  float carries an explicit logical `blockSize` (e.g. a sized image), the BFC
  applies that block-size to the emitted box itself — preserving the box's content
  children — rather than letting the box report only its content-derived size. So
  the float's PAINTED / hit-test rect matches the inline-size × block-size
  exclusion the `FloatEnvironment` reserves. (The same explicit-block-size
  application runs for an in-flow block with an explicit `blockSize`; see step 4
  of the algorithm.)

  Across page fragments, the BFC expresses every float-environment interaction
  (`placeFloat` / `clearance` / `lowestFloatBlockEdge` enclosure) in a
  **document-cumulative flow frame** — `blockFlowBase = pageFlowBase +
  nestedOrigin` — rather than page-local offsets, so a float narrows the lines
  beside it on the page it actually sits on instead of being displaced ~1 page.
  Box-render positions stay page-relative via a localized `− blockFlowBase`
  translation. See [`2.3-pagination.md`](../2.3-pagination.md) "Coherent float
  coordinate frame".

  **Cross-page float pushing.** A float that does not fit the remaining
  block-space on the current page is PUSHED (deferred as a whole box) to the top
  of the next page, while in-flow content keeps flowing on the current page —
  matching CSS Fragmentation float-pushing and Word/Pages/Google Docs (a figure
  near a page bottom moves to the next page; the text reflows). The fit check
  uses the float's ACTUAL landing offset (`FloatEnvironment.peekPlaceFloat` — a
  non-mutating run of the same push-below loop as `placeFloat`, since a float can
  be pushed down past prior same-side floats), NOT the requested offset: if
  `landingOffset + floatBlockSize` exceeds the page and the page is non-empty, the
  BFC records the float on the page-scoped `FloatEnvironment` pushed-floats channel
  (`pushFloat({node, side})`) and continues the in-flow loop without placing it. On
  an EMPTY page the float is placed anyway (overflow) — the termination bound, so a
  float taller than a whole page overflows rather than pushing forever. The page
  loop carries the pushed floats to the next page, where they are placed at the
  content top (active shadows seeded first, then pushed floats via `placeFloat` in
  source order, re-laid-out at the requested offset). The float never splits its
  own content across pages (pushing, not float-content fragmentation). Pushing is
  scoped to the virtualized fast-path (`FragmentationContext.enableFloatPushing`,
  set for single-column footnote-free float docs); the legacy `paginateRoot` path
  (float + multi-column / footnote / absolute) retains float overflow pending its
  virtualization. See [`2.3-pagination.md`](../2.3-pagination.md) "Cross-page
  float carry".

- **List markers.** Children with `display: list-item` get an associated
  `MarkerBox` emitted at the block-start of the item's first line. **The BFC
  COUNTS nothing** — the marker text is the render-baked `markerText` on the
  child's cascaded `ComputedStyle` (`childCs.markerText`), produced upstream
  by the render-time numbering service and the `list-item` component (see
  [`1.2-render.md`](../../1-core/1.2-render.md) "Numbering (list markers)"). The BFC
  only READS it. There is no per-BFC-level ordered-list counter, no
  consecutive-run reset, and no seed-on-resume replay — all of that
  (numbering, restart, the consecutive-run rule, the explicit-override
  resolution) is resolved at render time before layout sees the box. The old
  `layout/list-counter.ts` and its counting/seed-replay machinery were
  deleted.

  - **Marker presence.** A `display: list-item` child emits a `MarkerBox`
    iff `childCs.markerText` is a non-empty string. A list-item the numbering
    service did not number (no baked `markerText`) renders with no marker. An
    ordered marker arrives already formatted with its trailing `"."`; a
    bullet arrives as its glyph — the BFC paints the string verbatim.

  - **Marker emitted on the page where the item PLACES CONTENT (deferred push,
    #501).** The `MarkerBox` is BUILT before the item's content is laid out (so
    the auto-widen gutter math runs), but it is NOT appended to `layoutChildren`
    until the item actually places content on the CURRENT fragment — it is pushed
    immediately BEFORE the item's content box at every placement site (the
    normal end-of-iteration placement, and each C.6 overflow / partial-break /
    whole-block-overflow site). A fragment where the item places ZERO content
    (it overflowed past the fragment's remaining space) emits NO marker and never
    orphans one. This also keeps the marker out of `layoutChildren.length`, so a
    first-child list-item that overflows an empty fragment is correctly seen as
    "alone on an empty fragment" by the C.6 overflow rule.

  - **Split-item marker suppression (#431) + degenerate-resume exception (#501).**
    A list-item whose content splits MID-CONTENT across a page break emits its
    marker only on the page where it STARTS — NOT on both the origin-page tail
    and the resume-page head. The mid-content continuation is identified by
    `i === startIndex && firstChildResumeToken !== null &&
    !isResumeFromDegenerate(firstChildResumeToken)` (the first child of the
    resumed BFC, carrying a NON-NULL, NON-degenerate resume token). A
    **degenerate** resume token (`{ ifc, resumeAtLine: 0 }` or a null/child-0
    chain — `isResumeFromDegenerate`) means the prior page placed ZERO content
    for this item, so THIS fragment is where the item actually starts and MUST
    show its marker (#501). Only a genuine mid-content continuation
    (`resumeAtLine > 0`) suppresses it. On the suppressed continuation the
    ordered-list counter still advances UNCONDITIONALLY (the seed counts
    `[0, startIndex)`, EXCLUDING the resuming item, so subsequent items number
    correctly) but NO `MarkerBox` is created. The suppression covers both
    auto-counter and explicit-`markerText` items (and bullets). The auto-widen
    gutter computation still runs on the continuation so its content keeps the
    same content edge as the origin (the wrapped tail aligns with the head);
    only the marker box is suppressed. Google-Docs parity: a split list-item's
    mid-content continuation has no marker, but an item that simply got pushed
    whole to the next page shows its marker there.

  In the word-processor leaf model, the marker gutter is the list-item's OWN
  `paddingInlineStart`; an `outside` marker hangs into that gutter at
  `contentEdge − markerInlineSize − markerGap` (an `inside` marker sits AT
  the content edge). When the marker is WIDER than the item's
  `paddingInlineStart` (`markerInlineSize + markerGap > paddingInlineStart`),
  the effective indent **auto-widens** to `markerInlineSize + markerGap`, so
  the marker lands flush at the item's border edge instead of overflowing left
  of it, and the content shifts right to match (Google Docs parity). The gate
  is the item's OWN padding — not its absolute content edge — so an indented
  item (nonzero `marginInlineStart`) widens correctly rather than letting the
  marker hang into preceding/sibling content. The child is laid out against
  the widened padding only when widening fires; the non-widened path is
  unchanged.

- **Anonymous block-runs for mixed content.** When a block element
  contains a mix of block and inline children (paragraphs and runs of
  bare text adjacent to them), the BFC groups inline children into
  anonymous runs and dispatches each through the IFC, splicing the
  resulting lines back in among the block siblings.

- **Subtree reuse.** Before laying out a block, consult the
  `LayoutBoxCache` from the prior layout pass: if the render node is
  equivalent to the cached entry's, the prior `BlockBox` returns by
  reference and no further work happens for this subtree.

- **Fragmentation entry.** When pagination is enabled, the BFC reports
  per-block break-eligibility (`break-before`, `break-after`,
  `break-inside`, widows, orphans) to the fragmenter, which decides
  where pages split.

## Inputs and outputs

The BFC's entry function takes:

- The element's render node (with `ComputedStyle` and children).
- The block offset where layout starts (relative to the parent).
- The inline offset where layout starts.
- A `LayoutContext` carrying writing-mode, direction, containing-inline-size,
  the float environment, the previous-pass cache, and the shaper.

It returns a `BlockBox` containing positioned children
(`BlockBox`, `LineBox`, `TableBox`, `MarkerBox`).

## Float environment lifetime

A box that establishes a new BFC (root, `flow-root`, `inline-block`,
floats themselves, table cells, `overflow: hidden|auto`) gets a fresh
`FloatEnvironment` from `makeChildContext`. A box that does *not*
establish a new BFC inherits its parent's float environment, so its
floats rise to the nearest BFC ancestor and shape that ancestor's flow.
The flag `LayoutContext.isBFCRoot` distinguishes the two cases.

## Out-of-flow absolute positioning

`position: absolute` children are handled with a two-pass scheme that
mirrors the float precedent (see [`2.4-positioning.md`](../2.4-positioning.md)
for the full positioning model). The BFC owns both passes.

**First pass (in the in-flow child loop).** When a child's `cs.position` is
`absolute`, the BFC takes a dedicated branch BESIDE the float branch:
it skips ALL in-flow placement — no `childBlockOffset` advance, no margin
collapse, no `prevMarginBlockEnd` update — and instead REGISTERS the child into
the nearest absolute containing block's (abc's) pending list
(`ctx.absoluteContainingBlock.pending.register(...)`), then `continue`s, exactly
like a float. What it registers is a `PendingAbsChild`: the render node, its
computed + used style, and its STATIC position (where the in-flow algorithm
would have placed it — `childInlineStart` on the inline axis, `childBlockOffset`
on the block axis, both pre-advance), expressed in the abc's coordinate frame by
adding `ctx.originFromAbc` (zero for a direct child of the establishing box; the
accumulated intervening offsets for a deeper in-flow descendant). The static
position is the `auto`-inset fallback.

The abc and the pending sink ride on `LayoutContext`
(`absoluteContainingBlock` + `ownsAbsoluteContainingBlock` + `originFromAbc`);
`makeChildContext` gives a box that establishes an abc
(`establishesAbsoluteContainingBlock(cs)` = `position ∈ {relative, absolute}`
OR a non-empty `transform`) a FRESH abc with a fresh pending list, so
abs-pos descendants rise to the nearest establishing ancestor — the same
inherit-until-a-fresh-root discipline as `floatEnv`. See `layout-context.ts` /
`abs-pos-context.ts`.

**Second pass (post-loop, the box that OWNS its abc).** After the in-flow walk
completes, a box with `ctx.ownsAbsoluteContainingBlock` drains its pending list
(beside the float `lowestFloatBlockEdge()` pass — both deferred-out-of-flow
resolutions happen here, once the box's own size is known). It builds the
authoritative abc frame from its OWN resolved locals (content inline-size, total
block-size, padding origin), then for each pending child:

- resolves inline-axis insets against `abc.inlineSize` and block-axis insets
  against the abc's block percent-base (a px inset always applies; a percent
  resolves only against a DEFINITE block size, else collapses to `auto` per CSS
  §10.5 — an auto-height abc carries an `"indefinite"` block size);
- resolves the used inline/block size (`auto` with BOTH insets set fills the gap
  `abc.size − insetStart − insetEnd`; otherwise shrink-to-content via the same
  intrinsic-sizing path floats / inline-blocks use);
- resolves the position (inset-start wins; else inset-end anchors the end edge;
  else the captured static position);
- lays the child out as its OWN BFC root (`position: absolute` triggers
  `establishesNewBFC`) at the resolved position.

The laid-out boxes are attached to `box.absoluteChildren` (an optional
`readonly LayoutBox[]` on `LayoutBoxBase`, omitted when none). They are OUT of
`children`. The painter recurses `box.absoluteChildren` with the same parent
origin (incl. any `relativeOffset`) it uses for `children`, and
`cursor/line-flatten.ts` `collectLineBoxes` likewise descends them so abs-pos
content enters the flat `LineIndex` and stays reachable by hit-test / cursor /
selection / line-navigation.

**Paginated-fragmentation v1 follow-up.** The second pass runs ONLY on a box's
full, non-fragmented return. `buildPartialResult` (the fragmentation-break exit)
returns a partial box WITHOUT running the second pass, so abs children registered
before a break stay undrained in the pending list and are abandoned. Correct
behavior would drain the abs children whose static position falls in each placed
fragment onto that fragment; this is a named v1 follow-up, documented at the
omission site. Single-page abs-pos is complete.

## Margin-collapsing + clearance interaction

When a block has a non-zero margin AND a `clear` property AND the
previous siblings produced floats that would clear, CSS 8.3.1 specifies
a particular interaction: the larger of the collapsed margin and the
clearance distance applies, but the margin doesn't shift through the
clearance. The BFC tracks `clearanceApplied` per child to honor this.

## Incremental considerations

The BFC is the load-bearing site for layout reuse. Two reuse gates fire:

- **Strict identity** (`renderNode === entry.renderNode`): the input
  render node is the exact same reference as the one that produced the
  cached box. Most subtree reuses go through this path.

- **Layout-equivalent identity** (`renderNodesLayoutEquivalent`): the
  parent was rebuilt with a fresh children-array, but its children are
  reference-equal to the cached entry's. Used for the document root
  after a single-paragraph edit, where most paragraphs flow through
  unchanged. Without this gate the BFC would iterate every child;
  with it, the entire document subtree returns by reference.

Both gates additionally check `isLayoutBoxReusable` to confirm
container size, writing-mode, and float-env dirty offset haven't shifted.

## Reference

### Entry point

```ts
function layoutBlock(
  node: ElementBox,
  inlineOffset: number,        // parent-relative
  blockOffset:  number,        // parent-relative; the BFC's content origin sits at (paddingInlineStart, paddingBlockStart) within the box
  ctx: LayoutContext,
  shaper: TextShaper,
  hyphenator: Hyphenator | undefined,    // auto-hyphenation; undefined ⇒ no hyphenation
  fragmentation?: FragmentationContext,  // paginated mode: available block-size + resume token; absent ⇒ unpaginated full layout
  pageFlowBase: number = 0,    // cumulative document-flow offset of this page's content top (Σ prior pages' inFlowConsumed); feeds blockFlowBase = pageFlowBase + nestedOrigin (coherent float frame). 0 ⇒ page-0 / non-paginated, byte-identical to pre-fix
): LayoutResult<BlockBox>;     // { box: BlockBox | null; breakToken: BreakToken | null; inFlowConsumed: number }
```

### Algorithm

```
function layoutBlock(node, inlineOffset, blockOffset, ctx, shaper):

  // 1. Reuse gate
  if ctx.prevLayoutCache != null:
    entry = ctx.prevLayoutCache.get(node.key)
    if entry exists && entry.box.type == "block"
         && renderNodesLayoutEquivalent(node, entry.renderNode):
      dirtyOffset = ctx.prevFloatEnv != null
                    ? ctx.floatEnv.dirtyBlockOffsetSince(ctx.prevFloatEnv)
                    : +Infinity
      if isLayoutBoxReusable(entry.box, {
           computedStyle: cs, availableInlineSize: ctx.containingInlineSize,
           writingMode: ctx.writingMode, direction: ctx.direction,
           floatEnvDirtyBlockOffset: dirtyOffset
         }):
        return entry.box

  // 2. Resolve box dimensions
  cs = node.computedStyle
  usedStyle = computeUsedStyle(cs, ctx.containingInlineSize, ctx.containingBlockSize)
  pad{Block,Inline}{Start,End} = usedStyle.padding...
  finalInlineSize = resolveBoxInlineSize(cs, ctx.containingInlineSize, isFloat=false, node, shaper, ctx)
  contentInlineSize = finalInlineSize - paddingInlineStart - paddingInlineEnd

  // 3. Walk children
  childBlockOffset = paddingBlockStart
  layoutChildren = []
  prevMarginBlockEnd = 0
  groups = groupChildren(node)
  floatEnv = ctx.floatEnv
  // Coherent float frame: every float-env interaction below (clearance / placeFloat
  // / lowestFloatBlockEdge enclosure) and the IFC's paraFlowStart stamp are expressed
  // in the document-cumulative frame `blockFlowBase + childBlockOffset`; box-render
  // positions are translated back to page-relative by `− blockFlowBase`. See the
  // "Coherent float coordinate frame" note above.
  blockFlowBase = pageFlowBase + (ctx.isBFCRoot ? 0 : ctx.originFromAbc.blockOffset)

  // No list counter here: numbering is resolved at render time. The marker
  // text for a list-item is already baked onto childCs.markerText (see the
  // marker block below). The BFC counts nothing.

  for group in groups:
    if group.kind == "inline-run":
      // Synthesize anonymous element box, dispatch to IFC
      anonElement = synthesizeAnonElement(node, group, paddingInlineStart, contentInlineSize)
      ifcCtx = makeChildContext(ctx, cs, contentInlineSize, "indefinite")
      lines = layoutInlineContent(anonElement, paddingInlineStart, childBlockOffset, ifcCtx, shaper,
                                  hyphenator, paraFlowStart = blockFlowBase + childBlockOffset)
      append lines to layoutChildren
      childBlockOffset += height of lines
      prevMarginBlockEnd = 0       // anonymous boxes have no margins
      continue

    // group.kind == "block"
    child = group.child
    childCs = child.computedStyle
    childUsedStyle = ...

    // Margin collapsing — collapse with previous sibling
    collapsedMargin = max(prevMarginBlockEnd, childUsedStyle.marginBlockStart)
    if (parent and first-child have no top boundary): collapsedMargin = collapse with parent
    childBlockOffset += collapsedMargin

    // Clearance (queried in the cumulative frame, then translated back page-relative)
    if childCs.clear != "none":
      clearedOffset = floatEnv.clearance(childCs.clear, blockFlowBase + childBlockOffset) - blockFlowBase
      if clearedOffset > childBlockOffset:
        // Clearance "absorbs" the margin — CSS 8.3.1
        clearanceApplied = clearedOffset - childBlockOffset
        childBlockOffset = clearedOffset
        // If margin was greater than clearance, the leftover margin still applies
        if collapsedMargin > clearanceApplied:
          // (margin already added; nothing to add)

    // Float
    if childCs.float != "none":
      placement = floatEnv.placeFloat(
        side = childCs.float == "inline-start" ? "inline-start" : "inline-end",
        requestedBlockOffset = blockFlowBase + childBlockOffset,  // cumulative frame
        inlineSize = childInlineSize,
        blockSize = childBlockSize,
        containingInlineSize = contentInlineSize,
      )
      // Float doesn't advance childBlockOffset; just registers. Box-render block
      // offset is translated back page-relative: placement.blockOffset − blockFlowBase.
      append childBlockBox at { placement.inlineOffset, placement.blockOffset − blockFlowBase } to layoutChildren
      prevMarginBlockEnd = 0
      continue

    // List marker — read the render-baked markerText (no counting):
    //   non-empty childCs.markerText → emit a MarkerBox painting that string;
    //   absent/empty                 → no marker.
    // Numbering, restart, the consecutive-run rule, and explicit overrides
    // are all resolved at render time (see 1.2-render.md); the BFC only reads.
    markerText = (childCs.markerText is non-empty) ? childCs.markerText : null

    // Split-item marker suppression (#431) + degenerate-resume exception (#501):
    // a list-item whose content straddles a page break emits its marker only on
    // the page where it STARTS. A MID-CONTENT continuation (the first child of
    // the resumed BFC carrying a NON-degenerate resume token) creates NO
    // MarkerBox; a DEGENERATE resume (resumeAtLine 0 — the prior page placed zero
    // content) IS the item's start and DOES show the marker.
    isResumeFragment = (i == startIndex) && (firstChildResumeToken != null)
                       && not isResumeFromDegenerate(firstChildResumeToken)
    // BUILD the marker (so auto-widen math runs) but DEFER the push (#501):
    markerBox = (markerText != null && not isResumeFragment)
                ? MarkerBox at (childBlockOffset, marker-inline-position) : null

    // Recurse
    childBox = layoutBlock(child, paddingInlineStart, childBlockOffset, makeChildContext(...), shaper)
    // Push the deferred marker FIRST, then the content — only where the item
    // PLACES content on THIS fragment (#501). The same marker-before-content push
    // happens at every C.6 overflow / partial-break / whole-block-overflow site;
    // a fragment where the item placed zero content emits no marker.
    if markerBox != null: append markerBox to layoutChildren
    append childBox to layoutChildren
    childBlockOffset += childBox.blockSize
    prevMarginBlockEnd = childUsedStyle.marginBlockEnd

  // 4. Compute final block-size
  // An explicit cs.blockSize is applied to the BOX itself (honoring CSS height),
  // preserving the laid-out content children — the box reports the resolved
  // block-size, NOT the content-derived height. So a sized float / in-flow block
  // (e.g. a sized image) reports its real painted / hit-test rect, and a float's
  // box geometry agrees with the exclusion region the FloatEnvironment reserved.
  // childAreaHeight already includes paddingBlockStart (childBlockOffset started there).
  childAreaHeight = childBlockOffset + prevMarginBlockEnd
  // Enclosure: lowestFloatBlockEdge() is in the cumulative frame → translate back page-relative.
  if isOwnBFC: childAreaHeight = max(childAreaHeight, floatEnv.lowestFloatBlockEdge() − blockFlowBase)
  finalBlockSize = (cs.blockSize is explicit) ? resolved : (childAreaHeight + paddingBlockEnd)

  // inFlowConsumed = the in-flow content height (childBlockOffset-based, EXCLUDING the
  // out-of-flow float enclosure and any explicit cs.blockSize), so paginate.ts can
  // advance pageFlowBase gaplessly. Distinct from finalBlockSize, which an overflowing
  // float / explicit block-size can inflate. Carried on the box and the LayoutResult.
  return createBlockBox(node.key, inlineOffset, blockOffset,
                        finalInlineSize, finalBlockSize,
                        ctx.writingMode, ctx.direction,
                        cs, usedStyle,
                        layoutChildren,
                        ctx.containingInlineSize,
                        node.metadata,
                        inFlowConsumed)
```

### Margin-collapsing rules in detail

CSS Box Model 3 §6.2.

- **Adjacent siblings.** Two siblings A and B in the same block container collapse the bottom-margin of A with the top-margin of B. Result: `max(A.marginBlockEnd, B.marginBlockStart)` if both positive; per CSS rules with negative margins: `pos = max(positives_or_0)`, `neg = min(negatives_or_0)`; collapsed = `pos + neg`.

- **Parent / first-child.** If the parent has no top boundary (no `paddingBlockStart`, no `borderBlockStartWidth`), the first child's `marginBlockStart` collapses through the parent (becomes part of the parent's `marginBlockStart` for further collapsing with the parent's previous sibling). Symmetric for last-child / bottom.

- **Empty block.** A block with no content, no padding, no border collapses its top and bottom margins together (`max(top, bottom)` for the positive case, plus negative-margin rules), and the resulting margin folds into the surrounding collapse chain — the `childBlockOffset` does not advance for the empty block beyond what the collapsed margin alone produces.

- **Clearance + margins (CSS 8.3.1).** If a block has clearance AND a margin AND the margin would otherwise collapse with surrounding content: the clearance position is computed as if the margin were applied, then the larger of (margin, clearance) governs how far down the block lands. If the margin is greater, no extra clearance shift; if the clearance is greater, the difference becomes a "clearance-only" advance that doesn't propagate as a collapsing margin.

The implementation tracks `clearanceApplied` per child to honor the rule.

### `establishesNewBFC`

```ts
function establishesNewBFC(cs: ComputedStyle): boolean;
```

Returns `true` for `cs.display === "flow-root"`, `cs.display === "inline-block"`, `cs.display === "table-cell"`, `cs.float !== "none"`, or `cs.position === "absolute"` (an out-of-flow box is laid out as its own BFC root at its resolved position — see "Out-of-flow absolute positioning"). Future extensions: `overflow !== "visible"` once that property is consumed; `column-count` and `column-width` for multi-column.

### `FloatEnvironment`

```ts
interface PlacedFloat {
  readonly side: "inline-start" | "inline-end";
  readonly inlineOffset: number;
  readonly blockOffset:  number;
  readonly inlineSize:   number;
  readonly blockSize:    number;
}

interface FloatEnvironment {
  placeFloat(side, requestedBlockOffset, inlineSize, blockSize, containingInlineSize):
    { blockOffset: number; inlineOffset: number };
  availableInlineSizeAt(blockOffset, containingInlineSize):
    { inlineStartSize: number; inlineEndSize: number };
  clearance(side, currentBlockOffset): number;
  lowestFloatBlockEdge(): number;
  nextFloatBottomBelow(blockOffset): number;
  getPlacedFloats(): readonly PlacedFloat[];
  dirtyBlockOffsetSince(prev: FloatEnvironment): number;
}

function createFloatEnvironment(): FloatEnvironment;
```

Internal data structure: a flat array of `PlacedFloat`s in placement order. Queries walk the array (the `placed` count is tiny in practice — typically zero or single-digit per BFC).

### `placeFloat` algorithm (CSS 9.5.1)

```
function placeFloat(side, requested, inlineSize, blockSize, containingInlineSize):
  blockOffset = requested
  loop:
    occupiedAtThisOffset = availableInlineSizeAt(blockOffset, containingInlineSize)
    available = containingInlineSize - occupiedAtThisOffset.inlineStartSize - occupiedAtThisOffset.inlineEndSize
    sameSideOccupied = (side == "inline-start") ? occupiedAtThisOffset.inlineStartSize : occupiedAtThisOffset.inlineEndSize

    if inlineSize <= available:
      // Fits at this offset
      finalInlineOffset = (side == "inline-start") ? sameSideOccupied : (containingInlineSize - sameSideOccupied - inlineSize)
      placed.push({ side, blockOffset, inlineOffset: finalInlineOffset, inlineSize, blockSize })
      return { blockOffset, inlineOffset: finalInlineOffset }

    // Doesn't fit — push below the next float bottom
    nextBottom = nextFloatBottomBelow(blockOffset)
    if nextBottom == blockOffset:
      // No further float below; fits regardless of constraint per CSS spec degraded behavior
      // (this branch indicates the caller's float is wider than the container; place it anyway)
      finalInlineOffset = (side == "inline-start") ? 0 : max(0, containingInlineSize - inlineSize)
      placed.push({ side, blockOffset, inlineOffset: finalInlineOffset, inlineSize, blockSize })
      return { blockOffset, inlineOffset: finalInlineOffset }
    blockOffset = nextBottom
```

`availableInlineSizeAt(blockOffset)` walks `placed` and sums the inline-extents of floats whose vertical extent contains `blockOffset` (`f.blockOffset <= blockOffset < f.blockOffset + f.blockSize`), partitioned by side.

`clearance(side, currentBlockOffset)` returns the largest float-bottom `f.blockOffset + f.blockSize` for floats whose `side` matches the requested clear side ("both" → either), bounded below by `currentBlockOffset`.

### Performance contracts

- `layoutBlock` cold: O(N) over the descendants.
- `layoutBlock` cached: O(1) when both reuse gates pass; O(child-count) when only the structural-equivalent gate passes (each child cache-hits at O(1) and the parent rebuilds with its children-array).

## Fragmentation

When `EditorConfig.pageConfig` is set, BFC's child-placement loop is break-aware. Each call to `layoutBlock` may receive a `FragmentationContext { availableBlockSize, pageIndex, resumeFrom }` and returns a `LayoutResult<BlockBox> { box, breakToken }`.

The break-aware loop:

1. **Whole-block placement.** For each child, the recursive `layoutBlock` (or `layoutTable`) call returns either the full box, a partial box with a `breakToken`, or a null box with a `breakToken`. The BFC checks against the remaining space.

2. **Forced breaks.** Before placing a child, the BFC inspects `cs.breakBefore`. If `page` (or `always`) and the fragment already has placed content, the BFC returns immediately with a `BlockBreakToken { resumeChildIndex: K }`. Symmetrically, after placing a child, `cs.breakAfter` may force a break before the next child.

3. **`break-inside: avoid`.** When a child returns a partial result and `cs.breakInside === "avoid"`, the BFC discards the partial and pushes the whole child to the next fragment (returns a `BlockBreakToken` pointing back at the child).

4. **Margin truncation across breaks** (CSS Fragmentation L4 §5.4). The first child placed on a fresh fragment has its top-margin treated as 0 — the margin would otherwise span the fragmentation break. The BFC tracks "is this the first child of the current fragment?" via the placed-children count.

5. **Overflow rule** (CSS Fragmentation L4 §3.5). When a child can't fit on the current fragment AND the fragment is empty, the BFC re-invokes the layout call without fragmentation to obtain the unfragmented full box, places it (overflowing the page bottom), and continues. Subsequent children push cleanly to the next fragment.

6. **Resume.** When the parent BFC's `fragmentation.resumeFrom` is a `BlockBreakToken`, the loop starts at `resumeChildIndex` and threads `resumeChildToken` (if any) into the FIRST iteration's recursive call only. Subsequent iterations get a fresh `resumeFrom: null`.

The `BreakToken` types are defined in `packages/core/src/layout/fragmentation.ts`.
