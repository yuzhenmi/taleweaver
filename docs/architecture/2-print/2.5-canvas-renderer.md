# 2.5 — `canvas-renderer`

The canvas renderer paints a `LayoutBox` tree onto a `<canvas>`. It is
the only module in `print` that calls drawing APIs directly. It has two
entry points (`paintCanvas` for single-canvas, `paintPage` for
per-page) that share most of the same paint logic.

## Inputs

Both entry points take:

- A `CanvasRenderingContext2D` to draw into.
- The `LayoutBox` to paint (the document root for `paintCanvas`, a
  page box for `paintPage`).
- Selection rectangles (pre-computed by `core`'s
  `computeSelectionRects`).
- Match-highlight rectangles (`MatchHighlightRect[]` — a `SelectionRect`
  tagged with `active: boolean`; the find-match overlay, see "Find-match
  highlight band" below). Empty when find is inactive.
- Comment-highlight rectangles (`CommentHighlightRect[]` — a `SelectionRect`
  tagged with `commentId` + `active: boolean`; the comment overlay, see
  "Comment highlight band" below). Empty when no comments are lit.
- Cursor position + cursor state (`active` / `inactive` / `hidden`).
- Visible viewport bounds (top, bottom in canvas pixels) for
  viewport culling.
- An optional `ImageCache` for async-loaded image resources.
- An optional `PaintCache` for incremental paint.

`paintCanvas` additionally takes the canvas's logical width and height
for full-clear fallbacks. `paintPage` infers those from the page box.

## Output

The list of dirty rectangles painted in this pass. The host can ignore
the return value or use it for diagnostics; the canvas itself is
mutated as a side effect.

## Paint algorithm

Two paths, selected by whether a `PaintCache` was supplied.

### Incremental path (cache supplied)

1. **Walk for dirty.** Call `walkAndDetectChanges` to compare each
   layout box's paint-input hash against the cached one and accumulate
   the rectangles of boxes whose hashes differ. The walk's first action
   is a root short-circuit: if the layout tree's root is reference-equal
   to the previously walked one, the walk returns immediately with no
   dirty regions and no per-box hashing.

2. **Skip if nothing dirty.** If the dirty list is empty, return without
   touching the canvas. This is the fast path for cursor moves where
   layout didn't change.

3. **Clear dirty regions only.** For each dirty rect, `ctx.clearRect`.
   This clear happens once; the two-phase repaint below draws over the
   cleared regions.

4. **Repaint in two phases (background → comment highlights → match
   highlights → selection → foreground).** Walk the layout tree top-down twice,
   with viewport culling on both walks:
   1. `paintBox` with `phase: "background"` — block/inline/cell
      backgrounds, borders, text-run highlights, images, horizontal-rule
      metadata.
   2. Paint comment-highlight rectangles (the bottommost overlay band —
      inactive comments first, then the active comment).
   3. Paint match-highlight rectangles (the find overlay band — inactive
      matches first, then the active match, so its colour wins overlaps).
   4. Paint selection rectangles (the translucent overlay).
   5. `paintBox` with `phase: "foreground"` — text glyphs,
      underline/strikethrough decorations, list/footnote markers.
   The repaint is full because per-box compositing isn't yet implemented;
   clearing only dirty rects but repainting all visible boxes preserves
   correctness when a child's repaint would otherwise overlap a parent's
   stale background. See "Why two phases" below for the layering rationale.

5. **Paint cursor.** Draw the caret rectangle if the cursor state is
   `active` or `inactive`; skip when `hidden`.

### Non-incremental path (no cache)

1. Clear the entire canvas.
2. Paint the layout tree's **background** layer (`paintBox` with
   `phase: "background"`: block/inline/cell backgrounds, borders,
   text-run highlights, images, horizontal rules), with viewport culling.
3. Paint comment-highlight rectangles (comment overlay band — inactive
   first, then active).
4. Paint match-highlight rectangles (find overlay band — inactive first,
   then active).
5. Paint selection rectangles (the translucent overlay).
6. Paint the layout tree's **foreground** layer (`paintBox` with
   `phase: "foreground"`: text glyphs, underline/strikethrough,
   list/footnote markers), with viewport culling.
7. Paint cursor.

This is the fallback when a host doesn't supply a cache. Used by
unit tests and in degraded modes.

### Why two phases

The translucent selection tint must composite **over** content
backgrounds (text-run highlights from `SET_HIGHLIGHT`, block background
colors) and **under** the text glyphs — matching the browser and Google
Docs. A single top-down walk that paints each box's background and text
together would force the selection either entirely behind all content
(invisible on highlighted text, because the highlight overpaints it) or
entirely in front (washing out the glyphs). Splitting the walk into a
background phase and a foreground phase lets the selection overlay slot
**between** them. The cost is a deliberate double walk of the layout
tree, but it is bounded: both walks honor the same viewport culling, so
only the visible subtree is touched twice.

The page paths (`paintPage`) add a white-background pre-pass before the
background phase (see below); the selection still composites over that
white fill and over content backgrounds, under the text.

### Find-match highlight band

The find-match overlay (`matchHighlights: readonly MatchHighlightRect[]`)
paints in the same transient overlay layer as the selection, but **below**
it: the layering is `background → MATCH HIGHLIGHTS → selection → text`. Match
highlights are background highlights the blue selection and the glyphs
composite over (Google Docs' yellow find-highlights). `MatchHighlightRect =
SelectionRect & { active: boolean }` — a paint-layer type (it reuses the
selection-rect geometry wholesale), tagged with whether it belongs to the
active match (the one find next/prev currently sits on). Within the band the
renderer paints inactive matches first (`MATCH_HIGHLIGHT_FILL`, yellow) then
the active match (`ACTIVE_MATCH_HIGHLIGHT_FILL`, orange) so the active colour
wins any overlap. Empty `matchHighlights` is the no-find common case and adds
no draws (byte-identical to the pre-find paint stream). The controller resolves
the per-page `MatchHighlightRect[]` in a two-stage split (boundary positions
once per `update()`, per-page rects in `paintPages`) — see the editor-controller
doc; the renderer only consumes the already-computed rects.

### Comment highlight band

The comment overlay (`commentHighlights: readonly CommentHighlightRect[]`) is the
exact analog of the find-match band — it reuses the selection-rect geometry
machinery wholesale — but paints in the BOTTOMMOST overlay layer, BELOW the
find-match highlights: the full layering is `background → COMMENT HIGHLIGHTS →
match highlights → selection → text`. `CommentHighlightRect = SelectionRect &
{ commentId: CommentId; active: boolean }`; the `commentId` rides along for
future hover/click-to-thread mapping but does not affect pixels — paint and
dirty-tracking use only the geometry + `active`. The band paints inactive comments
first (`COMMENT_HIGHLIGHT_FILL`, a soft amber) then the active comment
(`ACTIVE_COMMENT_HIGHLIGHT_FILL`, a deeper amber, the hovered/selected one), both
distinct from find's yellow. Empty `commentHighlights` is the common no-comments
case and adds no draws. As with the find band, the controller resolves the per-page
rects in a two-stage split (range re-resolved + boundary positions once per
`update()`, per-page rects in `paintPages`); the renderer consumes the computed
rects.

The change-tracking suggestion overlay (`suggestionHighlights: readonly
SuggestionHighlightRect[]`, `SuggestionHighlightRect = SelectionRect &
{ suggestionId: SuggestionId; active: boolean }`) is the exact analog one band
LOWER still — the new bottommost overlay layer, so the full layering is
`background → SUGGESTION HIGHLIGHTS → comment highlights → match highlights →
selection → text`. It reuses the same two-stage resolve/emit + dirty-tracking
machinery (`SUGGESTION_HIGHLIGHT_FILL` inactive / `ACTIVE_SUGGESTION_HIGHLIGHT_FILL`
active, a teal distinct from comments' amber and find's yellow). Its Stage-1
resolve needs no `orphaned` check the comment band has — an id with no live
tagged content resolves to `null` and is skipped.

## Per-box drawing

`paintBox` dispatches on `box.type`, and each draw is gated on the
`phase` parameter (background vs foreground — see "Why two phases"). The
per-type behavior below names which phase each draw belongs to:

- **`text-run`** — in the **background** phase, fill the run's highlight
  rectangle (the computed-style `backgroundColor`, from `SET_HIGHLIGHT`)
  so the selection tint composites over it. In the **foreground** phase,
  set font + fill style and draw the text via `fillText`, then the
  text-decoration rule (underline / line-through). The font string is
  built from the computed-style font fields once per box and cached via a
  `lastFont` optimization to avoid redundant assignments.

- **`block` / `inline` / `inline-block`** — in the **background** phase,
  draw background (if any), then borders (each side independently using
  the used-style border-width), then image / horizontal-rule metadata
  (block only). Recurse into children in **both** phases.

- **`line` / `table` / `table-row`** — no self-paint; recurse into
  children in both phases.

- **`marker`** — **foreground** phase only: draw the marker text (bullet,
  digit, or roman) at the marker's position using the line's font.

- **`table-cell`** — in the **background** phase, draw cell background and
  borders (border-collapse logic compresses adjacent borders). Recurse in
  both phases.

- **`multicolumn`** — a section's multi-column body box. Recurse into its
  `columns` (each a `block`) in **both** phases, then paint any
  `absoluteChildren` anchored to the box itself. In the **background** phase
  (same phase as `paintBorders`, so it draws exactly once), draw the
  `columnRule` (CSS `column-rule`): for each adjacent column pair, a solid
  `fillRect` centered in the inter-column gap, spanning the box's block extent
  (NOT the column's own extent — an empty trailing column has `blockSize 0`).
  The inline axis is read off `box.writingMode` (horizontal-tb ⇒ a vertical
  line along physical X; vertical modes ⇒ a horizontal line along physical Y).
  Like `paintBorders`, any non-`none` style paints as a solid fill (no
  dash/dot); the gate (`columnRule !== null && width > 0 && style !== "none"`)
  short-circuits the common no-rule case.

- **`page` (if pagination is active)** — the page's white background is a
  **pre-pass** in `paintPage` (drawn before the background walk and the
  selection overlay), NOT in this branch (repainting it here would
  overwrite the selection layer). The branch recurses into `box.children`,
  then paints the `headerSlot`, `footerSlot`, and `footnoteSlot` — **named
  fields** on the page box (NOT entries in `box.children`) — **by name**
  after the children, at the same page-local origin, in the current phase.
  The footnote slot is handled by name exactly like header/footer (a slot
  dropped from `children` must still paint).

- **Images** — `block` boxes carrying image metadata draw via `drawImage`
  in the **background** phase, once the underlying image has finished
  loading (the image-cache module signals when it's ready and triggers
  re-paint); before it loads, a placeholder fill is drawn. The metadata is
  the typed `LayoutBoxMetadata`, so the paint reads `box.metadata.image`
  (a `{ src, width, height }`) after a presence check — no unchecked shape
  cast.

### Stacking-context paint order (z-index) `[implemented]`

Within a container branch (`block` / `inline-block` / `table` / `table-row` /
`table-cell`), children + `absoluteChildren` are painted in CSS 2.2 §E.2
stacking order when a stacking participant is present; otherwise in plain
document order (the common path). A box's `stackingContextRole` (`"self"` or
absent — computed by the core box factory from `computedStyle`, see
[`2.4-positioning.md`](./2.4-positioning.md)) and a child's `position`
classify each direct child / abs child into the §E.2 buckets:

1. negative-z stacking-context children (z<0, ascending) — painted in the
   **background** phase, BEFORE the box's own background, so they sit below;
2. the box's own background + borders (the branch's existing draw);
3–5. in-flow non-positioned descendants (recurse normally, both phases);
6. positioned `z:auto|0` descendants (`relative` AND `absolute`),
   tree order;
7. positive-z stacking-context children (z>0, ascending).

Buckets 6/7 paint ATOMICALLY (a child's whole subtree in BOTH sub-phases via two
`paintBox` calls) in the **foreground** phase, AFTER the box's in-flow glyphs, so
they composite above. A child that is itself a stacking context paints its own
§E.2 sub-walk atomically; nested stacking contexts therefore do not leak z across
their boundary. Helpers: `needsStackingReorder` (the common-path gate),
`partitionStackingChildren`, `paintNegativeZBeforeBackground`,
`paintContainerChildren`, `paintStackingChildAtomic`. The gate keeps the 99%
no-z-index / no-stacking document byte-identical to the pre-stacking painter.
`z-index` only applies to POSITIONED boxes (a `z-index` on a `position: static`
box is ignored, and never makes it a stacking context).

### Transform application `[implemented]`

A transformable (`block` / `inline-block` / `table*` / `page`) box with a
non-empty `transform` paints under a saved canvas matrix: `paintBox` does
`ctx.save()`, applies the box's matrix as a single `ctx.transform(a, b, c, d, e, f)`
(built by `applyBoxTransform` → core `resolveTransformOrigin` + `fromTransformFns`
— the IDENTICAL math the hit-test inverse uses, so paint and hit-test never
diverge), paints the subtree (a transform-bearing box is a stacking context, so it
paints atomically), then `ctx.restore()` in a `finally`. Generated `line` /
`text-run` / `marker` / `inline` fragments are SKIPPED (they copy their block's
`transform`; re-applying it would double-count). An untransformed box takes NO
save/restore (zero overhead, guarded on `cs.transform.length > 0`); viewport
culling is skipped for transformed boxes (their painted bounds can move out of the
pre-transform band). See [`2.4-positioning.md`](./2.4-positioning.md).

### Opacity compositing `[implemented]`

A box with `cs.opacity < 1` is a stacking context (so it paints atomically). At
the top of `paintBox`, `paintOpacityGroup` renders the box's WHOLE atomic subtree
(both paint sub-phases + all descendants, incl. its own transform and §E.2
stacking children) into a temporary offscreen surface at full opacity, then
composites it onto the parent ctx ONCE via `ctx.drawImage(surface.canvas, absX,
absY)` at `ctx.globalAlpha = cs.opacity` (restoring `globalAlpha` afterward). This
is CSS-spec opacity GROUPING — a half-opaque box with overlapping children reads
as ONE translucent region (composited once), not additive per-child alpha. The
composite runs in the FOREGROUND phase only (the background-phase entry is a
no-op), exactly like a bucket-6/7 stacking child whose atomic paint is foreground-
gated; a `skipOpacity` flag on the re-entrant offscreen `paintBox` call consumes
the box's own opacity exactly once (no infinite recursion). Nested opacity
composes (an inner group `drawImage`s into the outer group's offscreen ctx). The
offscreen surface comes from an injectable factory
(`offscreen-surface.ts`: `createOffscreenSurface` / `setOffscreenSurfaceFactory` /
`resetOffscreenSurfaceFactory`) — the default uses a detached `<canvas>` element
(a real `CanvasRenderingContext2D` + `CanvasImageSource`, no casts, zero
dependency); the seam lets tests inject a fake recording surface under jsdom.
**`opacity === 1` / `undefined` → the DIRECT path, ZERO
offscreen allocation, `globalAlpha` untouched** (the 99.99% common case is
byte-identical to the no-opacity painter). See
[`2.4-positioning.md`](./2.4-positioning.md).

## Writing-mode handling

### Logical → physical border/padding sides `[implemented]`

A box's border and padding are stored on the **logical** sides
(`borderBlockStartWidth`, `paddingInlineEnd`, etc.). The renderer maps each
logical side to a physical top / right / bottom / left before drawing via
`physicalBorderSides(usedStyle)`, an exhaustive `switch` over the
`WritingMode` union (its `default` arm calls `assertNeverWritingMode`, so a
future 4th mode is a compile error). It covers every `(writingMode,
direction)` combination — `horizontal-tb` (LTR/RTL), `vertical-rl`, and
`vertical-lr` — and is the paint-side counterpart to the mapping table in
[`1-core/1.0-styles.md`](../1-core/1.0-styles.md#borders-paddings-and-the-writing-mode-swap)
(`logicalToPhysical` is the source of truth for the axis→physical mapping).
`horizontal-tb` LTR stays byte-identical to the legacy direct top/right/
bottom/left reads.

### Vertical glyph rotation `[missing]`

For the vertical writing modes the renderer must rotate each text run ±90° so
a horizontal-script run paints downward along the inline axis (`text-orientation:
upright` for CJK is a future property). This is not yet implemented — the
renderer still paints glyphs horizontally regardless of `writingMode`, so
vertical documents lay out and edit correctly but do not yet render rotated
text. See [`1-core/1.0-styles.md`](../1-core/1.0-styles.md#painter-integration-missing).

### Caret-bar orientation `[missing]`

In a vertical writing mode the caret's extent runs along the block axis
(physical x), so the caret should draw as a horizontal bar. The renderer
still draws the caret as a vertical bar; vertical caret-bar orientation is
part of the same browser-gated paint remainder as glyph rotation.

## Viewport culling

`paintBox` early-returns when `absY + box.height < visibleTop` or
`absY > visibleBottom`. The bounds are passed in by the controller. The
culling propagates: skipping a parent skips its entire subtree. For
multi-page documents, only visible pages paint.

## Why the renderer is in `print`

Drawing depends on canvas APIs. `core` doesn't know about canvases.
Putting the renderer in `print` lets `core` stay platform-agnostic — a
non-browser host (Node.js for PDF rendering, native for desktop) can
implement its own renderer against the same `LayoutBox` tree without
touching anything in `core`.

## Reference

### Public API

```ts
type CursorState = "active" | "inactive" | "hidden";

interface Rect {
  readonly x: number;
  readonly y: number;
  readonly w: number;
  readonly h: number;
}

// (overlay rects in paint order: `matchHighlights` then `commentHighlights`
//  follow `selectionRects`)
function paintCanvas(
  ctx: CanvasRenderingContext2D,
  layoutTree: LayoutBox,
  selectionRects: readonly SelectionRect[],
  matchHighlights: readonly MatchHighlightRect[],
  commentHighlights: readonly CommentHighlightRect[],
  cursorPos: { x: number; y: number; height: number },
  cursorState: CursorState,
  canvasWidth: number,
  canvasHeight: number,
  visibleTop: number,
  visibleBottom: number,
  imageCache?: ImageCache,
  cache?: PaintCache | null,
): Rect[];

function paintPage(
  ctx: CanvasRenderingContext2D,
  pageBox: LayoutBox,
  selectionRects: readonly SelectionRect[],
  matchHighlights: readonly MatchHighlightRect[],
  commentHighlights: readonly CommentHighlightRect[],
  cursorPos: { x: number; y: number; height: number } | null,
  cursorState: CursorState,
  imageCache?: ImageCache,
  cache?: PaintCache | null,
): Rect[];
```

Both return the dirty rectangles painted in this pass. `[]` indicates either no work was needed (cache root short-circuit fired) or the non-incremental path was taken (cache was null/undefined).

### Per-box dispatch in `paintBox`

`paintBox` takes a `phase: "background" | "foreground"` parameter (see
"Why two phases" above). Each leaf branch gates its draws on the phase:
background-phase draws the box's background fill, borders, image content,
and text-run highlight; foreground-phase draws the glyphs and text
decorations (underline/strikethrough) and marker text. Structural boxes
(`block`, `line`, `inline`, `table*`, `page`) recurse into their children
in **both** phases, threading the same `phase` value unchanged — children
are always painted in the same phase as their parent.

```
type PaintPhase = "background" | "foreground"

function paintBox(ctx, box, parentX, parentY, visibleTop, visibleBottom, state, phase):
  absX = parentX + box.x; absY = parentY + box.y

  // Viewport culling (applies on BOTH the background and foreground walk)
  if absY + box.height < visibleTop || absY > visibleBottom: return

  cs = box.computedStyle; us = box.usedStyle

  switch box.type:
    case "block":
    case "table-cell":
      if phase == "background":
        // Background
        if cs.backgroundColor != "transparent":
          ctx.fillStyle = cs.backgroundColor
          ctx.fillRect(absX, absY, box.width, box.height)
        // Borders (per side)
        drawBorder(ctx, absX, absY, box, cs, us)
        // Image content + horizontal-rule metadata (block only)
        if box.metadata?.image: drawImage(...) else if box.metadata?.horizontalLine: drawRule(...)
      // Recurse children in the SAME phase
      for child in box.children: paintBox(ctx, child, absX, absY, visibleTop, visibleBottom, state, phase)

    case "line":
    case "table":
    case "table-row":
      // No self-paint; recurse children in the SAME phase
      for child in box.children: paintBox(ctx, child, absX, absY, visibleTop, visibleBottom, state, phase)

    case "text-run":
      if phase == "background":
        // Highlight (text background color) — painted so the selection tint
        // composites OVER it. Mirrors the block backgroundColor guard.
        if cs.backgroundColor != "transparent":
          ctx.fillStyle = cs.backgroundColor
          ctx.fillRect(absX, absY, box.width, box.height)
        return
      // FOREGROUND phase: glyphs + decorations (painted OVER the selection).
      fontStr = buildCssFontString(cs)
      if fontStr != state.lastFont: ctx.font = fontStr; state.lastFont = fontStr
      ctx.fillStyle = cs.color
      // #330: text is painted CLUSTER-BY-CLUSTER — one fillText per cluster at the
      // cluster's cumulative advance — NOT one whole-run `fillText(box.text, ...)`.
      // The whole-run form drifts from the shaper's per-cluster measurement and
      // caused caret/glyph drift in long tokens; the per-cluster paint keeps the
      // painter and the shaper's advances in lockstep.
      for cluster in box.clusters:
        ctx.fillText(cluster.text, absX + cluster.advanceFromStart, baselineY(absX, absY, cs))
      // Text-decoration (underline / line-through) drawn as rect at the appropriate y-offset
      drawTextDecoration(ctx, absX, absY, box, cs)

    case "marker":
      // Marker glyph (list bullet/number, footnote marker) — FOREGROUND only.
      if phase != "foreground": return
      ctx.font = buildCssFontString(cs); ctx.fillStyle = cs.color
      ctx.fillText(box.text, absX, absY + lineBaseline)

    case "inline":
      if phase == "background":
        // Background + borders honor box.fragmentEdge:
        //   "first" → left/start side has padding/border, right/end omitted
        //   "last" → right/end has, left/start omitted
        //   "middle" → no horizontal padding/border (continuation)
        //   "only" → both sides
        drawInlineFragment(ctx, absX, absY, box, cs, us)
      for child in box.children: paintBox(ctx, child, absX, absY, visibleTop, visibleBottom, state, phase)

    case "inline-block":
      // Like block — background + borders in background phase, then recurse.
      if phase == "background":
        if cs.backgroundColor != "transparent":
          ctx.fillStyle = cs.backgroundColor; ctx.fillRect(absX, absY, box.width, box.height)
        drawBorder(ctx, absX, absY, box, cs, us)
      for child in box.children: paintBox(ctx, child, absX, absY, visibleTop, visibleBottom, state, phase)

    case "page" (paginated):
      // The page white background is a pre-pass in paintPage (before the
      // background walk + selection). Recurse children in the SAME phase:
      for child in box.children: paintBox(ctx, child, absX, absY, ..., phase)
      // Then paint the NAMED slots by name (each may be null), SAME phase:
      if box.headerSlot   != null: paintBox(ctx, box.headerSlot,   absX, absY, ..., phase)
      if box.footerSlot   != null: paintBox(ctx, box.footerSlot,   absX, absY, ..., phase)
      if box.footnoteSlot != null: paintBox(ctx, box.footnoteSlot, absX, absY, ..., phase)
```

### Paint-relevant style fields

The `hashPaintInputs` set (and the renderer's reads) cover only the fields that affect what's drawn. From `ComputedStyle`:

- `backgroundColor`
- `color`
- `fontFamily`, `fontSize`, `fontWeight`, `fontStyle`
- `underline`, `lineThrough` (independent text-decoration flags)
- `borderBlockStartStyle`, `borderBlockEndStyle`, `borderInlineStartStyle`, `borderInlineEndStyle`
- `borderBlockStartColor`, `borderBlockEndColor`, `borderInlineStartColor`, `borderInlineEndColor`
- `direction`
- `transform` + `transformOrigin` (only hashed when `transform` is non-empty — paint applies them as a canvas matrix; the untransformed-box hash is unchanged)
- `opacity` (only hashed when `opacity < 1` — paint composites the box's group at `globalAlpha`; the fully-opaque-box hash is unchanged, byte-identical to before the field existed)

From `UsedStyle`:

- `paddingBlockStart`, `paddingBlockEnd`, `paddingInlineStart`, `paddingInlineEnd`
- `borderBlockStartWidth`, `borderBlockEndWidth`, `borderInlineStartWidth`, `borderInlineEndWidth`

Plus per-box-type fields:
- `text-run`: `text`
- `marker`: `text`
- `line`: `baseline`
- `inline`: `fragmentEdge`
- `table`: `columnPxWidths`

### Performance contracts

- Incremental path with cache and unchanged tree: O(1) (root short-circuit).
- Incremental path with N dirty boxes: O(N) hash compares + O(N) clearRects + O(visible-boxes) repaint with culling.
- Non-incremental path: O(visible-boxes) per call regardless of changes.
