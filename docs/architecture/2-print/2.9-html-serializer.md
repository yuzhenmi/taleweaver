# 2.9 — `taleweaver-html` + `print`'s `browserHtmlParser`

The human-friendly `taleweaver-html` `DocumentSerializer<string>` (format id
`taleweaver-html`) — readable AUTHORING of documents from an HTML string rather
than hand-built state — lives in `@taleweaver/core`'s `state/serialize/`,
alongside its json/binary peers (see
[`1.7-serialization.md`](../1-core/1.7-serialization.md)). It is NOT a lossless
interchange format; the `taleweaver-binary` serializer owns lossless,
id-preserving round-trips.

`print`'s piece is the BROWSER DOM ADAPTER that lets that core serializer decode
HTML while keeping core DOM-free.

## The headless seam: why decode is in `core`, the parser in `print`

`core` is platform-agnostic and must not reference DOM types. So the serializer's
DECODE half does NOT parse HTML itself — it walks a CORE-defined, DOM-free
`HtmlNode` interface (`core/src/state/serialize/html-node.ts`) and the actual
HTML parse is INJECTED as an `HtmlParser`. `decodeHtml(html, allocator,
parseHtml)` calls `parseHtml(html)` to get the body `HtmlNode`, then lowers the
walked tree to a declarative `BlockNode` tree and hands it to core's
`buildDocumentFromTree`, which mints block ids and derives every structural link.

A browser host supplies the adapter: `print`'s `browserHtmlParser` parses with
the browser-native `DOMParser` (zero new runtime dependency; jsdom supplies it
under the test env) and wraps each DOM `Node` as an `HtmlNode` — cast-free, via
`instanceof Element`/`HTMLElement`/`Text` narrowing. A non-browser host can adapt
any HTML parser (parse5/jsdom) the same way.

## Public surface

```ts
// @taleweaver/core
export const HTML_FORMAT = "taleweaver-html";
export interface HtmlNode { /* DOM-free parsed-node view */ }
export type HtmlParser = (html: string) => HtmlNode;
export function createHtmlDocumentSerializer(deps: {
  allocator: IdAllocator;
  parseHtml: HtmlParser;
}): DocumentSerializer<string>;

// @taleweaver/print
export const browserHtmlParser: HtmlParser;
```

The `IdAllocator` is injected at construction (decode mints fresh block ids); the
`HtmlParser` is the host's DOM adapter. The serializer exposes the standard
`format` / `encode` / `decode` contract.

## Internal structure

- `core/src/state/serialize/html-serializer.ts` — the public factory; wires the
  encode/decode helpers into a `DocumentSerializer`, threading `parseHtml` into decode.
- `core/src/state/serialize/html-encode.ts` — `encodeHtml(state): string`, pure (no DOM).
- `core/src/state/serialize/html-decode.ts` — `decodeHtml(html, allocator, parseHtml): State`,
  walking the DOM-free `HtmlNode`.
- `core/src/state/serialize/html-node.ts` — the `HtmlNode` / `HtmlParser` seam types.
- `print/src/html-parser.ts` — `browserHtmlParser`, the `DOMParser`-backed adapter.

## Supported subset

The format expresses the LOGICAL document — element nesting, document order, and
semantic marks — the way Google Docs' human interchange does. v1 round-trips
this subset **semantically** (structure + types + supported attrs + text +
mark-sets), NOT by block-id identity (decode mints fresh ids — decoding the same
HTML twice yields distinct ids by design):

| Engine | HTML |
|---|---|
| `document` root | `<body>` |
| `heading` (`attrs.level` 1–6) | `<h1>`…`<h6>` |
| `paragraph` | `<p>` |
| `list-item` (`listId`, `listLevel`) | grouped under `<ul>`/`<ol>`, nested by level |
| ordered vs unordered | `<ol>` vs `<ul>` (via `classifyListDef`) |
| `horizontal-line` | `<hr>` |
| `table` (`columnWidths`, `headerRowCount`) → `table-row` → `table-cell` (`rowSpan`/`colSpan`) | `<table>` (optional `<colgroup>` of `<col style="width:%">`) → `<tr>` → `<td>` (`rowspan`/`colspan` when > 1); cell content encoded/decoded recursively. **ENCODE + DECODE** (#480): decode flattens `<thead>`/`<tbody>`/`<tfoot>`, sets `headerRowCount` from a LEADING `<thead>`, reads `<col>` `%` widths via `getStyleProperty("width")`, and wraps a cell's bare inline text in a paragraph. |
| `image` block (`src`, `width`, `height`, `alt`) | block `<img src width height alt>` |
| `inline-image` embed (`src`, `width`, `height`, `alt`) | inline `<img>` within the parent block element (e.g. `<p>`) |
| mark `bold` | encode `<strong>` / decode `<strong>` + `<b>` |
| mark `italic` | encode `<em>` / decode `<em>` + `<i>` |
| mark `underline` | `<u>` |
| mark `strikethrough` | encode `<s>` / decode `<s>` + `<del>` |
| mark `link` (URL payload) | `<a href>` |
| `hard-break` embed | `<br>` |

**Lists** use the Google-Docs flat model: `list-item` blocks are siblings sharing
one `listId`, with `listLevel` for nesting depth (NOT nested `<li>` blocks).
ENCODE groups consecutive same-`listId` items into one `<ul>`/`<ol>`, opening and
closing nested lists by `listLevel` (arbitrary depth, via a nesting stack).
DECODE mints a fresh `listId` per TOP-LEVEL list and threads it through nested
lists (incrementing depth), emitting one flat `list-item` per `<li>`. Each
top-level list gets one default `listDefs` entry (`<ol>` → decimal, `<ul>` →
disc).

**Mark accumulation on decode is order-independent**: walking down an inline
subtree, each recognized mark element adds its attr to the active set, so
`<strong><em>x</em></strong>` and `<em><strong>x</strong></em>` both yield one
text run `x` with `{bold, italic}`. `<a href>` adds `link = href`. Unknown inline
wrappers (e.g. `<span>`) are recursed into so their text survives; unknown block
elements are ignored but recursed into so a wrapper's supported children surface.

## Lossiness boundary (binary is the lossless escape)

Out of v1 scope (dropped on encode, ignored on decode): footnotes,
cross-references, headers/footers, sections, `tab` embeds, and open
style attrs (color, fontSize, fontFamily, textTransform, textAlign, writingMode,
direction, margins, tabStops). **Tables** now ENCODE *and* DECODE
(`<table>`/`<tr>`/`<td>`, above) — the full table round-trip is complete for the
HTML format. One acknowledged asymmetry: encode emits flat `<tr>` rows (no
`<thead>`), so a table's `headerRowCount` is NOT re-emitted on encode and is lost
across an encode→decode round-trip; decode SETS `headerRowCount` only as an
enrichment when reading a LEADING `<thead>` from EXTERNAL HTML (a pasted Google
Docs / Word table). `taleweaver-binary` remains the lossless, `headerRowCount`-
preserving path. Two further accepted semantic losses are documented and
test-locked:

- **Content-bearing embed drops warn.** When encode skips a `footnote-anchor` or
  `cross-reference` embed (author-written content lost on HTML export), it emits a
  dev-mode `console.warn` — at most once per distinct dropped embed type — naming
  the dropped type and pointing at `taleweaver-binary` as the lossless path. Style
  attrs are dropped silently (they degrade to default rendering; no content is
  lost). Production pays nothing (the warn is dev-gated).
- **Non-consecutive same-`listId` runs split.** Two list-item runs sharing one
  `listId` but separated by a non-list block (a valid flat-model state) encode as
  two separate `<ul>`/`<ol>` elements and decode to two distinct lists. Rare in
  prose; documented, not silently surprising.
- **List start / restart ordinals round-trip through HTML.** An ordered list's
  start value (`listDefs` level `start`) encodes as `<ol start=N>` when N≠1, and a
  per-item restart/override (`SET_LIST_RESTART` → `listCounterOverride`) encodes as
  `<li value=N>` when the item breaks the natural +1 sequence. Encode resolves each
  item's ordinal through the SAME numbering engine the render path uses
  (`collectListEvents` → `computeCounters`) — the single source of truth, never
  re-derived in the serializer — so the exported numbers match the on-screen markers
  (and a paste target like Word / Google Docs renders them correctly). Decode is the
  inverse: `<ol start=N>` reconstructs that level's `listDefs` `start` (filling
  intermediate levels contiguously so the numbering engine's level lookup never
  clamps a deeper level onto a shallower start), and `<li value=N>` becomes the
  item's `listCounterOverride` — so `encode → decode → encode` is byte-stable for
  start-at / mid-list-restart lists. Ordinals are read only for ORDERED lists
  (bullets carry no number). `taleweaver-binary` remains the id-preserving lossless
  path; HTML round-trips the ordinal SEMANTICS, not block ids.

## Error contract

The HTML decoder NEVER throws `MalformedDocumentError`. `DOMParser` is lenient
(it recovers any string into a tree), the empty/all-unsupported body falls back
to a single empty `paragraph` (a valid minimal editable doc), the typed `string`
contract rules out non-string input, and the discriminated-union `BlockNode`
makes the container-XOR-leaf invariant a compile-time guarantee. Strictness is
per-serializer: the binary serializer still throws on a missing rootId.

## Untrusted-input sanitization (decode is a trust boundary)

Decoded HTML can come from an untrusted source (paste / `loadDocument`), so decode
sanitizes URL-bearing attributes SYMMETRICALLY with encode (`isExportSafeLinkUrl`
from `@taleweaver/core`'s `url-safety.ts` — shared with the PDF `/Link` exporter;
the allowlist `http`/`https`/`mailto`/`tel`/relative): an
`<a href>` or `<img src>` whose scheme is `javascript:`/`data:`/`vbscript:`/`file:`
is dropped (the `<a>`'s link text is kept; the `<img>`'s `src` becomes `""`), so a
decoded document never carries an executable-scheme URL into the click-nav path or
the canvas image loader. (`data:image` paste is a future rich-paste concern;
the boundary stays allowlist-only.) Decode also recovers a list nested DIRECTLY
inside a list with no intervening `<li>` (the `<ol><ol>` shape a list-LEVEL JUMP
encodes to, and a common Word/web paste shape) by recursing it one level deeper —
without which the deeper items were silently dropped.

## Registration

`core` cannot pre-wire this serializer into `createDefaultSerializerRegistry` (it
lives in `print` and needs an `IdAllocator`). The host composes it manually:

```ts
const reg = createDefaultSerializerRegistry();
reg.register(createHtmlDocumentSerializer({ allocator: productionAllocator }));
// loadDocument(html, HTML_FORMAT, reg, config)
```
