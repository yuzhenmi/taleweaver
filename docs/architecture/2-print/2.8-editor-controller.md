# 2.8 — `editor-controller`

The editor controller is the host orchestrator. The host application
constructs one per editor instance, hands it an HTML container, and
forwards its lifecycle (`update`, `focus`, `destroy`). Internally the
controller owns the canvases, the input listeners, the cursor blink
animation, and the paint flow. It is the point where `core`'s pure
engine connects to the browser's mutable DOM.

## Construction

`createEditorController(container, options) → EditorController` takes:

- The HTML container the editor will render into.
- A `measurer` — the host's `TextShaper` (or legacy `TextMeasurer`)
  implementation. The default in this package is `createCanvasShaper`.
- A `dispatch` callback — how the controller forwards `EditorAction`s
  to the host's reducer.
- Optional `pageHeight` and `pageGap` — pagination configuration.
  When set, the controller activates per-page canvases; when unset,
  it uses a single full-document canvas.

It returns the following methods:

- `update(state)` — call after every state change to repaint and
  reposition.
- `focus()` — programmatically focus the editor's hidden textarea.
- `destroy()` — tear down listeners, animation timers, canvases.
- `exportToPdf(emit)` — compose the live document into a navigable PDF
  byte stream (`Uint8Array`) via an injected `PdfEmitter`. A **pure query** —
  no mutation. See *PDF export* below.
- `getCaretRect(position)` — resolve a document `Position` to its caret's
  viewport-relative pixel rect (`{ left, top, height }` in CSS `position: fixed`
  space), or `null` when unresolvable / before the first `update()`. A **pure
  read-only query** — no mutation, no repaint. Reuses the live caret-resolution
  path (`resolvePixelPosition` → page-local x/y/height) mapped to the viewport
  via the container's bounding rect + the page's slot offset. Hosts use it to
  overlay position-anchored UI such as a collaborator's remote cursor (or a host
  picker anchored to a trigger).
- `version` / `mapPosition(position, version, assoc?)` / `createAnchor(from, to?,
  { inclusive?, assoc?, basedOn? })` — document versions and anchors (see
  [`1-core/1.9-decorations.md`](../1-core/1.9-decorations.md) "Anchors"); anchors advance
  in `update` with the decorations' transition mapping. The mapping log records every
  known transition (including several host dispatches batched into one `update`) and
  resets on an unknown one (a document replacement).
- **Collaboration:** the controller subscribes to the current document's Y.Doc
  (re-subscribing when `update` brings another document) and dispatches
  `APPLY_FOREIGN_CHANGE { dirtyIds }` to the host for every peer update
  (`subscribeRemoteChanges`); the host's reducer rebases the selection and the following
  `update` advances decorations / anchors / mapping log and repaints the dirty blocks.
  The dispatch happens SYNCHRONOUSLY from Yjs `afterTransaction`, i.e. inside the
  provider's `Y.applyUpdate` call: the host's dispatch must be re-entrancy-safe and must
  not forward updates to the provider from inside it (or must defer). Option
  `remoteChanges: "observe" | "ignore"` (default `"observe"`; also an `EditorView` prop):
  exactly ONE controller per document observes; any other controller over the same
  document passes `"ignore"`, else each would dispatch the same peer change. While an IME
  composition is active the accessibility mirror is not re-synced (its DOM / selection
  belong to the IME); composition end re-syncs it — the default textarea path never
  writes the textarea during composition.
- **HALTED (incompatible document storage).** A peer update carrying LEGACY inline
  storage (1.5 "Incompatible documents") is never dispatched: the subscription's
  `onIncompatible` halts the controller. The controller ALWAYS subscribes to the
  document's Y.Doc for this shape check — with `remoteChanges: "ignore"` it still halts,
  it only does not dispatch peer changes. `halted` turns true and the option
  `onIncompatibleDocument({ legacyBlocks })` is called once per halt (and again, while
  still halted, when legacy storage returns after `onDocumentCompatible` was reported —
  the controller is the source of truth for halted); an in-flight IME
  composition is abandoned (the textarea buffer is cleared; on the mirror path the
  mirror is rebuilt from its last synced tree — `2.11` `abandonComposition` — and a late
  `compositionend` is dropped the same way); pending proposals resolve `{ ok: false,
  reason: "halted" }`. From then on the controller dispatches nothing (input, keys,
  mouse, paste, commands and further remote changes are ignored; keydown does NOT
  prevent the browser default, so Tab / reload / browser shortcuts keep working), keeps
  the last good render on screen (pages are materialized from the last styled tree,
  never from the Y.Doc) and the accessibility mirror frozen at its last projection.
  Every member has a defined result without touching the Y.Doc: `focus` works;
  `destroy` always works; `update` is the document-replace exit (below); `decorations`
  → the last good host set; `version` → the last good State; `getCaretRect` /
  `mapPosition` / `createAnchor` → null; `propose` → halted; `findStart` / `findNext` /
  `findPrev` / `findStatus` / `replaceActive` / `replaceAll` → the empty status;
  `findClose` → no-op; `runCommand` → false; `exportToPdf` throws ("halted");
  `setDecorations` / `set*Highlights` / `clear*Highlights` / `setSuggestionStyles` →
  no-ops; copy / cut → an empty clipboard. While halted the subscription re-checks the
  known legacy blocks plus the touched ones on every transaction, local ones included;
  once the document is upgraded (by an upgraded peer or by this host), the option
  `onDocumentCompatible()` is called once (the controller stays halted). Exit: `update`
  with a FRESH EditorState — not reduced from the halted one (its `lastChange` chain
  never reaches the halted State; a fresh State with edits on top qualifies) — whose
  document holds no legacy storage (the `createState` load check; O(blocks), only on
  this path): a State built anew over the same, now upgraded, Y.Doc or one over another
  document. The halted State and any State reduced from it are ignored; a descendant
  whose bounded chain was trimmed past the halted State is indistinguishable from a
  fresh one and passes on the load check alone. A fresh State refused for legacy storage
  the watch never saw (another document, or a local write after `onDocumentCompatible`)
  moves the halted watch to its document and, if the host was told "compatible",
  reports the halt again; it is then forbidden like the halted State (any State reduced
  from it is ignored too). The same load check runs on EVERY replacement, halted or not
  (the first State, another Y.Doc, or a State not reduced from the current one — legacy
  storage can land between `createState` and `update`): a refused one halts the
  controller on it (`onIncompatibleDocument`), keeps the last good render, and watches
  its document halted. The resume re-subscribes to the document afresh and drops every decoration
  layer and the find session (the host sets them again). An internal option
  `startHaltedOn: EditorState` creates the controller already halted, watching that
  state's document (nothing shown; inspected once — a document upgraded meanwhile fires
  `onDocumentCompatible` on a microtask) — used by the React view re-created while its
  hook is halted (`4.2`).
- `propose(proposal, { basedOn? })` — offer a host proposal as ONE suggestion group,
  dispatched to the host as `PROPOSE` with `basedOn` (default: the version this
  controller shows). The host's reducer maps it through the edits made since and
  validates it, so it lands on the right text even when the host has applied edits the
  controller has not seen yet. Returns `Promise<ProposeResult>` resolving with the TRUE
  verdict when an `update` carrying it (`lastProposal`, matched by the dispatched object)
  arrives; "stale" if the document is replaced first; rejected "controller destroyed"
  if destroyed first. Dispatches apply in order, so once a LATER proposal's verdict
  arrives, an earlier pending one with no verdict was dropped by the host: rejected
  "proposal was not applied by the host" ("verdict aged out" when the chain no longer
  reaches the last verdict seen — a gap in `seq` — after more than `MAX_PROPOSAL_CHAIN`
  proposals between two updates). The controller walks back by `seq`, so trimmed copies
  are still recognised as seen. A host that never calls
  `update` again leaves the promise pending until the next update / document
  replacement / `destroy`. Before the first `update` ("no document yet") / after `destroy`
  ("controller destroyed"): resolved rejected at once, nothing dispatched. See [`1-core/1.5-editor.md`](../1-core/1.5-editor.md)
  "Host proposals".
- `setSuggestionStyles(styleOf | null)` — live per-group suggestion styling (e.g. per
  `metadata.source`), re-derived through proposals, accept / reject and undo (1.9).
- `runCommand(command)` — run a host command by name
  (`config.extensions.commands`) or value against the current state with the
  controller's `dispatch`; returns whether it ran.
- **Decorations** (see
  [`1-core/1.9-decorations.md`](../1-core/1.9-decorations.md)):
  `setDecorations(decorations, basedOn?)` replaces the HOST layer (computed
  against the current document — or against `basedOn`, an older State an
  asynchronous host computed them on; then position-mapped through every later
  `update()` until replaced; a decoration whose range is deleted disappears).
  For `basedOn` the controller keeps a core `MappingLog` (`createMappingLog`:
  reset on the first `update()` and whenever a transition is unknown — its
  `lastChange` does not start at the previous State — else
  `record(prev, next, mapping)` with the one `transitionMapping` computed per
  transition) and maps the decorations with `mapDecorations(decorations,
  log.mappingFrom(basedOn), state)`; an unknown or evicted `basedOn` drops them
  rather than draw them on the wrong text (same contract as digital; the React
  `EditorView` passes its `decorationsBasedOn`); `decorations` reads
  the mapped host set — before the first `update()`, the queued host set as
  given (not yet validated against a document). The controller owns a core
  `DecorationLayers` and every `update(state)` calls `layers.advance(prev,
  state)`. Inline decorations paint `style.backgroundColor` bands and
  `style.underline` strokes; block decorations paint a background in the block
  box's background slot (under its borders, image and children — a CSS
  background, as in digital); widget decorations render as DOM overlays
  (below). The optional `onDecorationPointer` option reports
  `PrintDecorationPointerEvent`s (`enter` / `leave` / `click`, the live
  decoration, the fragment's viewport `rect` and all its on-screen `rects`) —
  the same shape as digital's `DecorationPointerEvent`. Calls made before the
  first `update()` are queued and applied to its document (`decorations`
  option = initial host set).
- **Built-in highlights are decoration layers.** `setFindHighlights(matches,
  activeIndex)` / `clearFindHighlights()`, `setCommentHighlights(highlights)` /
  `clearCommentHighlights()` (`{ commentId, active }`), and
  `setSuggestionHighlights(highlights)` / `clearSuggestionHighlights()`
  (`{ suggestionId, active }`) set the find / comment / suggestion layers (core's
  `findHighlightDecorations` etc. — ids `tw-find:*`, `tw-comment:*`,
  `tw-suggestion:*` — a find decoration's id is `findDecorationId(match)` =
  `tw-find:${blockId}:${start}` — core's fill colours). There is ONE find
  layer: `setFindHighlights` / `clearFindHighlights` write it directly (no
  separate state; mapped through edits like any decoration; not a session, so
  `findStatus` / next / prev / replace ignore it); `findStart` takes it over;
  while a session is open, its refresh owns it after every document change;
  `findClose` clears it. Comment ranges are position-mapped too, and re-scanned
  from the document only when an edit adds, removes or moves a comment marker;
  suggestion ranges are mapped, and re-scanned when an edit touches a tracked
  run. The host re-calls only when the SET or active flag changes. The host owns
  WHICH comments/suggestions are lit (the engine owns WHERE). The
  `CommentHighlight` / `SuggestionHighlight` types are core's, re-exported.
- **Find session + navigation** (Find & Replace UI). Print and digital share ONE
  geometry-free find mechanism: core's `createFindSession()`
  (`core/src/editor/find-session.ts`) owns the query, the match list, the active
  index and navigation; the controller draws `matches()` / `activeIndex()` as the
  find decoration layer and owns only the print-specific scrolling.
  `findStart(query, options?)` starts the session from the caret (the first
  match at-or-after it is active — Google Docs "find from here", wrapping to 0;
  cross-context matches never count as "after") and scrolls the active match into
  view. `findNext()` / `findPrev()` advance/retreat with WRAP and scroll (no-op
  with no matches). `findClose()` closes the session and clears the highlights.
  They return core's `FindStatus = { total, activeIndex }` (re-exported by print;
  `{ 0, -1 }` with no session / no matches). **None of them move the document
  selection** — the active match is scrolled into view by its own start
  `PixelPosition` (`scrollActiveMatchIntoView` → `scrollVisualIntoView`, no focus
  guard, since the find bar holds focus), never by moving the caret. `options`
  defaults to `{ caseSensitive: false, wholeWord: false }`.
- **Find status + replace** (Find & Replace UI): `findStatus()` returns the
  session's status — the find bar polls it each render for the authoritative
  "n of N", because the replace methods dispatch asynchronously (the post-replace
  count only lands after the host reducer feeds the new state back through
  `update()`). `replaceActive(replacement)` / `replaceAll(replacement)` dispatch
  the session's `replaceActiveAction` / `replaceAllAction` (`REPLACE_MATCH` with
  the active match / `REPLACE_ALL` with every match, one undo step each) and
  return the current (pre-refresh) status; no-op (no dispatch) with no session /
  no active match. The active index is NOT advanced manually — the session's
  `refresh` on the next `update()` moves it to the first match after the
  replacement text (wrapping to the first match), so a replacement containing the
  query cannot trap Replace on the same spot (Google Docs "advance after
  replace"). The actual edit is the engine's job (the action handlers).

## Internal modules

The controller is a single file (`editor-controller.ts`) that composes
the other print modules:

- **Canvas management.** Owns either one canvas (non-paginated) or a
  pool of per-page canvases (paginated). Resizes them based on the
  document's layout output and the device-pixel-ratio.

- **Painting.** On each `update(state)`, selects the correct paint
  function (`paintCanvas` for single-canvas, `paintPage` per page) and
  passes the relevant `LayoutBox` plus the controller's `PaintCache`
  instance. The cache enables the renderer's incremental short-circuit;
  see [`2.5-canvas-renderer.md`](./2.5-canvas-renderer.md) and
  [`2.6-paint-cache.md`](./2.6-paint-cache.md).

- **Input listeners.** Installs DOM listeners on the container and a
  hidden textarea (the textarea captures keystrokes, IME composition,
  and clipboard events while the canvas captures mouse and scroll).
  Translates keyboard events through `key-handler` into a `KeyResult =
  EditorAction | NavIntent`: an `EditorAction` forwards straight to the
  dispatch callback (Enter → `SPLIT_NODE`; Shift+Enter → `INSERT_LINE_BREAK`, a soft
  line break); a `NavIntent` (the geometric keys — Arrow / Home /
  End / Cmd-Backspace) runs through `resolveNavIntent(intent, state,
  layoutTree, measurer, componentRegistry)` (see `2.1-layout-driver.md`)
  which returns the geometry-free `SET_SELECTION` / `DELETE_RANGE` to
  dispatch (or `null` for a no-op). Mouse/scroll use inline logic that
  also produces `EditorAction`s. Clipboard events are detailed in
  **Clipboard wiring** below.

- **Layout-driver.** Owns a `createLayoutDriver(layoutConfig)` instance.
  On every `update(state)` it calls `driver.rebuild(state.state,
  containerWidth, state.lastDirtyIds)` to build the layout tree (core's
  reducer holds none) — incrementally when `lastDirtyIds` is a non-null
  set, fully otherwise. The resulting `LayoutBox | VirtualLayoutTree` is
  what paint and the geometry queries read. See `2.1-layout-driver.md`.

- **Cursor blink.** A `setInterval`-driven timer that toggles cursor
  visibility every 500ms while the editor is focused. The timer calls
  the paint function with the current state; the renderer's root
  short-circuit + `paint.draw` viewport culling keep the cost minimal.

- **Scroll syncing.** When pagination is active, scrolls between page
  canvases by adjusting their CSS positions. When non-paginated,
  delegates scroll to the surrounding container.

- **Image cache.** A separate `ImageCache` instance manages async-
  loaded image resources for image blocks; when an image finishes
  loading, the controller re-paints to render it.

- **Decorations.** One mechanism for every decoration and built-in
  highlight. `decorationRectsFor(root, pageIndex)` resolves the merged set into
  `DecorationRect[]` for ONE paint target via `computeDecorationRects`
  (`decoration-geometry.ts`, internal): a page visits only the blocks with
  boxes / lines on it (`getLineIndex(page).byBlock`, plus a memoized block-box
  index for block decorations); the single canvas visits only the blocks with a
  box inside a band (a culled walk of the layout tree — O(visible), never the
  whole set or document) of the viewport plus
  one viewport each side (re-resolved when scrolling leaves the band). Each
  inline segment's per-line rects come from the selection-rect machinery
  (`computeSelectionRectsForPageRange` — a block on one page takes its page from
  the plan; a block straddling pages resolves its endpoints' pages via
  `resolvePixelPosition`). Resolution is LAZY (only pages being painted or
  hit-tested) and cached twice: per target by (layout tree, merged set, page
  box, document[, band]) — cleared on every `update()` and when a page's canvas
  is released, and never filled for off-screen pages resolved only for a
  pointer `rects` query — and per segment by (page box, decoration object,
  offsets, a `WeakMap` keyed by the page box). So a blink repaint resolves
  nothing, a keystroke re-resolves only the re-laid-out page, and a
  `setDecorations` that changes one decoration re-resolves only that one. The
  renderer's `addDecorationDirty` then repaints only the pages whose fragments
  actually changed. An empty set is detected by identity
  (`EMPTY_DECORATION_SET`). Fragments and block-box rects are in the PAINTED
  frame: the block-box walk applies each box's `relativeOffset` and records the
  cumulative `position: relative` shift per block, which is added to that
  block's line-geometry fragments — so paint, dirty tracking and pointer
  hit-testing share one frame.
  **Colours** are host CSS strings, so before painting each one is resolved
  (`resolveColor`) through a hidden probe inside the container, THROUGH THE
  PROPERTY IT STYLES (`background-color` for bands / block fills,
  `text-decoration-color` for underlines — exactly what digital sets): a plain
  colour is validated by setting that property and handed to the canvas as
  written; a `var()` colour is resolved natively — read back from
  `getComputedStyle(probe)` for that property, nested fallbacks included,
  against the editor's cascade — so an UNSET variable falls back the way CSS
  does for that property (a background to transparent → nothing painted, an
  underline colour to currentcolor → the run's text colour, detected via a
  sentinel probe `color`), never to an inherited `color`; manual substitution (innermost first,
  balanced parentheses, custom properties looked up on the probe and its
  ancestors) only where the engine leaves `var()` unresolved (jsdom). The
  CSS-wide keywords (`inherit` / `initial` / `unset` / `revert[-layer]`) are
  rejected; `currentColor` means the decorated run's / box's text colour. An
  invalid colour is DROPPED (that fill / underline is not painted) — a canvas
  silently ignores an invalid `fillStyle` and would otherwise reuse the previous
  fill. Resolutions are memoized per string; the memo is cleared on every
  decoration / highlight change (not per keystroke), so a theme switch applies
  on the next one. A colourless underline uses the decorated run's text colour.
  **Underline side.** Horizontal text: just under the line baseline. Vertical
  text: the line-right (physical right) side. CSS Text Decoration 3 leaves
  `text-underline-position: auto` to the UA (its sample UA stylesheet uses
  `right` for Japanese / Korean / Mongolian and `left` for Chinese); browsers
  draw an `auto` underline in vertical text on the right, which is what the
  digital backend's plain CSS underline shows — print matches it.
  **Widget overlays** (`decoration-overlay.ts`): the canvas cannot host DOM
  inline, so each widget is an absolutely-positioned element (host `toDom(doc)`
  node, else `text`; `class` and non-reserved `attributes` applied with digital's
  reserved-name filter; `data-tw-deco` / `data-tw-widget` stamped) in an overlay
  layer inside the container, placed at its anchor's caret rect
  (`resolvePixelPosition` with the page as caret hint + the page slot's `top`;
  `side: -1` translates it to end at the caret). Widgets are found through the
  VISIBLE pages' line indexes (`forBlock(id).widgets` per block on the page —
  never the whole set); a widget in a header/footer body gets one element per
  visible page showing it. Elements are re-placed after every paint whose
  layout / set / visible pages changed (reused when their look is unchanged) and
  removed when their page leaves the screen. Widgets occupy zero document
  offsets: they are not in the document, the caret and hit-test never see them,
  and copy never includes them (`user-select: none`, outside the focus host).
  They overlay the text after their anchor and do NOT reflow it; widgets that
  reflow the text around them (inline ghost text) are not built on this
  backend.
  **Pointer events** (`decoration-pointer.ts`, wired only when
  `onDecorationPointer` is set): `mousemove` / `mouseleave` / `click` on the
  container. The decorations under the pointer are the widget overlay under the
  target, else every painted fragment (from the same cached
  `decorationRectsFor`; each fragment carries its live decoration) whose rect
  contains the page-local point — geometric containment, so margins beside a
  line and the gaps between pages report nothing. Moves diff the set to emit
  `enter` / `leave`; a click reports every decoration under it. The tracker
  keeps each hovered decoration as last seen, and `sync()` — run after every
  `update()` and every decoration / highlight setter — re-hit-tests the resting
  pointer (re-deriving the element under it with
  `ownerDocument.elementFromPoint`, so a recycled canvas or rebuilt widget
  element is not mistaken for a change; the stored target is the fallback only
  when hit-testing is unavailable), so a decoration removed or reflowed out from under it emits `leave`
  (with the decoration as last seen). `rects` are the decoration's fragments on
  every on-screen page it covers (block-scoped page lookup via the page plan),
  mapped to the viewport (container rect + slot `top`).

- **Accessibility mirror.** Behind the default-off `accessibilityMirror`
  option, the controller owns a `DomMirrorHost` and, after each paint, calls
  `syncTree(buildAccessibilityTree(state), globalFieldValues)` +
  `syncSelection(...)`. The field-values argument is `layoutTree.globalFieldValues`
  in the virtualized paginated case (the layout-resolved page-count / cross-ref-page
  values the host binds onto page-valued field runs) and an EMPTY map on the
  non-virtual `LayoutBox` / null path (no pagination, no page-field resolution).
  The a11y tree's `suggestionView` must match the view the field values were
  resolved at (both `"suggesting"` today). See
  [`2.11-dom-mirror-host.md`](./2.11-dom-mirror-host.md).

## Paint cache lifetime

The controller creates one `PaintCache` per canvas at construction time
(or per page at first paint, in paginated mode). The cache lives for
the controller's lifetime. On `destroy()`, the cache is dropped along
with everything else.

Reuse fires across the controller's lifetime: the second call to
`update` benefits from the first call's hashes, the third from the
second's, etc. This is the load-bearing optimization for cursor blink
and cursor moves: when only the cursor's position changed, the layout
tree's root reference is unchanged, the cache short-circuits, and the
paint walk does no work beyond redrawing the cursor itself.

## Why the controller exists in `print` rather than `core`

The controller is mutable: it owns DOM listeners, animation timers,
canvases. `core` is pure — it cannot hold mutable references or react
to time. Putting the controller in `print` keeps the boundary clean: the
controller is the only mutable thing in the engine boundary, and
everything mutable lives behind its interface.

## Reference

### Public API

```ts
interface EditorControllerOptions {
  readonly measurer: TextShaper | TextMeasurer;
  readonly dispatch: (action: EditorAction) => void;
  readonly pageHeight?: number;
  readonly pageGap?: number;
  // Print-backend layout-driver inputs: the render→cascade→layout
  // pipeline lives in the controller's layout-driver now (not core's reducer), so
  // the HOST supplies these here. `pageConfig` + `hyphenator` LEFT core's
  // `EditorConfig`. See `2.1-layout-driver.md`.
  readonly pageConfig?: PageConfig;
  readonly hyphenator?: Hyphenator;
  // The host's core `EditorConfig` — pass the SAME object the reducer runs with.
  // The controller DERIVES both registries from it (there are no separate
  // registry options, so the controller cannot paint / hit-test / copy with a
  // registry that differs from the editing one): `attrRegistry` → the
  // layout-driver's render + cascade (host marks paint via `toStyle`) and copy/cut
  // (`copy: "drop"` marks stripped); `componentRegistry` → the layout-driver's
  // render, the object-selection hit-test pre-pass and NavIntent
  // resolution; `extensions` → the host keymap / `runCommand`. Omitted → the
  // built-in registries, no extensions.
  readonly config?: Pick<EditorConfig, "componentRegistry" | "attrRegistry" | "extensions">;
  readonly accessibilityMirror?: boolean;
  // initial host decorations + decoration pointer events.
  readonly decorations?: readonly Decoration[];
  readonly onDecorationPointer?: (event: PrintDecorationPointerEvent) => void;
  // A peer update carried legacy inline storage: the controller HALTED (once per halt;
  // again while halted if legacy storage returns after onDocumentCompatible).
  readonly onIncompatibleDocument?: (report: IncompatibleDocumentReport) => void;
```

### PDF export

`exportToPdf(emit)` composes the PDF without importing `@taleweaver/pdf` at all:
it builds a **PDF-type-free** `PrintPdfEmitInput` and hands it to the injected
`emit`. It is a **pure query**: it reads the controller's live `state` +
`virtualTree` + measurer and composes that input, mutating nothing.
The composition mirrors the three navigation features the PDF emitter exposes:

- **Pages** — `pageCount` from `virtualTree.plan.entries.length`; each `PageBox`
  from `virtualTree.getPage(i)` (the same per-page materialization paint uses).
- **Internal `/GoTo` links + `/Outlines` bookmarks** — the destination resolver
  from `core`'s `makeInternalDestinationResolver(state, virtualTree, measurer,
  parentOf)`, and the bookmark tree from `buildPdfOutline(state, virtualTree,
  measurer, parentOf)`, where `parentOf = makeBlockParentLookup(state)`. External
  `/URI` links ride along inside the page content streams.

It returns the PDF **bytes** (`Uint8Array`). Triggering a browser download
(`new Blob([bytes], { type: "application/pdf" })` + a download anchor) is the
**host's** concern — the engine does not own download UX.

**Font / image bytes are an injection seam, not a degraded cut.** The canvas
shaper carries no font-program or raster bytes, so the host supplies them through
the injected emitter: `createPdfEmitter({ fontProvider?, imageProvider? })` from
`@taleweaver/pdf` is the standard adapter — it maps the raw `accessibilityTree`
to the `PdfStructureNode` model and threads the providers into `emitPdf`. Absent a
`fontProvider`, text embeds with the standard-14 fonts; absent an `imageProvider`,
images draw as grey placeholders. The engine composes a complete, navigable PDF
either way. The dependency is **one-way**: `@taleweaver/print` imports zero
`@taleweaver/pdf` symbols; `@taleweaver/pdf` depends on `@taleweaver/print` for the
`PrintPdfEmitInput` bridge type.

**Boundaries.** `exportToPdf` throws when no document is loaded, and for the
non-paginated (float/clear) fallback (`virtualTree === null`) — paginated
documents only. A default `fontProvider` derived from the document's
actually-loaded fonts, and a download / save UI, are not implemented.

> ## ⚠️ Status: this controller is VIRTUALIZED (the section below predates it)
> The paginated controller does NOT eagerly materialize every page. `layoutTree`
> is `LayoutBox | VirtualLayoutTree` (discriminated by `type: "virtual-root"`); in
> virtual mode it holds a `PagePlan` and calls `getPage(visible ∪ cursorPage)` —
> positioning ONLY the pages it paints/measures (memoized), never the whole doc.
> No consumer positions the whole document: the non-paginated single-canvas paths
> (paint sizing, `pageIndex === null` selection/find/comment rects) read the
> already-positioned `LayoutBox` directly via a `nonPaginatedTree()` narrow; the
> whole-tree-positioning bridge has been deleted. Per-page canvases come from a pool driven
> by an `IntersectionObserver` whose `root` is the detected scroll parent
> (`scrollParent instanceof HTMLElement ? scrollParent : null` — an editor embedded
> in a scrollable `<div>` observes against that div; the window-scroll fallback maps
> to `null`/the viewport). Concretely the real internal state includes
> `layoutTree: LayoutBox | VirtualLayoutTree`, `virtualTree: VirtualLayoutTree |
> null`, `positionedPages: LayoutBox[]`, `pageSlotGeoms: PageSlotGeom[]` — NOT a
> single eager `pages: LayoutBox[]`. See
> `editor-controller.ts` for the authoritative model. The field/algorithm/listener
> lists below are kept for shape but are stale on these virtualization specifics.

### Internal state

The controller is a closure over private mutable state:

- `state: EditorState | null` — the most recent state passed via `update`.
- `singleCanvas: HTMLCanvasElement | null` — non-paginated mode only.
- `singleCtx: CanvasRenderingContext2D | null`.
- `activeCanvases: Map<number, HTMLCanvasElement>` — paginated mode; one per page index.
- `layoutTree: LayoutBox | VirtualLayoutTree | null` — BUILT BY the controller's
  layout-driver on each `update` from `state.state` + `state.lastDirtyIds` (core
  holds no layout tree); `virtualTree`, `positionedPages: LayoutBox[]`,
  `pageSlotGeoms: PageSlotGeom[]` — the virtualized page model (see the status
  banner above). [supersedes the old eager `pages: LayoutBox[]`]
- `canvasCache: PaintCache` — shared paint cache for non-paginated mode.
- `pageCaches: Map<number, PaintCache>` — per-page paint caches.
- `imageCache: ImageCache` — async image loader.
- `cursorPos: { x, y, height, lineY, lineHeight, pageIndex }` — last-resolved cursor.
- `selectionRects: SelectionRect[]` — last-resolved selection rectangles.
- `find: FindSession` — core's find session (query, matches, active index,
  navigation); its matches are drawn as the find decoration layer.
- `layers: DecorationLayers` — core's suggestion / comment / find / host layers,
  advanced on every `update()`; `pendingLayerOps` queues layer calls made before
  the first document arrives.
- `decoRectCache: Map<pageIndex | -1, …>` — per-paint-target decoration fragments
  (see *Decorations* above); cleared on every `update()`, pruned with released
  canvases and removed page slots.
- `pendingHost` — the queued host decorations before the first `update()`.
- `colorCache` + a hidden colour probe — decoration colour resolution.
- `widgetOverlay` — the widget DOM overlay layer.
- `focused: boolean` — whether the textarea has focus.
- `cursorVisible: boolean` — flips on each blink-timer tick.
- `blinkIntervalId: number | null` — `setInterval` handle.
- `isDragging: boolean`, `dragAnchor: Position | null` — drag-selection state.
- `isComposing: boolean` — IME composition state.
- `destroyed: boolean` — set by `destroy()` to short-circuit pending callbacks.

### Lifecycle in detail

`createEditorController(container, options)`:

1. Style the container (`position: relative`, `outline: none`, `cursor: text`, `userSelect: none`).
2. Create a hidden `<textarea>` inside the container, focus it.
3. Install event listeners: on the textarea (keydown, **input**, compositionstart, compositionend, copy, cut, paste, focus, blur); on the container (mousedown; plus mousemove / mouseleave / click for decoration pointer events when `onDecorationPointer` is set); on **`document`** (mousemove, mouseup — so a drag continues outside the editor and `destroy()` must remove them from `document`); and on the scroll parent (scroll, passive). (No `beforeinput`, `compositionupdate`, or `wheel` listener exists.)
4. Create the `canvasCache: PaintCache`.
5. Start the cursor-blink interval (paused when not focused).
6. Return the `EditorController` instance.

`controller.update(state)`:

1. Store `state` in the closure.
2. Resolve the caret. In virtual mode this positions ONLY the cursor's page via
   `getPage(cursorPageIndex)` (memoized) — never the whole tree.
3. Compute selection rects PER PAGE via `computeSelectionRectsForPage(...)` for the
   pages that intersect the selection — not one eager `computeSelectionRects` over
   a whole positioned tree. (In paginated mode the whole document is never
   positioned; only the non-paginated single-canvas path reads a positioned
   `LayoutBox` directly.) The MAIN document selection threads the `EditorState`'s
   `anchorAffinity` (anchor side) and `caretAffinity` (focus side) into these calls,
   enabling the bidi visual-extent highlight so a Shift+Arrow through an RTL
   run grows monotonically; decoration fragments (incl. the built-in highlights) pass
   NO affinities (plain logical spans → the logical-range path).
3a. Find live-recompute (Find & Replace): if the find session is open and the
   document changed, `find.refresh(state, mapping)` (the transition's mapping)
   re-finds only in the edited blocks, keeps the active occurrence through the
   edit and, right after a replace, moves to the first match after the
   replacement (wrapping); it returns `changedBlocks` — `null` ⇒
   `layers.setFind(...)`, else `layers.patchFind(..., changedBlocks)` redraws only
   those blocks' find decorations. The recompute does NOT scroll — only
   `findStart`/`findNext`/`findPrev` scroll, so a recompute mid-typing never
   yanks the viewport.
3b. Decoration layers: before the caret/selection work, ONE
   `transitionMapping(prev, state)` is computed and shared: it is recorded in the
   mapping log, `layers.advance(prev, state, mapping)` carries every layer
   through the transition (the first `update()` resets the log and replays
   queued layer calls instead), and an open find session refreshes with it (3a).
   The fragment cache is cleared. After the paint, the decoration pointer re-hit-tests a resting
   pointer. No geometry is resolved here — the per-page
   fragments are resolved lazily inside `paintPages` / `paintSingle` (see
   *Decorations* above), and widget overlays are re-placed after the paint.
4. Detect paginated vs non-paginated (`layoutTree.type === "virtual-root"`, or
   `LayoutBox` children containing `PageBox`es; an empty `pageSlotGeoms` ⇒ the
   single-canvas non-paginated path). The page slots / single canvas and the
   observer are re-synced only when the layout tree changed identity; a
   selection-only update (the driver returns the prior tree) just moves the
   textarea, so a caret move costs no per-page DOM work.
5. In non-paginated mode: ensure the single canvas exists, sized to
   `layoutTree.width × height × dpr`. Call `paintCanvas(...)` with `canvasCache`.
6. In paginated mode: the page-canvas POOL (driven by an `IntersectionObserver`
   whose `root` is the detected scroll parent — `scrollParent instanceof
   HTMLElement ? scrollParent : null`, so an editor inside a scrollable container
   observes against that container rather than the viewport) acquires/releases
   per-page canvases for visible pages; for each, call `paintPage(getPage(pageIndex),
   ...)` with the per-page `PaintCache`.
7. Smooth-scroll the cursor into view: `scrollCursorIntoView()` (guarded on
   `focused && state`) delegates to `scrollVisualIntoView(pos)` — a generalized
   smooth-scroller taking a `{ pageIndex, y, height }`. The cursor path passes
   `cursorPos`; the find session passes an active match's start `PixelPosition`.
   `scrollVisualIntoView` has NO focus/state guard (it reads only `pos` + the
   closure-local `pageSlotGeoms`/`container`/`scrollParent`), so the find bar — which
   holds focus, not the canvas — scrolls a match into view regardless of the editor's
   focus, by passing the match position explicitly (never by moving the caret).

`controller.destroy()`:

1. Set `destroyed = true`.
2. Clear the blink interval.
3. Cancel pending RAFs.
4. Remove DOM listeners.
5. Remove the textarea, canvases, spacer divs.
6. Clear `canvasCache` and `pageCaches`; close the find session; drop queued layer calls and the decoration
   fragment cache; remove the widget overlay and the decoration pointer
   listeners.

### Clipboard wiring

The print controller implements the full three-flavor clipboard:

**copy / cut:** `extractFragment(state, selection)` produces a fragment `State` (`copy: "drop"` marks stripped)
(see [`1.5-editor.md`](../1-core/1.5-editor.md#clipboard-and-paste) and
[`1.7-serialization.md`](../1-core/1.7-serialization.md#clipboard-fragment-helpers)).
Three flavors are written synchronously in the `ClipboardEvent` handler:
- `text/plain` — `extractText` (unchanged from the plain-text path).
- `text/html` — `encodeHtml(fragment)` (the `taleweaver-html` encoder).
- `TALEWEAVER_CLIP_MIME` (`"application/x-taleweaver-clip"`) — `encodeFragmentClip(fragment)` (lossless: binary-serialize → base64).

**paste (structured):** the `ClipboardEvent` handler calls `preventDefault`
unconditionally before the `!state` early-return guard (blocking the browser's
default paste from leaking into the hidden textarea), then reads all three flavors
from `e.clipboardData` and dispatches `PASTE { text?, html?, clip? }` with
whichever are non-empty. Core's `handlePaste` resolves the fragment by priority
(clip → html → text) and calls `insertFragment` or the suggesting-mode path.

**paste without formatting (Ctrl/Cmd+Shift+V):** a `keydown` handler for this chord
calls `navigator.clipboard.readText()` (async — requires a secure context +
Clipboard API permission) and dispatches `PASTE { text }` once the promise resolves.
Because only `text` is present in the payload, `handlePaste` falls straight to the
plain-text line path even when the clipboard contains richer flavors. On permission
denied or unavailable secure context the call is a graceful no-op.

`browserHtmlParser` is injected into `EditorConfig.htmlParser` by the HOST — for
example, the React adapter (`packages/react/src/use-editor.ts`) sets
`htmlParser: browserHtmlParser` in the `EditorConfig` it passes to `reduceEditor`.
The print controller itself takes only a `dispatch` callback and is unaware of HTML
parsing; it never constructs an `EditorConfig` or touches `htmlParser`.

### Cursor-blink timer

```
const BLINK_INTERVAL_MS = 500;

function startBlink():
  stopBlink();
  cursorVisible = true;
  if (!focused) return;
  blinkIntervalId = setInterval(() => {
    cursorVisible = !cursorVisible;
    paint();
  }, BLINK_INTERVAL_MS);

function stopBlink():
  if (blinkIntervalId !== null) {
    clearInterval(blinkIntervalId);
    blinkIntervalId = null;
  }
```

When the engine state hasn't changed between blinks, the layout tree is reference-equal across `paint()` calls; the renderer's root short-circuit keeps the cost negligible.
