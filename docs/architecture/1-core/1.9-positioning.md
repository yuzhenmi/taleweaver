# 1.9 — Positioning, transforms, opacity

This module covers the CSS positioning scheme (`position: relative | absolute`),
2D transforms (`transform`), and opacity. It cuts across the layout pass
(absolute positioning's containing-block resolution and out-of-flow
placement), the paint pass (transform application + alpha blending), and
the cascade (the schema additions).

## Schema additions

Three new property families on `Style` and `ComputedStyle`.

### Positioning

```ts
type Position = "static" | "relative" | "absolute" | "fixed";

interface Style {
  // ... existing fields
  readonly position?: Position;

  // Logical-axis insets (used by relative + absolute + fixed)
  readonly insetBlockStart?:  LengthOrAuto;
  readonly insetBlockEnd?:    LengthOrAuto;
  readonly insetInlineStart?: LengthOrAuto;
  readonly insetInlineEnd?:   LengthOrAuto;

  readonly zIndex?: number | "auto";
}
```

`Position`'s initial value is `"static"`. `inset*` initial values are `"auto"`. `zIndex`'s initial is `"auto"` (auto-stacking; see below).

The four logical inset properties (`insetBlockStart`, etc.) follow the same logical/physical mapping as margins/paddings (per [`1.0-styles.md`](1.0-styles.md)).

`fixed` is **out of scope** per [CLAUDE.md](../../../CLAUDE.md) — the engine paints to canvases that scroll with content, and `fixed` is a viewport-relative concept. Listed in the type for symmetry but treated as `"absolute"` by layout.

### Transforms

```ts
type TransformFn =
  | { readonly fn: "translate"; readonly tx: Length; readonly ty: Length }
  | { readonly fn: "translateX"; readonly tx: Length }
  | { readonly fn: "translateY"; readonly ty: Length }
  | { readonly fn: "rotate"; readonly angleRad: number }
  | { readonly fn: "scale"; readonly sx: number; readonly sy: number };

interface Style {
  readonly transform?: readonly TransformFn[];        // applied right-to-left per CSS spec
  readonly transformOrigin?: { readonly x: LengthOrPercent; readonly y: LengthOrPercent };
}
```

`transform` is a sequence of functions composed in CSS order (right-to-left when read in CSS string form; left-to-right in the array). `transformOrigin` defaults to `{ x: "50%", y: "50%" }` — the box's center.

Transforms apply at paint time and at hit-test time; they do **not** affect layout. A transformed box's `LayoutBox` geometry stays in the pre-transform coordinate space.

### Opacity

```ts
interface Style {
  readonly opacity?: number;        // 0..1; default 1
}
```

## Layout integration

### `position: relative`

A relatively-positioned box lays out in flow (its `LayoutBox` keeps the static position) and then offsets by `inset*` values at paint time. The offset is purely visual; the box's `LayoutBox` geometry remains pre-offset.

Concretely: the BFC lays out the box normally. The painter reads `cs.position`, `cs.insetBlockStart`, etc. and adds the resolved offsets to the box's physical coordinates before drawing.

`position: relative` does NOT establish a new BFC by default. It does establish a **containing block for absolutely-positioned descendants** — see below.

### `position: absolute`

An absolutely-positioned box is removed from normal flow. It does not contribute to the parent BFC's block-axis advancement. Its containing block is the nearest ancestor that:

- Has `position: relative`, `absolute`, or `fixed`, or
- Has `transform` set (transformed boxes establish a containing block per CSS Transforms 1), or
- Is the document root (the initial containing block).

The layout pass collects absolutely-positioned descendants during its main walk and lays them out in a separate phase against their resolved containing block.

#### Containing-block stack

`LayoutContext` gains a field:

```ts
interface LayoutContext {
  // ... existing fields
  readonly absoluteContainingBlock: AbsoluteContainingBlock;
}

interface AbsoluteContainingBlock {
  readonly box: LayoutBox;             // the establishing ancestor's layout box
  readonly inlineSize: number;
  readonly blockSize: number;
  readonly origin: { x: number; y: number };  // physical absolute position of the containing block's content area
}
```

`makeChildContext` updates `absoluteContainingBlock` when entering a box that establishes one (the predicate above). The root context's `absoluteContainingBlock` is the viewport / page.

#### Out-of-flow collection and layout

During the main BFC/IFC walk, when a child has `cs.position === "absolute"` (or `"fixed"`):

1. Skip the child for in-flow placement (the BFC's `childBlockOffset` does not advance).
2. Add the child to the current `absoluteContainingBlock`'s pending-list.

After the in-flow walk completes for the box that established the absolute containing block, the layout pass takes a second pass over the pending-list:

```
for absChild in pending:
  containingBlockInlineSize = abc.inlineSize
  containingBlockBlockSize  = abc.blockSize

  // Resolve box position from inset values
  insetStart = resolveInset(abc.cs.insetInlineStart, containingBlockInlineSize)
  insetEnd   = resolveInset(abc.cs.insetInlineEnd, containingBlockInlineSize)
  inlineSize = (cs.inlineSize == "auto")
                 ? (containingBlockInlineSize - insetStart - insetEnd)
                 : resolveBoxInlineSize(...)
  blockSize  = (cs.blockSize == "auto")
                 ? lay-out-against-content-then-measure
                 : resolveBoxInlineSize-style for block axis

  // Position
  if (cs.insetInlineStart != "auto"):
    childInlineOffset = abc.origin.inlineOffset + insetStart
  else if (cs.insetInlineEnd != "auto"):
    childInlineOffset = abc.origin.inlineOffset + (containingBlockInlineSize - insetEnd - inlineSize)
  else:
    childInlineOffset = abc.origin.inlineOffset    // static-position fallback (where the box would have been in flow)

  // Symmetric for block axis

  // Lay out the absolutely-positioned box recursively at this position
  absBox = layoutBlock(absChild, childInlineOffset, childBlockOffset, abcCtx, shaper)
  abc.box.absoluteChildren.push(absBox)
```

The result: `LayoutBox` gains an optional `absoluteChildren: readonly LayoutBox[]` field (empty when no abs-pos descendants). The painter walks `box.children` then `box.absoluteChildren` in z-index order.

### Transforms in layout

Transforms are paint-time only. A `transform`-bearing box still occupies its untransformed space in the layout tree. Its scrollable area, hit-test region, and parent's flow position all use the pre-transform geometry.

Exception: a `transform`-bearing box establishes a containing block for its absolutely-positioned descendants (per CSS Transforms 1 §6). Layout honors this when computing `absoluteContainingBlock`.

## Paint integration

### Stacking contexts and z-index

Boxes paint in document order by default. Three triggers establish a new **stacking context**:

- `position: relative | absolute | fixed` with `z-index !== "auto"`.
- `opacity < 1`.
- `transform` set.
- (Future: `filter`, `mix-blend-mode` — out of scope per CLAUDE.md.)

Within a stacking context, children paint in this order:

1. Negative `z-index` boxes (sorted by z-index ascending).
2. The box's own background and borders.
3. In-flow non-positioned descendants (recursive paint of normal children).
4. Floats.
5. In-flow `position: relative` descendants without z-index, in document order.
6. `position: absolute | fixed` descendants with `z-index: "auto"`, in document order (per their stacking context).
7. Positive `z-index` boxes (sorted by z-index ascending).

The painter walks the layout tree in this order. `LayoutBox` gains a `stackingContextRole: "none" | "self" | "child"` (computed at layout time from `cs.position`, `cs.zIndex`, `cs.opacity`, and `cs.transform`) so the painter can detect stacking-context boundaries cheaply.

### Transform application

Before painting a transformed box, the painter:

1. Computes the transform-origin in absolute coordinates: `origin = box.physicalOrigin + transformOrigin`.
2. Saves the canvas context (`ctx.save()`).
3. Translates to `origin`.
4. Applies each `TransformFn` in array order: `translate`, `rotate`, `scale` etc., as `ctx.translate` / `ctx.rotate` / `ctx.scale` calls.
5. Translates back by `-origin`.
6. Paints the box and its descendants.
7. `ctx.restore()`.

Each transform multiplies into the canvas's current transform matrix. Hit-testing applies the inverse: a click at physical `(x, y)` walks the tree, and at each transformed box inverts the transform to get pre-transform coordinates before testing children.

### Opacity

Boxes with `opacity < 1` paint into a **temporary offscreen canvas** at full opacity, then composite onto the parent canvas with `globalAlpha = opacity`. This honors CSS-spec opacity grouping: a half-opaque box with overlapping children reads as one half-opaque region rather than additive opacity blending.

```
function paintBoxWithOpacity(ctx, box, ...):
  if cs.opacity < 1:
    offscreen = new OffscreenCanvas(box.width, box.height)
    paintBoxContents(offscreen.context, box, ...)
    ctx.globalAlpha = cs.opacity
    ctx.drawImage(offscreen.canvas, box.x, box.y)
    ctx.globalAlpha = 1
  else:
    paintBoxContents(ctx, box, ...)
```

## Hit-test integration

`resolvePositionFromPixel` reverses transforms when descending into transformed boxes:

```
function hitTest(layoutTree, x, y):
  walk(box, parentTransform):
    localTransform = parentTransform composed with box.transform
    inversePoint = applyInverse(localTransform, [x, y])
    if inversePoint inside box.bounds:
      candidate = (box, inversePoint)
      for child in box.absoluteChildren ++ box.children:
        recurse(child, localTransform)
```

For untransformed boxes the local transform is identity and the existing hit-test logic applies unchanged.

## Cascade integration

`position`, `transform`, `opacity`, and the `inset*` properties are all in `PROPERTY_META` with `inherits: false`. Cascade resolves them to their initial values when not declared, otherwise applies the declared value verbatim (transforms don't combine via inheritance).

## Performance contracts

- Two-phase layout (in-flow + abs-pos pending-list): O(N + A) where N is in-flow descendants and A is abs-pos descendants. The pending list is small in practice.
- Stacking-context determination: O(1) per box (computed from local computedStyle).
- Transform application during paint: O(1) per transformed box (canvas matrix multiply).
- Hit-test: O(depth × 1) per click; transform inversion is O(1) per transformed box.
