# 1.9 — Positioning, transforms, opacity

This module covers the CSS positioning scheme (`position: relative | absolute`),
2D transforms (`transform`), and opacity. It cuts across the layout pass
(absolute positioning's containing-block resolution and out-of-flow
placement), the paint pass (transform application + alpha blending), and
the cascade (the schema additions).

Positioning is layout **substrate**, not a directly user-exposed Google Docs
feature: Google Docs does not expose raw `position: absolute` to end users.
Positioning is the substrate that a future anchored-object feature (images /
drawings / text boxes) builds on, implemented CSS-correctly so those consumers
can sit on it.

## Status overview

The capability is built in separable whole-capability slices:

- **Schema vocabulary** (`position`, four `inset*`, `zIndex`, `transform`,
  `transformOrigin`, `opacity`) — `[implemented]`.
- **`position: relative`** (paint-time offset) — `[implemented]` (block-level;
  inline-block-relative and caret-for-relative-content are named follow-ups).
- **`position: absolute`** (out-of-flow two-pass layout against an absolute
  containing block) — `[partial]` (single-page complete; the paginated abs-pos
  fragmentation case is a named v1 follow-up).
- **z-index / stacking contexts** — `[implemented]`.
- **`transform`** (paint apply + per-line inverse hit-test) — `[implemented]`
  (translate / translateX / translateY / rotate / scale; transformed-content
  selection-rect and caret geometry are named follow-ups — see below).
- **`opacity`** (offscreen group compositing) — `[implemented]`.

All functional positioning slices — schema / `position: relative` / `position:
absolute` / z-index + stacking contexts / `transform` / `opacity` — are now
built. (`position: absolute` stays `[partial]` ONLY for the paginated abs-pos
fragmentation follow-up; single-page absolute is complete.) The spec
`docs/superpowers/specs/2026-06-08-positioning-design.md` records the slice plan
and resolved design decisions; this doc describes the shipped reality.

## Schema additions `[implemented]`

Three new property families on `Style` and `ComputedStyle` (slice 1). The
position vocabulary lives in `styles/position.ts` (`Position`, `TransformFn`,
`TransformOrigin`); the cascade resolves all nine fields (`position`, four
`inset*`, `zIndex`, `transform`, `transformOrigin`, `opacity`) with
`inherits: false`. **No positioning property enters `UsedStyle`** — every
positioning property is read at its use-site from `ComputedStyle`, and insets in
particular are resolved against the containing block where both the inline and
block percent bases are available (relative in the BFC, absolute in the abs-pos
second pass). `inset*` percents would otherwise resolve against the wrong base:
the abs containing block is a possibly-distant ancestor `computeUsedStyle`
cannot see, and `inset-block-*: %` resolves against block size while
`inset-inline-*: %` resolves against inline size — two distinct bases.

### Positioning

```ts
type Position = "static" | "relative" | "absolute" | "fixed";

interface Style {
  // ... existing fields
  readonly position?: Position;

  // Logical-axis insets (used by relative + absolute + fixed)
  readonly insetBlockStart?:  LengthOrAuto;
  readonly insetBlockEnd?:    LengthOrAuto;
  readonly insetInlineStart?: LengthOrAuto;
  readonly insetInlineEnd?:   LengthOrAuto;

  readonly zIndex?: number | "auto";
}
```

`Position`'s initial value is `"static"`. `inset*` initial values are `"auto"`. `zIndex`'s initial is `"auto"` (auto-stacking; see below).

The four logical inset properties (`insetBlockStart`, etc.) follow the same logical/physical mapping as margins/paddings (per [`1.0-styles.md`](1.0-styles.md)).

`fixed` is **out of scope** per [CLAUDE.md](../../../CLAUDE.md) — the engine paints to canvases that scroll with content, and `fixed` is a viewport-relative concept. Listed in the type for symmetry but treated as `"absolute"` by layout.

### Transforms

```ts
type TransformFn =
  | { readonly fn: "translate"; readonly tx: Length; readonly ty: Length }
  | { readonly fn: "translateX"; readonly tx: Length }
  | { readonly fn: "translateY"; readonly ty: Length }
  | { readonly fn: "rotate"; readonly angleRad: number }
  | { readonly fn: "scale"; readonly sx: number; readonly sy: number };

interface TransformOrigin {
  readonly x: Length;   // percent resolves against the box's own width/height at paint time
  readonly y: Length;
}

interface Style {
  readonly transform?: readonly TransformFn[];        // applied right-to-left per CSS spec
  readonly transformOrigin?: TransformOrigin;
}
```

There is no `LengthOrPercent` alias — `Length` already includes the
`{ unit: "percent" }` variant, so `transformOrigin`'s `x`/`y` are plain `Length`.

`transform` is a sequence of functions composed in CSS order (right-to-left when read in CSS string form; left-to-right in the array). `transformOrigin` defaults to `{ x: 50%, y: 50% }` — the box's center.

In `ComputedStyle` (all required, resolved): `position` defaults to `"static"`;
the four `inset*` are `ComputedLength | "auto"` (default `"auto"`; `em` flattened
to px at cascade time, `percent` kept symbolic for use-site resolution); `zIndex`
is `number | "auto"` (default `"auto"`); `transform` is `readonly TransformFn[]`
(default `[]`); `transformOrigin` defaults to 50%/50%; `opacity` is `number`
(default `1`).

Transforms apply at paint time and at hit-test time; they do **not** affect layout. A transformed box's `LayoutBox` geometry stays in the pre-transform coordinate space.

### Opacity

```ts
interface Style {
  readonly opacity?: number;        // 0..1; default 1
}
```

## Layout integration

### `position: relative` `[implemented]`

A relatively-positioned box lays out in flow (its `LayoutBox` keeps the static position) and then offsets by `inset*` values at paint time. The offset is purely visual; the box's `LayoutBox` geometry remains pre-offset.

Concretely: because inset percents need both axis bases, the **BFC resolves the
physical relative offset during layout** — where the parent's content inline+block
sizes (the relative box's containing block) are both in hand. It maps the box's
logical `inset*` to a physical delta (`logicalToPhysical` axis map;
`insetInlineStart` wins over `insetInlineEnd` when both are set, symmetric for the
block axis; `auto` → 0) and stamps it onto the box as an optional
`relativeOffset?: { readonly dx: number; readonly dy: number }` on `LayoutBoxBase`
(set only when `position === "relative"` and a non-zero offset results, keeping
the untransformed fast path read-free). The painter, after computing the box's
accumulated `(absX, absY)`, adds `dx`/`dy` so the box AND its descendants shift
together (`canvas-renderer.ts` `paintBox`; the dirty-region walk
`walkAndDetectChanges` mirrors the same shift so stale pixels don't linger).
Paint stays dumb — it reads a pre-resolved delta, not the `cs.inset*`.

`position: relative` does NOT establish a new BFC by default. It does establish a **containing block for absolutely-positioned descendants** — see below.

**Known follow-ups (not degraded splits — separable lower-stakes capabilities):**
the `LayoutBox` geometry (and thus the flat `LineIndex`) stays pre-offset, so
caret / hit-test / selection for content INSIDE a `position: relative` box reads
the un-shifted geometry — a NAMED FOLLOW-UP (resolving it reuses the same
per-line transform mechanism a `transform` would). And inline-block `relative`
is wired through the box factory but the IFC does not yet resolve/stamp the
offset — also a NAMED FOLLOW-UP (block-level relative is complete: px/percent on
both axes, start-wins, `auto`, indefinite-block → 0, all writing modes,
descendants shift).

### `position: absolute` `[partial]`

An absolutely-positioned box is removed from normal flow. It does not contribute to the parent BFC's block-axis advancement. Its containing block is the nearest ancestor that:

- Has `position: relative`, `absolute`, or `fixed`, or
- Has `transform` set (transformed boxes establish a containing block per CSS Transforms 1), or
- Is the document root (the initial containing block).

The layout pass collects absolutely-positioned descendants during its main walk and lays them out in a separate phase against their resolved containing block.

#### Containing-block stack

`LayoutContext` (in `layout/layout-context.ts`) gains four positioning fields:

```ts
interface LayoutContext {
  // ... existing fields
  readonly absoluteContainingBlock: AbsoluteContainingBlock;
  // true when the box laid out under this context OWNS the abc (its pending-list
  // is its own fresh one, not shared with an ancestor). The owner drains it in
  // its post-loop second pass; non-owners pass abs children up. Mirrors isBFCRoot.
  readonly ownsAbsoluteContainingBlock: boolean;
  // offset from the current abc's CONTENT origin to this context's box frame, in
  // the abc's coordinate system. Accumulated through non-establishing in-flow
  // descendants so a captured static position stays abc-frame-relative.
  readonly originFromAbc: { readonly inlineOffset: number; readonly blockOffset: number };
}

interface AbsoluteContainingBlock {
  readonly inlineSize: number;                  // abc content-area inline-size (always definite)
  readonly blockSize: number | "indefinite";    // content-area block-size, or "indefinite" when not yet known
  readonly origin: { readonly inlineOffset: number; readonly blockOffset: number };  // content-box top-left in the establishing box's OWN frame
  readonly pending: AbsPosEnvironment;           // shared mutable sink the establishing box drains in its second pass
}
```

Notes on the shipped shape (these correct the earlier sketch): `origin` uses
LOGICAL `{ inlineOffset, blockOffset }`, not `{ x, y }`; `blockSize` is
`number | "indefinite"`, not plain `number`, because the abc box's block-size is
not yet known when `makeChildContext` runs for it (`totalBlockSize` is computed
post-loop). An auto-height containing block therefore carries `"indefinite"`,
and per CSS Positioned Layout §5 a block-axis percent inset against an indefinite
abc resolves as `auto`. `inlineSize` is always concrete (resolved top-down before
children lay out). There is no `box` field on the abc itself — the abc carries
sizes/origin/pending only. The draining box resolves the authoritative abc frame
from its OWN resolved locals (content inline-size, total block-size, padding) in
the second pass, so the placeholder carried in context never mis-positions.

`makeChildContext` replaces `absoluteContainingBlock` with a FRESH abc (fresh
`pending` list, via `createAbsPosEnvironment()`) when the entered box establishes
one — `establishesAbsoluteContainingBlock(cs)` = `position ∈ {relative, absolute,
fixed}` OR `cs.transform.length > 0` (CSS Transforms 1 §6; the transform clause is
inert until the transform slice). Otherwise the parent's abc is inherited, so
abs-pos descendants rise to the nearest establishing ancestor (mirroring how a
`floatEnv` is inherited until a new BFC root). `makeRootContext` seeds the root's
abc to the page/viewport content area (origin `{0,0}`, `blockSize: "indefinite"`)
and sets `ownsAbsoluteContainingBlock: true`. The pending sink is `AbsPosEnvironment`
(`layout/abs-pos-context.ts`): `register(child: PendingAbsChild)` /
`drain(): readonly PendingAbsChild[]`; a `PendingAbsChild` carries the render
node, its computed + used style, and its `staticInlineOffset` / `staticBlockOffset`
(the abc-frame static position used as the `auto`-inset fallback).

#### Out-of-flow collection and layout

This is the absolute-positioning case of the BFC's two-pass out-of-flow handling
(see `1.4-layout/1.4.1-bfc.md` "Out-of-flow absolute positioning"). During the
main BFC walk, when a child has `cs.position === "absolute"` (or `"fixed"`), the
BFC mirrors the float branch: it skips ALL in-flow placement (no `childBlockOffset`
advance, no margin collapse), captures the child's static position (where the
in-flow algorithm would have placed it, expressed in the abc frame by adding
`ctx.originFromAbc`), `register`s it into the current abc's `pending` list, and
`continue`s.

After the in-flow walk completes, the box that OWNS its abc
(`ctx.ownsAbsoluteContainingBlock`) drains the pending list in a SECOND PASS
(beside the float `lowestFloatBlockEdge()` pass). For each pending child it
resolves size + position from `cs.inset*` against the now-resolved abc frame:
inline-axis insets against `abc.inlineSize`; block-axis insets against the abc's
block percent-base (a px inset always applies; a percent resolves only against a
definite block size, else collapses to `auto`). `auto` size with BOTH insets set
fills the gap; otherwise it shrinks to content via the same intrinsic-sizing path
floats/inline-blocks use. Position: inset-start wins; else inset-end anchors the
end edge; else the captured static position. The child is then laid out as its own
BFC root (`position: absolute` triggers `establishesNewBFC`) at the resolved
position, and the results are attached to the establishing box's
`absoluteChildren`.

The result: `LayoutBox` gains an optional `absoluteChildren?: readonly LayoutBox[]`
on `LayoutBoxBase` (lives on the base, not just `BlockBox`, because abc-establishment
can occur on inline-block / table boxes too; omitted when none). These boxes are
OUT of `children`. The painter recurses `box.absoluteChildren` with the SAME parent
origin (incl. any `relativeOffset`) it uses for `children`; in the current slice
they paint in document order after normal children (z-order is the stacking slice).

**Cursor reachability.** `cursor/line-flatten.ts` `collectLineBoxes` ALSO descends
`box.absoluteChildren` (with the box's accumulated absolute origin), so lines
inside an abs-pos subtree enter the flat `getLineIndex().all` — the single source
of truth for hit-test, cursor-position, selection-geometry, and line-navigation.
Without this descent, abs content (reachable only via `absoluteChildren`, never
`children`) would be invisible to every cursor op.

**Named v1 follow-up (not a degraded split).** The second pass runs ONLY on a
box's full, non-fragmented return. When a box fragments across a page break,
`buildPartialResult` returns a partial box WITHOUT running the second pass, so abs
children registered before the break stay undrained in the pending list and are
abandoned. Correct behavior would drain the abs children whose static position
falls in each placed fragment onto that fragment; this PAGINATED abs-pos
fragmentation case is documented at the omission site and deferred as a separable
follow-up. Single-page abs-pos is complete. Separately, an establishing box's own
EXPLICIT block-size is not folded into the abc block percent-base in every path (a
pre-existing BFC limitation, not introduced here).

### Transforms in layout `[implemented]`

Transforms are paint-time + hit-test only. A `transform`-bearing box still occupies its untransformed space in the layout tree. Its scrollable area, layout `LayoutBox` geometry, the flat `LineIndex` bounds, and parent's flow position all use the PRE-transform geometry; the transform is applied at paint (forward) and hit-test (inverse) only.

Exception: a `transform`-bearing box establishes a containing block for its absolutely-positioned descendants (per CSS Transforms 1 §6) AND a stacking context (CSS Transforms 1 §6). Both are handled by `establishesAbsoluteContainingBlock(cs)` (= `position !== static` OR `transform.length > 0`) and `computeStackingContextRole(cs)` (`"self"` when `transform.length > 0`).

#### The `Mat2D` helper (shared paint + hit-test math)

A zero-dependency 2×3 affine matrix (`layout/mat2d.ts`, like the bidi / line-break
tables) is the single source of transform math, used IDENTICALLY by paint and
hit-test so they can never diverge. `Mat2D` is `{ a, b, c, d, e, f }` mapping
`(x, y) → (a·x + c·y + e, b·x + d·y + f)` — exactly the `ctx.transform(a, b, c, d, e, f)`
convention. It exposes `identity` / `compose(outer, inner)` (matrix-multiply,
`inner`-applied-first to match canvas accumulation) / builders `translate` /
`rotate` / `scale` / `apply(m, x, y)` / `invert(m): Mat2D | null` (`null` when
`det === 0` — a singular transform) / `fromTransformFns(fns, originX, originY,
boxW, boxH)` (composes `translate(origin) ∘ fn1 ∘ … ∘ translate(−origin)`, fns in
ARRAY order, resolving percent translates against the box's own size) /
`resolveTransformOrigin(origin, boxX, boxY, boxW, boxH)` (percent against the box's
own width/height; `50% 50%` default = box center).

**Only a TRANSFORMABLE box** (block / inline-block / table / table-row /
table-cell / page) reads its `transform`. The IFC STAMPS its block's
`computedStyle` (incl. `transform`) onto the generated `line` fragments, and a
non-atomic `inline` / `text-run` / `marker` copies a parent cs — so those fragment
types are SKIPPED (both in paint and in the hit-test thread) to avoid
double-applying the establishing block's transform. Paint and hit-test apply the
identical gate so their cumulative matrices match.

## Paint integration

### Stacking contexts and z-index `[implemented]`

Boxes paint in document order by default. A box establishes a new **stacking
context** when ANY of these CSS triggers hold (CSS 2.2 §9.9 / Positioned Layout 3):

- it is POSITIONED (`position !== "static"`) AND has a non-`auto` `z-index`
  (z-index is ignored on a static box, so the position gate is load-bearing);
- `opacity < 1`;
- `transform` is non-empty.
- (Future: `filter`, `mix-blend-mode` — out of scope per CLAUDE.md.)

`LayoutBox` carries an optional `stackingContextRole?: "self"` on `LayoutBoxBase`,
computed DETERMINISTICALLY by the box factory (`createBoxBase` →
`computeStackingContextRole(cs)` in `styles/position.ts`) from the box's
`computedStyle`. It is **two-valued**: `"self"` when the box is a stacking
context, ABSENT (`undefined`) otherwise — "none" is the field's absence. Because
the role is a pure function of `computedStyle`, every factory and every
clone/rebuild path that re-runs the factory with the same style carries it without
separate threading (no clone-drop risk). A `PageBox` mirrors the field for union
coherence but is never a stacking context (always absent).

Within a stacking context, children paint in the corrected CSS 2.2 §E.2 order
(this supersedes the earlier seven-step sketch and the three-valued role — note
that `position: relative` is a POSITIONED descendant for paint, so a `relative`
box with `z-index: auto` shares ONE bucket with an `absolute`/`fixed` box with
`z-index: auto`, in tree order):

1. negative-z stacking-context children (z<0, sorted by z ascending);
2. the box's own background + borders;
3. in-flow non-positioned BLOCK descendants (recursive, static only);
4. floats;
5. in-flow non-positioned INLINE content;
6. **all positioned descendants with `z-index: auto | 0` — `relative` AND
   `absolute`/`fixed` together — in tree (document) order;**
7. positive-z stacking-context children (z>0, sorted by z ascending).

Sorting is STABLE with a document-order tiebreak. A child that is ITSELF a
stacking context (`stackingContextRole === "self"`) paints ATOMICALLY — its whole
subtree, its own §E.2 walk — at its z-position in the parent context (buckets
1/6/7 by its z). A positioned non-stacking child shares the current context
(bucket 6, atomic-as-a-unit).

**Two-phase reconciliation.** The painter is two-phase (a background pass then a
foreground pass; the translucent selection tint composites between them — §1.2 /
`2.2-canvas-renderer.md`). The GLOBAL two-phase walk still drives the box's own
background (bucket 2) and its in-flow non-positioned descendants (buckets 3–5,
both phases). Buckets 1/6/7 paint atomically (a child's whole subtree in BOTH
sub-phases via two `paintBox` calls) but gated to run EXACTLY ONCE: negative-z
(bucket 1) in the BACKGROUND phase, before the box's own background, so it sits
below; buckets 6/7 in the FOREGROUND phase, after the box's in-flow glyphs, so
they sit above. Canvas paint order is composite order, so this yields §E.2
stacking.

**Known v1 limitation (named follow-up): selection tint under positioned-child
backgrounds.** Because bucket-6/7 children paint their full atomic subtree —
including their own `backgroundColor` — in the FOREGROUND phase, which runs AFTER
the global selection rects, a `position:relative|absolute` child with a
non-transparent background overpaints the selection tint (selection invisible on
that child's background region). Negative-z (bucket 1) children are unaffected
(they paint before selection). The fix needs a third paint sub-phase
(positioned-backgrounds before selection) or per-box selection compositing — an
architectural change deferred to a named follow-up (alongside the relative-caret
and transform-selection follow-ups). Z-index ORDERING itself is complete + correct;
this is a separable compositing-fidelity gap, not yet user-reachable.

**Common-path guarantee.** The painter partitions into buckets ONLY when a box has
≥1 child / abs child that is a stacking context OR is positioned. A box with no
such participant (the 99% case — no z-index, no stacking context anywhere in the
doc) takes the unmodified document-order path (children loop + abs-children walk),
byte-identical to the pre-slice-4 painter. (`canvas-renderer.ts`:
`needsStackingReorder` / `partitionStackingChildren` / `paintContainerChildren` /
`paintNegativeZBeforeBackground`.)

### Transform application `[implemented]`

There is NO `physicalOrigin` field — the painter accumulates the box's absolute
origin as `absX = parentX + box.x` (`canvas-renderer.ts` `paintBox`) and the
transform-apply reads that accumulated origin. Before painting a transformable
`transform`-bearing box, the painter (`paintBox`):

1. Resolves the transform-origin in absolute coords via `resolveTransformOrigin(cs.transformOrigin, absX, absY, box.width, box.height)` (the SAME helper the hit-test thread uses).
2. `ctx.save()`.
3. Builds the box's matrix `fromTransformFns(cs.transform, originX, originY, box.width, box.height)` — which already folds `translate(origin) ∘ fns ∘ translate(−origin)`, fns in ARRAY order — and applies it as a SINGLE `ctx.transform(a, b, c, d, e, f)`.
4. Paints the box + descendants (the box is a stacking context, so it paints atomically — its whole subtree under this matrix; descendant fragments do NOT re-apply the transform per the transformable-box gate).
5. `ctx.restore()` (in a `finally` so every early `return`/throw balances the save).

An UN-transformed box takes NO save/restore (zero overhead, guarded on
`cs.transform.length > 0`). Viewport culling is skipped for a transformed box
(its painted bounds can move outside the pre-transform band). Because paint uses
`fromTransformFns` / `resolveTransformOrigin` and the hit-test thread uses the
SAME two helpers, the painted forward matrix and the baked inverse are derived
from byte-identical math.

### Opacity `[implemented]`

A box with `cs.opacity < 1` is a stacking context (it paints ATOMICALLY — its
whole subtree, both paint sub-phases, all descendants incl. its own transform and
its §E.2 stacking children, are one self-contained unit). The painter renders that
COMPLETE atomic paint into a **temporary offscreen surface** at full opacity, then
composites the surface onto the parent canvas ONCE with `globalAlpha = cs.opacity`
(`globalAlpha` is restored afterward so no alpha leaks to siblings). This honors
CSS-spec opacity GROUPING: a half-opaque box with OVERLAPPING children reads as ONE
half-opaque region (the group composites a single time), NOT additive per-child
alpha.

**`opacity === 1` (or `undefined`) → the DIRECT paint path, ZERO offscreen
allocation** (the 99.99% common case is byte-identical to the no-opacity painter).
Only `opacity < 1` takes the offscreen path.

The offscreen surface is sized to the box's border-box and the subtree paints with
the box's absolute origin mapped to the surface's top-left, so a single
`ctx.drawImage(surface.canvas, absX, absY)` lands the group back at the right place.
The composite runs in the FOREGROUND phase only (the atomic content spans both
sub-phases, but composites once, above the box's background-phase siblings); the
background-phase entry for an opacity box is a no-op — exactly like a bucket-6/7
stacking child whose atomic paint is gated to the foreground phase. **Nested opacity
composes** naturally: an inner `opacity < 1` descendant allocates its OWN offscreen
and `drawImage`s into THIS group's offscreen ctx, so the inner group composites into
the outer group's surface before the outer composites onto the page.

The offscreen surface is obtained through an INJECTABLE factory
(`packages/dom/src/offscreen-surface.ts` `createOffscreenSurface` /
`setOffscreenSurfaceFactory` / `resetOffscreenSurfaceFactory`) — the default uses a
DETACHED `<canvas>` element (the same primitive the editor controller already uses
for page canvases; a real `CanvasRenderingContext2D` + `CanvasImageSource`, no type
bridging, zero dependency), and the seam lets tests inject a fake recording surface
under jsdom (whose canvas 2D context is a stub). See
[`2.2-canvas-renderer.md`](../2-dom/2.2-canvas-renderer.md) "Opacity compositing".

## Hit-test integration `[implemented]` (per-line inverse transform — approach (b))

The flat `getLineIndex().all` hit-test reaches abs-pos content via the
`collectLineBoxes` descent into `absoluteChildren` (slice 3), and TRANSFORM
inversion is resolved per-line — NOT by a box-tree descent. When building the
LineIndex, `collectLineBoxes` threads the CUMULATIVE ancestor `transform`
(composing each transformable ancestor's `fromTransformFns` matrix about its
accumulated absolute origin — the same frame the painter uses), and bakes onto
each `AbsoluteLineBox` a three-state `inverseTransform`:

- `undefined` → no transform anywhere in the chain → IDENTITY fast-path. The
  line's `(absoluteX, absoluteY)` bounds ARE its painted bounds; the existing
  bounds test runs verbatim with ZERO overhead (the 99% untransformed document).
- a `Mat2D` → an invertible cumulative transform (= `invert(cumulative)`). The
  line's bounds stay PRE-transform; the hit-test maps the click point through this
  inverse (`apply(inverseTransform, x, y)`) BEFORE the existing bounds + leaf pick.
  Because point-in-transformed-quad ≡ inverse-point-in-pretransform-rect, this
  handles translate / rotate / scale uniformly, O(1) per transformed line.
- `"singular"` → a degenerate cumulative transform (`invert` returned `null`,
  e.g. `scale(0)`) → the painted region is zero-area / invisible → the line-pick
  SKIPS the line (no hit), matching CSS Transforms 1. The three-state field keeps
  identity (`undefined`) and singular (`"singular"`) type-distinct — no `!`.

`resolvePositionFromPixel` calls `mapClickForLine(line, x, y)` for both the
block-axis band pick and the in-line leaf/offset pick, so the click is resolved in
each line's own pre-transform frame. The untransformed path is byte-identical to
the pre-slice hit-test.

**Named v1 follow-ups (not degraded splits — separable lower-stakes geometry).**
Hit-test (click → offset) IS corrected. NOT yet projected through the transform:
(i) **selection-geometry rects** are returned in PRE-transform (layout) space, so
a selection highlight on transformed content paints at offset/wrong-size regions;
(ii) the **cursor-position caret** (offset → pixel) for transformed content is
also pre-transform, so a click lands at the right offset but its caret may render
pre-transform. Both reuse the per-line `Mat2D` mechanism applied FORWARD; bundled
as the "transformed-content caret + selection-geometry" follow-up. (A
`position: relative` box that is ALSO transformed resolves its transform-origin
in the pre-`relativeOffset` frame, since the flat LineIndex stays pre-offset per
the relative-caret follow-up — a corner of the same follow-up.) (iii)
**Incremental dirty-rect** (`walkAndDetectChanges`): a transformed box's dirty
rectangle is recorded in PRE-transform bounds, which can be smaller than the
painted (rotated / large-translated) region, so an incremental repaint may leave
stale pixels at the prior painted position. No functional bug today — a `transform`
edit changes the box's computedStyle → a new `LayoutBox` ref → the root
short-circuit breaks and the full walk fires; and transforms are not user-reachable
yet. The fix expands the dirty rect to the transformed painted bounding box, bundled
with the same follow-up.

## Cascade integration `[implemented]`

All nine positioning fields — `position`, the four `inset*`, `zIndex`,
`transform`, `transformOrigin`, `opacity` — are in `PROPERTY_META` with
`inherits: false`. Cascade resolves them to their initial values when not declared
(`"static"` / `"auto"` insets / `"auto"` z / `[]` transform / 50%-50% origin /
opacity 1), otherwise applies the declared value verbatim (transforms don't
combine via inheritance). `composeComputed` needs no change — it is generic over
`PROPERTY_META` keys. None of these properties enter `UsedStyle` (see "Schema
additions"); they are read at their use-sites from `ComputedStyle`.

## Performance contracts

- Two-phase layout (in-flow + abs-pos pending-list): O(N + A) where N is in-flow descendants and A is abs-pos descendants. The pending list is small in practice.
- Stacking-context determination: O(1) per box (computed from local computedStyle).
- Transform application during paint: O(1) per transformed box (canvas matrix multiply).
- Hit-test: O(depth × 1) per click; transform inversion is O(1) per transformed box.
