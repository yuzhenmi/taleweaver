# 1.1 — `state/`

The state module is the document model. It is the single source of
truth for everything semantic about the document — what nodes exist,
what their properties and styles are, where the cursor is. It owns no
geometry, no styles-as-resolved-values, and no visual concerns.

## What state is

A document is an immutable tree of `StateNode`s. Each node has an
opaque type (`paragraph`, `text`, `list-item`, etc.), a frozen property
bag, declared inline styles, and an ordered children array. Node identity
is preserved via `id`; the tree is structurally shared across edits, so
any node not on the path of an edit retains its prior reference.

Positions are paths plus offsets: a `Position` names a path of child
indices from the root plus a character offset within the destination
text node. A `Span` is a directed pair of positions (`anchor`, `focus`);
collapsed spans are cursors.

## Submodules

- **`state-node`** — the `StateNode` type definition.

- **`create-node`** — frozen factories that produce `StateNode`s with
  shared empty-styles references when nothing is declared.

- **`operations`** — path-based tree manipulation. `getNodeByPath`,
  `updateAtPath`, `insertChild`, `removeChild`, `updateProperties`. All
  operations preserve sibling references on the unchanged side of the
  path; only the path from root to the touched node is rebuilt.

- **`transformations`** — high-level edits that compose operations.
  `insertText`, `deleteRange`, `replaceRange`, `splitNode`. Each takes a
  state plus a position or span and returns a `Change` (old state + new
  state + timestamp).

- **`formatting`** — inline-style application across spans.
  `applyInlineStyle`, `getStyleInRange`, `remapPosition`.

- **`normalize`** — structural-paragraph maintenance. Ensures, for
  example, that opaque blocks (tables, images) sit between paragraphs
  rather than mid-paragraph; injects empty paragraphs where needed.

- **`position`** — the position/span types and pure manipulations
  (`comparePositions`, `normalizeSpan`, `createPosition`, `createSpan`).

- **`history`** — bounded undo/redo. `createHistory`, `pushChange`,
  `undo`, `redo`. The editor reducer uses this to manage user-visible
  undo grouping.

- **`change`** — the `Change` type returned by transformations:
  `{ oldState, newState, timestamp }`.

- **`dirty`** — `findDirtyPaths(oldState, newState)` walks both trees by
  reference equality and returns the paths where they diverge. Used by
  the editor reducer to decide which subtrees the rendering pipeline
  must rebuild.

- **`extract-text`** — `extractText(state, span)` flattens a span into
  a plain string. Used by clipboard, find/replace, accessibility.

- **`find-path`** — `findPathById` walks the tree to locate a node by
  `id`. Used by external integrations that hold a node reference and
  need to translate to a path.

- **`text-utils`** — `getTextContent`, `getTextContentLength`,
  `clampOffset`. Helpers for working with text-node `content` properties.

- **`new-node`** — the partial-shape type used for `INSERT_NODE`-style
  actions that haven't been assigned an `id` yet.

- **`initial-state`** — `createEmptyDocument()` builds a fresh state
  with a single empty paragraph.

## How submodules connect

`state-node` and `position` are foundational types — every other
submodule imports them.

`operations` and `transformations` are the write API. Editor action
handlers call `transformations` to produce a `Change`; the reducer
records the change in `history` and propagates the new state through the
pipeline.

`dirty` is the bridge to the rendering pipeline: after the state changes,
the reducer compares old and new states via `findDirtyPaths` to drive
incremental rebuild downstream.

`formatting` and `normalize` are higher-level edits that compose
`transformations` and `operations`.

`extract-text`, `find-path`, `text-utils`, `change`, `new-node`,
`initial-state` are utilities consumed by the reducer or by external
integrations.
