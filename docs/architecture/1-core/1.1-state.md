# 1.1 — `state/`

The state module is the document model. It is the single source of
truth for everything semantic about the document — what blocks exist,
their attributes, the rich-text content inside leaf blocks, and the
relationships between them. It owns no geometry, no resolved styles, and
no visual concerns.

The current design is the block-tree of styled-run arrays committed to in
2026-05-02 (see `docs/superpowers/specs/2026-05-02-state-model-block-tree-of-ropes-design.md`
for the design spec, decisions log, and migration history). The spec
filename says "ropes," but that was brainstorm framing that was never
built: `InlineContent` is a plain `{ items: ReadonlyArray<InlineItem> }`
array of styled runs, not a rope.

## What state is

A document is a **block tree** keyed by stable `BlockId`s. Each block is
a flat record with a parent pointer and a doubly-linked-list of children
(`firstChildId` / `lastChildId` / `prevSiblingId` / `nextSiblingId`).
Container blocks (sections, tables) hold child blocks; leaf
blocks (paragraphs, headings, list-items, table-cells) carry their rich
text as `inlineContent` — a flat array of styled inline items (text runs
and embed items).

**Lists are flat, not containers (the Google-Docs model).** A "list" is
NOT a container block. It is a maximal document-order run of `list-item`
LEAF blocks that share a `listId` attr; nesting is the per-item
`listLevel` attr (0–8). There is no `list` block type and no `listType`
attr. Per-list numbering configuration (which marker style, start value,
and restart rule each level uses) lives in a separate top-level config
side-table, `listDefs` (see "The `listDefs` map" below). The marker text
itself (a bullet glyph or a number like "1.") is COMPUTED at render time
by the `numbering/` service and baked onto the list-item element — it is
never stored on the block. See `1.2-render.md` (numbering) and
`1.7-editor.md` (list editing actions).

Storage is backed by a Yjs `Y.Doc`. The Yjs container holds three
block-tree `Y.Map`s keyed by `BlockId` — the main document tree, the
embed-content subtrees (footnote bodies, etc.), and the template-content
subtrees (header/footer bodies) — plus three top-level SIDE-TABLE maps that
are not block trees: `listDefs` (keyed by `listId`, the per-list numbering
config), `comments` (keyed by `CommentId`, the comment-thread records), and
`suggestions` (keyed by `SuggestionId`, the change-tracking records).
The three block trees are owned by the state module and exposed only
through opaque snapshot accessors (`getBlock`, `getEmbedContent`,
`getTemplateContent`, and the provenance-aware `resolveBlock`); `listDefs`
is exposed through its own accessors (`getListDefsForState`, see below),
and `comments` through `getComments`. (`suggestions` — the change-tracking
side-table — is read through `getSuggestions`, with `getSuggestionsMap` the
state-internal map accessor. See "The `comments` map" and "The `suggestions`
map" below.)
BlockIds are globally unique across all three block-tree maps. Yjs is an
implementation choice that gives the engine cheap structural sharing across
versions and a forward path to collaborative editing without a
state-module rewrite.

### The `listDefs` map (per-list numbering config)

`listDefs` is the fourth top-level `Y.Map` (alongside the three block
trees; `comments` is the fifth, see below). It maps each `listId` to a `ListDef { levels: ReadonlyArray<ListLevelConfig> }`,
where `ListLevelConfig = { style: CounterStyle; start: number; restart: CounterRestart }`
gives the marker style, starting value, and restart rule per nesting
level. It is a config side-table — NOT in `TREE_MAP_GETTERS`, so it is
deliberately EXCLUDED from the block-tree dirty-capture scan (a
`listDefs`-only write captures no block dirty ids; the writing op
contributes the affected list-item ids through the dirty-union channel,
see "Dirty-union channel" below). The `Y.UndoManager` tracks it as a
fourth scope (so a list-type change undoes), and `createYDoc` seeds it.

Accessors (state-module-internal where they take a `Y.Doc`, public where
they take a `State`):
- `getListDef(doc, listId) → ListDef | undefined`
- `getListDefs(doc) → Map<listId, ListDef>`
- `getListDefsForState(state) → Map<listId, ListDef>` — the render-pass
  entry point (reaches the Y.Doc through the `STATE_INTERNAL` seam, like
  the other accessors). The numbering engine consumes the result as its
  `CounterDefs` (see `1.2-render.md`).
- `writeListDefInTx(doc, listId, def)` — the in-transaction writer.
- `classifyListDef(def) → "ordered" | "unordered"` — classifies a def by
  its level-0 marker style (the bullet styles disc/circle/square →
  "unordered", else "ordered"). The one place the ordered-vs-unordered
  rule lives; shared by the toggle/set-type editor handlers.

`newListId()` mints a fresh list id (a plain string namespace, DISTINCT
from `BlockId` — a `listId` groups list-items, it is not itself a block).

### The `comments` map (anchored comment threads)

`comments` is the fifth top-level `Y.Map` (alongside the three block trees
and `listDefs`). It maps each `CommentId` to a `CommentRecord` — the thread
data: `{ id, author, body, createdAt, replies, resolved }`, where `replies`
is a `Y.Array<Y.Map>` (NOT a plain array) so concurrent reply appends MERGE
under collab rather than clobbering the list. Like `listDefs` it is a
side-table — NOT in `TREE_MAP_GETTERS`, so it is deliberately EXCLUDED from
the block-tree dirty-capture scan. `getCommentsMap` mirrors `getListDefsMap`;
`createYDoc` seeds it.

**The range is NOT stored in the record — the markers ARE the anchor.** A
comment's RANGE is delimited by a paired pair of zero-width inline embed
items in content: a `comment-start` and a `comment-end` `EmbedItem`
(`COMMENT_START_EMBED_TYPE` / `COMMENT_END_EMBED_TYPE`), each carrying
`properties.commentId`. Because the markers ARE inline content (exactly like
a footnote-anchor embed), the existing structural ops move and clone them
with surrounding text for free — they survive insert, delete, split, merge,
and paste with no anchor-maintenance code. A spike (`comment-anchor-survival.test.ts`)
rejected a Yjs `RelativePosition`-based anchor, which orphaned on
delete / split-right / merge because the engine's ops rebuild `Y.Text`
rather than mutate it in place; the marker-embed model is the durable
alternative. Each marker occupies exactly one offset (an atomic embed, one
cursor stop), preserving the `offset↔box` 1:1 invariant; it renders as a
ZERO-WIDTH inline-block atom (no glyph; see `1.2-render.md`), serializes to
`""` in `extract-text.ts` (excluded from `extractText` / `getWordCount`),
and is STRIPPED from pasted content by `clonePastedSubtree` (Google-Docs-faithful:
pasting commented text does not duplicate the comment).

**Orphaning is DERIVED, not stored.** `buildCommentRangeIndex(state) →
Map<CommentId, CommentRange>` scans the main-tree inline content ONCE,
tallying each `commentId`'s markers. A comment's range is LIVE (`orphaned:
false`) iff content holds EXACTLY ONE start AND EXACTLY ONE end with start
strictly before end (`comparePositions`); otherwise `orphaned: true` —
one-sided (a delete crossed one marker), inverted, or duplicated. A comment
whose markers are BOTH gone produces no index entry (orphaned-by-absence);
the read side surfaces it from the record list with a degenerate origin
range. `resolveCommentRange(state, commentId)` is the single-comment lookup.
Undo of a delete that orphaned a comment restores its markers, so the next
read reports it live again — no eager cleanup hook.

**Comment ops are UNDOABLE AS CONTENT — the deliberate, documented deviation
from Google Docs.** Because the markers are content, a comment reverts
atomically with them through the NORMAL `applyOperation` content-op path,
and the `comments` map is the FIFTH tracked scope of the `Y.UndoManager`
(beside the three block trees and `listDefs`). Per-transaction tracking means
a pure text edit — which never touches the `comments` map — undoes WITHOUT
disturbing any comment, while a comment op (markers + record together)
reverts as one unit. Google Docs streams comments separately so undo never
touches them; the marker-embed anchor forces a content-based model here.
This is collab-safe: `Y.UndoManager` is per-origin, so a user only ever
undoes their OWN comments, never a collaborator's. The accessors and ops
(below) live in `comments.ts` and `ops/comment-ops.ts`; the read surface is
`getComments(state) → ResolvedComment[]` (each record plus its scanned
range).

### The `suggestions` map (change-tracking / Suggesting mode)

`suggestions` is the sixth top-level `Y.Map` (alongside the three block trees,
`listDefs`, and `comments`). It maps each `SuggestionId` to a `SuggestionRecord`
— `{ id, kind: "insertion"|"deletion"|"formatting", author, createdAt,
proposedAttrs? }` — where `proposedAttrs` (the formatting variant only) is a
nested `Y.Map` (built via `buildYAttrs`, read back via the public `yMapAsObject`)
so concurrent proposal edits merge under collab. Like `listDefs`/`comments` it is
a side-table — NOT in `TREE_MAP_GETTERS`, excluded from the block-tree
dirty-capture scan; `getSuggestionsMap` mirrors `getCommentsMap`; `createYDoc`
seeds it. `suggestions.ts` holds the types + `writeSuggestionRecordInTx`/
`readSuggestionRecord` (state-internal, mirroring `comments.ts`).

**The range is NOT stored in the record — three independent inline-attr
dimensions ARE the anchor.** A single `TextItem` can simultaneously be an
INSERTION by one author and a pending DELETION by another (and carry a pending
formatting proposal), so suggestions are three independent `attrs` keys on a
`TextItem`, NOT one mutually-exclusive state: `insertionSuggestionId`,
`deletionSuggestionId`, `formattingSuggestionId` (the `*_SUGGESTION_ATTR`
consts), each valued with the owning `SuggestionId`. The structural
paragraph-break cases use two zero-width embeds instead — a
`block-join-suggestion` (a suggested deletion of a block boundary with no
adjacent text to tag) and a `block-split-suggestion` (a suggested insertion of a
break) — each carrying `properties` `SuggestionId`, each one atomic offset / one
zero-width IFC token (the `offset↔box` 1:1 invariant), serializing to `""` in
`extract-text.ts`. The attrs/embeds move and clone with the text for free, so a
suggestion's range is range-stable across edits and DERIVED by a content scan
(mirror of the comments marker-scan), not a stored anchor. Why attrs not
bracketing markers (the comments model): a suggestion's range IS its text — an
insertion's items survive until accepted (strip the attr → plain text), a
deletion's until rejected — so it has no need to survive deletion of its own
interior.

**Range is DERIVED by a content scan.** `buildSuggestionRangeIndex(state) →
Map<SuggestionId, SuggestionRange>` walks the main tree once
(`iterateBlocksInDocumentOrder`), recording each id's enclosing `[start, end)`
from the three inline attr dimensions on text items and `properties.suggestionId`
on the two break embeds — the mirror of `buildCommentRangeIndex`.
`resolveSuggestionRange(state, id)` is the single-id lookup. The read surface is
`getSuggestions(state) → ResolvedSuggestion[]` (each record joined with its
scanned range; a record whose id tags no item is `orphaned: true, range: null` —
orphaned-by-absence, like comments).

**Suggestion ops are UNDOABLE AS CONTENT; accept/reject are NOT.** Creating a
suggestion writes the tagged items/embeds + the record in one NORMAL
`applyOperation`, and the `suggestions` map is the SIXTH tracked scope of the
`Y.UndoManager` (per-transaction tracking → a pure text edit leaves suggestions
untouched). Accepting/rejecting a suggestion, by contrast, is non-undoable (the
Google-Docs convention): the resolve op passes `SUGGESTION_RESOLVE_ORIGIN` as the
optional `origin` of `applyOperation` (threaded to `runTransaction` →
`doc.transact(fn, origin)`), a non-`null` origin excluded from the UndoManager's
`trackedOrigins`. Because such a txn skips `History.commit` (no StackItem fires),
the resolve op then calls `History.advanceState(newState)` to reconcile the
cached `currentState` — otherwise the next undo/redo, built via
`freshState(currentState, dirtyIds)`, would serve any block the resolve changed
but the undo did not re-dirty from a STALE snapshot. (The accept/reject ops
themselves, the mode flag, and the render/overlay are built in later
change-tracking slices; slices 1–2 shipped the state vocabulary + the range
index, read surface, and the `origin`/`advanceState` Layer-1 hooks.)

A non-undoable resolve applies an **identity-preserving, minimal-diff** rewrite to
each touched block (`applyResolveDecisionsInTx`): it walks a per-item decision list
(`ScanItemResult[]`, computed by `resolveBlockScan`) against the live inline
`Y.Array`, mutating only what changed — `keep` is a no-op, `rewrite` swaps just the
item's `attrs` sub-`Y.Map` in place (stripping a provenance key and/or applying the
proposal — every resolve rewrite is attrs-only, so the item's `Y.Text` /
`embedType` / `properties` are untouched), and `drop`/`breakDrop` delete the item by
index. A post-pass `mergeAdjacentSameAttrsTextItems` restores the no-adjacent-same-
attrs / no-empty-run normalization invariants, sacrificing `Y.Text` identity ONLY
for runs that genuinely converge to equal attrs. Because UNTOUCHED runs keep their
per-character CRDT identity, a tracked edit that preceded the resolve IN THE SAME
BLOCK keeps a valid undo `StackItem` — `undo()` after a resolve is a real revert,
not the silent no-op the earlier full-replace seam produced (it rebuilt the whole
`Y.Array`, tombstoning every run's `Y.Text`). This mirrors the surgical pattern of
`applyAttrsToRangeInTx`. (`History.undo`/`redo` still treat a genuinely-dead
`StackItem` as a graceful `null` no-op — defense in depth — but the resolve path no
longer manufactures dead items.) The deletion-strike CREATE ops (`markDeletion`, the
replace/split strike-writes) are surgical (`applyDeletionStrikeInTx` — #491), the
start-block insert of `replaceWithSuggestion` is surgical (#492), and
`replaceWithSuggestedFragment` (the multi-block fragment interleave) is now surgical
too (#493 — per-block strikes + the `insert-items` primitive: `split-in-place` for
the n≤1 start block + every intervener/end block, `replace-tail` for the n>1 start
block's truncation). The full-replace seam (`writeBlockInlineContentInTx`) is GONE —
EVERY suggestion write preserves untouched runs' `Y.Text` CRDT identity, completing
the identity-preservation arc (#484/#491/#492/#493).

The suggestion-CREATION ops live in `state/ops/suggestion-ops.ts`. The first,
`markFormatting(state, span, proposedAttrs, input)`, records a FORMATTING
suggestion: it stamps `formattingSuggestionId` over the span (via
`applyAttrsToRangeInTx`) and writes a `formatting` `SuggestionRecord` carrying
`proposedAttrs` — the format delta the action WOULD have applied — in one tracked
`applyOperation` (one undo unit). The run's LIVE format attrs are untouched (the
proposal is shown, not applied; accept applies it later). Same-author, same-
`proposedAttrs` marks adjacent to an existing formatting suggestion COALESCE by
reusing that id (the before-neighbor preferred), so a continuous re-format is one
suggestion.

`markDeletion(state, span, input)` records a SUGGESTED DELETION (soft-delete). Per
text run inside the span: plain text → stamp `deletionSuggestionId` (the text STAYS
VISIBLE until resolved); a run carrying an `insertionSuggestionId` by a DIFFERENT
author → also gains `deletionSuggestionId` (NESTING — it keeps its insertion id
too); a run carrying an `insertionSuggestionId` by THIS author (the deleter's OWN
pending insertion) → REMOVED FOR REAL (it never became real text, so un-suggesting
= removing — and only the in-range portion; surviving halves keep the insertion
id). It does NOT use `applyAttrsToRangeInTx` (which cannot selectively drop runs,
and would tag VISIBLE field embeds in range); instead it plans the per-owning-block
strike ranges pre-transaction, then strikes each block IDENTITY-PRESERVINGLY in place
via `applyDeletionStrikeInTx` (#491 — whole-covered runs get the deletion attr set in
place, only a straddling run splits, own-insertion runs are deleted by index;
untouched runs keep their `Y.Text` identity). A `deletion`
`SuggestionRecord` (no `proposedAttrs`) is written unless coalescing into a
same-author adjacent deletion, or unless the whole span was own-insertions
(nothing tagged → no record; the real removal IS the change). A cross-block span
tags the in-range text of each block with the SAME id (one suggestion spanning the
boundary). Embeds inside a deletion span are preserved untagged (embed/inline-object
soft-deletion is a named follow-up — the range scan reads suggestion attrs only on
text items + break-embed `properties`). The structural break-deletion (a
`block-join-suggestion` embed for a deleted paragraph boundary) is added by the
editor-action slice, not here.

`mintInsertion(state, position, text, attrs, input)` is the INSERT_TEXT/PASTE
suggesting-mode op: it INSERTS `text` carrying an `insertionSuggestionId` (composing
`insert-text`'s `planInsertText`/`insertTextInTx`, not the public `insertText`) and
writes an `insertion` `SuggestionRecord`, in one tracked `applyOperation`. `attrs`
is the intended formatting of the inserted text; the op stamps the resolved
insertion id on top (`{ ...attrs, [INSERTION_SUGGESTION_ATTR]: id }`, overwriting
only the provenance id). It COALESCES at the insertion point: if the run
immediately before (`position.offset - 1`) or after (`position.offset`) carries an
`insertionSuggestionId` whose record is an `insertion` by the same author, it reuses
that id (before-neighbor preferred) and writes no new record — so a continuous
typing run is ONE suggestion, not N (mirrors undo-coalescing). The author's own
suggestion-creation is undoable (Ctrl+Z removes the text + record atomically).

`replaceWithSuggestion(state, span, text, attrs, input, registry?)` is the
TYPE-OVER-A-SELECTION suggesting-mode op — the suggestion analog of `replaceRange`.
It SOFT-DELETES the selection AND inserts `text` at the selection start, in ONE
tracked `applyOperation` (one undo entry / one collab event), producing TWO records:
an `insertion` and a `deletion` that SHARE `input.createdAt` as the render-layer
"this was one replace" grouping signal. It composes the strike's pure plan
(`planMarkDeletion`, extracted from `markDeletion` for this reuse) with
`planInsertTextSplitInPlace`. The whole op is IDENTITY-PRESERVING (#492): the in-tx
body runs THREE steps in order — (1) strike every NON-start block surgically via
`applyDeletionStrikeInTx`; (2) strike the START block surgically via the SAME
`applyDeletionStrikeInTx` (NOT via the insert); (3) insert the suggested run via
`insertTextInTx` with a `split-in-place` plan. Steps 1–2 leave every struck block's
untouched runs with their original `Y.Text` identity; step 3 splits at most the ONE
run straddling the insertion offset, leaving the rest untouched. The insert plan is
built PRE-tx against the start block's strike `writes` items (byte-identical to the
live Y.Array after step 2's surgical strike), so the `split-in-place` indices resolve
correctly — this step ordering is LOAD-BEARING (inserting before the start strike
would mis-resolve the offset). The new run lands at the selection start — BEFORE the
struck text — carrying `insertionSuggestionId`. A single-block replace therefore
PRESERVES the identity of every run it does not directly touch (collab peers' concurrent
edits to those runs survive sync; `planInsertTextFullReplace` now serves only
`replaceRange`). Each
half coalesces INDEPENDENTLY (insertion at the start vs deletion per
`planMarkDeletion`); a coalesced half writes no new record. Degenerate inputs
delegate: empty `text` → a pure `markDeletion`; a collapsed span (or a strike plan
that yields nothing) → a pure `mintInsertion` at the span start. The resulting
cursor (`start.offset + text.length`) is the editor's to compute (a later slice).

`splitWithSuggestion(state, position, allocator, input, newBlockInit?)` is the
ENTER / paragraph-SPLIT suggesting-mode op. It performs a REAL block split (the same
`planSplitBlockAtPosition` + `splitBlockAtPositionInTx` as `splitBlockAtPosition`, so
both halves are immediately real, laid-out, navigable blocks) AND marks the new
boundary as a tracked suggestion, in ONE tracked `applyOperation` (one undo entry /
one collab event). The marker is a zero-width `block-split-suggestion` embed appended
at the END of the FIRST block (block N) carrying the owning `suggestionId` in its
`properties`, plus an `insertion` `SuggestionRecord` (a suggested split IS a tracked
insertion of a paragraph break). The embed occupies exactly ONE `Position` offset
(every embed does) and serializes to ""; it is the marker `buildSuggestionRangeIndex`
reads to surface the suggestion's range. The structural split writes block N's content
as `[0, offset)` in place (identity-preserving); this op then APPENDS just the break
embed to block N's live `inlineContent` Y.Array (the embed is a merge barrier, so it
stays the LAST item) — preserving N's text-run CRDT identity (no full-replace, no
double-write of N), while block N+1 and the sibling rewiring stay as the split left
them. `newBlockInit`
overrides N+1's `type`/`attrs` (the "style for the following paragraph" hook); the embed
always lands on N. Validation (block missing / non-leaf / root / offset out of range)
is delegated to `planSplitBlockAtPosition`, whose canonical errors throw before any
read. NO coalescing — a paragraph break is a discrete structural change, each Enter is
its own suggestion. RESOLUTION (in `resolve`, below): accept removes the embed (the
split stays — the break becomes permanent); reject re-merges the two blocks (the break
is discarded).

`splitWithSuggestionOverSelection(state, span, allocator, input, newBlockInit?, registry?)`
is the ENTER-over-a-NON-COLLAPSED-selection suggesting-mode composite — the SPLIT_NODE
analog of `replaceWithSuggestion`. It SOFT-DELETES the selection (the struck text STAYS,
tagged with `deletionSuggestionId`) AND inserts a suggested split AFTER it, in ONE tracked
`applyOperation` (one undo entry / one collab event), producing TWO records (a `deletion`
and an `insertion` that SHARE `input.createdAt` as the render-layer "this was one replace"
grouping signal). It composes the strike's pure plan (`planMarkDeletion`) with the
structural `planSplitBlockAtPosition`/`splitBlockAtPositionInTx` + the `block-split-suggestion`
embed-append discipline of `splitWithSuggestion`. SINGLE-BLOCK scope only (the editor
caller routes `spanStart.blockId === spanEnd.blockId` here; a cross-block Enter-over-selection
goes through `replaceWithSuggestedFragment` with an empty two-line break fragment instead —
struck text rides BEFORE the break here vs AFTER in the fragment model, so the two are not
interchangeable). The KEY hazard
mirrors `replaceWithSuggestion`: the strike is IDENTITY-PRESERVING (`applyDeletionStrikeInTx`
in place over block N's live Y.Array — #491; only boundary straddlers lose identity), and —
critically — `markDeletion` REMOVES the author's OWN pending insertions in-range, which
SHORTENS the block, so the split offset is computed against the POST-strike length
(`splitOffset = postLen − (preLen − end.offset)`), NOT the pre-strike `end.offset`. After
the in-place strike + in-place split, the break embed is APPENDED to N's live Y.Array
(identity-preserving) — N is never full-replaced. The struck selection stays in N (followed
by the break embed); the unstruck tail ends up in N+1.
The deletion record is written only when ≥1 run was tagged AND not coalesced (the
`markDeletion` contract); the insertion record is always written (a suggested split is its
own discrete insertion — NO coalescing). Degenerate: a normalized-collapsed span (strike
plan `null`) reduces to a pure `splitWithSuggestion` at the span start (no deletion record).
`newBlockInit` (the heading follow-on) is threaded through to the split. RESOLUTION is per
the underlying deletion + split-insertion records (see `resolve`).

`markBlockJoinSuggestion(state, secondBlockId, input)` is the BACKSPACE-at-block-start /
DELETE-at-block-end paragraph-JOIN suggesting-mode op — the SYMMETRIC mirror of
`splitWithSuggestion`, but simpler: it does NOT merge the two blocks. It marks the
paragraph break BEFORE `secondBlockId` (the boundary between `secondBlockId` and its
previous sibling, block N) as a tracked suggested DELETION by appending a zero-width
`block-join-suggestion` embed (the shipped break-suggestion embed type) at the END of
block N (the prev sibling) carrying the owning `suggestionId` in its `properties`, plus
a `deletion` `SuggestionRecord` (a suggested join IS a tracked deletion of a paragraph
break), in ONE tracked `applyOperation` (one undo entry / one collab event). The embed
occupies exactly ONE `Position` offset and serializes to ""; it is the marker
`buildSuggestionRangeIndex` reads to surface the suggestion's range. The break embed is
APPENDED to block N's live `inlineContent` Y.Array (the embed is a merge barrier, so it
stays the LAST item) — preserving N's text-run CRDT identity (no full-replace); it
is a SINGLE block write — no structural change, no double-write. Both paragraphs remain
REAL separate, linked blocks (Google Docs keeps them intact while the deletion is
pending). Identity no-op (returns the input `state` reference + empty `dirtyIds`) when
there is no boundary to mark: `secondBlockId` missing, `secondBlockId` is a first-child
(no preceding break), or block N is missing / a container (can't hold an inline embed).
NO coalescing — each removed break is its own suggestion. RESOLUTION (in `resolve`,
below): accept merges the two blocks (the break is removed); reject removes the embed
(the break stays).

`acceptSuggestion(state, id)` / `rejectSuggestion(state, id)` RESOLVE one suggestion
(spec §6), dispatching on the record's `kind` via a shared `resolve(state, id,
mode)`. Each is ONE **NON-undoable** `applyOperation(state, fn, { origin:
SUGGESTION_RESOLVE_ORIGIN })` (the slice-2 Layer-1 hook — the UndoManager tracks
only `null`-origin txns, so a resolve fires no StackItem; accept/reject is a final
resolution Ctrl+Z cannot revert, per Google Docs). Resolution per dimension:
accept-insertion STRIPS `insertionSuggestionId` (promote to plain text) /
reject-insertion DROPS the run; accept-deletion DROPS the soft-deleted run /
reject-deletion STRIPS `deletionSuggestionId` (text stays); accept-formatting
MERGES `proposedAttrs` into live attrs + STRIPS `formattingSuggestionId` /
reject-formatting STRIPS it. Implemented IDENTITY-PRESERVINGLY (#484): a pre-tx
per-owning-block decision scan, then `applyResolveDecisionsInTx` walks those
decisions against the LIVE Y.Array in place — `keep` no-ops, `rewrite` swaps only the
item's `attrs` sub-`Y.Map` (`Y.Text` untouched), `drop`/`breakDrop` delete by index —
so untouched runs keep their `Y.Text` identity; then `getSuggestionsMap.delete(id)`. The record-delete is non-undoable, so the EDITOR
HANDLER (a later slice) calls `History.advanceState(newState)` after a resolve to
reconcile the cached state (the op itself only passes the origin). An ORPHANED
record (no run carries its id — already-resolved) deletes the record + surfaces
`state.rootId`. The scan walks ALL THREE trees (main, then each `embedContents`
body, then each `templateContents` body) in document order via
`iterateAllBlocksInDocumentOrder` (matching `buildSuggestionRangeIndex`), each write
carrying its owning block's tree `kind` — so a suggestion tagged in a footnote /
header / footer body resolves in-place in that body tree.

A BREAK suggestion (a suggested paragraph SPLIT or JOIN) carries its id on a
zero-width `block-split-suggestion` / `block-join-suggestion` embed at the END of
the owning block N (`properties.suggestionId`), NOT on a text run, so `resolve`
handles it additively: the scan classifies the break embed as a `breakDrop` —
ALWAYS dropping the embed (an in-place `yItems.delete` by index on N, so N's
surviving runs keep their identity) and recording N as a merge owner when `(insertion && reject) || (deletion &&
accept)` — split-reject UNDOES the split, join-accept DOES the join. After the
phase-1 writes, `resolve` MERGES block N with its next sibling N+1 in the SAME
transaction via the live `mergeWithNextSiblingLiveInTx` primitive; the other two
cases (split-accept, join-reject) keep the blocks split. (A single-id resolve can own
MULTIPLE break embeds: a cross-block suggested replace/delete tags k+1
`block-join-suggestion` embeds with ONE deletion id — one per crossed boundary — so
accepting it cascades k+1 merges. The reverse-order merge loop is therefore
load-bearing even for a single id, exactly as in the bulk path.) The live primitive
reads the owner's CURRENT next sibling LIVE from
the Y.Doc inside the open transaction and is a no-op when there is no next sibling or
the pair is not a valid same-parent adjacent leaf pair (the defensive moved-boundary
skip — subsuming any pre-tx boundary-validity check). Phase-1 only rewrites N's
content (drops the embed), so the merge reads N's post-phase-1 (embed-free) content.

Single-id `resolve` / `acceptSuggestion` / `rejectSuggestion` and bulk `acceptAll` /
`rejectAll` share ONE resolve engine (`resolveBlockScan` + `runResolve`): a common
document-order block scan that, per item, applies a per-caller `classify`
(single-id-test vs all-ids) yielding keep / rewrite / drop / breakDrop, accumulating
the per-block decision lists (`ResolveDecisionWrite`) + the (doc-order) break-merge
owners; then ONE non-undoable transaction applies the decisions in place via
`applyResolveDecisionsInTx`, runs the conditional break merges in
REVERSE document order via `mergeWithNextSiblingLiveInTx`, deletes the resolved
record(s), and surfaces `state.rootId` when nothing was touched (the orphaned case).
Single-id `resolve` additionally deletes any CO-TENANT record it fully orphans: a
run can carry multiple authors' ids (Google-Docs nesting — insertion-by-A +
deletion-by-B), so a resolve that DROPS that run (reject-insertion / accept-deletion)
would strand the co-tenant. `collectResolveRecordDeletes` pre-scans all blocks with
the SAME `classify`, collecting co-tenant ids carried ONLY by dropped items (not by
any surviving item), and includes them in the delete batch — so a nested-author run
drop never leaves a dangling orphaned record (no equivalent gap on the bulk path,
which deletes ALL records).

`acceptAll(state)` / `rejectAll(state)` resolve EVERY suggestion in ONE
non-undoable transaction (via a shared `resolveAll(state, mode)`) and delete all
records. Because a single run can carry insertion+deletion+formatting ids at once,
they do NOT loop the single-id `resolve` (which would clobber blocks); instead each
block is walked ONCE and every run resolves all its ids in a COMBINED rewrite with
a dominance order — **acceptAll:** a `deletionSuggestionId` run is DROPPED (accept-
deletion wins; a char inserted-by-A AND deletion-by-B, both accepted, ends up
deleted), else the run keeps with the insertion id stripped + the formatting
proposal applied; **rejectAll:** an `insertionSuggestionId` run is DROPPED (reject-
insertion wins; the suggested text never lands), else the run keeps with the
deletion + formatting ids stripped. (A run that is both insertion AND deletion is
dropped under both.) Empty doc → identity no-op.

`resolveAll` also resolves BREAK suggestions in bulk, through the SAME shared
engine: the scan classifies every `block-split-suggestion` / `block-join-suggestion`
embed as `breakDrop` (dropping it; a non-break embed — footnote-anchor/tab/comment —
is kept) and, when `(insertion && reject) || (deletion && accept)`, records the
owning block N as a MERGE OWNER. The bulk case — and a single-id cross-block
delete/replace, which owns k+1 join embeds (see above) — makes the shared engine's
REVERSE-document-order merge loop load-bearing: a run of CONSECUTIVE owners may all merge in ONE transaction, so a pre-tx
plan would be unusable — owner B's plan would capture `B.next = C`, but C is
merged-away before B's plan applies, and a static plan would read a DELETED block.
Walking owners in **reverse document order** (each owner is still alive when
processed — an owner is removed only by its PREVIOUS sibling's merge, which comes
later in reverse order) and merging each via the live `mergeWithNextSiblingLiveInTx`
primitive — which reads the owner's CURRENT next sibling LIVE from the Y.Doc inside
the open transaction (never a stale pre-computed `nextSiblingId`) and no-ops on a
no-next / moved / non-leaf boundary — makes a chain of consecutive merges reflect the
prior merges. The phase-1 content writes (which dropped each embed) run BEFORE the
merge loop, so each merge reads N's embed-free, resolved content.

Positions are **id-and-offset**: `Position = { blockId, offset }`. The
offset counts UTF-16 code units across the block's inline content; each
embed item contributes one offset unit (a single cursor stop). Cursor
movement at the user-visible level enforces grapheme-cluster boundaries
via `Intl.Segmenter` (logic lives in `cursor/`, not here). Positions are
stable across edits to other blocks — only edits that touch the named
block can shift the named offset.

A `Span` is a directed pair `{ anchor, focus }`. Collapsed spans are
cursors. A span lives within a single **selection context** (the main
document tree, or one specific embed body); cross-context spans are not
supported.

Inline styles are **attributes on text runs and embeds**, not wrapper
nodes in state. The render module reconstructs `span` element boxes from
same-attribute neighbouring runs. State stores semantics; render
produces structure.

## Yjs encapsulation

The state module's public surface hides `Y.Doc` and its maps. Consumers
(cursor, render, cascade, layout, editor, components) import only:

- Layer 1 types (`State`, `Block`, `InlineContent`, etc.) — Yjs-free.
- Layer 1 snapshot accessors (`getBlock`, `getEmbedContent`,
  `getTemplateContent`, `resolveBlock`) returning
  frozen `Block` snapshots.
- Narrow Y.Doc-free accessors for specialized needs (e.g.
  `getEmbedContentIds(state)` / `getTemplateContentIds(state)` — used by
  render to iterate the embed/template subtree ROOTS without naming the
  underlying Y.Map).
- Layer 2 utilities and Layer 3 operations (defined below).

**Two import surfaces (intra-core vs cross-package).** Sibling core
modules import the state module through `state/index.ts` — the **barrel**
that is the intra-core API contract, grouped by layer (types/access,
utilities, ops + history, boot). It re-exports the Layer 1/2/3 surface
with named exports only and deliberately excludes the infrastructure
files (it cannot leak `STATE_INTERNAL` or any Yjs type). Separately, the
package-level `packages/core/src/index.ts` is the **cross-package**
surface consumed by `packages/dom`, `packages/react`, and examples. The
two surfaces are distinct on purpose; the barrel is the canonical
intra-core contract.

`State`'s only public field is `rootId`. The underlying `Y.Doc` and the
per-State `SnapshotCache` live behind a non-exported `STATE_INTERNAL`
symbol (defined in `state-internal.ts`). Modules outside `state/`
cannot import the symbol — only state-module-internal code can spell
`state[STATE_INTERNAL].doc`. Attempting `state.doc` from any module
outside `state/` is a TypeScript compile error (asserted by
`state/encapsulation.test.ts`).

`STATE_INTERNAL` MUST NOT be re-exported from `packages/core/src/index.ts`
or any other barrel. Its containment is the whole encapsulation.

Yjs may surface in a few well-defined seams (e.g. a future collab
transport will subscribe to update events on the doc), but those seams
will be additive, narrow, and documented here.

## Submodules

Submodules are organized by the three-layer API surface (types and
access; pure utilities; state-mutating operations) plus the
infrastructure pieces.

**Layer 1 — types and access primitives**:

- **`state`** — the `State` container type, `createState`, the
  `OperationResult` shape, `applyOperation` (the transaction-runner
  every Layer 3 op composes), `freshState` (rebuilds the per-state
  snapshot cache after external Y.Doc mutations like undo). Snapshot
  accessors: `getBlock` (main tree), `getEmbedContent`,
  `getTemplateContent`, and `resolveBlock(state, id) → { block, kind }`
  which resolves across all three trees (precedence main →
  embedContents → templateContents) and reports the `ResolvedBlockKind`
  provenance so a caller can route a follow-up write to the right map.
  Callers that only need the value use
  `resolveBlock(state, id)?.block ?? null`. Also exports the narrow
  `getEmbedContentIds(state)` / `getTemplateContentIds(state)` accessors
  that iterate the embed/template subtree ROOT BlockIds (blocks with
  `parentId === null`; body children are reached via the root's child
  chain, not enumerated) without exposing the underlying Y.Map (used by
  render).
- **`index`** — the `state/index.ts` barrel: the intra-core API contract,
  grouped by layer. Named re-exports only; infra is excluded.
- **`state-internal`** — the non-exported `STATE_INTERNAL` symbol that
  gates access to State's underlying Y.Doc + snapshot cache. Must not
  be re-exported from any barrel.
- **`build-state-from-blocks`** — state-module-internal builder that
  materializes Block fixtures directly into a fresh Y.Doc-backed State.
  Bypasses Layer 3 ops; intended for test-utils / boot helpers that
  need to construct an arbitrary state shape. The public test-utils
  `buildState` delegates here.
- **`build-document-from-tree`** — the SAFE public construction
  primitive. `buildDocumentFromTree(root, listDefs, allocator)` lowers a
  declarative NESTED `BlockNode` tree (a discriminated union of
  `ContainerBlockNode` — children, no inlineContent — and `LeafBlockNode`
  — inlineContent, no children; container-XOR-leaf is a compile-time
  guarantee) into a `State`: it mints a fresh `BlockId` per node and
  DERIVES every structural link (parentId / prevSiblingId / nextSiblingId
  / firstChildId / lastChildId) from tree position, then delegates to
  `build-state-from-blocks`. The root node's minted id becomes
  `State.rootId`; `listDefs` keys are the caller-minted listIds referenced
  by `list-item` leaves. Unlike `build-state-from-blocks` (whose manual
  link fields are a footgun, so it stays barrel-excluded), this is the
  declarative shape that owns link derivation in one tested place and is
  exported from the state + core barrels. It is the format-agnostic
  foundation any importer (e.g. the HTML serializer) targets. Builds the
  main tree only (embed/template declarative roots are a future
  extension).
- **`block`** — the `Block` snapshot type.
- **`block-id`** — branded `BlockId` type, `IdAllocator` interface,
  `productionAllocator` (UUID v4 via `crypto.randomUUID()`),
  `createTestAllocator` (deterministic sequence for tests).
- **`block-init`** — the partial-block shape used by ops that create
  new blocks before assigning an id.
- **`block-position`** — `Position`, `Span`, `Selection` types and pure
  builders (`createPosition`, `createSpan`).
- **`inline-content`** — `InlineContent`, `InlineItem`, `TextItem`,
  `EmbedItem` types, plus pure normalization helpers
  (`mergeAdjacentTextItems`).
- **`attrs`** — `ReadonlyAttrs` type, `attrsEqual` (deep-value compare),
  `mergeAttrs`.
- **`block-schema`** — declared shape of a Y.Map-stored block, with a
  compile-time coverage check (`satisfies + DeclaredKeys`) so the
  read-path and write-path never drift.
- **`block-kinds`** — defines the `BlockKind` taxonomy
  (`inline-bearing-leaf` / `atomic-leaf` / `container`) and a narrow
  `BlockKindResolver` interface (`getBlockKind(type) → BlockKind | null`).
  The component registry implements the resolver; state ops that need to
  judge shape (e.g., `setBlockType` for cross-kind refusal, `INSERT_NODE`'s
  shape validation) accept a resolver parameter. State no longer
  hardcodes type-string sets — taxonomy is owned by component
  definitions (`kind: "container"` for containers; leaf components
  declare `leafShape: "inline-bearing" | "atomic"`).

**Layer 2 — pure utilities**:

- **`block-traversal`** — `nextBlockInDocOrder`, `prevBlockInDocOrder`,
  `ancestorChain`, `firstLeafBlock`, `lastLeafBlock`. Step-bounded by
  the main-tree size to guard against corruption.
- **`block-compare`** — `compareBlocksInDocOrder` via LCA walk;
  `selectionContextOf`.
- **`document-order`** — recursive document-order block walkers:
  `iterateBlocksInDocumentOrder` (the MAIN tree only) and
  `iterateAllBlocksInDocumentOrder` (the main tree, then each `embedContents`
  body subtree, then each `templateContents` body subtree — the all-three-trees
  walk change-tracking's range index + resolve scan use so a suggestion tagged in
  a footnote / header / footer body is found and resolved). Also `docHasLists`
  (early-exit main-tree scan). Active-path cycle guard + `blockCount`-bounded
  sibling loop, both summing all three trees.
- **`span-iteration`** — `iterateSpan` (yields per-leaf-block ranges
  in document order) and `iterateBlocksInSpan` (yields each block,
  including containers, overlapped by the span).
- **`extract-text`** — flattens a span to a plain string for clipboard,
  find/replace, accessibility. Walks block boundaries via `iterateSpan`
  (no hardcoded block-type list); embeds serialize via a hook so plugins
  control their textual representation.
- **`table-context`** — `resolveTableContext(state, blockId) → TableContext
  | null` walks the `ancestorChain` to locate the enclosing
  table/row/cell, returning row/column indices, the row-id and per-row
  cell-id grids, and three span flags: `spanned` (any cell carries a real
  rowSpan/colSpan, per `isSpan`), `ragged`, and `hasSpans = spanned || ragged`
  (a derived convenience — see below for why it is NOT the editor no-op
  boundary). `ragged` is SPAN-AWARE: it is true when the
  `buildTableGrid` occupancy has a HOLE (an uncovered slot) — i.e. the table is
  not a clean rectangle once spans tile it. A well-formed spanned table fills its
  grid completely (`ragged` false → P15b runs); genuinely-missing cells OR a
  span that leaves a gap produce a hole (`ragged` true → the degenerate carve-out
  stays gated). (Computing `ragged` from raw per-row cell COUNTS would wrongly
  flag every colSpan/rowSpan table as ragged — a span legitimately makes a row
  hold fewer cells than the grid is wide.) `spanned` and `ragged` are exposed
  SEPARATELY because P15b dispatches them differently — a `ragged` table stays
  gated, a `spanned` (non-ragged) table routes to the span-aware op; a handler
  checks `ragged` FIRST so a spanned-AND-ragged table still no-ops. It resolves via
  `getBlock`, so it is the main-tree guard for the table editor ops.
  `getChildIds(state, parentId)` is the sibling-chain walk helper
  (cycle-bounded by `blockCount`). `hasSpans = ragged || spanned` is a derived
  convenience (kept for callers wanting "is this a plain uniform table?"); it is
  NOT the editor no-op boundary — that is `ragged` alone (a degenerate table),
  with `spanned` routing to the span-aware op. `DELETE_TABLE` ignores all span
  flags (always safe). The context also caches the pre-mutation `grid`
  (`TableGrid | null`, the same grid `ragged` is derived from) so a span-aware
  handler reuses it for caret targeting instead of re-scanning the tree.
  `buildTableGrid(state, tableId) → TableGrid | null` is the STATE-side grid
  builder (P15b): it walks the table's rows/cells and calls `table-grid-core`'s
  `assignTableGrid` with each cell's span read as `spanValue(attrs) ?? 1` (the
  F1 byte-identical contract), so the span-aware ops reason in grid coordinates
  from the pre-mutation `State` exactly as the layout Table FC does.
- **`table-cell-range`** — `resolveCellRange(state, selection) → CellRange |
  null` turns a linear editor `Selection` into a rectangular cell range in grid
  coordinates (`CellRange = {tableId, minRow, minCol, maxRow, maxCol}`, inclusive
  bounds), the input to the P15b span-aware editing ops (merge/split). The editor
  `Selection` stays linear; this is the pure resolver. It resolves the anchor and
  focus cells via `resolveTableContext` (so it is main-tree-only and returns
  `null` unless BOTH endpoints sit in the SAME table), bounding-boxes their full
  grid rectangles over `buildTableGrid`'s occupancy, then expands to a fixpoint —
  for each slot `(r,c)` in the box it unions the owning cell's whole rectangle
  until a pass adds nothing. This guarantees a rectangle of WHOLE cells (a merge
  region never bisects a merged cell, matching Google Docs / Word); convergence
  is bounded by the grid area.
- **`table-cell-span`** — the shared span predicate. `spanValue(v)` returns
  the integer span when `v` is an integer `> 1`, else `undefined`;
  `isSpan(v) = spanValue(v) !== undefined`. Consumed by `table-context`,
  the resolver, and `tableCellComponent`.
- **`table-column-widths`** — pure column-width array maths for column
  edits: `spliceColumnWidth(widths, at)` (insert a proportional column) and
  `removeColumnWidth(widths, at)` (drop one); both renormalize to Σ = 1 for
  float-drift safety. `isColumnWidths(v)` is the shared predicate the column
  ops use to detect explicit sizing vs. auto-layout (absent → no attr change).
- **`table-grid-core`** — the layering-neutral occupancy-grid scan (CSS Tables
  §17.5), shared by the layout Table FC and the (P15b) state-side span-aware
  editing ops. `assignTableGrid(rows: GridCell[][]) → TableGrid` where
  `GridCell = {cellId, rowSpan, colSpan}` (spans PRE-NORMALIZED by the caller to
  integers ≥ 1) and `TableGrid = {cells: AssignedCell[], columnCount,
  occupancy: (BlockId|null)[][]}`. Occupancy scan: first-free-column placement
  skipping down-spanned reservations, `rowSpan` clamped to remaining rows,
  first-writer-wins overlap guard (dev-assert), rectangular occupancy matrix.
  Layer agreement is byte-identical because each caller pre-normalizes spans its
  own way: the layout adapter (`layout/table-grid.ts`) via `cellSpan`/metadata;
  the state adapter via `spanValue(attrs) ?? 1` (NOT `clampSpan` — `clampSpan(2.9)
  = 2` would diverge from the layout path's 1×1).

**Layer 3 — state-mutating operations** (one file per op in the `ops/`
subdirectory, re-exported from the `state/index.ts` barrel — there is no
separate `operations.ts`). The barrel's prose groupings (inline / structural
/ attrs / section / template) are the category taxonomy; `ops/` itself is
flat. File names below are relative to `ops/`:

**The `plan*` / `*InTx` split (atomic composition).** Each op file also holds
that op's `plan*` / `*InTx` primitives, so several ops can compose into ONE
Y.Doc transaction (one undo entry / one collab event) instead of each opening
its own. The split is uniform: a pure-data `*Plan` produced by a `plan*`
function that does ALL validation + snapshot reads BEFORE the transaction
(returning `null` for a no-op); a `*InTx(doc, …)` primitive guarded by
`requireInTransaction(doc, opName)` that performs the writes; and a thin
public op = `applyOperation(state, (doc) => *InTx(doc, …))`. Ops exposing the split:
`deleteRange` (`planDeleteRange` / `deleteRangeInTx` / `DeleteRangePlan`),
`replaceRange` (`planReplaceRange` / `replaceRangeInTx` / `ReplaceRangePlan` —
the plan folds the collapsed-insert / delete-only / re-collapsed cases into two
optional sub-plans so `replaceRangeInTx` is a straight-line `deleteRangeInTx?` +
`insertTextInTx?` that NEVER opens a nested transaction),
`insertBlock`, `splitBlockAtPosition`, `insertText`, `reparentChildren`
(`computeReparentWrites` / `reparentChildrenInTx`), `applyAttrsToRange`
(`planApplyAttrsToRange` / `applyAttrsToRangeInTx` / `ApplyAttrsToRangePlan`),
`insertBlocksAfter` (`planInsertBlocksAfter` / `insertBlocksAfterInTx` /
`InsertBlocksAfterPlan`), and `applySectionBreak` (`buildSectionBreakPlan` /
`applySectionBreakInTx` / `SectionBreakPlan` — a single-shape plan carrying a
`kind: "implicit" | "explicit"` field; one branch-free applier handles both
cases).

Most `*InTx` primitives are **read-free structural appliers**: the `plan*`
function snapshots everything needed and the primitive only writes (e.g.
`reparentChildrenInTx` reads nothing). `applyAttrsToRangeInTx` is the
exception — it reads live Y items by necessity, because the attr update is an
in-place, Y.Text-identity-preserving rewrite that walks the live `Y.Array` to
locate item boundaries and split partially-covered text (so a fully-covered
item keeps its per-character CRDT identity). Consequence: a read-free
primitive composes correctly after any prior in-tx op, but
`applyAttrsToRangeInTx` is correct only when prior in-tx ops do NOT shift this
span's offsets. Composing it atomically AFTER an offset-changing op
(delete/insert) needs mid-transaction span re-resolution against live Y state;
that is not yet implemented and lands with the consuming feature.

- **`insert-text`** — `insertText(state, position, text, attrs, allocator) → OperationResult`.
- **`delete-range`** — `deleteRange(state, span, allocator) → OperationResult`.
  Refuses cross-parent spans (action handlers decompose).
- **`replace-range`** — `replaceRange(state, span, text, attrs, allocator) → OperationResult`.
  Composes delete + insert atomically in one Y.Doc transaction.
- **`replace-matches`** — the Find & Replace batch primitive.
  `planReplaceMatches(state, matches, replacement, registry?) → ReplaceAllPlan`
  is the pure per-block planner: it groups `TextMatch[]` by block, applies each
  block's matches RIGHT-TO-LEFT (descending start, so earlier offsets stay valid)
  via a `spliceRun` composition over `splitInlineContentAtOffset` +
  `mergeAdjacentTextItems`, takes the replacement's formatting from the run
  containing `match.start`, and collects embed-content subtree ids of any removed
  slice into `embedContentIdsToDelete`. `ReplaceAllPlan = { blockWrites:
  {blockId, kind, items}[], embedContentIdsToDelete: Set<BlockId> }`.
  `replaceAllMatches` / `applyReplaceAllPlan` apply it in ONE `applyOperation` —
  each `blockWrite` is an `insertTextInTx` full-replace, then the collected embed
  bodies are cascade-deleted — so a whole replace-all is one undo entry. Batching
  PER BLOCK is required because N `replaceRangeInTx` calls in the same block would
  each full-replace from a stale plan and clobber prior calls.
- **`split-block`** — `splitBlockAtPosition`.
- **`merge-blocks`** — `mergeAdjacentBlocks` (same-parent neighbours).
- **`apply-attrs`** — `applyAttrsToRange` (inline) and the in-place run
  normalizer that merges adjacent same-attr items post-edit. Exposes the
  `plan*` / `*InTx` split (`planApplyAttrsToRange` / `applyAttrsToRangeInTx`)
  with the read-live-items caveat noted above. VISIBLE embeds in range inherit
  the merged attrs (a field takes on surrounding run formatting); zero-width
  STRUCTURAL MARKER embeds (`isStructuralMarkerEmbedType` — the comment/
  suggestion markers in `state/embed-markers.ts`) are SKIPPED, so an inline
  format never pollutes a marker or dangles a tracked-change provenance id on
  one after the suggestion resolves.
- **`set-block-attrs`** / **`merge-block-attrs`** — block-level attribute
  replace vs. merge semantics. Also exports `setBlockAttrsInTx(doc, blockId,
  attrs, opName)`, the in-transaction REPLACE primitive (main-tree only) for
  composing an attr write into another op's single transaction WITHOUT
  reentering `applyOperation` — used by `insertTableColumn` (and the later
  `deleteTableColumn`) to rewrite `columnWidths` atomically with the cell edits.
- **`set-block-type`** — type change, refusing cross-kind transitions.
- **`insert-block`** / **`remove-block`** — structural ops on the block
  tree; `remove-block` cascades to embed-referenced content blocks.
- **`insert-blocks-after`** — `insertBlocksAfter(state, afterId, inits,
  allocator)`: atomic bulk-insert of a run of sibling blocks after a given
  block, in one transaction (the paste-migration / cloned-subtree primitive).
  Exposes the `plan*` / `*InTx` split (`planInsertBlocksAfter` /
  `insertBlocksAfterInTx`): `planInsertBlocksAfter` allocates ids + resolves
  the boundary relink pre-tx into an `InsertBlocksAfterPlan`, and
  `insertBlocksAfterInTx` is a read-free structural applier.
- **`reparent-children`** — `reparentChildren(state, blockIds, newParentId,
  beforeSiblingId?) → OperationResult`: bulk-move a CONTIGUOUS run of sibling
  blocks between parents in one transaction. The relink is a pure function
  (`computeReparentWrites`) that builds a fully-resolved write-list from the
  pre-mutation snapshot; `reparentChildrenInTx` applies it (reads nothing).
  Empty list / identity self-move → no-op (same `State` ref). Shared core for
  outline moves and `section-break`.
- **`section-break`** — `applySectionBreak(state, cursor, allocator) →
  SectionBreakResult` (extends `OperationResult` with `newCursorBlockId`):
  splits the document into FLAT (never-nested) `section` blocks at the cursor's
  boundary block, in ONE transaction (create section(s) via `buildYBlock` +
  reparent bodies via `reparentChildrenInTx`). Breaking at a container's first
  child is a no-op (no empty leading section).
- **`merge-section`** — `mergeSectionWithPrevious(state, sectionId)`: the
  inverse of `applySectionBreak` — reparents a `section`'s bodies back into
  the previous section (or the document root) and removes the now-empty
  section, in one transaction. Drives section-break removal on delete-backward
  / delete-forward at a section boundary.
- **`set-list-type`** — `setListType(state, listId, "ordered" | "unordered")`:
  writes (or overwrites) the shared `ListDef` for `listId` via
  `writeListDefInTx` (Google Docs: changing a list's type changes ALL its
  items). Because this touches only the `listDefs` config map, it uses the
  dirty-union channel — it collects the run of list-items carrying `listId`
  from the pre-tx state and returns them so they re-render.
- **`set-list-restart`** — `setListRestart(state, blockId, number | undefined)`:
  sets or clears the focus item's `listCounterOverride` attr (Google Docs'
  "restart numbering at N" / "continue previous numbering"). This is a plain
  block-attr edit (`mergeBlockAttrs`), so it needs no dirty-union; `undefined`
  removes the attr.
- **`comment-ops`** — the comment thread CRUD, all NORMAL tracked
  `applyOperation` ops (the `comments` map is an UndoManager scope, so each is
  undoable). `addComment(state, span, input)` inserts the paired `comment-end`
  then `comment-start` marker embeds AND writes the thread record in ONE
  transaction (composing `insert-comment-markers`' `plan*` / `*InTx` so markers
  + record land as one undo unit). `resolveComment` / `reopenComment` flip the
  record's `resolved` flag; `deleteComment` strips BOTH markers from their
  owning block(s) AND removes the record; `addReply` pushes a reply `Y.Map`
  onto the record's `replies` `Y.Array`. `getComments(state) → ResolvedComment[]`
  is the read surface. Because resolve / reopen / addReply (and `deleteComment`
  on its orphaned-by-absence path, where both markers are already gone) write
  ONLY the `comments` side-table — which is excluded from dirty-capture — they
  surface `state.rootId` as the dirtyId (the `setListType` extra-dirty
  precedent) so the op advances state and lands a committable, undoable entry
  instead of short-circuiting to identity.
- **`insert-comment-markers`** — the marker-insert primitive `addComment`
  composes: `planCommentMarkers(state, start, end, commentId)` validates both
  endpoints and computes the bodyless `comment-start` / `comment-end`
  `EmbedItem` writes (each carrying `properties.commentId`, owning no embed
  body — like a cross-reference pointer); `applyCommentMarkerWritesInTx` applies
  them. The standalone `insertCommentMarkers(state, span, commentId)` op wraps
  the same plan in its own transaction. End-marker is placed first so the
  start-insert does not shift the end offset; a same-block span splices both
  into one items array, a cross-block span lands each marker in its own leaf.
- **`insert-table-row`** — `insertTableRow(state, ctx, position, allocator)`
  (`position: "above" | "below"`): materializes a full row (one `table-cell`
  per column, each holding an empty paragraph) and splices it into the table's
  row chain in one transaction. Exposes the `plan*` / `*InTx` split
  (`planInsertTableRow` THROWS on a degenerate (no-cell) row;
  `insertTableRowInTx` is the read-free applier — both deliberately NOT
  re-exported from the barrel, only `insertTableRow`). The caller supplies a
  `TableContext` from `resolveTableContext` (Layer-2 helper, below). Keeps a
  table's `headerRowCount` attr valid across the insert (`adjustHeaderRowCount`,
  #487 below). Main-tree only.
- **`delete-table-row`** — `deleteTableRow(state, ctx)`: removes the caret's row
  (its `table-row` subtree, via `planRemoveBlock` / `removeBlockInTx`) in one
  transaction; the plain (non-spanned) counterpart to `deleteTableRowSpanAware`.
  Composes the row removal with the `headerRowCount` adjustment
  (`headerRowAttrsAfterRowEdit` + `setBlockAttrsInTx`, #487) in the SAME
  transaction (one undo entry). `plan*` / `*InTx` split. The `DELETE_TABLE_ROW`
  handler routes a non-spanned table here and a spanned table to the span-aware op.
  Main-tree only.
- **`insert-table-column`** — `insertTableColumn(state, ctx, position, allocator)`
  (`position: "left" | "right"`): inserts one new `table-cell` (holding an empty
  paragraph) at `targetCol = position === "left" ? colIndex : colIndex + 1` in
  EVERY row, in one transaction. Column ops touch one cell per row (multiple
  parents), so they cannot reuse the single-parent `insertBlocksAfter`; this is a
  dedicated `plan*` / `*InTx` op like `reparentChildren`. When the table carries
  an explicit `columnWidths` attr, the plan re-splices it (`spliceColumnWidth`)
  and the applier writes it via `setBlockAttrsInTx` IN THE SAME transaction (one
  undo entry reverts both cells and widths); auto-layout tables (no
  `columnWidths`) get no attr change. Main-tree only.
- **`delete-table-column`** — `deleteTableColumn(state, ctx)`: removes the caret's
  column (one cell + its subtree per row, via per-row `planRemoveBlock` /
  `removeBlockInTx`) in one transaction; re-removes the column from `columnWidths`
  (`removeColumnWidth` + `setBlockAttrsInTx`) when present. THROWS on a 1-column
  table — the caller routes the last-column case to `deleteTableWithReplacement`.
  Main-tree only.
- **`delete-table`** — `deleteTableWithReplacement(state, tableId, allocator) →
  OperationResult & { newParagraphId: BlockId | null }`: removes the whole
  table subtree. When the table is its parent's sole child, removal would empty
  the parent, so the op composes `removeBlockInTx` + a direct empty-paragraph
  write in ONE transaction and returns the new paragraph's id (`newParagraphId`);
  otherwise it is a plain `removeBlockInTx` (`newParagraphId` null). Span-agnostic
  (deleting a whole table is always safe) and main-tree only.
- **`split-cell`** (P15b) — `splitCell(state, ctx, allocator)`: unmerges a merged
  (spanned) cell into 1×1 cells in ONE transaction. NO-OP (same `State` ref) when
  the caret cell is not a real span. `planSplitCell` reads the PRE-mutation
  `buildTableGrid` occupancy: the survivor keeps its content and drops its
  `rowSpan`/`colSpan` (becoming the top-left 1×1 cell, via `setBlockAttrsInTx`),
  and `rowSpan*colSpan − 1` new empty 1×1 cells fill the rest of its grid
  rectangle. Splice positions per grid row come from the cells ORIGINATING in that
  row (`AssignedCell.gridRow === r` — exactly that row's sibling chain), so a cell
  spanning down from an earlier row is correctly excluded and the new run lands
  relative to the row's own cells. The grid column count is unchanged, so
  `columnWidths` is untouched. `plan*` / `*InTx` split, both op-internal (only
  `splitCell` is barrel-exported). Main-tree only.
- **`merge-cells`** (P15b) — `mergeCells(state, range: CellRange)`: merges a
  rectangular `range` (from `resolveCellRange`) into one spanned cell in ONE
  transaction. NO-OP (same `State` ref) when the range is a single cell. The
  SURVIVOR (cell originating at `(minRow,minCol)`) keeps its content FIRST and
  grows its span to the range dims (`setBlockAttrsInTx`; attr dropped at 1); every
  OTHER in-range cell's block-children are appended row-major onto the survivor
  then the cell is removed — EXCEPT a single-empty-paragraph cell contributes
  nothing (F9: `inlineContent.items.length === 0`, no piled-up blank lines).
  `planMergeCells` reads the PRE-mutation grid: it relies on `resolveCellRange`
  having expanded the range to whole span-rectangles, so cells partition cleanly
  into in-range (origin in range) vs out-of-range. `mergeCellsInTx` reparents the
  migrated children, RE-CHAINS every affected row's surviving cells (a row wholly
  covered by the new rowSpan becomes an empty `table-row`), and deletes the donor
  cells (+ empty donors' paragraphs). `plan*` / `*InTx` split, op-internal (only
  `mergeCells` is barrel-exported). Main-tree only.
- **`insert-table-row-span-aware`** (P15b / D5) — `insertTableRowSpanAware(state,
  ctx, position, allocator)`: the span-aware INSERT_TABLE_ROW for well-formed
  SPANNED tables (the handler routes 1×1 tables to the byte-identical P15a
  `insertTableRow`). Insertion boundary `gr` = the caret cell's grid edge
  (`position==="above"` → its origin row; `"below"` → just past its last row) so it
  never bisects a rowSpanning caret cell. For each grid column, a cell owning BOTH
  the slot directly above and below `gr` CROSSES → its `rowSpan += 1` (dedup via a
  Set so a colSpan cell bumps once); uncovered columns get a new empty 1×1 cell.
  The new `table-row` holds only the new cells (grid-column order; possibly none,
  fully covered → an empty row). Column count unchanged → `columnWidths` untouched.
  `plan*` / `*InTx` split, op-internal. Main-tree only.
- **`insert-table-column-span-aware`** (P15b / D5) — `insertTableColumnSpanAware(
  state, ctx, position, allocator)`: the column-axis mirror. Boundary `gc` = the
  caret cell's column edge (`"left"` → origin column; `"right"` → just past its last
  column). A cell owning BOTH the slot left and right of `gc` in some row CROSSES →
  its `colSpan += 1` (Set-deduped over its rows); uncovered ROWS each get a new empty
  1×1 cell spliced into that row at the position dictated by the row's ORIGINATING
  cells (the split-cell pattern). A new column raises the count, so an explicit
  `columnWidths` attr is re-spliced (`spliceColumnWidth` at `gc` via
  `setBlockAttrsInTx`) — one undo reverts cells + widths; auto-layout tables get no
  attr change. `plan*` / `*InTx` split, op-internal. Main-tree only.
- **`delete-table-row-span-aware`** (P15b / D5) — `deleteTableRowSpanAware(state, ctx)`:
  the span-aware DELETE_TABLE_ROW (the hardest op — content re-homing). Deletes the
  caret cell's grid row `gr`. Per the PRE-mutation grid: a cell COVERING `gr` from
  above → `rowSpan -= 1` (shrinks); a cell ORIGINATING at `gr` with `rowSpan > 1` →
  RE-HOMES one row down (reparented to the next row, `rowSpan -= 1`, content kept,
  spliced at its grid-column position via a full next-row re-chain); a plain 1×1 cell
  at `gr` → removed (subtree + embed cascade, via `planRemoveBlock` per cell). The
  now-empty row block is deleted and spliced out of the table's row chain. NO-OP when
  the grid can't be built or the table has ≤1 grid row (the last-row case collapses
  the whole table — the editor handler's job, as in P15a). Column count unchanged →
  `columnWidths` untouched. `plan*` / `*InTx` split, op-internal. Main-tree only.
- **`delete-table-column-span-aware`** (P15b / D5) — `deleteTableColumnSpanAware(state, ctx)`:
  the column-axis mirror of delete-row, but SIMPLER — a column delete never reparents
  a cell. Deletes the caret cell's grid column `gc`. Per the PRE-mutation grid: a cell
  COVERING `gc` from the left, OR ORIGINATING at `gc` with `colSpan > 1` → `colSpan -= 1`
  (both stay in their row; the origin column renumbers down by one); a plain 1×1 cell at
  `gc` → removed (subtree + embed cascade, via `planRemoveBlock` per cell). The removed
  1×1 cells live in DISTINCT rows (a column owns one slot per row), so each is spliced
  out of its own row independently. A removed column lowers the count, so an explicit
  `columnWidths` attr is re-shrunk (`removeColumnWidth` at `gc` via `setBlockAttrsInTx`) —
  one undo reverts cells + widths; auto-layout tables get no attr change. NO-OP when the
  grid can't be built or the table has ≤1 grid column (the last-column case collapses the
  whole table — the editor handler's job, as in P15a). `plan*` / `*InTx` split,
  op-internal. Main-tree only.
- **`set-table-header-rows`** (#487) — `setTableHeaderRows(state, tableId, count)`:
  writes the `table` block's `headerRowCount` attr — "the first `headerRowCount`
  rows are repeating header rows" (Google-Docs "pin header rows" model; the layout
  reads it to repeat those rows at the top of each page/column fragment a tall table
  spans). `count` is clamped to `[0, rowCount]` AND to `largestCleanHeaderCount`
  (the **clean-cut invariant**: no merged cell may originate in a header row and
  span past the `[0, count)` boundary — clamps down to the nearest clean boundary,
  possibly 0). NO-OP (same `State` ref) when unchanged. `plan*` / `*InTx` split.
  Main-tree only. The pure validators `largestCleanHeaderCount(grid, requested)` and
  `adjustHeaderRowCount(count, op, rowIndex)` live in `table-header-rows.ts`; the
  latter keeps `headerRowCount` naming the leading contiguous block across row edits
  (delete a header row → −1, incl. last-header → 0; insert at `r < count` → +1;
  insert at the boundary `r === count` → unchanged = body row). **All four
  row-structural ops** (`insert-table-row`, `insert-table-row-span-aware`,
  `delete-table-row`, `delete-table-row-span-aware`) apply this adjustment
  (`headerRowAttrsAfterRowEdit` + `setBlockAttrsInTx`) in the SAME transaction as the
  row mutation, so a row edit and its `headerRowCount` fix-up are one undo entry.

## How submodules connect

Layer 3 ops compose Layer 2 utilities (for traversal and span iteration)
and call `applyOperation` to wrap their write-side work in a Y.Doc
transaction. Layer 3 is the **audited surface** — all state-mutating
logic lives here, nothing outside can corrupt state.

Editor action handlers (`packages/core/src/editor/actions/*`) are the
sole external callers of Layer 3 ops. Each handler typically composes
one or more Layer 3 ops, then calls `history.commit(opResult, selections)`
to record the unit's selection meta; the reducer has already decided whether
that unit opens a fresh undo group or coalesces into the open one (via
`beginEntry` / `breakCoalescing`, see the History reference). Handlers MUST
short-circuit before calling `commit` on a no-op operation
(`opResult.state === input.state`, equivalently `opResult.dirtyIds.size === 0`).
The render pipeline consumes `dirtyIds` to decide which subtrees to
rebuild (see `1.2-render.md`).

Layer 2 is read-only and consumed both by Layer 3 internally and by
external read paths (cursor, render, editor geometry queries).

## Reference

### `State` and `OperationResult`

```ts
interface State {
  readonly rootId: BlockId;
  // The underlying Y.Doc and SnapshotCache live behind a non-exported
  // STATE_INTERNAL symbol — reachable only from state-module-internal
  // code, not from any consumer. `state.doc` / `state.snapshotCache`
  // are TypeScript compile errors outside `state/`.
  readonly [STATE_INTERNAL]: {
    readonly doc: Y.Doc;
    readonly snapshotCache: SnapshotCache;
  };
}

interface OperationResult {
  readonly state: State;
  readonly dirtyIds: ReadonlySet<BlockId>;
}
```

`createState({ rootId, doc? })` constructs an opaque container with a
fresh snapshot cache. `applyOperation(state, fn)` runs `fn` inside one
Y.Doc transaction, passing it the doc, and returns `{ state, dirtyIds }`. Op
appliers use the passed `doc` to perform their writes rather than re-reading it
from `state`.

**Dirty-union channel.** `fn` has type `(doc: Y.Doc) => void | ReadonlySet<BlockId>`.
Most ops mutate the block tree and return `void` — their dirty ids are
captured automatically from the Y.Doc transaction's change set. But an op
that writes ONLY a non-block-tree map (e.g. a `listDefs`-only write that
changes a list's marker style without touching any `list-item` block)
captures NO block dirty ids on its own, yet still needs the affected
list-items to re-render. Such an op returns the affected `BlockId`s as a
`ReadonlySet`; `applyOperation` UNIONS that set into the captured dirty
set BEFORE the `size === 0` no-op short-circuit and BEFORE cache
invalidation, so the contributed ids both keep the op from being seen as a
no-op and invalidate the right snapshot entries. `setListType` (rewriting
a shared `ListDef`) is the first consumer; it collects the run of
list-items carrying the target `listId` from the pre-transaction state and
returns them.

**No-op identity contract.** When the transaction produces no Y.Doc
mutations (`dirtyIds.size === 0`), `applyOperation` returns the literal
input `state` reference unchanged. Callers use
`result.state === input.state` as an O(1) "did anything change?" guard.

**Carry-forward.** On the non-no-op branch, the new `State`'s
snapshot cache inherits every non-dirty entry from the input cache.
Snapshots of unchanged blocks remain reference-equal across edits;
memoized renderers can `prev === next` to skip unchanged subtrees.

### `Block`

```ts
interface Block {
  readonly id: BlockId;
  readonly type: string;            // open string, registered as a component type
  readonly attrs: ReadonlyAttrs;    // open-schema (closed schema lives in ComputedStyle)
  readonly parentId: BlockId | null;
  readonly prevSiblingId: BlockId | null;
  readonly nextSiblingId: BlockId | null;
  readonly firstChildId: BlockId | null;
  readonly lastChildId: BlockId | null;
  readonly inlineContent: InlineContent | null;  // non-null iff leaf
}
```

`Block` is a frozen snapshot view returned by `getBlock(state, id)` /
`getEmbedContent(state, id)`. Mutations go through Layer 3 ops; reading
through the snapshot accessor is O(1).

**List-item attrs (the flat list model).** A `list-item` leaf block carries
its list membership entirely in `attrs` (the open-schema `ReadonlyAttrs`):
- `listId: string` — which list this item belongs to (its grouping key).
- `listLevel?: number` — nesting depth 0–8 (absent ⇒ level 0).
- `listCounterOverride?: number` — an explicit "restart numbering at N" for
  this item (consumed by the numbering service).

There is no `list` container and no `listType` attr — the ordered/unordered
distinction and per-level marker styling live in the `listDefs` config for
`listId` (see "The `listDefs` map" above). Reading list attrs uses the
standard untyped-attr access (`attrs["listId"]` with a `typeof` guard), the
same pattern the cascade uses for custom attrs.

### `Position`, `Span`, `Selection`

```ts
interface Position {
  readonly blockId: BlockId;
  readonly offset: number;          // UTF-16 code units across the block's inlineContent.items
}

interface Span {
  readonly anchor: Position;
  readonly focus: Position;
}

type Selection = Span;              // alias used by cursor / editor modules
```

Each text item contributes `text.length` (UTF-16 code units) to the
offset; each embed item contributes 1 (a single cursor stop, like one
character). `normalizeSpan(state, span)` returns the span in document
order via `compareBlocksInDocOrder` (LCA walk) plus an offset compare
when anchor and focus share a block.

### `InlineContent` and `InlineItem`

```ts
interface InlineContent {
  readonly items: ReadonlyArray<InlineItem>;
}

type InlineItem = TextItem | EmbedItem;

interface TextItem {
  readonly kind: "text";
  readonly text: string;
  readonly attrs: ReadonlyAttrs;
}

interface EmbedItem {
  readonly kind: "embed";
  readonly embedType: string;
  readonly attrs: ReadonlyAttrs;
  readonly properties: Readonly<Record<string, unknown>>;
}
```

`items` is kept normalized post-edit: adjacent text items with equal
attrs are merged, empty text items dropped. Equality respects the
attribute interpreter registry (see `1.3-cascade.md`).

Primitive embeds (images, mentions, equations, hard-breaks) carry their
data in `properties` inline. Substantial-content embeds (footnote
anchors) carry `properties.contentBlockId: BlockId` referencing a block
in the embed-contents subtree, whose own block-tree holds the body.
Zero-width MARKER embeds (`comment-start` / `comment-end`) carry only
`properties.commentId` and own no body — they delimit a comment range
purely by their position in content (see "The `comments` map").

Each `EmbedItem.contentBlockId` references a **unique** embedContent root:
every body has exactly one owning anchor. Sharing one body across two
anchors is unsupported by design — Word and Google Docs both follow the
"each anchor owns its own body" model, and the unconditional
cascade-delete on anchor removal relies on it. Copy-paste preserves the
1:1 mapping by remapping every `contentBlockId` to a freshly-cloned body
via `clonePastedSubtree`. In dev builds the two halves of this mapping are
enforced after every op: `assertNoOrphanedEmbedContent` catches a
reference with zero owners, and `assertNoSharedEmbedContent` catches a
body with two-plus owners. See
`docs/superpowers/specs/2026-05-30-367-shared-embedcontent-decision.md`.

### `BlockId` and `IdAllocator`

```ts
type BlockId = string & { readonly __brand: "BlockId" };

interface IdAllocator {
  allocate(): BlockId;
}
```

`productionAllocator` uses `crypto.randomUUID()`. `createTestAllocator(prefix?)`
returns a deterministic counter for reproducible tests. Every Layer 3
op that creates blocks accepts an `IdAllocator` argument.

**Lifecycle:**

1. **Creation** — always allocate fresh.
2. **Deletion** — remove from the main map; cascade-delete any blocks
   referenced by `EmbedItem.properties.contentBlockId` from the deleted
   subtree (`embed-content-cascade`).
3. **Copy/paste** — `clonePastedSubtree` walks the source subtree,
   allocates fresh ids, rewrites references.
4. **Undo/redo** — no allocation. Yjs restores prior ids.

### History

```ts
interface SelectionEntry {
  readonly before: Selection | null;
  readonly after: Selection | null;
}

interface UndoRedoResult {
  readonly state: State;
  readonly selection: Selection | null;
  // BlockIds whose subtrees were mutated by the undo/redo's reversal,
  // captured via the same `afterTransaction` channel `runTransaction`
  // uses (Y.UndoManager.undo / .redo each wrap their Y.Doc surgery in
  // an internal transaction). Lets the editor's incremental render
  // pipeline rebuild only the affected RenderNodes.
  readonly dirtyIds: ReadonlySet<BlockId>;
}

type BeginKey = "insert" | "delete" | "command";

class History {
  constructor(state: State);
  beginEntry(key: BeginKey, now: number): void;
  breakCoalescing(): void;
  commit(opResult: OperationResult, selections: SelectionEntry): void;
  undo(): UndoRedoResult | null;
  redo(): UndoRedoResult | null;
  canUndo(): boolean;
  canRedo(): boolean;
}

function createHistory(state: State): History;
```

`History` wraps a `Y.UndoManager` configured with
`captureTimeout: Number.MAX_SAFE_INTEGER` — Yjs never auto-merges or
auto-closes groups by its own wall-clock; `History` owns **every** undo-group
boundary explicitly. A single action handler may compose multiple
`applyOperation` calls; they merge into one undo entry at the action
boundary. The boundary between consecutive actions is decided by
`beginEntry` / `breakCoalescing` (see **Undo coalescing** below), not by
`commit`.

**Selection lives on `StackItem.meta`.** Each undo unit's `SelectionEntry`
(pre- and post-unit selection) is stored on its `Y.UndoManager`
`StackItem.meta` rather than in a parallel array. `commit` writes the
entry onto the unit's StackItem (the item Yjs has already pushed/merged in
`afterTransaction`); `undo` / `redo` read it from the item Yjs pops. Because
Yjs mints a fresh (empty-`meta`) item on the opposite stack for each
undo/redo, `undo` / `redo` re-weld the entry onto that new top so it survives
the round-trip. `undo` returns `before`, `redo` returns `after`. Welding the
selection to the live stack item means it cannot index-desync from the Yjs
stacks — there is no second structure to keep aligned. A dev-mode check
confirms a popped item carries an entry.

**`advanceState` reconciles `currentState` after a NON-undoable change.**
`currentState` (the snapshot the next undo/redo rebuilds from via
`freshState(currentState, dirtyIds)`) is normally advanced only by `commit` /
`undo` / `redo`. A change made under a non-`null` `Y.UndoManager` origin (e.g. a
suggestion accept/reject under `SUGGESTION_RESOLVE_ORIGIN`) is non-undoable and
fires no StackItem, so it skips `commit` — and must call `advanceState(newState)`
(which sets `currentState` only, touching no stack/coalescing state). Without it,
a later undo would serve any block the non-undoable change touched but the undo
did not re-dirty from a stale pre-change snapshot.

**Undo coalescing.** A run of typing collapses into a single undo unit,
matching Google Docs. Two edit kinds are **coalescible**: `insert`
(`INSERT_TEXT`) and `delete` (`DELETE_BACKWARD` / `DELETE_FORWARD` /
`DELETE_WORD` / `DELETE_LINE`). Consecutive **same-kind** coalescible edits
whose gap is `< UNDO_COALESCE_PAUSE_MS` merge into one unit; the merged unit
keeps the run's **original** `before` selection and the **latest** `after`
selection. Coalescing is purely time-based (no word-boundary logic) — a
continuous burst collapses regardless of spaces. A group is **broken** (the
next edit starts a fresh unit) by any of: a **pause** (gap `≥` the window), a
**kind switch** (`insert ↔ delete`), any **discrete command** (split, paste,
formatting, block-type, list, section, header/footer/footnote — each is its
own unit and never coalesces, not even with an identical neighbour), or a
**selection jump** (caret move / selection change / click). `UNDO` / `REDO`
also break the open group; a window resize (`SET_CONTAINER_WIDTH`) is inert —
it neither edits nor breaks coalescing.

The boundary is decided **before** an edit's Y.Doc transaction (under
`captureTimeout: MAX` a transaction merges into the open `StackItem` unless
`stopCapturing` was already called, and a merge cannot be undone). So the
decision is a pre-operation hook, not part of `commit`:

- `beginEntry(key, now)` — called before each committing action. Coalesces
  with the open group iff the key is coalescible, matches the open group's
  key, and the gap is within `UNDO_COALESCE_PAUSE_MS`; otherwise it
  `stopCapturing`s to start a fresh unit. Commands set the open key to null
  (so the next edit also breaks). `BeginKey` is the `insert`/`delete`/`command`
  subset; selection/inert never reach it.
- `breakCoalescing()` — called on selection jumps and on undo/redo. Closes the
  open group so the next edit is fresh. Idempotent and cheap.
- `commit` — no longer closes the group; it only records selection meta. On a
  coalesced merge it preserves the group's original `before` and advances only
  `after`.

The editor reducer is the single chokepoint: it classifies each action with
the pure, exhaustive `coalesceKeyOf` (`editor/coalesce-key.ts`, a `switch`
with a `never` default so a new action forces a classification at compile
time) into `ActionClass = insert | delete | command | selection-break | inert`,
then routes `insert`/`delete`/`command` → `beginEntry`, `selection-break` →
`breakCoalescing`, and ignores `inert`. The clock is injected via
`EditorConfig.now` (defaults to `Date.now`) so the pause window is
deterministically testable. `UNDO_COALESCE_PAUSE_MS` is a `history`-module
constant. See `1.7-editor.md` for the reducer wiring. (Accepted edge: the
boundary advances before the per-action no-op short-circuit, so a no-op
committing action can still close an open typing group — the policy lives in
one place by design.)

**Tracked scopes.** The `Y.UndoManager` is constructed over SIX tracked
scopes: the three block-tree maps, the `listDefs` side-table, the
`comments` side-table, and the `suggestions` side-table. Tracking `comments`
makes a comment thread record revert atomically with its in-content
`comment-start` / `comment-end` markers (undoable-as-content — see "The
`comments` map"); tracking `suggestions` makes a suggestion's tagged items /
break embeds + record revert atomically as one unit (see "The `suggestions`
map"). Per-transaction tracking means a pure text edit, which never touches
either side-table, undoes without disturbing any comment or suggestion.

**Meta-map non-undoability.** Writes to the doc's meta `Y.Map` (which
holds `rootId`) are intentionally not undoable — `rootId` is
session-immutable. Future meta-map writers MUST explicitly consider
undoability.

**Error recovery.** `undo` / `redo` order their work as
`undoManager.{undo,redo}` → `freshState` → advance `currentState` (and
re-weld the entry onto the opposite stack's new top), all wrapped in
try/catch. `currentState` is advanced last, only after the Yjs reversal
and `freshState` succeed, so a throw from the first two leaves the wrapper
retriable. The caller sees a wrapped error identifying the failure as
history-internal.

**Undo-depth cap.** `commit` trims the oldest entries past `maxDepth`
(default 1000) via `undoManager.undoStack.splice` — the trimmed items
carry their `.meta` away with them, so no separate selection-stack trim is
needed.

### Comments

```ts
type CommentId = string & { readonly __brand: "CommentId" };

interface CommentReply {
  readonly id: string;
  readonly author: string;
  readonly body: string;
  readonly createdAt: number;
}

interface CommentRecord {
  readonly id: CommentId;
  readonly author: string;
  readonly body: string;
  readonly createdAt: number;       // host-injected (deterministic/testable)
  readonly replies: readonly CommentReply[];
  readonly resolved: boolean;
  // NO anchor field — the comment-start/comment-end markers ARE the anchor.
}

interface CommentRange {
  readonly start: Position;         // the comment-start marker's position
  readonly end: Position;           // the comment-end marker's position
  readonly orphaned: boolean;       // DERIVED from marker presence + ordering
}

interface ResolvedComment extends CommentRecord {
  readonly range: CommentRange;     // scanned each read; orphaned ⇒ no highlight
}

// State scan + read surface (state/comments.ts):
function buildCommentRangeIndex(state: State): Map<CommentId, CommentRange>;
function resolveCommentRange(state: State, id: CommentId): CommentRange | null;
function getComments(state: State): readonly ResolvedComment[];

// Tracked content ops (state/ops/comment-ops.ts):
function addComment(state: State, span: Span, input: AddCommentInput): OperationResult;
function resolveComment(state: State, id: CommentId): OperationResult;
function reopenComment(state: State, id: CommentId): OperationResult;
function deleteComment(state: State, id: CommentId): OperationResult;
function addReply(state: State, id: CommentId, input: AddReplyInput): OperationResult;
```

`createdAt`, `id`, and reply `id`s are host-injected via the op inputs
(`AddCommentInput` / `AddReplyInput`) — never generated in the engine —
mirroring `EditorConfig.now` + the `IdAllocator`. `getComments` freezes
each record (including its `replies` array) and attaches the range scanned
by `buildCommentRangeIndex`; a record with both markers gone gets a
degenerate orphaned range pinned to the document origin.

### Dirty-set contract (rendering bridge)

Every Layer 3 operation returns an `OperationResult` carrying
`dirtyIds: ReadonlySet<BlockId>` produced at write-time by the
underlying Y.Doc transaction's change set — never by post-hoc tree
comparison.

**Raw vs closure-expanded.** The `dirtyIds` returned by `applyOperation`
(and `History.undo` / `History.redo`) is the **raw mutated set** —
exactly the blocks whose own Y.Doc data changed under the transaction.
The render module's `dirtyIds` input (in `RenderOptions`) is the
**closure-expanded set**: `mutated ∪ ancestors(mutated) ∪
descendants(mutated)`. State emits the raw set; render owns the
closure expansion. The same name across module boundaries refers to
DIFFERENT sets — state's raw set is a strict subset of render's
closure-expanded set. See `1.2-render.md` for the expansion rule.

The renderer contract: `dirtyIds` contains both updated and deleted ids.
Consumers distinguish them with `getBlock(state, id) === null` (deleted)
vs. non-null (updated, re-render). Deletions in `embedContents` use the
same contract via `getEmbedContent`.

This is the engine's incremental-rebuild driver; see `1.2-render.md` for
how the render module consumes `dirtyIds`.

### Inline-attribute interpretation and run merging

State stores attributes openly (any key, any value). Equality for the
purpose of merging adjacent same-attr text items defaults to deep value
equality and consults a per-key `equals` from the **attribute
interpreter registry** (defined in `1.3-cascade.md`).

The cascade module translates `attrs` into declarable `Style` via the
same registry, producing `ComputedStyle` through the existing
resolution pipeline (em/rem flattening, inheritance, defaults). State
holds the open schema; cascade closes it.

### Initial state and creation

- `createEmptyDocument({ allocator? })` returns a `State` whose root is
  a `document` container block holding one empty `paragraph` child. The
  document block is `state.rootId`; the paragraph sits beneath it.

### Performance contracts

- `getBlock` / `getEmbedContent` / `getTemplateContent` — O(1) cache lookup.
- `getEmbedContentIds` / `getTemplateContentIds` — O(roots) to yield from
  the cached root-id set; no per-call scan of the map. The set is
  recomputed (O(N_map_keys)) only after a root is added/removed, which is
  rare relative to keystrokes — so these accessors do not tie per-keystroke
  render cost to embed/template body size.
- All Layer 3 ops — O(N_block) on the touched block(s) plus O(1) per
  affected sibling pointer; structural sharing on the snapshot cache
  preserves reference equality of unchanged block snapshots.
- `compareBlocksInDocOrder` — O(depth + LCA-fanout); bounded by ~100
  sibling-pointer hops at the target document scale.
- `applyOperation` no-op path — O(1) identity return.

The target document scale is smooth editing at ≤ 10,000 blocks per
document; graceful degradation to ≤ 100,000. See the spec doc for the
rationale (recalibrated from the prior "1M blocks" framing).
