# 1.1 — `state/`

The state module is the document model. It is the single source of
truth for everything semantic about the document — what blocks exist,
their attributes, the rich-text content inside leaf blocks, and the
relationships between them. It owns no geometry, no resolved styles, and
no visual concerns.

The design is a block-tree of styled-run arrays: `InlineContent` is a plain `{ items: ReadonlyArray<InlineItem> }`
array of styled runs, not a rope.

## What state is

A document is a **block tree** keyed by stable `BlockId`s. Each `Block` snapshot
is a flat record with a parent pointer and a doubly-linked-list of children
(`firstChildId` / `lastChildId` / `prevSiblingId` / `nextSiblingId`) — DERIVED
from the structural storage below, never stored.
Container blocks (sections, tables) hold child blocks; leaf
blocks (paragraphs, headings, list-items, table-cells) carry their rich
text as `inlineContent` — a flat array of styled inline items (text runs
and embed items).

**Lists are flat, not containers (the Google-Docs model).** A "list" is
NOT a container block. It is a maximal document-order run of `list-item`
LEAF blocks that share a `listId` attr; nesting is the per-item
`listLevel` attr (0–8). There is no `list` block type and no `listType`
attr. Per-list numbering configuration (which marker style, start value,
and restart rule each level uses) lives in a separate top-level config
side-table, `listDefs` (see "The `listDefs` map" below). The marker text
itself (a bullet glyph or a number like "1.") is COMPUTED at render time
by the `numbering/` service and baked onto the list-item element — it is
never stored on the block. See `1.2-render.md` (numbering) and
`1.5-editor.md` (list editing actions).

Storage is backed by a Yjs `Y.Doc`: a block REGISTRY plus FLOWS (the structural
storage below), and three top-level SIDE-TABLE maps that are not block structures:
`listDefs` (keyed by `listId`, the per-list numbering config), `comments` (keyed by
`CommentId`, the comment-thread records), and `suggestions` (keyed by `SuggestionId`,
the change-tracking records). Blocks are read only through opaque snapshot accessors
(`getBlock`, `getEmbedContent`, `getTemplateContent`, and the provenance-aware
`resolveBlock`); `listDefs` through `getListDefsForState`, `comments` through
`getComments`, `suggestions` through `getSuggestions`. BlockIds are globally unique.
Yjs gives cheap structural sharing across versions and real-time collaboration
without a state-module rewrite.

### Structural storage — registry + flows of pieces with end marks (schema 3) `[implemented]`

**Why end marks.** A Yjs item never changes parent, so a split puts a boundary between
two characters of one parent: either the tail is re-minted under a new parent (which
loses or misplaces a peer's concurrent typing and breaks undo), or the boundary is an
ITEM inside the character sequence. Blocks are therefore RANGES of a CRDT sequence
delimited by END-mark items — Word's paragraph mark (¶), Google Docs's paragraph-end
`\n`, Quill's line-ending `\n` — and no structural op ever moves a character.

- **Registry** — the root `registry` map, `BlockId → entry Y.Map`
  (`state/registry.ts`): `type`, `attrs` (a `Y.Map`, per-key merge), `tree`
  (`block | embedContent | templateContent`, written at creation), `shape`
  (`text | atomic | section | container | table | row | cell`), optional
  `implicitOf`; a flow holder adds `flow`; a table `{ columns, rows, columnWidths }`, a
  row `{ table, cells }`, a cell `{ row, col, colSpanTo?, rowSpanTo?, flow }`. No
  pointer fields, no inline content, no Yjs item ids. A new entry's `shape` comes from
  the COMPONENT registry (`BlockKindResolver.getStorageShape(type)`: inline-bearing leaf
  → `text`, atomic leaf → `atomic`, container → `container`, unless the component
  declares `storage` — table / row / cell / section), never from the snapshot's child
  count, so an empty childless host container is still a flow holder. The resolver is
  bound to the doc by `createState({ rootId, doc?, resolver })` (required; also required
  by `buildStateFromBlocks`, `createEmptyDocument`, the codecs' factories,
  `decodeFragmentClip` and `upgradeDocument`) and read by every writer
  (`state/storage-shapes.ts`); an unregistered type at a write boundary is an error,
  except in `upgradeDocument`, which infers a legacy type the host no longer registers
  (inline content → text, children → container, else atomic) and lists it in
  `UpgradeReport.unregisteredTypes`. Readers stay resolver-free (the shape persists in
  the entry). `setBlockType` refuses a change of storage shape within one kind.
- **Flow** — a `Y.Array<Y.Text>` of PIECES at an entry's `flow` (the document root,
  footnote / template bodies, table cells, host containers). Touched only through
  `state/y-flow.ts` (pointer walks, `insertPieceAfter` / `insertPieceBefore` via the
  Yjs `Item` constructor + `integrate`); its index API is never used outside that
  module.
- **End mark (the ¶)** — `insertEmbed({ end: BlockId, section?, implicitOf? })`,
  immutable plain JSON, the LAST unit of its paragraph. A text block is everything after
  the previous boundary item (a ¶, an object item, a section-end, a container item, or
  the flow start) up to and including its own ¶, possibly spanning pieces. Offsets count
  the content before the ¶ (UTF-16 + 1 per inline embed; ¶s and sub-flows count 0), so
  `Position` is `(block, offset ≤ content length)` and `(P, len)` is the gap just BEFORE
  ¶P. A ¶ carrying `section: S` is a SECTION-END: it ends paragraph `end` and section `S`
  (Word's sectPr in the section's last ¶).
- **¶ properties.** The ¶'s registry entry holds the paragraph's `type` and `attrs` (Word:
  the ¶ holds pPr, stored by reference) and `markAttrs` — a `Y.Map` of the INCLUSIVE
  inline-format keys OF THE ¶ itself (Word's ¶ rPr / Google Docs's text style of the
  paragraph-end `\n`): the keys the host `AttrRegistry` marks inclusive (`markAttrsOfRun`), so never a link and never a
  provenance or suggestion key. They style an empty
  paragraph's line (its strut sentinel), the selected-¶ glyph, the list marker's characters
  and the typing attrs at `(P, 0)` of an EMPTY paragraph. Writers keep them in step with
  the text the ¶ ends (`mergeMarkAttrs` / `writeTypedMarkAttrs`, written only when the
  filtered set differs): typing at `(P, len)`, inline formatting over a span that covers
  ¶P or ends at `(P, len)`, a split (the new ¶ gets the inclusive subset at the caret),
  a merge (L's `markAttrs` travel with L's attrs). Deleting characters never writes them.
  The host `AttrRegistry` is bound to the doc ONCE (`bindAttrRegistry(doc, registry)`,
  `state/mark-attrs.ts`; the editor binds `EditorConfig.attrRegistry` when it adopts a
  State — `createEditorStateFromState`; `decodeFragmentClip` binds its
  clip doc) and every reader judging an attr — inclusive `markAttrs`, a split's one-shot
  attrs, the upgrade's derived ¶ props, per-key `equals` (canonical run storage, no-op
  formatting / block-attr writes, resolve diffs, mark ranges), copy-drop marks, typing
  attrs, atomic marks — reads it there (`inclusiveKeysOf` / `attrRegistryOf`; the editor
  helpers `requireAttrRegistry`); no state op or editor helper takes it as a parameter,
  so every caller applies one rule. With none bound no `markAttrs` are written, equality
  is deep, and only the built-in one-shot attrs are honoured; the editor helpers and
  `upgradeDocument` throw (`requireAttrRegistry`).
  They live on the entry, not as a Y.Text format on the ¶ item, so a concurrent insert next
  to the ¶ cannot inherit them (Peritext's boundary anomaly). `Block.markAttrs` is the read
  field; the JSON codec stores it.
- **Sub-flow** — `insertEmbed(Y.Map{ pieces })` inside a piece, read in place: it
  bounds a piece's size without moving content.
- **Object blocks** (image, horizontal-line, toc, table, host atomic leaves, a host
  container with its own flow) are ONE self-delimiting `{ end }` item with no ¶ and no
  content; **sections** are section-end items in the root flow plus a final section (below).
- **Text** inside pieces is characters with Yjs formatting attributes and inline embeds
  (`{ embedType, properties }`), exactly as before; `BlockText` (`state/block-text.ts`)
  is a `Y.Text`-like surface (`length`, `insert`, `insertEmbed`, `delete`, `format`,
  `toDelta`) over a block's region, through which every inline primitive in
  `y-inline.ts` writes.

**Piece-size bound.** No write inserts into a piece holding `PIECE_SOFT_MAX` (1024)
structs, tombstones and formats included: at the piece end the write goes to a fresh
piece after it, at the start to one before it, mid-piece to a fresh piece in a sub-flow
(depth capped at 4; past the cap writes enter the full piece — a residue that grows
with the edit history at one spot, never with document size). Bulk inserts are chunked
the same way.

**Derived read model** (`state/flow-read.ts`). Every `Block` field, pointers included,
is derived by LOCAL walks from a boundary item; the tree cannot cycle.
- A ¶ whose registry entry is missing is HIDDEN (structurally inert): its content
  reads into the following block.
- **Invariant I** (Word / Google Docs: every story ends with a ¶, text always belongs to
  a ¶-terminated paragraph, a paragraph follows every table). On a flow's unit sequence,
  where a BOUNDARY is a ¶ (a section-end counts as one), an object / table / container
  item, or the flow end: **I1** every non-¶ unit (content or an object item) has a ¶ as its
  next boundary; **I2** a ¶ that is the flow's LAST unit is never deleted (evaluated at
  deletion time — whichever ¶ is last when the deletion runs stays). So a flow is
  non-empty, no two objects are adjacent, and the caret can never sit after a flow's final
  ¶. Every writer keeps I in STORAGE after a local op (a flow's creator writes its one
  final ¶; nothing "ensures" a trailing ¶ lazily on bind, which would race between peers).
  Only concurrency or undo / redo can break it, and the read model covers that:
- **Implicit entities** stand in where storage breaks I, with a derived id: the implicit
  paragraph `${anchor}#i` (content — or nothing, after an object or in an empty flow — with
  no ¶ before the next object or the flow end; the anchor is the entity ending at the
  previous boundary, or the holder) and the implicit table cell `${row}|${col}` (an empty
  grid slot). The first local write that needs a real entity MATERIALIZES it: a fresh
  id with `implicitOf: <derived id>` (a ¶ at the END of the run + an entry; for a cell an
  entry appended to `row.cells`), so creation never contends on a registry key.
- **Joins.** Consecutive ¶s with the same id, or the same `implicitOf`, form ONE
  entity: id = the first in flow order, attrs merged key-wise in that order (first
  holder wins), content in flow order. The first local write to a joined entity
  COLLAPSES it physically (the later ¶s are deleted; only keys the survivor lacks are
  written into it; an entry is deleted only for a candidate whose id differs from the
  survivor's) — idempotent under concurrent collapses.
- **Duplicates** (concurrent undos, move × move): non-consecutive live ¶s of one id
  resolve deterministically — the canonical one (smallest Item id) keeps the id, the
  others read as `${id}@${client}:${clock}`.
- **Sections** (Word's model). There is ALWAYS a final section: a real registry entry of
  shape `section`, created with the document by its single creator (`createState`,
  `writeRoot`, upgrade) and named by the root entry's `finalSection` (written once, never
  contested). It has no item: its region is everything after the last section-end, to the
  flow end. The read shape is therefore always root → sections (≥ 1) → blocks; nothing
  flips when the first break is inserted or the last one deleted, and a block's `parentId`
  is the first section-end after it, else the final section (memoized per item).
  A section always holds the paragraph its section-end terminates, so EMPTY SECTIONS CANNOT
  EXIST (no folding rules). Section attrs are page-setup OVERRIDES (an absent key falls
  back to the host `PageConfig`); the ROOT carries document defaults only — no page key.
- **Tables** are a grid: rows = the live `rows`, columns = the live `columns`, a cell
  is keyed by its column id, candidates for one (row, col) are joined (cell-id order,
  attrs merged, never collapsed), an empty slot is an implicit cell. Spans are id
  RANGES (`colSpanTo` / `rowSpanTo`): a span whose target is no longer live collapses
  to 1; spans are applied in row-major order of their anchors and one overlapping an
  earlier one reads as 1×1. A span's covered cells are hidden and their flows are read
  CONCATENATED into the anchor (anchor first, then row-major), each flow keeping its own
  final ¶, except an EMPTY covered cell (a flow holding only its final empty ¶), which
  contributes nothing (Word / Google Docs). A cell whose column is not live is hidden.

**MarkIndex** (`state/mark-index.ts`) — per `Y.Doc`, in memory, derived, never synced:
`BlockId → live ¶ / object Items` (keyed by `end`) plus the live section-end Items. Built by one scan when a doc
is first bound (`createState`); ops update it eagerly inside their transaction (so a
composed in-transaction step sees its own writes); an `afterTransaction` pass
reconciles from the transaction's new structs (`beforeState → afterState`) and deleted
structs — O(changed), idempotent, and the only path for remote and undo transactions.
Undo/redo create new structs, so a restored ¶ is indexed like any insert; nothing
reads `Item.redone`. The same pass checks every new struct is an instance of this
module's `Y.Item` / `Y.GC`: a struct decoded by a second Yjs instance marks the doc
incompatible.

**Ops are sequence edits** (`state/flow-ops.ts`; no op moves a character):
- **split / Enter** at `(B, k)` inserts a fresh ¶ H at the caret (Word: the NEW ¶ ends the
  head; the tail keeps ¶B, its id and its entry). The head `[0, k)` is the new paragraph
  H with B's type and attrs and the inclusive `markAttrs` at the caret; the tail keeps
  B's id. `splitBlockAtPosition` returns `{ newBlockId }` — always the HEAD's id. Enter at
  offset 0 therefore leaves an empty paragraph above and the content keeps its id. One-shot
  attrs (`AttrInterpreter.inheritOnSplit === false` in the registry bound to the doc, plus
  the built-in `listCounterOverride`; see `state/one-shot-attrs.ts`) follow the CONTENT that carried them: copied to H and removed
  from B when k > 0; stay on B when k = 0 of a non-empty B; move to H for an empty B. At
  k = len the "style for the following paragraph" (`newBlockInit`) is written onto B's
  entry and H keeps the original (Quill's header-enter). Start markers (`bookmark-start`,
  `comment-start`) adjacent to the caret bind to the FOLLOWING text and end markers to
  the PRECEDING text: the new ¶ goes before adjacent start markers and after adjacent end
  markers (`splitOffsetBetweenMarkers`).
- **merge / Backspace / Delete across a ¶** (`joinWithNext(L)`): ¶L (every live ¶ of its
  chain) is deleted through `deleteUnits`; the survivor is R, which keeps its id.
  Formatting: L's type + attrs + `markAttrs` are written onto R's entry as a key-wise
  diff (Word / Google Docs / Quill: the first paragraph's formatting wins), EXCEPT when L
  is an empty DEFAULT paragraph (type `paragraph`, no block attrs), which simply loses.
  `mergeAdjacentBlocks` returns `survivorId`. A range delete deletes its characters and
  every ¶ it crosses; the multi-¶ rule runs once (the anchor's paragraph wins unless it is
  an empty default). ¶R is never touched.
- **`deleteUnits`** is the ONLY code that deletes content units or ¶ / section-end items.
  Backspace, Delete, range delete (and so type-over / paste over a selection), find /
  replace, `removeEntity`, resolve (accept-deletion / reject-insertion: every drop of one
  resolve in ONE call), a suggested deletion's removal of the deleter's OWN pending
  insertions (`applyDeletionStrikeInTx`: every block's removals in ONE call),
  `joinWithNext`, replace-with-fragment's delete phase and
  section-break deletion route through it, so the bookmark deletion rule (see "Bookmarks
  and cross-reference targets") is applied in this one place. Phase 1 deletes the content
  spans (in document order, several per block allowed, each snapped OUT to grapheme
  boundaries; one read per block, or the caller's read model) and the object items; phase 2 visits the requested ¶s in document order, tentatively deleting
  each and keeping it when invariant I would break (I1 for the units it terminates, I2
  when the flow end follows it) — so a ¶ before a table survives a delete that ends at the
  table, and a flow's final ¶ is never deleted. The derived skip costs O(changed + #¶
  requested). Bypassing it deliberately (none needs the bookmark rule): a MOVE's source
  (whole entities, re-inserted elsewhere with the same ids and their content — bookmark
  markers included), undo / redo (restores a prior state), `deleteComment` stripping
  its own comment markers (markers, not content), and a sub-flow drop: `removeEntity` of a
  table / container and table row / column deletion (`table-storage.ts`) delete each cell's
  or container's flow wholesale (`deleteContainerEntry`). The drop is safe for the bookmark
  rule because a bookmark pair never straddles a sub-flow boundary, so a dropped sub-flow
  only ever holds complete pairs: markers are written inside one paragraph
  (`insertCrossReference`), Enter splits inside the paragraph's own flow, a merge never
  crosses a flow (`joinWithNext` joins along one flow's chain; text never merges into or
  out of a table), a range delete refuses cross-parent spans, a pasted fragment carries
  only complete pairs, and the one MOVE (`reparentChildren`, core-internal, no editor
  action) carries markers with their text.
- **`insertItemsAt`** is the only code that places object / table / container items,
  places entities at a boundary (`insertNodesAfter` / `insertNodesBefore` route through it)
  or re-inserts moved entities. After placing it runs ONE repair on every window it
  touched (each placed item and its next boundary, plus a move's source gap): a unit whose
  next boundary is not a ¶ gets a FRESH empty ¶ (new id) right before that boundary, and a
  window reaching the flow end whose last unit is not a plain ¶ (content, an object or a
  section-end) gets a fresh final plain ¶. Fresh ¶s are default paragraphs with the
  inclusive `markAttrs` of the preceding run. O(placed + touched windows).
- **remove** deletes the block's units (through `deleteUnits`, so a required ¶ stays and
  the paragraph empties instead); a LEAF's registry entry survives (hidden — so a
  concurrent move keeps its type and attrs, and undo restores just the ¶); a CONTAINER's
  entry (own flow, rows, cells, bodies) is deleted — delete wins. Unreferenced leaf
  entries accumulate as a storage cost in the same class as Yjs tombstones; read cost is
  zero; compaction is document replacement. (Records held only by tracked-¶ keys on a dead
  ¶ are the same cost class.)
- **insert / paste / fragment** write content + ¶s (`insertChildren`, `FlowWriter`); a
  paragraph is its content then its ¶, an object its item, a section its children with
  the last one's ¶ a section-end, and two adjacent objects get a fresh ¶ between them.
  Object insert at `(P, k > 0)` writes ¶H, then the object (head H, object, tail P); at
  `(P, 0)` only the object item, so an object is always followed by a paragraph.
- **sections** are section-end items: a break at `(P, k)` is a split whose new terminator
  is a section-end — head H (copies P's attrs), new section S′ (copies the containing
  section's attrs; the containing section is the first section-end after the caret, else
  the final section). `deleteSectionBreak` deletes the item in ONE step: the paragraphs
  merge by the rule above and the content joins the FOLLOWING section with no attr copy
  (Word, "Delete a section break"). The final section has no item, so there is nothing to
  delete at its end. A moved paragraph CARRIES its section-end.
- **tables** write the grid (`state/table-storage.ts`): a row / column inserted inside
  a span is covered by it automatically; deleting the row / column a span ends at
  retargets it, an anchor in a deleted row / column is re-homed to the next row /
  column of its span; MERGE moves nothing (the anchor's span keys are set; an empty
  donor cell's flow collapses out of the concatenation); UNMERGE clears the span keys, so every covered
  cell shows its PHYSICAL flow again (text typed into the merged cell stays in the flow
  that holds it — deliberately unlike Word, which keeps all text in the first cell,
  because moving content on unmerge would duplicate text under concurrent unmerges).
  Each cell flow ends with its own undeletable final ¶. `deleteTable` never needs a
  replacement paragraph: a paragraph always follows an object.
- **attr / type** writes go to the entry key-wise (`writeBlockAttrs`,
  `writeBlockType`); a joined cell's write (set or clear) applies to every candidate;
  a table's `columnWidths` array is stored per column id.
- **MOVE** (`moveEntities` / `reparentChildren`): one transaction deletes the source
  units (raw item deletes, not `deleteUnits`) and re-inserts, through `insertItemsAt`,
  content + ¶s with the SAME ids + re-minted content; registry entries are kept, so undo is
  exact. A peer's concurrent edit inside the moved block stays visible at the source
  (misplaced, never lost). move × move of one block yields two live copies (the
  duplicate rule: copies at one target join; at different targets the canonical keeps
  the id). move × delete: a leaf survives at the target (move wins); a container's
  orphan ¶ is hidden (delete wins). A derived entity (`${anchor}#i`, a duplicate copy
  `X@c:k`, a joined chain) is made real before it moves (`realIdForWrite`): no derived id
  is ever written as a ¶ or a registry key.
- **Never deleted**: piece and sub-flow items, by ops or by undo (the History's
  `UndoManager` `deleteFilter`): undoing a paste deletes the pasted characters and ¶s,
  and a peer's text typed inside survives. The only concurrent-text loss is a container
  delete (delete wins, as in Google Docs / Word OT) and merge × block-removal (both ¶s go;
  convergent and loss-free of characters the peers saw).

**Dirty blocks** (`state/flow-dirty.ts`, two tiers, O(changed + touched paragraphs)):
- *Content tier.* A new / deleted character, inline embed or format dirties its owning
  paragraph (the one whose ¶ follows it); siblings are never dirtied. A run terminated by
  a ¶ changes no link, so a KEYSTROKE (local or remote) and every ¶-key write dirty exactly
  {owner}. Only a run with no ¶ before the next object / the flow end (an implicit
  paragraph) has a gap bit; its 0 ↔ non-0 flip is structural.
- *Structural tier.* A boundary item p (¶, section-end, object) inserted or deleted
  affects the entity it terminates in each version, the entity owning p's position now, the
  entity ending at the boundary before p (its `nextSiblingId`; with no boundary before p,
  the holder start's implicit run) and the one after p (its `prevSiblingId`). A section-end re-parents exactly the entities between the previous
  section-end and itself; those, the sections around it and the root are dirty.
- Registry `keysChanged` dirties that block (attrs / type / `markAttrs` / ¶ keys); a grid
  field dirties the table, its rows, cells and the cells' children.
- The transaction's exact mapping (1.9) supplies the previous-version side: ids that
  left the read model (renamed / joined / gone) and the siblings / parent whose links
  named them, closed under rename (a renamed id's referrers are examined too). The
  structural neighbourhoods and the mapping's ids are only CANDIDATES: each is dirty iff
  its derived record differs between the two versions (presence, type, attrs, links, ¶
  keys, tags, content), so an untouched neighbour keeps its snapshot — over-dirtying is not
  accepted. An id dirty outright is not compared and opens no rename closure: the
  neighbourhoods above already name its siblings, edge parent and children.

**Locating and costs.** Block → ¶ is a `MarkIndex` lookup; the holder is O(depth) up
the piece / sub-flow parents. An offset resolves to a `(piece, index)` by walking the
block's cached LOCATOR (`state/locator.ts`: its extents, one per run of content keyed by
the run's boundary item; O(extents)), then the piece index by a bounded walk (O(piece) ≤
`PIECE_SOFT_MAX`); the `Y.Text` index op itself is O(piece). A locator is built on a
miss by one region walk and maintained incrementally per transaction (1.6 "Locators").
A joined text chain reads (and counts offsets) from the start of its region — right after
the previous boundary — over every ¶ of the chain. A keystroke is therefore independent of document size (1.6).

Invariants upheld by the inline primitives (unchanged from the per-block `Y.Text`
storage they now write through `BlockText`):
1. **Single attr boundary.** `toYAttributes` is the only path into Yjs: `null` /
   `undefined` values are dropped — stored attrs never hold either (Yjs `null` means
   "remove"); a format delta's `null` / `undefined` removes the key.
2. **Complete attrs on insert.** Yjs negates unlisted neighbour keys, so every insert
   passes the run's complete attrs; a first / last inserted text item registry-equal
   to its non-marker neighbour is written with the neighbour's stored value.
3. **Markers never carry formatting.** `format` is clamped to the content and split
   around structural marker embeds (and items the delta would not change); the READ
   path projects each marker's attrs to `{}`.
4. **Offsets are aligned, never rejected.** Every endpoint is snapped OUT to a
   grapheme-cluster boundary, once per composed op, so Yjs never splits a surrogate
   pair. In dev mode `applyOperation` checks it after every op
   (`assertInlineStorageInvariants`, `state/block-text.ts`): no piece item of a dirty
   block's content holds a lone surrogate (checked per item — a pair split across two
   runs, two items or two pieces reads whole once joined).
5. **Read-model coalescing.** Adjacent runs with deep-equal attrs read back as one run.

**Yjs internal surface.** `yjs` is an EXACT peer dependency (13.6.30) of core, print
and digital; the examples pin it. Internals used: `Item.left / right / deleted /
countable / length / content / parent / parentSub / id`, `AbstractType._item / _start`,
the `Content*` classes, `Y.getItem`, `Y.findIndexSS`, `Y.iterateDeletedStructs`,
transaction `beforeState / afterState / deleteSet`, and the `Item` constructor +
`integrate` (piece insertion). `Item.redone` is not used.
`state/yjs-internals.contract.test.ts` exercises each and asserts a single Yjs instance.

**Schema version, legacy storage and upgrade** (`state/upgrade.ts`). Schemas 1 and 2
kept a pointer tree of block maps in the `blocks` / `embedContents` /
`templateContents` roots, with inline content as a run array (1) or one `Y.Text` per
block (2); schema 3 (`CURRENT_SCHEMA_VERSION`) is the registry + flows of END marks. The effective
version is `meta.schemaVersion ?? inferFromShape` (`inspectDocument`). There is NO
engine-side auto-migration of a live collaborative document: the HOST runs
`upgradeDocument(doc, { resolver, clearLegacy? })` once with a single authority. It rewrites
every tree into the registry + flows (content re-minted, chunked at `PIECE_SOFT_MAX`;
tables as grid entries; legacy attrs normalized by `normalizeLegacyAttrs`), writes
`schemaVersion = 3`, is idempotent (a current doc only gains a missing marker and needs no
bound registry) and runs under the untracked `UPGRADE_ORIGIN`. The
end-mark conversion:
- every paragraph gets its own ¶; its `markAttrs` = the INCLUSIVE keys of its last run's
  attrs, judged by the attr registry bound to the doc (an editor adopting the doc binds
  it; a host upgrading before that calls `bindAttrRegistry` first; none bound → upgrading a
  pre-current doc THROWS before writing anything — it is one-shot, so unjudged ¶ props would be
  lost for good);
- a flow with no content gets its one final ¶; a section whose last child is a table /
  object gets an empty terminating paragraph (Word's mandatory paragraph after a table —
  a visible change); two adjacent objects get a ¶ between them;
- sections become section-end ¶s; the LAST schema-2 section becomes the final section
  entry (id and attrs kept); a section-less document gets a fresh empty final section.
  The root's page keys (`headerBlockId`, `footerBlockId`, `columnCount`, `columnGap`,
  `columnRule`) leave the root, which keeps its other attrs (`pageKeysOntoSections`): a
  section-less root's move onto the final section; a sectioned root's go onto every
  section lacking that key (the value it inherited; a section's own value wins);
- each `cross-reference` embed whose `targetId` resolves to a text block is re-anchored to
  a bookmark (one bookmark per target, `bookmark-start` / `bookmark-end` markers around the
  target's text) and stores `{ bookmarkId, refMode, numberStyle? }`; an unresolvable or
  non-text target stores no `bookmarkId` and renders broken.
  `UpgradeReport.crossReferences` lists the `rewritten` and `broken` host blocks;
- legacy pending-break embeds become tracked-¶ keys (see "Tracked paragraph marks").
- By default the legacy roots are FROZEN — never written, overwritten or deleted — so a
  legacy peer's later write stays DETECTABLE: any transaction touching a type under a
  legacy root halts every editor; the report carries the touched legacy blocks and
  their current legacy text. It is surfaced, not merged, and a re-upgrade does not
  recover it — the host decides what to do with the report.
- The upgrade records the frozen roots' BASELINE in `meta` (state vector + deleted
  length per legacy block). `legacyWritesSinceUpgrade(doc)` (O(legacy content)) finds a
  legacy write that landed while no gate was watching — between the upgrade or
  `createState` and a backend subscribing — as an item past the baseline state vector
  or a deleted length past the baseline; every compatibility gate runs it once at
  start and halts on it (a document never upgraded has an empty baseline).
- `clearLegacy: true` is an explicit host assertion that no legacy peer is connected:
  the legacy roots are cleared (a legacy write after that lands in a deleted type and
  is garbage-collected silently — hence the assertion). Frozen roots keep the legacy
  content until the host compacts by document replacement.
- `createState` / binary decode throw `LegacyDocumentError` on an older schema (its
  message tells the host to bind the attr registry, `bindAttrRegistry`, then run
  `upgradeDocument`) and
  `IncompatibleDocumentError` on a newer one; `decodeFragmentClip` upgrades a legacy
  clip before pasting; outstanding `RelativePosition`s are invalidated by an upgrade,
  as by any document replacement.
- The subscriptions' compatibility gate (`state/collab.ts`) halts on a legacy-root
  write, a second Yjs instance, or a peer raising `schemaVersion` past this engine's,
  calling `onIncompatible(report: IncompatibleDocumentReport { reason, legacyBlocks,
  legacyText })` (1.5 "Incompatible documents").

### The `listDefs` map (per-list numbering config)

`listDefs` is the fourth top-level `Y.Map` (alongside the three block
trees; `comments` is the fifth, see below). It maps each `listId` to a `ListDef { levels: ReadonlyArray<ListLevelConfig> }`,
where `ListLevelConfig = { style: CounterStyle; start: number; restart: CounterRestart }`
gives the marker style, starting value, and restart rule per nesting
level. It is a config side-table — not a block structure, so it is
deliberately EXCLUDED from the block-tree dirty-capture scan (a
`listDefs`-only write captures no block dirty ids; the writing op
contributes the affected list-item ids through the dirty-union channel,
see "Dirty-union channel" below). The `Y.UndoManager` tracks it as a
fourth scope (so a list-type change undoes), and `createYDoc` seeds it.

Accessors (state-module-internal where they take a `Y.Doc`, public where
they take a `State`):
- `getListDef(doc, listId) → ListDef | undefined`
- `getListDefs(doc) → Map<listId, ListDef>`
- `getListDefsForState(state) → Map<listId, ListDef>` — the render-pass
  entry point (reaches the Y.Doc through the `STATE_INTERNAL` seam, like
  the other accessors). The numbering engine consumes the result as its
  `CounterDefs` (see `1.2-render.md`).
- `writeListDefInTx(doc, listId, def)` — the in-transaction writer.
- `classifyListDef(def) → "ordered" | "unordered"` — classifies a def by
  its level-0 marker style (the bullet styles disc/circle/square →
  "unordered", else "ordered"). The one place the ordered-vs-unordered
  rule lives; shared by the toggle/set-type editor handlers.

`newListId()` mints a fresh list id (a plain string namespace, DISTINCT
from `BlockId` — a `listId` groups list-items, it is not itself a block).

### The `comments` map (anchored comment threads)

`comments` is the fifth top-level `Y.Map` (alongside the three block trees
and `listDefs`). It maps each `CommentId` to a `CommentRecord` — the thread
data: `{ id, author, body, createdAt, replies, resolved }`, where `replies`
is a `Y.Array<Y.Map>` (NOT a plain array) so concurrent reply appends MERGE
under collab rather than clobbering the list. Like `listDefs` it is a
side-table — not a block structure, so it is deliberately EXCLUDED from
the block-tree dirty-capture scan. `getCommentsMap` mirrors `getListDefsMap`;
`createYDoc` seeds it.

**The range is NOT stored in the record — the markers ARE the anchor.** A
comment's RANGE is delimited by a paired pair of zero-width inline embed
items in content: a `comment-start` and a `comment-end` `EmbedItem`
(`COMMENT_START_EMBED_TYPE` / `COMMENT_END_EMBED_TYPE`), each carrying
`properties.commentId`. Because the markers ARE inline content (exactly like
a footnote-anchor embed), the existing structural ops move and clone them
with surrounding text for free — they survive insert, delete, split, merge,
and paste with no anchor-maintenance code. A spike (`comment-anchor-survival.test.ts`)
rejected a Yjs `RelativePosition`-based anchor: every in-block edit keeps each
character's identity (one `Y.Text` per block), but `split-right` and `merge` still
orphan a `RelativePosition` because they move characters into another block's
`Y.Text` (Yjs cannot reparent items, so the moved characters are re-minted — the
structural-op limit above). RelativePosition is therefore not viable as the sole
comment anchor; the marker-embed model is the durable alternative. Each marker occupies exactly one offset (an atomic embed, one
cursor stop), preserving the `offset↔box` 1:1 invariant; it renders as a
ZERO-WIDTH inline-block atom (no glyph; see `1.2-render.md`), serializes to
`""` in `extract-text.ts` (excluded from `extractText` / `getWordCount`),
and is STRIPPED from pasted content by `clonePastedSubtree` (Google-Docs-faithful:
pasting commented text does not duplicate the comment).

**Orphaning is DERIVED, not stored.** `buildCommentRangeIndex(state) →
Map<CommentId, CommentRange>` scans the main-tree inline content ONCE,
tallying each `commentId`'s markers. A comment's range is LIVE (`orphaned:
false`) iff content holds EXACTLY ONE start AND EXACTLY ONE end with start
strictly before end (`comparePositions`); otherwise `orphaned: true` —
one-sided (a delete crossed one marker), inverted, or duplicated. A comment
whose markers are BOTH gone produces no index entry (orphaned-by-absence);
the read side surfaces it from the record list with a degenerate origin
range. `resolveCommentRange(state, commentId)` is the single-comment lookup.
Undo of a delete that orphaned a comment restores its markers, so the next
read reports it live again — no eager cleanup hook.

**Comment ops are UNDOABLE AS CONTENT — the deliberate, documented deviation
from Google Docs.** Because the markers are content, a comment reverts
atomically with them through the NORMAL `applyOperation` content-op path,
and the `comments` map is the FIFTH tracked scope of the `Y.UndoManager`
(beside the three block trees and `listDefs`). Per-transaction tracking means
a pure text edit — which never touches the `comments` map — undoes WITHOUT
disturbing any comment, while a comment op (markers + record together)
reverts as one unit. Google Docs streams comments separately so undo never
touches them; the marker-embed anchor forces a content-based model here.
This is collab-safe: `Y.UndoManager` is per-origin, so a user only ever
undoes their OWN comments, never a collaborator's. The accessors and ops
(below) live in `comments.ts` and `ops/comment-ops.ts`; the read surface is
`getComments(state) → ResolvedComment[]` (each record plus its scanned
range).

### The `suggestions` map (change-tracking / Suggesting mode)

`suggestions` is the sixth top-level `Y.Map` (alongside the three block trees,
`listDefs`, and `comments`). It maps each `SuggestionId` to a `SuggestionRecord`
— `{ id, kind: "insertion"|"deletion"|"formatting", author, createdAt, order?,
proposedAttrs?, groupId?, metadata? }` — where `order` is the mint sequence number
(`nextSuggestionOrder`, strictly increasing per editor; absent = 0) — the PRIMARY
suggestion order key — preserved by paste re-minting and the JSON format. A formatting
mint's `order` is bumped Lamport-style to at least 1 + the largest `order` of every
formatting suggestion tagged in its span (and the mint counter advances past it), so
`order` is causal: a new formatting suggestion ranks above everything it stacks on,
across reloads and peers, regardless of clocks (`createdAt` skew); suggestions that
never overlap never interact, and records without an `order` (0) fall back to
`createdAt`, then id. A valid `order` is a non-negative safe integer: a stored invalid
one (a peer-written `Infinity` / `1e300` / negative / fraction) reads as absent, the mint
counter ignores it, and the bump and the counter saturate at `Number.MAX_SAFE_INTEGER`; and where `proposedAttrs` (the formatting variant only) is a
nested `Y.Map` (built via `buildYAttrs`, read back via the public `yMapAsObject`)
so concurrent proposal edits merge under collab. Like `listDefs`/`comments` it is
a side-table — not a block structure, excluded from the block
dirty-capture scan; `getSuggestionsMap` mirrors `getCommentsMap`; `createYDoc`
seeds it. `suggestions.ts` holds the types + `writeSuggestionRecordInTx`/
`readSuggestionRecord` (state-internal, mirroring `comments.ts`).

**The range is NOT stored in the record — three independent inline-attr
dimensions ARE the anchor.** A single `TextItem` can simultaneously be an
INSERTION by one author and a pending DELETION by another (and carry a pending
formatting proposal), so suggestions are three independent `attrs` keys on a
`TextItem`, NOT one mutually-exclusive state: `insertionSuggestionId` and
`deletionSuggestionId` (the `*_SUGGESTION_ATTR` consts), each valued with the
owning `SuggestionId`, and one TAG PER formatting suggestion,
`formattingSuggestionId:<id>` (`formattingSuggestionKey(id)`; `FORMATTING_SUGGESTION_ATTR`
is the key prefix), so several formatting suggestions stack on the same characters
and each stays independently resolvable (see "Stacked formatting suggestions"
below). The `:` separator is deliberately not the mark-instance `#`: provenance is
not a mark, so `markTypeOf` / `getMarkRanges` / `AttrRegistry` never see a tag as
one. The structural
paragraph-break / section-break cases are NOT inline items: they are TAGS on the ¶'s own
registry entry (see "Tracked paragraph marks" below). The attrs move and clone with the text for free, so a
suggestion's range is range-stable across edits and DERIVED by a content scan
(mirror of the comments marker-scan), not a stored anchor. Why attrs not
bracketing markers (the comments model): a suggestion's range IS its text — an
insertion's items survive until accepted (strip the attr → plain text), a
deletion's until rejected — so it has no need to survive deletion of its own
interior.

**Range is DERIVED by a content scan.** `buildSuggestionRangeIndex(state) →
Map<SuggestionId, SuggestionRange>` walks every block tree once
(`iterateAllBlocksInDocumentOrder`: the main tree, then each `embedContents` body, then
each `templateContents` body — a suggestion id is context-local, so its occurrences stay
contiguous within one tree's segment of the walk), recording each id's enclosing `[start, end)`
from the three inline attr dimensions on text items (a run with several
formatting tags contributes to every one of their ranges), the formatting tags on
visible field embeds (a formatting suggestion may cover only an embed) and the
live ¶ keys (`boundaryRangeParts`: a keyed ¶'s range is `[(P, len P), (N, 0)]`, a
section-end's included) — the mirror of `buildCommentRangeIndex`.
`resolveSuggestionRange(state, id)` is the single-id lookup. The read surface is
`getSuggestions(state) → ResolvedSuggestion[]` (each record joined with its
scanned range). **A record with no live carrier is never surfaced** — not by
`getSuggestions`, `getSuggestionGroups`, render, ranges or a11y — the same rule as a
tag whose record is absent. Write ops never delete records; the next resolve deletes
every record with no carrier at all (no tagged char / embed and no key on a live ¶; see
"Tracked paragraph marks").

**Suggestion ops — create AND resolve — are UNDOABLE.** Creating a suggestion writes
the tagged items/embeds + the record in one NORMAL `applyOperation`, and the
`suggestions` map is the SIXTH tracked scope of the `Y.UndoManager` (per-transaction
tracking → a pure text edit leaves suggestions untouched). Accepting / rejecting is an
ordinary tracked transaction too, committed by the editor as ONE history entry: undo
restores the record(s) and the tagged runs exactly (Word / Google Docs: Accept /
Reject can be undone).

**Groups and metadata.** A record may carry `groupId` (a reviewable GROUP — a host
proposal spanning several insertions / deletions / formatting changes) and `metadata`
(host-defined opaque JSON, e.g. `{ source, reason }`); both are plain values on the
record `Y.Map`. Every suggestion belongs to exactly one group:
`suggestionGroupOf(record) = groupId ?? id` (a record without one — every pre-group
record, every suggesting-mode edit — is a group of one), so old documents read
unchanged. `getSuggestionGroups(state) → SuggestionGroup[]` (`{ id, author,
createdAt, metadata, suggestions, ranges }`, document order). Create ops never extend
a grouped record (coalescing skips records with a `groupId`) and accept a
`noCoalesce` input flag (host proposals always mint fresh records);
`assignSuggestionGroup(state, ids, groupId, metadata, perId?)` stamps the group (a
side-table write surfacing the root). A pasted copy of a group's runs becomes a NEW
group (`insertFragment` re-mints one group id per source group). A host proposal and
the resolve of a group is one tracked, undoable change; a host proposal is UNTRACKED —
another author's change, not in the user's undo stack (1.5 "Host proposals"). Its transactions carry an
`UntrackedOrigin(owner)` (`state/yjs-doc.ts`; `owner` = the proposing host's own
origin): no History tracks it, and `subscribeForeignChanges` (`state/collab.ts`)
treats it as self for the host whose `selfOrigin === owner` and as foreign for any
other host on the same doc. A record is VISIBLE in
`getSuggestionGroups` iff it still tags ≥1 char / embed (the user's undo can remove
every char an untracked proposal tagged); a hidden record is dropped by the next
resolve of its group.

A resolve applies a **minimal offset diff** to the touched blocks
(`applyResolveDecisionsInTx(doc, writes)`, one `ResolveDecisionWrite` = `{ blockId, items,
decisions }` per block): it walks a per-item decision list (`ScanItemResult[]`, computed by `resolveBlockScan`, aligned to
the block's snapshot items) — `keep` writes nothing, `rewrite` formats the item's range
with the attrs diff (stripping a provenance key and/or applying the proposal — every
resolve rewrite is attrs-only, so the characters keep their identity), and
`drop` deletes the item's range — every drop of every block in ONE `deleteUnits` call on
the snapshots, so the bookmark rule judges the resolve's whole deletion (accepting a tracked
deletion of exactly a bookmark's text removes the bookmark, as the direct deletion does); the ¶ keys resolve
separately (see "Tracked paragraph marks"). A tracked edit that
preceded the resolve keeps a valid undo `StackItem`. (`History.undo`/`redo` still treat
a genuinely-dead `StackItem` as a graceful `null` no-op — defense in depth.) Every
suggestion CREATE op is likewise an offset write: the deletion strike
(`applyDeletionStrikeInTx` — formats the struck runs, deletes the deleter's own
pending insertions), the inserted run of `replaceWithSuggestion`, and
`replaceWithSuggestedFragment` (per-block strikes + the `insert-items` primitive:
`insert` for the start block's line0, one split ¶ + insertion tag per further line,
a deletion key on each crossed ¶).

The suggestion-CREATION ops live in `state/ops/suggestion-ops.ts`. The first,
`markFormatting(state, span, proposedAttrs, input)`, records a FORMATTING
suggestion: it stamps its own tag `formattingSuggestionId:<id>` over the span (via
`applyAttrsToRangeInTx`) and writes a `formatting` `SuggestionRecord`
carrying `proposedAttrs` — the format delta the action WOULD have applied — in one
tracked `applyOperation` (one undo unit). Another formatting suggestion already on
the text keeps its own tag. The run's LIVE format attrs are untouched (the proposal
is shown, not applied; accept applies it later). Same-author, same-`proposedAttrs`
marks adjacent to an existing formatting suggestion COALESCE by reusing that id (the
before-neighbor preferred), so a continuous re-format is one suggestion — unless the
span holds a formatting suggestion ordered after the candidate, or a span character
carries the candidate's tag SHADOWED (in both cases reusing the id would leave the new
action beneath another value): then a fresh, newest id is minted.

**Stacked formatting suggestions.** The pending formatting suggestions on a run are
ordered by (record `order`, `createdAt`, id) (`compareSuggestionOrder`) — deterministic
on every peer. A tag's value is
`true`, or the canonical JSON of the sorted attr keys SHADOWED on that run. The
composite (render preview and the `"final"` view) is `live ⊕ S1.delta ⊕ S2.delta ⊕ …`
in that order, each minus its shadowed keys (`resolveFormattingSuggestionTags` with
every suggestion accepted). Accepting S on a run applies `S.delta − S.shadowed` to the
live attrs and adds those keys to the shadowed set of every OLDER suggestion still
pending on the run; rejecting S removes its tag (a pending suggestion never shadows).
So every sequential accept/reject order, and a set resolve (group / all, applied in
creation order), gives the creation-order result; undo restores tags and shadows
exactly (they are ordinary tracked formatting). A tag whose record is missing is
ignored by every reader and stripped by the next resolve of that run. Two peers
resolving overlapping suggestions CONCURRENTLY converge to identical attrs; for a key
both set, the winner follows Yjs's concurrent-format order (client order), like two
peers formatting the same text directly — a per-key creation-order register inside
attribute values would cost every attr read for this rare conflict.

`markDeletion(state, span, input)` records a SUGGESTED DELETION (soft-delete). Per
text run inside the span: plain text → stamp `deletionSuggestionId` (the text STAYS
VISIBLE until resolved); a run carrying an `insertionSuggestionId` by a DIFFERENT
author → also gains `deletionSuggestionId` (NESTING — it keeps its insertion id
too); a run carrying an `insertionSuggestionId` by THIS author (the deleter's OWN
pending insertion) → REMOVED FOR REAL (it never became real text, so un-suggesting
= removing — and only the in-range portion; surviving halves keep the insertion
id). It does NOT use `applyAttrsToRangeInTx` (which cannot selectively drop runs,
and would tag VISIBLE field embeds in range); instead it plans the per-owning-block
strike ranges pre-transaction, then strikes each block with offset writes via
`applyDeletionStrikeInTx` (struck runs are FORMATTED with the deletion id, so
their characters keep their identity; own-insertion portions are deleted). A `deletion`
`SuggestionRecord` (no `proposedAttrs`) is written unless coalescing into a
same-author adjacent deletion, or unless the whole span was own-insertions
(nothing tagged → no record; the real removal IS the change). A cross-block span
tags the in-range text of each block with the SAME id (one suggestion spanning the
boundary). Embeds inside a deletion span are preserved untagged (embed/inline-object
soft-deletion is a known gap — the range scan reads suggestion attrs only on
text items). A run already carrying a LIVE deletion (any author) is left untouched — the
same rule as a ¶ that carries a live deletion. Every ¶ the span crosses
gets the per-¶ deletion rule (see "Tracked paragraph marks"). When
nothing would change (every run and ¶ in the span already carries a live deletion)
the op is an identity no-op, and the editor only moves the caret (no history entry).

`mintInsertion(state, position, text, attrs, input)` is the INSERT_TEXT/PASTE
suggesting-mode op: it INSERTS `text` carrying an `insertionSuggestionId` (composing
`insert-text`'s `planInsertText`/`insertTextInTx`, not the public `insertText`) and
writes an `insertion` `SuggestionRecord`, in one tracked `applyOperation`. `attrs`
is the intended formatting of the inserted text; the op stamps the resolved
insertion id on top (`{ ...attrs, [INSERTION_SUGGESTION_ATTR]: id }`, overwriting
only the provenance id). It COALESCES at the insertion point: if the run
immediately before (`position.offset - 1`) or after (`position.offset`) carries an
`insertionSuggestionId` whose record is an `insertion` by the same author, it reuses
that id (before-neighbor preferred) and writes no new record — so a continuous
typing run is ONE suggestion, not N (mirrors undo-coalescing). The author's own
suggestion-creation is undoable (Ctrl+Z removes the text + record atomically).

`replaceWithSuggestion(state, span, text, attrs, input)` is the
TYPE-OVER-A-SELECTION suggesting-mode op — the suggestion analog of `replaceRange`.
It SOFT-DELETES the selection AND inserts `text` at the selection start, in ONE
tracked `applyOperation` (one undo entry / one collab event), producing TWO records:
an `insertion` and a `deletion` that SHARE `input.createdAt` as the render-layer
"this was one replace" grouping signal. It composes the strike's pure plan
(`planMarkDeletion`, extracted from `markDeletion` for this reuse) with
an offset insert at the strike's seam. The in-tx body strikes every struck block
(`applyDeletionStrikeInTx`), then inserts the suggested run at the plan's `seam` — the
selection start, or where a bookmark start marker the strike's own-insertion removal
takes was; the strike changes nothing before it, so it is a pre- and post-strike offset.
The new run lands BEFORE the struck text, carrying `insertionSuggestionId`. Every
character the edit does not delete keeps its identity (collab peers' concurrent edits
survive sync). Each
half coalesces INDEPENDENTLY (insertion at the start vs deletion per
`planMarkDeletion`); a coalesced half writes no new record. Degenerate inputs
delegate: empty `text` → a pure `markDeletion`; a collapsed span (or a strike plan
that yields nothing) → a pure `mintInsertion` at the span start. It returns
`endPosition` (right after the inserted run): the editor's caret.

`splitWithSuggestion(state, position, allocator, input, newBlockInit?)` is the
ENTER / paragraph-SPLIT suggesting-mode op. It performs a REAL block split (the same
`planSplitBlockAtPosition` + `splitBlockAtPositionInTx` as `splitBlockAtPosition`, so
both halves are immediately real, laid-out, navigable blocks) AND keys the NEW ¶ (the
head H's) as a tracked suggestion (`writeSplitSuggestionInTx`: `insertionSuggestionId` on
H's entry), in ONE tracked `applyOperation`, plus an `insertion` record. No inline item is
written. The tracked ¶ is always the head's, including Enter at offset 0 (the empty
paragraph above; see "Tracked paragraph marks"). `newBlockInit` overrides the tail's `type`/`attrs` at k = len. NO coalescing — each Enter is its own suggestion. Splits are always
allowed.

`splitWithSuggestionOverSelection(state, span, allocator, input, newBlockInit?)`
is the ENTER-over-a-NON-COLLAPSED-selection suggesting-mode composite — the SPLIT_NODE
analog of `replaceWithSuggestion`. It SOFT-DELETES the selection (the struck text STAYS,
tagged with `deletionSuggestionId`) AND inserts a suggested split AFTER it, in ONE tracked
`applyOperation` (one undo entry / one collab event), producing TWO records (a `deletion`
and an `insertion` that SHARE `input.createdAt` as the render-layer "this was one replace"
grouping signal). It composes the strike's pure plan (`planMarkDeletion`) with the
structural `planSplitBlockAtPosition`/`splitBlockAtPositionInTx` + the break key of
`splitWithSuggestion`. SINGLE-BLOCK scope only (the editor
caller routes `spanStart.blockId === spanEnd.blockId` here; a cross-block Enter-over-selection
goes through `replaceWithSuggestedFragment` with an empty two-line break fragment instead —
struck text rides BEFORE the break here vs AFTER in the fragment model, so the two are not
interchangeable). The KEY hazard
mirrors `replaceWithSuggestion`: the strike is an offset write (`applyDeletionStrikeInTx`),
and — critically — `markDeletion` REMOVES the author's OWN pending insertions in-range, which
SHORTENS the block (with the markers of a bookmark that removal takes), so the split
offset is `end.offset` minus the units the strike deletes before it (the
`deletedUnits`), NOT the pre-strike `end.offset`. After
the strike + split, the new block N+1 is tagged `insertionSuggestionId`. The struck
selection stays in N; the unstruck tail ends up in N+1.
The deletion record is written only when ≥1 run was tagged AND not coalesced (the
`markDeletion` contract); the insertion record is always written (a suggested split is its
own discrete insertion — NO coalescing). Degenerate: a normalized-collapsed span (strike
plan `null`) reduces to a pure `splitWithSuggestion` at the span start (no deletion record).
`newBlockInit` (the heading follow-on) is threaded through to the split. RESOLUTION is per
the underlying deletion + split-insertion records (see `resolve`).

`markParagraphMarkDeletion(state, leftBlockId, input) → JoinSuggestionResult` is the
BACKSPACE-at-block-start / DELETE-at-block-end paragraph-JOIN suggesting-mode op (a
section-end ¶ included): the per-¶ deletion rule on ¶L, in ONE tracked transaction. It does
NOT merge (Google Docs keeps both paragraphs while the deletion is pending). The author's
own live split ¶ is removed for real (`removedBoundary` reports the survivor + caret
offset); a live deletion already there (any author) is never overwritten, and a ¶ that
accepting would not delete (invariant I on the "final" projection) is left → identity no-op
(the editor moves the caret across the ¶); else `deletionSuggestionId` + a `deletion`
record are written.

`acceptSuggestion(state, id)` / `rejectSuggestion(state, id)` RESOLVE one suggestion,
dispatching on the record's `kind` via a shared `resolve(state, id,
mode)`. Each is ONE ordinary (undoable) `applyOperation`. Resolution per dimension:
accept-insertion STRIPS `insertionSuggestionId` (promote to plain text) /
reject-insertion DROPS the run; accept-deletion DROPS the soft-deleted run /
reject-deletion STRIPS `deletionSuggestionId` (text stays); accept-formatting
MERGES `proposedAttrs` (minus the run's shadowed keys) into live attrs, shadows them
on older pending suggestions and STRIPS its tag / reject-formatting STRIPS its tag
(on text runs and visible field embeds alike). Implemented as offset writes: a pre-tx
per-owning-block decision scan, then `applyResolveDecisionsInTx` applies them — `keep`
writes nothing, `rewrite` formats the item's range with the attrs diff, `drop` deletes
its range — so surviving characters keep their identity and every earlier undo
StackItem stays valid across the resolve; then `getSuggestionsMap.delete(id)`, along with
every co-tenant record left with no occurrence and every record with NO carrier at all
(lazy cleanup — see "Record lifecycle"). Resolving a carrier-less record deletes it and
surfaces `state.rootId`; a record with no live carrier is not visible and is not offered
(identity no-op). The scan walks ALL THREE trees (main, then each `embedContents`
body, then each `templateContents` body) in document order via
`iterateAllBlocksInDocumentOrder` (matching `buildSuggestionRangeIndex`), each write
carrying its owning block's tree `kind` — so a suggestion tagged in a footnote /
header / footer body resolves in-place in that body tree.

BREAK suggestions resolve through their keys (see "Tracked paragraph marks").

Single-id `resolve` / `acceptSuggestion` / `rejectSuggestion` and bulk `acceptAll` /
`rejectAll` share ONE resolve engine (`resolveBlockScan` + `runResolve`): a common
document-order block scan that, per item, applies a per-caller `classify`
(single-id-test vs all-ids) yielding keep / rewrite / drop, accumulating the per-block
decision lists (`ResolveDecisionWrite`); `planBoundaryResolution` plans the boundary
tags; then ONE (undoable) transaction applies the decisions in place via
`applyResolveDecisionsInTx`, applies the boundary ops (reverse document order, each
re-reading its blocks live), deletes the resolved record(s), and surfaces
`state.rootId` when nothing was touched (the carrier-less case). Every resolve also deletes
any CO-TENANT record it fully orphans: a run or a boundary can carry several authors'
ids (insertion-by-A + deletion-by-B), so a resolve that DROPS that run or removes that
boundary would strand the co-tenant. The scan collects, per non-resolved id, whether
it occurs on content / tags that survive or that go; an id that only goes is deleted
in the same batch.

`acceptAll(state)` / `rejectAll(state)` resolve EVERY visible suggestion in ONE
transaction (via a shared `resolveAll(state, mode, registry, only?)`) and delete their
records (¶ keys resolve through `planBoundaryResolution`; see "Tracked paragraph marks");
`acceptSuggestionGroup(state, groupId)` / `rejectSuggestionGroup` run the
same engine restricted to the group's ids (`only`) — the dominance rules apply to the
group's dimensions only, a co-tenant outside the group survives (or is deleted when it
loses all its content). Because a single run can carry insertion+deletion+formatting ids at once,
they do NOT loop the single-id `resolve` (which would clobber blocks); instead each
block is walked ONCE and every run resolves all its ids in a COMBINED rewrite with
a dominance order — **acceptAll:** a `deletionSuggestionId` run is DROPPED (accept-
deletion wins; a char inserted-by-A AND deletion-by-B, both accepted, ends up
deleted), else the run keeps with the insertion id stripped + the formatting
proposal applied; **rejectAll:** an `insertionSuggestionId` run is DROPPED (reject-
insertion wins; the suggested text never lands), else the run keeps with the
deletion + formatting ids stripped. (A run that is both insertion AND deletion is
dropped under both.) Empty doc → identity no-op.

### Tracked paragraph marks (break suggestions as ¶ keys)

A suggested paragraph split / join, or a suggested section-break insertion / removal, is a
revision ON a ¶ (Word's model — a tracked paragraph-mark insertion / deletion), not an
inline item. It is stored as two plain string keys on the registry entry of the ¶'s OWN
block — the entry its `end` names, a section-end's included (`state/break-tags.ts`):

| key | meaning |
|---|---|
| `insertionSuggestionId` | this ¶ was inserted (a suggested split / section-break insertion) |
| `deletionSuggestionId` | this ¶ is suggested for removal (a suggested join / section join) |

Both may coexist (inserted by one author, struck by another). The keys are NOT attrs:
never cascaded, never copied into fragments (`extractFragment` omits them, so a copied
suggested break pastes as a real break), never inherited on split, never touched by
`setBlockAttrs`. They are registry writes, so they are undo-scoped and atomic with the
split / record. `writeBreakTagInTx` is the only writer. A key whose record is absent is
dead: readers ignore it, writers may overwrite it. A ¶ id is minted per ¶, so the key
sits 1:1 with Word's "revision in the ¶'s own properties"; consecutive same-id duplicate
¶s are one ¶ by the join rule. It is deliberately NOT a Y.Text format on the ¶ item: a
concurrent insert next to a formatted item inherits the format by client-id order
(Peritext's boundary anomaly), which would make accepting the deletion delete a peer's
text. Entry keys have no range, so ¶ revisions cannot leak. Character revisions still
have the anomaly `[missing]`: a peer's concurrent insert at a character revision's edge
inherits its suggestion attrs.

**One rule, no step classification.** A tracked ¶ is simply the keys of a block's own
¶, shown while its record exists and the ¶ is live (`state/break-suggestions.ts`):
- `endMarkOf(state, E) → BoundaryMark | null` — the ¶ drawn at the END of text block E,
  from E's own keys. `kind` ∈ `split` / `join` / `split+join`, or `section-insert` /
  `section-join` / `section-insert+section-join` when the ¶ is a section-end item (the
  block ends a section another follows). O(1). `Block.breakSuggestion?: { insertionId?,
  deletionId? }` is the raw keys; inline content holds no break item.
- `boundaryMergesInView(state, L, R, view)` — L and R read as ONE paragraph in a view iff
  ¶L is hidden in it (insertion-keyed in `"original"`, deletion-keyed in `"final"`, never
  in `"suggesting"`) AND the unit after ¶L starts a paragraph, so a key on a required ¶
  (before a table) never renders text glued to the table. `extractText` / word count drop
  the "\n" accordingly. O(1).
- `boundaryRangeParts` (read by `buildSuggestionRangeIndex`) — ONE part per keyed ¶:
  `(B, len)`–`(N, 0)` with N the text block after ¶B, collapsed at `(B, len)` when an
  object or the flow end follows. A record is VISIBLE iff it has ≥ 1 live carrier (a tagged
  char / embed, or a live key).
- `blockBefore` / `blockAfter` (`state/paragraph-neighbour.ts`) give the caret-holding
  neighbour across a ¶ and name the `sectionBreak` whose section-end item IS that ¶.

**Writers.**
- *Suggesting Enter:* the split of 1.1 "Ops" plus `insertionSuggestionId` on the new ¶H
  (`writeSplitSuggestionInTx`). Enter at offset 0 needs no special case: H is the empty
  paragraph above and its ¶ is drawn on the empty line (Word's look).
- *Suggesting delete over a span:* characters get the inline attribute; each ¶ in
  `paragraphMarksInSpan` gets the deletion key — the ¶ of every block in the span except the
  last segment's (a span ending at `(Q, 0)` covers the ¶ of Q's predecessor), EXCEPT a ¶
  that `deleteUnits` would skip if the suggestion were accepted: the same invariant-I check
  run on the "final" projection (`markDeletableInFinal`; struck content and earlier keyed ¶s
  count as deleted). So deleting `(P, a)–(T, 0)` strikes text only, and a whole-paragraph
  suggesting delete before a table leaves ¶P unkeyed. O(span + #¶). The per-¶ rule
  (`markDeletionOf`): the author's own pending insertion is REMOVED for real (its reject);
  a live deletion (any author) is left; otherwise the deletion key is written.
- *Backspace / Delete at a ¶:* `markParagraphMarkDeletion(state, leftId, input)` applies the
  same rule to one ¶ (a section-end included) in one tracked transaction, never merging; it
  is an identity no-op when nothing would be written.
- *Section-break insertion* keys the section-end item's paragraph entry; in suggesting mode
  Backspace after a section-end keys that item, uniformly with every ¶.
- A MOVE (untracked) and paste / fragments never carry the keys.

**Resolve** (`planBoundaryResolution`, one per resolve / group / bulk): per keyed ¶ —
accept insertion / reject deletion deletes the key; reject insertion / accept deletion
deletes the ¶ by the merge rule (`deleteParagraphMarkInTx`: `joinWithNext`, a section-end
merging the sections too, else `deleteUnits`), its other key with it. A ¶ that invariant I
keeps (only a concurrency-born key on a ¶ before an object / at a flow end) keeps the ¶ and
drops the key. Each resolve is one `applyOperation` (one undo entry); the ¶ ops apply in
reverse document order. Accept All / Reject All walk the same parts.

**Record lifecycle.** Write ops never delete records. Readers hide a record with no live
carrier. The resolve scan deletes a record only when it has NO carrier at all (no tagged
char / embed and no key on a live ¶ — e.g. a same-key write lost by last-writer-wins, a key
on a ¶ a peer deleted).

**Collaboration.** Key × key on one ¶ is per-key LWW (the loser record is carrier-less →
hidden → lazily deleted). Delete-¶ × key-write leaves a key on a dead ¶: not drawn, record
hidden, cleaned lazily. Key × concurrent typing next to the ¶ cannot leak. Undoing a
suggesting Enter deletes ¶H, and with it the key. A key change dirties the owner only (the
¶ is drawn from its own block).

**Migration.** Schema ≤ 2 stored a pending break as a zero-width inline embed in N (types
private to `state/legacy-break-embeds.ts`). The upgrade drops each one and keys N's own ¶
(`insertionSuggestionId` for a split, `deletionSuggestionId` for a join; the first id of a
kind wins); an embed whose N has no next text sibling, or a repeated kind, is listed in
`UpgradeReport.orphanedBreakSuggestions`. The dev-mode storage check rejects a legacy break
embed in schema 3. The JSON codec stores `breakSuggestion: { insertionId?, deletionId? }`.

### Bookmarks and cross-reference targets

Block ids are not durable reference targets (a split renames text; Enter at the end of B
gives B's text the new head id), so cross-references follow Word: REF / PAGEREF target a
BOOKMARK. A bookmark is a pair of zero-width inline markers `bookmark-start` /
`bookmark-end` with `properties.bookmarkId` (`state/bookmarks.ts`), structural markers
(`state/embed-markers.ts`) like `comment-start` / `comment-end`: never formatted, never
tracked (in suggesting mode the cross-reference FIELD is a tracked insertion but its
markers are written untracked; rejecting the field leaves the bookmark, as Word does),
zero-width in render and text extraction, one Position offset each.
- **Pairing** (`pairBookmarkMarkers` over one id's markers in document order — the one rule
  `collectBookmarks` and the render cross-reference index both apply; deterministic and
  convergent under concurrency / undo):
  in document order the FIRST live `bookmark-start` of an id pairs with the first live
  `bookmark-end` of that id after it; every other marker of the id is inert (not rendered,
  not resolved, dropped on copy). `BookmarkRange.start` is the position just AFTER the start
  marker, `end` the end marker's position. A bookmark missing a marker is BROKEN (the field
  renders "Error! Reference source not found.").
- **Cross-reference fields** store `{ bookmarkId, refMode, numberStyle? }`
  (`insertCrossReference` reuses a bookmark whose LIVE pair spans exactly the target's text,
  else writes the markers in the same transaction; pairing a candidate is O(document)). `text` = the
  bookmarked range's text, `number` = the list counter of the paragraph holding the start, `page` = the page of the start.
  The render cross-reference index (bookmarkId → hosts, bookmarkId → its (start, end)
  Positions) is maintained incrementally from each pass's dirty blocks (1.2).
- **Caret affinity.** Markers are not caret stops: `caretAfterMarkers(state, position)`
  (`cursor/cursor-ops.ts`) moves a position past every marker adjacent on its right, and
  every caret-producing point applies it — core's insertion entry (`reduceEditor`, once for
  typing, paste, line break and inline embeds / fields) and character moves, print's
  hit-test / arrow keys, digital's DOM bridge. Typing at a bookmark's start is inside it, at
  its end outside (Word); `comment-start` / `comment-end` follow the same rule. It is
  block-local, O(items before the caret in the block), never a document scan.
- **Splits** bind start markers to the following text and end markers to the preceding text
  (see "Ops").
- **Deletion** (Word: deleting part of a marked item keeps the bookmark on the remaining
  text). `bookmarksRemovedBy` is SIDED: a bookmark is removed only when the deleted parts
  cover ALL its content — start marker inside a part or at a LEFT edge, end marker inside or
  at a RIGHT edge (an empty bookmark beside the span survives). `bookmarkDeletionSpan(state,
  span)` (`state/ops/delete-range.ts`) returns the span widened over the edge markers of the
  removed bookmarks (`widenOverBookmarkMarkers`) plus the `removedBookmarks` set. The
  parts of one deletion are judged per CONTIGUOUS run: content the deletion keeps between
  two parts (a resolve or a suggested deletion removes non-adjacent runs) separates them.
  Every delete that has a seam (range, type-over, find / replace, paste over a selection) and
  `extractFragment` use that one computation, so the seam and the caret sit where a removed
  start marker was and a cut of exactly a bookmark's text carries the pair. A suggested
  deletion plans its own-insertion removals the same way (`planMarkDeletion`: the removed
  set over them, the seam widened backward), and the suggested type-over / paste / Enter
  over a selection insert or split at that seam (the caret after the inserted text). The
  deletion itself is `deleteUnits` alone (given that set, or computing it over its spans —
  resolve): `deleteKeepingBookmarks` keeps the other markers inside the span at its
  collapse point. Replacing the last characters of a
  bookmark keeps the new text inside it (the replacement goes where the replaced text began).
- **Copy / paste** (`clonePastedSubtree`): an extracted fragment carries ONLY the bookmarks
  its span covers entirely; a paste keeps a pair iff the destination has NO live pair of that
  id — a copy within the document drops it, cut + paste keeps it, a paste into another
  document keeps it (a pair whose id is already live in the destination is dropped, as in
  Word — no re-minting). If only a cut is undone both pairs are live and the pairing rule picks the
  earlier one.
- **Upgrade** re-anchors schema-2 `targetId` fields to bookmarks (see "Schema version").

### Positions and spans

Positions are **id-and-offset**: `Position = { blockId, offset }`. The
offset counts UTF-16 code units across the block's inline content; each
embed item contributes one offset unit (a single cursor stop). Cursor
movement at the user-visible level enforces grapheme-cluster boundaries
via `Intl.Segmenter` (logic lives in `cursor/`, not here). Positions are
stable across edits to other blocks — only edits that touch the named
block can shift the named offset.

**The ¶ is a text unit (Word's CP / Google Docs's index).** `(P, k)` for `0 ≤ k ≤ len(P)` is
the gap before P's k-th unit, so `(P, len)` is the gap just BEFORE ¶P and `(N, 0)` — N the
next caret-holding block — the gap just AFTER it: ¶P is exactly the unit between them. No
caret position is lost or doubled, and the gap after a flow's final ¶ is unrepresentable
(`offset ≤ len`). A section-end item and an object / table / container item are one unit
each (the gap before an object is `(obj, 0)`; the gap after it is `(N, 0)` of the paragraph
that follows). The document-level index (`idx(P, k) = base(P) + k`, `base(N) = base(P) +
len(P) + 1`) is conceptual only — never stored, since maintaining it would be O(doc); the
exact transaction mapping already works in that coordinate (a split inserts one unit, a
merge deletes one; the exact hunks flip with the end-mark orientation: a split renames the
PREFIX to H and shifts B's suffix offsets by −k, a merge renames L into R and shifts R by
+len(L)). A span from `(P, a)` to `(N, 0)` covers ¶P: its fragment ends with a CLOSED
paragraph, and `extractText` emits one "\n" per crossed ¶; a span ending at `(N, b > 0)`
ends with an OPEN paragraph that adopts the destination's attrs on paste. No flat
`indexOf(Position)` / `positionAt(index)` API exists. Select-all + delete is the range
`(first, 0)–(last, len)`: every ¶ except the final one goes.

A `Span` is a directed pair `{ anchor, focus }`. Collapsed spans are
cursors. A span lives within a single **selection context** (the main
document tree, or one specific embed body); cross-context spans are not
supported.

Inline styles are **attributes on text runs and embeds**, not wrapper
nodes in state. The render module reconstructs `span` element boxes from
same-attribute neighbouring runs. State stores semantics; render
produces structure.

## Yjs encapsulation

The state module's public surface hides `Y.Doc` and its maps. Consumers
(cursor, render, cascade, layout, editor, components) import only:

- Layer 1 types (`State`, `Block`, `InlineContent`, etc.) — Yjs-free.
- Layer 1 snapshot accessors (`getBlock`, `getEmbedContent`,
  `getTemplateContent`, `resolveBlock`) returning
  frozen `Block` snapshots.
- Narrow Y.Doc-free accessors for specialized needs (e.g.
  `getEmbedContentIds(state)` / `getTemplateContentIds(state)` — used by
  render to iterate the embed/template subtree ROOTS without naming the
  underlying Y.Map).
- Layer 2 utilities and Layer 3 operations (defined below).

**Two import surfaces (intra-core vs cross-package).** Sibling core
modules import the state module through `state/index.ts` — the **barrel**
that is the intra-core API contract, grouped by layer (types/access,
utilities, ops + history, boot). It re-exports the Layer 1/2/3 surface
with named exports only and deliberately excludes the infrastructure
files (it cannot leak `STATE_INTERNAL` or any Yjs type). Separately, the
package-level `packages/core/src/index.ts` is the **cross-package**
surface consumed by `packages/print`, `packages/react`, and examples. The
two surfaces are distinct on purpose; the barrel is the canonical
intra-core contract.

`State`'s only public field is `rootId`. The underlying `Y.Doc` and the
per-State `SnapshotCache` live behind a non-exported `STATE_INTERNAL`
symbol (defined in `state-internal.ts`). Modules outside `state/`
cannot import the symbol — only state-module-internal code can spell
`state[STATE_INTERNAL].doc`. Attempting `state.doc` from any module
outside `state/` is a TypeScript compile error (asserted by
`state/encapsulation.test.ts`).

`STATE_INTERNAL` MUST NOT be re-exported from `packages/core/src/index.ts`
or any other barrel. Its containment is the whole encapsulation.

Yjs may surface in a few well-defined seams (e.g. a future collab
transport will subscribe to update events on the doc), but those seams
will be additive, narrow, and documented here.

## Submodules

Submodules are organized by the three-layer API surface (types and
access; pure utilities; state-mutating operations) plus the
infrastructure pieces.

**Layer 1 — types and access primitives**:

- **`state`** — the `State` container type, `createState`, the
  `OperationResult` shape, `applyOperation` (the transaction-runner
  every Layer 3 op composes), `freshState` (rebuilds the per-state
  snapshot cache after external Y.Doc mutations like undo). Snapshot
  accessors: `getBlock` (main tree), `getEmbedContent`,
  `getTemplateContent`, and `resolveBlock(state, id) → { block, kind }`

  Callers that only need the value use
  `resolveBlock(state, id)?.block ?? null`. Also exports the narrow
  `getEmbedContentIds(state)` / `getTemplateContentIds(state)` accessors
  that iterate the embed/template subtree ROOT BlockIds (blocks with
  `parentId === null`; body children are reached via the root's child
  chain, not enumerated) without exposing the underlying Y.Map (used by
  render).
- **`index`** — the `state/index.ts` barrel: the intra-core API contract,
  grouped by layer. Named re-exports only; infra is excluded.
- **`state-internal`** — the non-exported `STATE_INTERNAL` symbol that
  gates access to State's underlying Y.Doc + snapshot cache. Must not
  be re-exported from any barrel.
- **`build-state-from-blocks`** — state-module-internal builder that
  materializes Block fixtures directly into a fresh Y.Doc-backed State.
  Bypasses Layer 3 ops; intended for test-utils / boot helpers that
  need to construct an arbitrary state shape. The public test-utils
  `buildState` delegates here.
- **`build-document-from-tree`** — the SAFE public construction
  primitive. `buildDocumentFromTree(root, listDefs, allocator)` lowers a
  declarative NESTED `BlockNode` tree (a discriminated union of
  `ContainerBlockNode` — children, no inlineContent — and `LeafBlockNode`
  — inlineContent, no children; container-XOR-leaf is a compile-time
  guarantee) into a `State`: it mints a fresh `BlockId` per node and
  DERIVES every structural link (parentId / prevSiblingId / nextSiblingId
  / firstChildId / lastChildId) from tree position, then delegates to
  `build-state-from-blocks`. The root node's minted id becomes
  `State.rootId`; `listDefs` keys are the caller-minted listIds referenced
  by `list-item` leaves. Unlike `build-state-from-blocks` (whose manual
  link fields are a footgun, so it stays barrel-excluded), this is the
  declarative shape that owns link derivation in one tested place and is
  exported from the state + core barrels. It is the format-agnostic
  foundation any importer (e.g. the HTML serializer) targets. Builds the
  main tree only (embed/template declarative roots are a future
  extension).
- **`block`** — the `Block` snapshot type.
- **`block-id`** — branded `BlockId` type, `IdAllocator` interface,
  `productionAllocator` (UUID v4 via `crypto.randomUUID()`),

- **`block-init`** — the partial-block shape used by ops that create

- **`block-position`** — `Position`, `Span`, `Selection` types and pure

- **`inline-content`** — `InlineContent`, `InlineItem`, `TextItem`,
  `EmbedItem` types, plus pure helpers (`mergeAdjacentTextItems`,
  `splitInlineContentAtOffset`, `findItemAtOffset`) used by planners.
- **`y-inline`** — the inline STORAGE: one `Y.Text` per leaf (read model,
  offset write primitives, attr boundary, grapheme snapping, `LegacyDocumentError`).
  See "Inline storage".
- **`upgrade`** — `inspectDocument` / `upgradeDocument` / `CURRENT_SCHEMA_VERSION`
  and the shape checks the subscriptions use (`legacyBlocksAmong`).
- **`attrs`** — `ReadonlyAttrs` type, `attrsEqual` (deep-value compare),
  `mergeAttrs`.
- **`block-schema`** — declared shape of a Y.Map-stored block, with a
  compile-time coverage check (`satisfies + DeclaredKeys`) so the
  read-path and write-path never drift.
- **`block-kinds`** — defines the `BlockKind` taxonomy
  (`inline-bearing-leaf` / `atomic-leaf` / `container`) and a narrow
  `BlockKindResolver` interface (`getBlockKind(type) → BlockKind | null`).
  The component registry implements the resolver; state ops that need to
  judge shape (e.g., `setBlockType` for cross-kind refusal, `INSERT_NODE`'s
  shape validation) accept a resolver parameter. State no longer
  hardcodes type-string sets — taxonomy is owned by component
  definitions (`kind: "container"` for containers; leaf components
  declare `leafShape: "inline-bearing" | "atomic"`).

**Layer 2 — pure utilities**:

- **`block-traversal`** — `nextBlockInDocOrder`, `prevBlockInDocOrder`,
  `ancestorChain`, `firstLeafBlock`, `lastLeafBlock`. Step-bounded by
  the main-tree size to guard against corruption.
- **`block-compare`** — `compareBlocksInDocOrder` via LCA walk;
  `selectionContextOf`.
- **`document-order`** — recursive document-order block walkers:
  `iterateBlocksInDocumentOrder` (the MAIN tree only),
  `iterateLeafBlocksInDocumentOrder` (a leaf-only filter over it — the cycle-safe
  walk every main-tree pure query uses: `getOutline`, `getWordCount`,
  `findMatches`, `computeOutlineSignature`; it replaces an unbounded
  `firstLeafBlock` + `nextBlockInDocOrder` cursor sweep that could infinite-loop on
  a malformed two-parents topology), and
  `iterateAllBlocksInDocumentOrder` (the main tree, then each `embedContents`
  body subtree, then each `templateContents` body subtree — the all-three-trees
  walk change-tracking's range index + resolve scan use so a suggestion tagged in
  a footnote / header / footer body is found and resolved). Also `docHasLists`
  (early-exit main-tree scan). Active-path cycle guard + `blockCount`-bounded
  sibling loop, both summing all three trees.
- **`span-iteration`** — `iterateSpan` (yields per-leaf-block ranges
  in document order) and `iterateBlocksInSpan` (yields each block,
  including containers, overlapped by the span).
- **`extract-text`** — flattens a span to a plain string for clipboard,
  find/replace, accessibility. Walks block boundaries via `iterateSpan`
  (no hardcoded block-type list); embeds serialize via a hook so plugins
  control their textual representation.
- **`table-context`** — `resolveTableContext(state, blockId) → TableContext
  | null` walks the `ancestorChain` to locate the enclosing
  table/row/cell, returning row/column indices, the row-id and per-row
  cell-id grids, and three span flags: `spanned` (any cell carries a real
  rowSpan/colSpan, per `isSpan`), `ragged`, and `hasSpans = spanned || ragged`
  (a derived convenience — see below for why it is NOT the editor no-op
  boundary). `ragged` is SPAN-AWARE: it is true when the
  `buildTableGrid` occupancy has a HOLE (an uncovered slot) — i.e. the table is
  not a clean rectangle once spans tile it. A well-formed spanned table fills its
  grid completely (`ragged` false → the span-aware ops run); genuinely-missing cells OR a
  span that leaves a gap produce a hole (`ragged` true → the degenerate carve-out
  stays gated). (Computing `ragged` from raw per-row cell COUNTS would wrongly
  flag every colSpan/rowSpan table as ragged — a span legitimately makes a row
  hold fewer cells than the grid is wide.) `spanned` and `ragged` are exposed
  SEPARATELY because the editor dispatches them differently — a `ragged` table stays
  gated, a `spanned` (non-ragged) table routes to the span-aware op; a handler
  checks `ragged` FIRST so a spanned-AND-ragged table still no-ops. It resolves via
  `getBlock`, so it is the main-tree guard for the table editor ops.
  `getChildIds(state, parentId)` is the sibling-chain walk helper
  (cycle-bounded by `blockCount`). `hasSpans = ragged || spanned` is a derived
  convenience (kept for callers wanting "is this a plain uniform table?"); it is
  NOT the editor no-op boundary — that is `ragged` alone (a degenerate table),
  with `spanned` routing to the span-aware op. `DELETE_TABLE` ignores all span
  flags (always safe). The context also caches the pre-mutation `grid`
  (`TableGrid | null`, the same grid `ragged` is derived from) so a span-aware
  handler reuses it for caret targeting instead of re-scanning the tree.
  `buildTableGrid(state, tableId) → TableGrid | null` is the STATE-side grid
  builder: it walks the table's rows/cells and calls `table-grid-core`'s
  `assignTableGrid` with each cell's span read as `spanValue(attrs) ?? 1` (a
  span-free cell reads exactly as before spans existed), so the span-aware ops reason in grid coordinates
  from the pre-mutation `State` exactly as the layout Table FC does.
- **`table-cell-range`** — `resolveCellRange(state, selection) → CellRange |
  null` turns a linear editor `Selection` into a rectangular cell range in grid
  coordinates (`CellRange = {tableId, minRow, minCol, maxRow, maxCol}`, inclusive
  bounds), the input to the span-aware editing ops (merge/split). The editor
  `Selection` stays linear; this is the pure resolver. It resolves the anchor and
  focus cells via `resolveTableContext` (so it is main-tree-only and returns
  `null` unless BOTH endpoints sit in the SAME table), bounding-boxes their full
  grid rectangles over `buildTableGrid`'s occupancy, then expands to a fixpoint —
  for each slot `(r,c)` in the box it unions the owning cell's whole rectangle
  until a pass adds nothing. This guarantees a rectangle of WHOLE cells (a merge
  region never bisects a merged cell, matching Google Docs / Word); convergence
  is bounded by the grid area.
- **`table-cell-span`** — the shared span predicate. `spanValue(v)` returns
  the integer span when `v` is an integer `> 1`, else `undefined`;
  `isSpan(v) = spanValue(v) !== undefined`. Consumed by `table-context`,
  the resolver, and `tableCellComponent`.
- **`table-column-widths`** — pure column-width array maths for column
  edits: `spliceColumnWidth(widths, at)` (insert a proportional column) and
  `removeColumnWidth(widths, at)` (drop one); both renormalize to Σ = 1 for
  float-drift safety. `isColumnWidths(v)` is the shared predicate the column
  ops use to detect explicit sizing vs. auto-layout (absent → no attr change).
- **`table-grid-core`** — the layering-neutral occupancy-grid scan (CSS Tables
  §17.5), shared by the layout Table FC and the state-side span-aware
  editing ops. `assignTableGrid(rows: GridCell[][]) → TableGrid` where
  `GridCell = {cellId, rowSpan, colSpan}` (spans PRE-NORMALIZED by the caller to
  integers ≥ 1) and `TableGrid = {cells: AssignedCell[], columnCount,
  occupancy: (BlockId|null)[][]}`. Occupancy scan: first-free-column placement
  skipping down-spanned reservations, `rowSpan` clamped to remaining rows,
  first-writer-wins overlap guard (dev-assert), rectangular occupancy matrix.
  Layer agreement is byte-identical because each caller pre-normalizes spans its
  own way: the layout adapter (`layout/table-grid.ts`) via `cellSpan`/metadata;
  the state adapter via `spanValue(attrs) ?? 1` (NOT `clampSpan` — `clampSpan(2.9)
  = 2` would diverge from the layout path's 1×1).

**Layer 3 — state-mutating operations** (one file per op in the `ops/`
subdirectory, re-exported from the `state/index.ts` barrel — there is no
separate `operations.ts`). The barrel's prose groupings (inline / structural
/ attrs / section / template) are the category taxonomy; `ops/` itself is
flat. File names below are relative to `ops/`:

**The `plan*` / `*InTx` split (atomic composition).** Each op file also holds
that op's `plan*` / `*InTx` primitives, so several ops can compose into ONE
Y.Doc transaction (one undo entry / one collab event) instead of each opening
its own. The split is uniform: a pure-data `*Plan` produced by a `plan*`
function that does ALL validation + snapshot reads BEFORE the transaction
(returning `null` for a no-op); a `*InTx(doc, …)` primitive guarded by
`requireInTransaction(doc, opName)` that performs the writes; and a thin
public op = `applyOperation(state, (doc) => *InTx(doc, …))`. Ops exposing the split:
`deleteRange` (`planDeleteRange` / `deleteRangeInTx` / `DeleteRangePlan`),
`replaceRange` (`planReplaceRange` / `replaceRangeInTx` / `ReplaceRangePlan` —
the plan folds the collapsed-insert / delete-only / re-collapsed cases into two
optional sub-plans so `replaceRangeInTx` is a straight-line `deleteRangeInTx?` +
`insertTextInTx?` that NEVER opens a nested transaction),
`insertBlock`, `splitBlockAtPosition`, `insertText`, `reparentChildren`
(`computeReparentWrites` / `reparentChildrenInTx`), `applyAttrsToRange`
(`planApplyAttrsToRange` / `applyAttrsToRangeInTx` / `ApplyAttrsToRangePlan`),
`insertBlocksAfter` (`planInsertBlocksAfter` / `insertBlocksAfterInTx` /
`InsertBlocksAfterPlan`), and `applySectionBreak` (`buildSectionBreakPlan` /
`applySectionBreakInTx` / `SectionBreakPlan` — a single-shape plan carrying a
`kind: "implicit" | "explicit"` field; one branch-free applier handles both
cases).

Most `*InTx` primitives are **read-free structural appliers**: the `plan*`
function snapshots everything needed and the primitive only writes (e.g.
`reparentChildrenInTx` reads nothing). The inline primitives read the edited
block's live items (to snap offsets, split a format around markers, materialize a
split's tail), but every inline write is an offset op on the block's `Y.Text`.
`applyAttrsToRangeInTx`'s plan carries pre-transaction offsets. Consequence: a read-free
primitive composes correctly after any prior in-tx op, but
`applyAttrsToRangeInTx` is correct only when prior in-tx ops do NOT shift this
span's offsets. Composing it atomically AFTER an offset-changing op
(delete/insert) needs mid-transaction span re-resolution against live Y state;
that is not yet implemented and lands with the consuming feature.

- **`insert-text`** — `insertText(state, position, text, attrs, allocator) → OperationResult`.
- **`delete-range`** — `deleteRange(state, span, allocator) → OperationResult`.
  Refuses cross-parent spans (action handlers decompose).
  The same-block branch is one offset `Y.Text.delete`: every surviving character
  keeps its CRDT identity. The cross-block branch cuts the anchor's tail and appends
  the focus block's surviving suffix (`DeleteRangePlan.focusSuffix` — those moved
  characters are re-minted, the structural-op limit), then removes the focus +
  intervening leaves.
- **`replace-range`** — `replaceRange(state, span, text, attrs, allocator) → OperationResult`.
  Composes delete + insert atomically in one Y.Doc transaction: both are offset writes
  on the anchor block's `Y.Text`, the insert (`planInsertTextAt`) targeting the deletion
  seam (the normalized anchor offset).
- **`replace-block-with-text`** — `replaceBlockWithText(state, blockId, target, text, attrs, allocator) → OperationResult`.
  Composes `removeBlockInTx` (remove a whole block) + `insertTextInTx` (insert at a
  DIFFERENT block) in ONE `applyOperation` → one undo entry. Both plans are computed
  against the pre-mutation snapshot; removing `blockId` relinks sibling pointers but
  does not touch the insert target's inline content, so the insert plan stays
  valid after the removal (the same pre-plan-then-apply discipline as `replaceRange`).
  Used by the object-selection "type over a selected image" path (`object-edits.ts`).
- **`replace-matches`** — the Find & Replace batch primitive.
  `planReplaceMatches(state, matches, replacement) → ReplaceAllPlan`
  is the pure per-block planner: it groups `TextMatch[]` by block, lists each
  block's replacements in DESCENDING start order (so each offset write leaves the
  earlier matches' offsets valid), takes the replacement's formatting from the run
  containing `match.start`, and collects embed-content subtree ids of any removed
  slice into `embedContentIdsToDelete`. `ReplaceAllPlan = { blockWrites:
  {blockId, kind, replacements: {start, end, removedBookmarks, text, attrs}[]}[],
  embedContentIdsToDelete: Set<BlockId> }` (each match planned through `bookmarkDeletionSpan`).
  `replaceAllMatches` / `applyReplaceAllPlan(state, plan)`
  apply it in ONE `applyOperation` — each replacement is a `deleteUnits` + an offset insert at its start,
  then the collected embed bodies are cascade-deleted — so a whole replace-all is one
  undo entry.
- **`split-block`** — `splitBlockAtPosition` (a fresh ¶ ends the head; returns the head's id).
- **`merge-blocks`** — `mergeAdjacentBlocks` (delete ¶L; the survivor is R) and
  `markParagraphMarkDeletion`.
- **`insert-line-break`** — `insertLineBreak(state, position)`: inserts the `hard-break`
  inline embed (Word's `\v` / Google Docs's `\u000b`; `state/hard-break.ts`) at a position —
  an inline character that never splits the paragraph.
- **`apply-attrs`** — `applyAttrsToRange` (inline): one `Y.Text.format` per maximal
  changed, non-marker subrange (`formatInlineRange`). Exposes the
  `plan*` / `*InTx` split (`planApplyAttrsToRange` / `applyAttrsToRangeInTx`)
  with the read-live-items caveat noted above. VISIBLE embeds in range inherit
  the merged attrs (a field takes on surrounding run formatting); zero-width
  STRUCTURAL MARKER embeds (`isStructuralMarkerEmbedType` — the comment/
  suggestion markers in `state/embed-markers.ts`) are SKIPPED, so an inline
  format never pollutes a marker or dangles a tracked-change provenance id on
  one after the suggestion resolves.
- **`set-block-attrs`** / **`merge-block-attrs`** — block-level attribute
  replace vs. merge semantics. Also exports `setBlockAttrsInTx(doc, blockId,
  attrs, opName)`, the in-transaction REPLACE primitive (main-tree only) for
  composing an attr write into another op's single transaction WITHOUT
  reentering `applyOperation` — used by `insertTableColumn` (and the later
  `deleteTableColumn`) to rewrite `columnWidths` atomically with the cell edits.
- **`set-block-type`** — type change, refusing cross-kind transitions.
- **`insert-block`** / **`remove-block`** — structural ops on the block
  tree; `remove-block` cascades to embed-referenced content blocks.
- **`insert-blocks-after`** — `insertBlocksAfter(state, afterId, inits,
  allocator)`: atomic bulk-insert of a run of sibling blocks after a given
  block, in one transaction (the paste-migration / cloned-subtree primitive).
  Exposes the `plan*` / `*InTx` split (`planInsertBlocksAfter` /
  `insertBlocksAfterInTx`): `planInsertBlocksAfter` allocates ids + resolves
  the boundary relink pre-tx into an `InsertBlocksAfterPlan`, and
  `insertBlocksAfterInTx` is a read-free structural applier.
- **`reparent-children`** — `reparentChildren(state, blockIds, newParentId,
  beforeSiblingId?) → OperationResult`: MOVE a CONTIGUOUS run of sibling blocks
  under a new parent in one transaction (source marks + characters deleted, the
  same ids re-inserted at the target with re-minted content, registry entries
  kept — see "Structural storage"). Empty list → no-op (same `State` ref).
- **`section-break`** — `applySectionBreak(state, cursor, allocator) →
  SectionBreakResult` (extends `OperationResult` with `newCursorBlockId`): a SPLIT of the
  caret's root-flow paragraph whose new terminator is a section-end item (Word) — head H
  (new id, P's type + attrs) ends the new section S′, which copies the containing section's
  attrs; a caret inside a top-level object (a table cell) gets S′ ended by a fresh empty
  paragraph placed before that block. One transaction; `applySectionBreakAsSuggestion` keys
  the section-end ¶ as a tracked insertion.
- **`merge-section`** — `deleteSectionBreak(state, sectionId)`: deletes the section break
  that ENDS the section (the section-end ¶ of its last paragraph) in ONE step — the
  paragraphs merge by the paragraph rule and the content joins the FOLLOWING section and
  takes its attrs. Identity no-op for the final section and when invariant I keeps the ¶.
  Drives Backspace / Delete at a section boundary.
- **`set-list-type`** — `setListType(state, listId, "ordered" | "unordered")`:
  writes (or overwrites) the shared `ListDef` for `listId` via
  `writeListDefInTx` (Google Docs: changing a list's type changes ALL its
  items). Because this touches only the `listDefs` config map, it uses the
  dirty-union channel — it collects the run of list-items carrying `listId`
  from the pre-tx state and returns them so they re-render.
- **`set-list-restart`** — `setListRestart(state, blockId, number | undefined)`:
  sets or clears the focus item's `listCounterOverride` attr (Google Docs'
  "restart numbering at N" / "continue previous numbering"). This is a plain
  block-attr edit (`mergeBlockAttrs`), so it needs no dirty-union; `undefined`
  removes the attr.
- **`comment-ops`** — the comment thread CRUD, all NORMAL tracked
  `applyOperation` ops (the `comments` map is an UndoManager scope, so each is
  undoable). `addComment(state, span, input)` inserts the paired `comment-end`
  then `comment-start` marker embeds AND writes the thread record in ONE
  transaction (composing `insert-comment-markers`' `plan*` / `*InTx` so markers
  + record land as one undo unit). `resolveComment` / `reopenComment` flip the
  record's `resolved` flag; `deleteComment` strips BOTH markers from their
  owning block(s) AND removes the record; `addReply` pushes a reply `Y.Map`
  onto the record's `replies` `Y.Array`. `getComments(state) → ResolvedComment[]`
  is the read surface. Because resolve / reopen / addReply (and `deleteComment`
  on its orphaned-by-absence path, where both markers are already gone) write
  ONLY the `comments` side-table — which is excluded from dirty-capture — they
  surface `state.rootId` as the dirtyId (the `setListType` extra-dirty
  precedent) so the op advances state and lands a committable, undoable entry
  instead of short-circuiting to identity.
- **`insert-comment-markers`** — the marker-insert primitive `addComment`
  composes: `planCommentMarkers(state, start, end, commentId)` validates both
  endpoints and computes the bodyless `comment-start` / `comment-end`
  `EmbedItem` writes (each carrying `properties.commentId`, owning no embed
  body — like a cross-reference pointer); `applyCommentMarkerWritesInTx` applies
  them. The standalone `insertCommentMarkers(state, span, commentId)` op wraps
  the same plan in its own transaction. End-marker is placed first so the
  start-insert does not shift the end offset; a same-block span splices both
  into one items array, a cross-block span lands each marker in its own leaf.
- **Table ops** (`insert-table-row` / `-column`, their `-span-aware` variants,
  `delete-table-row` / `-column` and `-span-aware`, `delete-table`, `merge-cells`,
  `split-cell`) — each a `plan*` / `*InTx` split whose planner reads the PRE-mutation
  occupancy grid (`buildTableGrid` over the read model's `colSpan` / `rowSpan`) and
  whose applier writes the grid storage through `state/table-storage.ts`; only the
  public op is barrel-exported, and the `TableContext` comes from
  `resolveTableContext`. Spans are id RANGES, so the planners' crossing / covering span
  bumps need no write. Insert row / column: a new row id (after / before the caret's
  row) or column id (at `targetCol`) and a fresh cell (+ empty paragraph) for every
  slot left uncovered; an explicit `columnWidths` is re-spliced
  (`spliceColumnWidth`) and stored per column id in the SAME transaction. Delete row /
  column: anchors in it whose span continues are re-homed to the next row / column
  (content kept), spans ending at it retarget the previous one, its remaining cells'
  entries are deleted (delete wins), `columnWidths` loses the column. `delete-table`
  (`deleteTable`) removes the table (entry + its rows / cells); no replacement paragraph
  is ever needed because a paragraph always follows an object (invariant I). `merge-cells` sets the survivor's `colSpanTo` / `rowSpanTo` and
  moves nothing (covered cells' flows read concatenated into it; a EMPTY covered
  cell contributes nothing — no piled-up blank lines); `split-cell` clears the
  span keys (each covered cell's physical flow shows again; empty slots get fresh
  cells). Every table op keeps `headerRowCount` valid (`adjustHeaderRowCount`, below)
  and is main-tree only.
- **`set-table-header-rows`** — `setTableHeaderRows(state, tableId, count)`:
  writes the `table` block's `headerRowCount` attr — "the first `headerRowCount`
  rows are repeating header rows" (Google-Docs "pin header rows" model; the layout
  reads it to repeat those rows at the top of each page/column fragment a tall table
  spans). `count` is clamped to `[0, rowCount]` AND to `largestCleanHeaderCount`
  (the **clean-cut invariant**: no merged cell may originate in a header row and
  span past the `[0, count)` boundary — clamps down to the nearest clean boundary,
  possibly 0). NO-OP (same `State` ref) when unchanged. `plan*` / `*InTx` split.
  Main-tree only. The pure validators `largestCleanHeaderCount(grid, requested)` and
  `adjustHeaderRowCount(count, op, rowIndex)` live in `table-header-rows.ts`; the
  latter keeps `headerRowCount` naming the leading contiguous block across row edits
  (delete a header row → −1, incl. last-header → 0; insert at `r < count` → +1;
  insert at the boundary `r === count` → unchanged = body row). **All four
  row-structural ops** (`insert-table-row`, `insert-table-row-span-aware`,
  `delete-table-row`, `delete-table-row-span-aware`) apply this adjustment
  (`headerRowAttrsAfterRowEdit` + `setBlockAttrsInTx`) in the SAME transaction as the
  row mutation, so a row edit and its `headerRowCount` fix-up are one undo entry.

## How submodules connect

Layer 3 ops compose Layer 2 utilities (for traversal and span iteration)
and call `applyOperation` to wrap their write-side work in a Y.Doc
transaction. Layer 3 is the **audited surface** — all state-mutating
logic lives here, nothing outside can corrupt state.

Editor action handlers (`packages/core/src/editor/actions/*`) are the
sole external callers of Layer 3 ops. Each handler typically composes
one or more Layer 3 ops, then calls `history.commit(opResult, selections)`
to record the unit's selection meta; the reducer has already decided whether
that unit opens a fresh undo group or coalesces into the open one (via
`beginEntry` / `breakCoalescing`, see the History reference). Handlers MUST
short-circuit before calling `commit` on a no-op operation
(`opResult.state === input.state`, equivalently `opResult.dirtyIds.size === 0`).
The render pipeline consumes `dirtyIds` to decide which subtrees to
rebuild (see `1.2-render.md`).

Layer 2 is read-only and consumed both by Layer 3 internally and by
external read paths (cursor, render, editor geometry queries).

## Reference

### `State` and `OperationResult`

```ts
interface State {
  readonly rootId: BlockId;
  // The underlying Y.Doc and SnapshotCache live behind a non-exported
  // STATE_INTERNAL symbol — reachable only from state-module-internal
  // code, not from any consumer. `state.doc` / `state.snapshotCache`
  // are TypeScript compile errors outside `state/`.
  readonly [STATE_INTERNAL]: {
    readonly doc: Y.Doc;
    readonly snapshotCache: SnapshotCache;
  };
}

interface OperationResult {
  readonly state: State;
  readonly dirtyIds: ReadonlySet<BlockId>;
}
```

`createState({ rootId, doc?, resolver })` constructs an opaque container with a
fresh snapshot cache. `applyOperation(state, fn)` runs `fn` inside one
Y.Doc transaction, passing it the doc, and returns `{ state, dirtyIds }`. Op
appliers use the passed `doc` to perform their writes rather than re-reading it
from `state`.

**Dirty-union channel.** `fn` has type `(doc: Y.Doc) => void | ReadonlySet<BlockId>`.
Most ops mutate the block tree and return `void` — their dirty ids are
captured automatically from the Y.Doc transaction's change set. But an op
that writes ONLY a non-block-tree map (e.g. a `listDefs`-only write that
changes a list's marker style without touching any `list-item` block)
captures NO block dirty ids on its own, yet still needs the affected
list-items to re-render. Such an op returns the affected `BlockId`s as a
`ReadonlySet`; `applyOperation` UNIONS that set into the captured dirty
set BEFORE the `size === 0` no-op short-circuit and BEFORE cache
invalidation, so the contributed ids both keep the op from being seen as a
no-op and invalidate the right snapshot entries. `setListType` (rewriting
a shared `ListDef`) is the first consumer; it collects the run of
list-items carrying the target `listId` from the pre-transaction state and
returns them.

**No-op identity contract.** When the transaction produces no Y.Doc
mutations (`dirtyIds.size === 0`), `applyOperation` returns the literal
input `state` reference unchanged. Callers use
`result.state === input.state` as an O(1) "did anything change?" guard.

**Carry-forward.** On the non-no-op branch, the new `State`'s
snapshot cache inherits every non-dirty entry from the input cache.
Snapshots of unchanged blocks remain reference-equal across edits;
memoized renderers can `prev === next` to skip unchanged subtrees.

### `Block`

```ts
interface Block {
  readonly id: BlockId;
  readonly type: string;            // open string, registered as a component type
  readonly attrs: ReadonlyAttrs;    // open-schema (closed schema lives in ComputedStyle)
  readonly parentId: BlockId | null;
  readonly prevSiblingId: BlockId | null;
  readonly nextSiblingId: BlockId | null;
  readonly firstChildId: BlockId | null;
  readonly lastChildId: BlockId | null;
  readonly inlineContent: InlineContent | null;  // non-null iff leaf
  readonly breakSuggestion?: BreakSuggestion;     // keys on the block's own ¶ (see "Tracked paragraph marks")
  readonly markAttrs?: ReadonlyAttrs;             // the ¶'s own inclusive character props (Word's ¶ rPr)
}
```

`Block` is a frozen snapshot view returned by `getBlock(state, id)` /
`getEmbedContent(state, id)`. Mutations go through Layer 3 ops; reading
through the snapshot accessor is O(1).

**List-item attrs (the flat list model).** A `list-item` leaf block carries
its list membership entirely in `attrs` (the open-schema `ReadonlyAttrs`):
- `listId: string` — which list this item belongs to (its grouping key).
- `listLevel?: number` — nesting depth 0–8 (absent ⇒ level 0).
- `listCounterOverride?: number` — an explicit "restart numbering at N" for
  this item (consumed by the numbering service).

There is no `list` container and no `listType` attr — the ordered/unordered
distinction and per-level marker styling live in the `listDefs` config for
`listId` (see "The `listDefs` map" above). Reading list attrs uses the
standard untyped-attr access (`attrs["listId"]` with a `typeof` guard), the
same pattern the cascade uses for custom attrs.

### `Position`, `Span`, `Selection`

```ts
interface Position {
  readonly blockId: BlockId;
  readonly offset: number;          // UTF-16 code units across the block's inlineContent.items
}

interface Span {
  readonly anchor: Position;
  readonly focus: Position;
}

type Selection = Span;              // alias used by cursor / editor modules
```

Each text item contributes `text.length` (UTF-16 code units) to the
offset; each embed item contributes 1 (a single cursor stop, like one
character). `normalizeSpan(state, span)` returns the span in document
order via `compareBlocksInDocOrder` (LCA walk) plus an offset compare
when anchor and focus share a block.

### `InlineContent` and `InlineItem`

```ts
interface InlineContent {
  readonly items: ReadonlyArray<InlineItem>;
}

type InlineItem = TextItem | EmbedItem;

interface TextItem {
  readonly kind: "text";
  readonly text: string;
  readonly attrs: ReadonlyAttrs;
}

interface EmbedItem {
  readonly kind: "embed";
  readonly embedType: string;
  readonly attrs: ReadonlyAttrs;
  readonly properties: Readonly<Record<string, unknown>>;
}
```

`items` is the read model of the block's `Y.Text` (`inlineItemsFromYText`): no empty
text items, adjacent text items with deep-equal attrs coalesced, structural marker
embeds carrying `{}` attrs. Registry equality is applied when writing (see "Inline
storage").

Primitive embeds (images, mentions, equations, hard-breaks) carry their
data in `properties` inline. Substantial-content embeds (footnote
anchors) carry `properties.contentBlockId: BlockId` referencing a block
in the embed-contents subtree, whose own block-tree holds the body.
Zero-width MARKER embeds (`comment-start` / `comment-end`) carry only
`properties.commentId` and own no body — they delimit a comment range
purely by their position in content (see "The `comments` map").

Each `EmbedItem.contentBlockId` references a **unique** embedContent root:
every body has exactly one owning anchor. Sharing one body across two
anchors is unsupported by design — Word and Google Docs both follow the
"each anchor owns its own body" model, and the unconditional
cascade-delete on anchor removal relies on it. Copy-paste preserves the
1:1 mapping by remapping every `contentBlockId` to a freshly-cloned body
via `clonePastedSubtree`. In dev builds the two halves of this mapping are
enforced after every op: `assertNoOrphanedEmbedContent` catches a
reference with zero owners, and `assertNoSharedEmbedContent` catches a
body with two-plus owners.

### `BlockId` and `IdAllocator`

```ts
type BlockId = string & { readonly __brand: "BlockId" };

interface IdAllocator {
  allocate(): BlockId;
}
```

`productionAllocator` uses `crypto.randomUUID()`. `createTestAllocator(prefix?)`
returns a deterministic counter for reproducible tests. Every Layer 3
op that creates blocks accepts an `IdAllocator` argument.

**Lifecycle:**

1. **Creation** — always allocate fresh.
2. **Deletion** — remove from the main map; cascade-delete any blocks
   referenced by `EmbedItem.properties.contentBlockId` from the deleted
   subtree (`embed-content-cascade`).
3. **Copy/paste** — `clonePastedSubtree` walks the source subtree,
   allocates fresh ids, rewrites references.
4. **Undo/redo** — no allocation. Yjs restores prior ids.

### History

```ts
interface SelectionEntry {
  readonly before: Selection | null;
  readonly after: Selection | null;
}

interface UndoRedoResult {
  readonly state: State;
  readonly selection: Selection | null;
  // BlockIds whose subtrees were mutated by the undo/redo's reversal,
  // captured via the same `afterTransaction` channel `runTransaction`
  // uses (Y.UndoManager.undo / .redo each wrap their Y.Doc surgery in
  // an internal transaction). Lets the editor's incremental render
  // pipeline rebuild only the affected RenderNodes.
  readonly dirtyIds: ReadonlySet<BlockId>;
}

type BeginKey = "insert" | "delete" | "command";

class History {
  constructor(state: State);
  beginEntry(key: BeginKey, now: number, selection?: Selection): void;
  breakCoalescing(): void;
  commit(opResult: OperationResult, selections: SelectionEntry): void;
  undo(): UndoRedoResult | null;
  redo(): UndoRedoResult | null;
  canUndo(): boolean;
  canRedo(): boolean;
}

function createHistory(state: State): History;
```

`History` wraps a `Y.UndoManager` configured with
`captureTimeout: Number.MAX_SAFE_INTEGER` — Yjs never auto-merges or
auto-closes groups by its own wall-clock; `History` owns **every** undo-group
boundary explicitly. A single action handler may compose multiple
`applyOperation` calls; they merge into one undo entry at the action
boundary. The boundary between consecutive actions is decided by
`beginEntry` / `breakCoalescing` (see **Undo coalescing** below), not by
`commit`.

**Selection lives on `StackItem.meta`.** Each undo unit's `SelectionEntry`
(pre- and post-unit selection) is stored on its `Y.UndoManager`
`StackItem.meta` rather than in a parallel array. `commit` writes the
entry onto the unit's StackItem (the item Yjs has already pushed/merged in
`afterTransaction`); `undo` / `redo` read it from the item Yjs pops. Because
Yjs mints a fresh (empty-`meta`) item on the opposite stack for each
undo/redo, `undo` / `redo` re-weld the entry onto that new top so it survives
the round-trip. `undo` returns `before`, `redo` returns `after`. Welding the
selection to the live stack item means it cannot index-desync from the Yjs
stacks — there is no second structure to keep aligned. A dev-mode check
confirms a popped item carries an entry.

**Stored selections are CRDT-anchored.** Each endpoint is stored as
`{ blockId, rel }`: in a leaf, `rel` is a Yjs `RelativePosition` on the block's
`Y.Text` (type-anchored for an empty text); in a container `rel` is null and the
endpoint is `(blockId, 0)`. A caret anchors to the character on its LEFT (Yjs
`assoc −1`, as `rebaseSelection` treats a caret), or to its right one at offset 0 — so
a peer's insert right after the caret (including at the end of the text) never drags
the restored caret along. `before` is encoded against the PRE-action doc —
`beginEntry`'s `selection` argument (the editor passes `editor.selection`; a `commit`
whose `before` differs falls back to encoding against the post-action doc), and a
batch encodes its `before` at `beginBatch`; `after` is encoded at `commit`. On
undo / redo (after the change is applied) the endpoint resolves to its character's
CURRENT position: the block is DERIVED from the resolved `Y.Text`'s owning block
(never the stored id, except for a null-`rel` endpoint) and the offset snapped to a
grapheme boundary. An endpoint is UNRESOLVABLE when its anchor character (left, or right at offset 0) is deleted
and was not restored by this undo (followed through Yjs's redone copies), its text or
block is gone, or the position is unknown to the doc; `undo()` / `redo()` then return
`selection: null` and the editor uses the selection the undo's own change produces —
the current selection rebased through it (`rebaseSelection`). So an untracked change
(a peer's edit, a host proposal) applied after the entry was recorded never leaves the
restored selection stale.

**`advanceState` reconciles `currentState` after an untracked change.**
`currentState` (the snapshot the next undo/redo rebuilds from via
`freshState(currentState, dirtyIds)`) is normally advanced only by `commit` /
`undo` / `redo`. A change made under a non-`null` `Y.UndoManager` origin (the generic
`applyOperation(…, { origin })` opt-out) fires no StackItem, so it skips `commit` —
and must call `advanceState(newState)`
(which sets `currentState` only, touching no stack/coalescing state). Without it,
a later undo would serve any block the untracked change touched but the undo
did not re-dirty from a stale pre-change snapshot.

**Undo coalescing.** A run of typing collapses into a single undo unit,
matching Google Docs. Two edit kinds are **coalescible**: `insert`
(`INSERT_TEXT`) and `delete` (`DELETE_BACKWARD` / `DELETE_FORWARD` /
`DELETE_WORD` / `DELETE_LINE`). Consecutive **same-kind** coalescible edits
whose gap is `< UNDO_COALESCE_PAUSE_MS` merge into one unit; the merged unit
keeps the run's **original** `before` selection and the **latest** `after`
selection. Coalescing is purely time-based (no word-boundary logic) — a
continuous burst collapses regardless of spaces. A group is **broken** (the
next edit starts a fresh unit) by any of: a **pause** (gap `≥` the window), a
**kind switch** (`insert ↔ delete`), any **discrete command** (split, paste,
formatting, block-type, list, section, header/footer/footnote — each is its
own unit and never coalesces, not even with an identical neighbour), or a
**selection jump** (caret move / selection change / click). `UNDO` / `REDO`
also break the open group; a window resize (`SET_CONTAINER_WIDTH`) is inert —
it neither edits nor breaks coalescing.

The boundary is decided **before** an edit's Y.Doc transaction (under
`captureTimeout: MAX` a transaction merges into the open `StackItem` unless
`stopCapturing` was already called, and a merge cannot be undone). So the
decision is a pre-operation hook, not part of `commit`:

- `beginEntry(key, now)` — called before each committing action. Coalesces
  with the open group iff the key is coalescible, matches the open group's
  key, and the gap is within `UNDO_COALESCE_PAUSE_MS`; otherwise it
  `stopCapturing`s to start a fresh unit. Commands set the open key to null
  (so the next edit also breaks). `BeginKey` is the `insert`/`delete`/`command`
  subset; selection/inert never reach it.
- `breakCoalescing()` — called on selection jumps and on undo/redo. Closes the
  open group so the next edit is fresh. Idempotent and cheap.
- `commit` — no longer closes the group; it only records selection meta. On a
  coalesced merge it preserves the group's original `before` and advances only
  `after`.

The editor reducer is the single chokepoint: it classifies each action by the
`coalesce` field of its spec in the reducer's `ACTIONS` table
(`editor/reduce-editor.ts`, a mapped type over the action union so a new action
forces a classification at compile time) into
`ActionClass = insert | delete | command | selection-break | inert`,
then routes `insert`/`delete`/`command` → `beginEntry`, `selection-break` →
`breakCoalescing`, and ignores `inert`. The clock is injected via
`EditorConfig.now` (defaults to `Date.now`) so the pause window is
deterministically testable. `UNDO_COALESCE_PAUSE_MS` is a `history`-module
constant. See `1.5-editor.md` for the reducer wiring. (Accepted edge: the
boundary advances before the per-action no-op short-circuit, so a no-op
committing action can still close an open typing group — the policy lives in
one place by design.)

**Tracked scopes.** The `Y.UndoManager` is constructed over FOUR tracked
scopes: the `registry` (whose entries hold every flow), the `listDefs` side-table,
the `comments` side-table, and the `suggestions` side-table. Its `deleteFilter`
never deletes a piece or sub-flow item (undoing a paste deletes the pasted
characters and marks; a peer's text typed inside survives). Undo selections are
`RelativePosition`s on pieces, resolved back to the owning block + offset. Tracking `comments`
makes a comment thread record revert atomically with its in-content
`comment-start` / `comment-end` markers (undoable-as-content — see "The
`comments` map"); tracking `suggestions` makes a suggestion's tagged items +
record revert atomically as one unit (break keys are registry keys, undo-scoped with
the registry) (see "The `suggestions`
map"). Per-transaction tracking means a pure text edit, which never touches
either side-table, undoes without disturbing any comment or suggestion.

**Meta-map non-undoability.** Writes to the doc's meta `Y.Map` (which
holds `rootId`) are intentionally not undoable — `rootId` is
session-immutable. Future meta-map writers MUST explicitly consider
undoability.

**Error recovery.** `undo` / `redo` order their work as
`undoManager.{undo,redo}` → `freshState` → advance `currentState` (and
re-weld the entry onto the opposite stack's new top), all wrapped in
try/catch. `currentState` is advanced last, only after the Yjs reversal
and `freshState` succeed, so a throw from the first two leaves the wrapper
retriable. The caller sees a wrapped error identifying the failure as
history-internal.

**Undo-depth cap.** `commit` trims the oldest entries past `maxDepth`
(default 1000) via `undoManager.undoStack.splice` — the trimmed items
carry their `.meta` away with them, so no separate selection-stack trim is
needed.

### Comments

```ts
type CommentId = string & { readonly __brand: "CommentId" };

interface CommentReply {
  readonly id: string;
  readonly author: string;
  readonly body: string;
  readonly createdAt: number;
}

interface CommentRecord {
  readonly id: CommentId;
  readonly author: string;
  readonly body: string;
  readonly createdAt: number;       // host-injected (deterministic/testable)
  readonly replies: readonly CommentReply[];
  readonly resolved: boolean;
  // NO anchor field — the comment-start/comment-end markers ARE the anchor.
}

interface CommentRange {
  readonly start: Position;         // the comment-start marker's position
  readonly end: Position;           // the comment-end marker's position
  readonly orphaned: boolean;       // DERIVED from marker presence + ordering
}

interface ResolvedComment extends CommentRecord {
  readonly range: CommentRange;     // scanned each read; orphaned ⇒ no highlight
}

// State scan + read surface (state/comments.ts):
function buildCommentRangeIndex(state: State): Map<CommentId, CommentRange>;
function resolveCommentRange(state: State, id: CommentId): CommentRange | null;
function getComments(state: State): readonly ResolvedComment[];

// Tracked content ops (state/ops/comment-ops.ts):
function addComment(state: State, span: Span, input: AddCommentInput): OperationResult;
function resolveComment(state: State, id: CommentId): OperationResult;
function reopenComment(state: State, id: CommentId): OperationResult;
function deleteComment(state: State, id: CommentId): OperationResult;
function addReply(state: State, id: CommentId, input: AddReplyInput): OperationResult;
```

`createdAt`, `id`, and reply `id`s are host-injected via the op inputs
(`AddCommentInput` / `AddReplyInput`) — never generated in the engine —
mirroring `EditorConfig.now` + the `IdAllocator`. `getComments` freezes
each record (including its `replies` array) and attaches the range scanned
by `buildCommentRangeIndex`; a record with both markers gone gets a
degenerate orphaned range pinned to the document origin.

### Dirty-set contract (rendering bridge)

Every Layer 3 operation returns an `OperationResult` carrying
`dirtyIds: ReadonlySet<BlockId>` produced at write-time by the
underlying Y.Doc transaction's change set — never by post-hoc tree
comparison.

**Raw vs closure-expanded.** The `dirtyIds` returned by `applyOperation`
(and `History.undo` / `History.redo`) is the **raw mutated set** —
exactly the blocks whose own Y.Doc data changed under the transaction.
The render module's `dirtyIds` input (in `RenderOptions`) is the
**closure-expanded set**: `mutated ∪ ancestors(mutated) ∪
descendants(mutated)`. State emits the raw set; render owns the
closure expansion. The same name across module boundaries refers to
DIFFERENT sets — state's raw set is a strict subset of render's
closure-expanded set. See `1.2-render.md` for the expansion rule.

The renderer contract: `dirtyIds` contains both updated and deleted ids.
Consumers distinguish them with `getBlock(state, id) === null` (deleted)
vs. non-null (updated, re-render). Deletions in `embedContents` use the
same contract via `getEmbedContent`.

This is the engine's incremental-rebuild driver; see `1.2-render.md` for
how the render module consumes `dirtyIds`.

### Inline-attribute interpretation and run merging

State stores attributes openly (any key, any value; never `null` / `undefined` —
see "Inline storage"). The read model merges adjacent deep-equal text runs; a
per-key `equals` from the **attribute interpreter registry** (defined in
`1.3-cascade.md`) is applied at WRITE time — an insert next to a registry-equal run
writes that run's stored value, and a format skips items that already hold an
equal value.

The cascade module translates `attrs` into declarable `Style` via the
same registry, producing `ComputedStyle` through the existing
resolution pipeline (em flattening, inheritance, defaults). State
holds the open schema; cascade closes it.

### Initial state and creation

- `createEmptyDocument({ allocator? })` returns a `State` whose root is
  a `document` container block holding one empty `paragraph` child. The
  document block is `state.rootId`; the paragraph sits beneath it.

### Performance contracts

- `getBlock` / `getEmbedContent` / `getTemplateContent` — O(1) cache lookup.
- `getEmbedContentIds` / `getTemplateContentIds` — O(roots) to yield from
  the cached root-id set; no per-call scan of the map. The set is
  recomputed (O(N_map_keys)) only after a root is added/removed, which is
  rare relative to keystrokes — so these accessors do not tie per-keystroke
  render cost to embed/template body size.
- All Layer 3 ops — O(N_block) on the touched block(s) plus O(1) per
  affected sibling pointer; structural sharing on the snapshot cache
  preserves reference equality of unchanged block snapshots.
- `compareBlocksInDocOrder` — O(depth + LCA-fanout); bounded by ~100
  sibling-pointer hops at the target document scale.
- `applyOperation` no-op path — O(1) identity return.

The target document scale is smooth editing at ≤ 10,000 blocks per
document; graceful degradation to ≤ 100,000. See the spec doc for the
rationale (recalibrated from the prior "1M blocks" framing).
