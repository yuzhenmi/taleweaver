> through the `editor/` module. P11.x migrates the editor in stages;
> P11.4 cuts over the renderer + cursor pipeline. P16 rewrites this doc.

The editor module is the engine's outermost orchestrator. It owns the
reducer that dispatches `EditorAction`s through the rendering pipeline
and the read-only geometry-query API that hosts call to translate
between document positions and pixels. The cursor module supplies the
selection primitives that action handlers compose.

## Two coupled modules

`editor/` and `cursor/` are separate directories but coupled
responsibilities: `cursor/` defines the `Selection` type and pure
operations on it (`moveByCharacter`, `moveByWord`, `expandSelection`,
`selectWord`); `editor/` consumes those operations from action handlers
and queries layout output to translate selections to pixels.

## What the reducer owns

`reduceEditor(state, action, config) → newState` is the single
state-transition function the host calls per user action. Inputs:

- The current `EditorState` — semantic state (state tree, selection,
  history) plus cached pipeline output (render tree, layout tree).
- An `EditorAction` — a discriminated union of every supported action
  (`INSERT_TEXT`, `DELETE_BACKWARD`, `MOVE_CHAR`, `INSERT_NODE`,
  `APPLY_INLINE_STYLE`, `SET_CONTAINER_WIDTH`, etc.).
- An `EditorConfig` — engine-wide configuration (component registry,
  text shaper, container width, optional pagination settings).

Output: a fresh `EditorState`. Always immutable; references shared with
the input `EditorState` for unchanged subtrees.

The reducer:

1. Dispatches the action to the appropriate action handler (one per
   action type, organized in `editor/actions/`).
2. The handler produces a new `state`, `selection`, and `history`.
3. The reducer rebuilds the cached pipeline output (`renderTree`,
   `layoutTree`) by calling `renderTreeIncremental`,
   `cascadePassIncremental`, and `layoutTreeIncremental` in sequence.
4. Each incremental call passes the prior pass's output so unchanged
   subtrees flow through by reference.

## Submodules

### `editor/`

- **`editor-action`** — the `EditorAction` discriminated union.

- **`editor-state`** — the `EditorState` interface, the initial-state
  constructor, the reducer entry point, and the history-push helper.

- **`actions/`** — one file per action handler. Examples:
  `insert-text`, `insert-node`, `delete-backward`, `delete-forward`,
  `delete-line`, `delete-word`, `move-char`, `move-word`, `move-line`,
  `apply-inline-style`, `set-block-type`, `expand-selection`. Each
  takes `(state, action, config)` and returns the next semantic state
  + selection + history. The shared helper `rebuildTrees` in
  `actions/helpers.ts` runs the pipeline.

- **`cursor-position`** — `resolvePixelPosition(layout, position)`.
  Translates a document `Position` to its screen `PixelPosition` (x, y,
  height) by descending the layout tree.

- **`hit-test`** — `resolvePositionFromPixel(layout, x, y)`. Reverse:
  given screen pixels, find the `Position` in the document. Used for
  click-to-place-cursor.

- **`selection-geometry`** — `computeSelectionRects(layout, span)`.
  Produces the rectangles the painter draws as selection highlight
  (one rect per visual line within the span).

- **`line-navigation`** — `moveToLine(state, position, direction,
  targetX)` and `moveToLineBoundary(state, position, edge)`. Up/Down
  arrow and Home/End logic. Uses the layout tree to find the line above
  or below the current position.

- **`layout-utils`** — `collectAllTextBoxes(layout)` and helpers that
  flatten a layout tree to the leaf text-runs in document order. Used
  by selection-geometry, cursor-position, and find/replace.

### `cursor/`

- **`selection`** — the `Selection` type (an alias for `Span`) plus
  `createSelection`, `createCursor`, `isCollapsed`, `selectionStart`,
  `selectionEnd`.

- **`cursor-ops`** — `moveByCharacter`, `moveByWord`, `selectWord`,
  `expandSelection`, `expandSelectionByCharacter`. Pure operations on
  state + selection. Compose to build action handlers.

## How modules connect

```
              EditorAction
                   │
                   ▼
       ┌───────────────────────┐
       │ reduceEditor (entry)  │
       └───────────┬───────────┘
                   │
                   ▼
       ┌───────────────────────┐
       │ actions/<handler>     │
       │                       │
       │  uses: cursor/ ops    │  produces new (state, selection, history)
       │        state/         │
       │        transformations│
       └───────────┬───────────┘
                   │
                   ▼
       ┌───────────────────────┐
       │ rebuildTrees helper   │
       │                       │
       │  render → cascade →   │  produces new (renderTree, layoutTree)
       │  layout (incremental) │
       └───────────┬───────────┘
                   │
                   ▼
            new EditorState
```

The geometry queries (`cursor-position`, `hit-test`,
`selection-geometry`, `line-navigation`) are read-only — hosts call them
against `EditorState.layoutTree` whenever they need to translate between
document and screen coordinates. They never mutate.

## Why cursor sits in its own module

Cursor operations are pure and reusable across action handlers:
`MOVE_CHAR_LEFT` and `EXPAND_CHAR_LEFT` both want "move one character
backward in the document," differing only in whether selection
collapses or extends. Factoring those primitives into `cursor/` lets
action handlers stay small and uniform.

## Reference

### `EditorState` and `EditorConfig`

```ts
interface EditorState {
  state:        StateNode;
  selection:    Selection;
  history:      EditorHistory;

  renderTree:   RenderNode;        // post-cascade
  layoutTree:   LayoutBox;         // post-layout

  containerWidth: number;
  nextId:         number;          // id allocator for INSERT_NODE
  targetX:        number | null;   // sticky x for vertical motion (MOVE_LINE / EXPAND_LINE)
}

interface EditorConfig {
  measurer:       TextShaper | TextMeasurer;
  registry:       ComponentRegistry;
  containerWidth: number;
  pageConfig?:    PageConfig;      // when set, layout produces PageBoxes
}
```

`targetX` semantics: when MOVE_LINE or EXPAND_LINE action runs, it remembers the column-pixel of the cursor at the start of the vertical motion sequence. Subsequent vertical moves prefer landing at that column (subject to line content) so a series of arrow-down + arrow-up returns the cursor to its original column. Any non-vertical action clears `targetX`.

### `EditorHistory` (selection-aware)

```ts
interface EditorHistoryEntry {
  change: Change;                  // semantic state diff (state-tree level)
  selectionBefore: Selection;
  selectionAfter:  Selection;
}

interface EditorHistory {
  undoStack: readonly EditorHistoryEntry[];
  redoStack: readonly EditorHistoryEntry[];
  lastEditTimestamp: number;
  lastEditTag: string;
}

function pushEditorChange(history: EditorHistory, entry: EditorHistoryEntry, mergeTag?: string): EditorHistory;
```

**History merging rule.** When `mergeTag !== "" && mergeTag === history.lastEditTag && (entry.timestamp - history.lastEditTimestamp <= 500ms)`, the new entry merges with the top of the undo stack: result `{ change: { oldState: prev.oldState, newState: entry.newState, timestamp: now }, selectionBefore: prev.selectionBefore, selectionAfter: entry.selectionAfter }`. Otherwise the entry is pushed as-is. The redo stack is cleared on every push. Tags used by handlers: `"insert"` for INSERT_TEXT (consecutive single-char insertions group), `"delete"` for DELETE_BACKWARD/FORWARD (groups), other actions pass `""` to break the merge chain.

`MAX_HISTORY_DEPTH = 500`; older entries are dropped when the cap is exceeded.

### Per-action behavior table

| Action | State | Selection | History tag |
|---|---|---|---|
| `INSERT_TEXT` | replace selection range with text; insert text at cursor | cursor → end of inserted text | `"insert"` |
| `INSERT_NODE` | insert node at `position` (or current cursor) | cursor → after inserted node | `""` |
| `PASTE` | replace selection range with pasted text (multi-line splits paragraphs) | cursor → end of pasted | `""` |
| `DELETE_BACKWARD` | if selection is non-collapsed: delete range; else: delete one cluster before cursor | cursor → at deletion point | `"delete"` |
| `DELETE_FORWARD` | symmetric, at-or-after cursor | cursor → at deletion point | `"delete"` |
| `DELETE_WORD` | delete one word in `direction` | cursor → at deletion point | `""` |
| `DELETE_LINE` | delete the line containing cursor | cursor → at deletion point | `""` |
| `SPLIT_NODE` | split the containing block at cursor (Enter behavior) | cursor → start of new block | `""` |
| `MOVE_CURSOR` | none | move one character (cluster) in `direction`; collapse selection | (no history) |
| `MOVE_WORD` | none | move one word in `direction`; collapse | (no history) |
| `MOVE_LINE` | none | move to corresponding column on next/prev visual line; preserve `targetX` | (no history) |
| `MOVE_LINE_BOUNDARY` | none | move to start/end of current visual line | (no history) |
| `MOVE_DOCUMENT_BOUNDARY` | none | move to first/last position in document | (no history) |
| `EXPAND_*` | none | extend `selection.focus` per the analogous MOVE_*; keep `anchor` | (no history) |
| `SELECT_ALL` | none | anchor → start of document, focus → end | (no history) |
| `SET_SELECTION` | none | replace selection wholesale | (no history) |
| `TOGGLE_STYLE` | apply or remove inline style across selection | unchanged or remapped | `""` |
| `SET_BLOCK_TYPE` | change containing block's `type` (e.g., paragraph → heading) | remapped | `""` |
| `TOGGLE_LIST` | wrap or unwrap containing block in a list | remapped | `""` |
| `SET_CONTAINER_WIDTH` | none | unchanged | (no history) |
| `UNDO` / `REDO` | restore prior state | restore prior selection | (history mutation only) |

### Reducer flow

```
function reduceEditor(editor, action, config) -> EditorState:
  isVertical = (action.type == "MOVE_LINE" || action.type == "EXPAND_LINE")

  // Dispatch to handler
  result = handlers[action.type](editor, action, config)

  // Clear targetX on non-vertical actions
  if not isVertical:
    result = { ...result, targetX: null }

  return result
```

Handlers live in `editor/actions/` (one file each). Each handler:

1. Updates state (via `transformations`) and selection (via `cursor-ops`).
2. Pushes a history entry via `pushEditorChange` if the action mutates state.
3. Calls `rebuildTrees(newEditor, oldEditor, config)` to refresh `renderTree` and `layoutTree`. `rebuildTrees` invokes `renderTreeIncremental → cascadePassIncremental → layoutTreeIncremental` in sequence.

### Hit-test descent

```
function resolvePositionFromPixel(layoutTree, x, y):
  // Walk layout tree depth-first, accumulating parent offsets cumulatively
  candidates = []
  walk(layoutTree, 0, 0):
    absX = parent.x + box.x; absY = parent.y + box.y
    if x in [absX, absX + box.width] && y in [absY, absY + box.height]:
      if box.type == "text-run":
        // Find the cluster boundary closest to (x - absX) within the box
        clusterIdx = findClusterAt(box, x - absX)
        candidates.push({ box, clusterIdx, depth })
      for child in box.children: walk(child, absX, absY)
    else if y in box's vertical range and box is a line:
      // Pointer landed beyond the line's text horizontally — clamp to nearest end
      candidates.push(box, clusterIdx = (x < absX ? 0 : last), depth)

  pick deepest candidate (most-specific)
  translate (box, clusterIdx) → Position via the box's source-text mapping
  return position
```

### Mouse event handling (in `dom`'s editor-controller)

The keymap above is keyboard-only. Mouse handling is in the controller (separate from `core`). The controller maps DOM mouse events to engine actions:

| Event | Action |
|---|---|
| `mousedown` (single click) | `SET_SELECTION` with collapsed cursor at hit-test result |
| `mousedown` + shift | `SET_SELECTION` extending current anchor to hit-test result |
| `mousedown` (double click) | `SET_SELECTION` covering the word at hit-test result |
| `mousedown` (triple click) | `SET_SELECTION` covering the paragraph (or sentence, configurable) at hit-test result |
| `mousemove` while button down | `SET_SELECTION` with anchor preserved, focus = hit-test result (drag selection) |
| `mouseup` | release drag |

### IME composition state machine (target architecture)

DOM events: `compositionstart`, `compositionupdate`, `compositionend`. The controller manages a small state machine:

```
state = "idle"
on compositionstart(): state = "composing"; compositionStart = current selection
on compositionupdate(data): replace [compositionStart, current cursor] with data; show composition styling
on compositionend(data): commit data via INSERT_TEXT; state = "idle"
```

While `state === "composing"`:
- The text under composition is rendered with distinct styling (underline) so the user can see in-progress IME input.
- `keydown` events for non-composition keys (arrow keys, etc.) are ignored — the IME owns input until `compositionend`.

### Performance contracts

- `reduceEditor`: O(D) where D is the dirty subtree size (state mutation + render/cascade/layout incremental).
- Geometry queries: O(depth × log) at minimum; viewport-aware versions descend only into visible pages.
- `MOVE_CURSOR`, `MOVE_WORD`: O(1) per call (operates on cluster boundaries near current position).
- `MOVE_LINE`: O(line-count-on-page) — needs to traverse layout to find the next line.
