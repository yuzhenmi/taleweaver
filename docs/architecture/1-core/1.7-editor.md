# 1.7 — `editor/` and `cursor/`

The editor module is the engine's outermost orchestrator inside `core`.
It owns the reducer that dispatches `EditorAction`s, the read-only
geometry-query surface that hosts call to translate between document
positions and pixels, and the `History` integration that captures
before/after selection pairs per action. The cursor module supplies the
selection primitives (pure functions over `State` + `Position`) that
action handlers compose.

These two modules together form the boundary between `core` (engine) and
shells like `dom` and `react` (controllers, keymap, renderer). Shells
receive an `EditorState`, dispatch `EditorAction`s, and call the
geometry queries.

## Two coupled modules

`editor/` and `cursor/` are separate directories but share one
responsibility cluster.

- **`cursor/`** owns:
  - The `Selection` type (re-exported alias for `Span` from
    `state/block-position`) and the derived predicate `isCollapsed(span)`.
  - Pure operations on `(State, Position)` — `moveByCharacter`,
    `moveByWord`, `selectWord`, `expandSelection`.
  - Read-only geometry queries that take a `LayoutBox` —
    `resolvePixelPosition`, `resolvePositionFromPixel`,
    `computeSelectionRects`, `moveToLine`, `moveToLineBoundary`.
  - Shared utilities: `grapheme-utils`, `box-key-utils`.

- **`editor/`** owns:
  - The `EditorState` interface and the `reduceEditor` entry point.
  - The `EditorAction` discriminated union.
  - Per-action handlers in `editor/actions/` (one file per handler) that
    compose state-tree mutations, cursor operations, and `History`
    commits.
  (The pre-LineBox-canonical `editor/layout-utils.ts` text-run
  flatten was removed once the geometry queries migrated; line-
  level traversal now lives in `cursor/line-flatten.ts`.)

## What the reducer owns

`reduceEditor(editor, action, config) → newEditor` is the single
state-transition function shells call per user action. Inputs:

- `editor: EditorState` — semantic state (state tree, selection,
  history) plus cached pipeline output (render tree, layout tree).
- `action: EditorAction` — a discriminated union of every supported
  action.
- `config: EditorConfig` — engine configuration (text measurer,
  component + attribute registries, container width, optional
  pagination settings).

Output: a fresh `EditorState`. The reducer:

1. Classifies the action with `coalesceKeyOf` and opens the undo
   boundary BEFORE dispatching: `history.beginEntry(key, now)` for
   committing actions (`insert` / `delete` / `command`) or
   `history.breakCoalescing()` for selection jumps / undo / redo
   (`selection-break`); `inert` actions (`SET_CONTAINER_WIDTH`) do
   neither. This runs before any handler so the Yjs capture boundary is
   set before the Y.Doc transaction. See the undo-coalescing section
   below.
2. Dispatches the action to the appropriate handler (one per action
   type, defined in `editor/actions/<handler>.ts`).
3. The handler produces a new `(state, selection, history)`, calls
   `history.commit(opResult, {before, after})` when the action mutated
   state, and runs `rebuildTrees(newEditor, oldEditor, config)` to
   refresh the cached pipeline output.
4. The reducer clears `targetX` to `null` if the action is not a
   vertical motion (`MOVE_LINE` / `EXPAND_LINE`).

## Submodules

### `editor/`

- **`editor-action`** — the `EditorAction` discriminated union.
- **`editor-state`** — the `EditorState` interface, the initial-state
  constructor `createInitialEditorState`, and the reducer entry point
  `reduceEditor`.
- **`coalesce-key`** — `coalesceKeyOf(action) → ActionClass`: a pure,
  exhaustive classifier over the `EditorAction` union mapping each
  action to `insert | delete | command | selection-break | inert` for
  the reducer's undo-coalescing pre-dispatch. The `never` default makes
  a newly-added action a compile error until it is classified.
- **`actions/`** — one file per handler. Each takes `(editor, args...,
  config)` and returns the next `EditorState`. Shared helper
  `rebuildTrees` lives in `actions/helpers.ts`.

### `cursor/`

- **`selection`** — the `Selection` type alias for `Span` plus
  `isCollapsed(span)`. Other span operations live in `state/`:
  `createSpan`, `createPosition`, `positionsEqual` in
  `state/block-position`; `spanStart`, `spanEnd` in
  `state/block-compare`.
- **`cursor-ops`** — pure cursor primitives over `(State, Position)`:
  `moveByCharacter`, `moveByWord`, `selectWord`, `expandSelection`.
- **`cursor-position`** — `resolvePixelPosition(state, position,
  layoutTree, shaper)`. Document `Position` → screen `PixelPosition`.
- **`hit-test`** — `resolvePositionFromPixel(state, layoutTree, shaper,
  x, y, pageIndex?)`. Reverse: screen pixels → document `Position`.
- **`selection-geometry`** — `computeSelectionRects(state, span,
  layoutTree, shaper)`. Produces the rectangles a painter draws as the
  selection highlight (one rect per visual line within the span).
- **`line-navigation`** — `moveToLine(state, position, layoutTree,
  shaper, direction, targetX)` and `moveToLineBoundary(state, position,
  layoutTree, shaper, edge)`. Up/Down arrow + Home/End logic; consumes
  the layout tree to find the line above or below the current
  position.
- **`line-bidi`** — the per-line bidi primitive (`buildLineBidiView` →
  `LineBidiView`) the four geometry concerns read FROM, plus the
  direction-aware converters `caretXInLeaf` / `offsetInLeaf`, the
  visual-order step `moveVisually`, and the selection segmenter
  `selectionRectsForLineRange`. See **Bidi cursor** below.
- **`visual-motion`** — shared helpers for the visual-order move/expand
  handlers: `resolveLineForPosition` (the `AbsoluteLineBox` owning a
  position, virtual- and positioned-tree aware) and
  `buildBlockGraphemeStepper` (a block-scoped `GraphemeStepper`).
- **`grapheme-utils`** — UAX #29 grapheme-cluster utilities shared by
  cursor primitives and hit-test.
- **`box-key-utils`** — parsers for the layout-box composite key
  format used to retrieve owning blockId / inline ancestor key.

## How modules connect

```
              EditorAction
                   │
                   ▼
       ┌───────────────────────┐
       │ reduceEditor (entry)  │
       └───────────┬───────────┘
                   │
                   ▼
       ┌───────────────────────┐
       │ actions/<handler>     │
       │                       │
       │  uses: cursor/ ops    │  → new (state, selection)
       │        state/         │  → history.commit(opResult, {before, after})
       │        transformations│
       └───────────┬───────────┘
                   │
                   ▼
       ┌───────────────────────┐
       │ rebuildTrees helper   │
       │                       │
       │  render → layoutTree  │  → new (renderTree, layoutTree)
       └───────────┬───────────┘
                   │
                   ▼

```

The geometry queries (`cursor/cursor-position`, `cursor/hit-test`,
`cursor/selection-geometry`, `cursor/line-navigation`) are read-only —
shells call them against `EditorState.layoutTree` whenever they need to
translate between document and screen coordinates. They never mutate.

## Why cursor sits in its own module

Cursor primitives are pure and reusable across action handlers:
`MOVE_CURSOR` (forward) and `EXPAND_SELECTION` (forward) both want
"advance one cluster," differing only in whether the selection collapses
or extends. Factoring those primitives into `cursor/` lets action
handlers stay small and uniform, and lets shells call the same
primitives directly for non-editor use (e.g. find/replace's "highlight
match" needs a `Position` for a click target without dispatching an
action).

## Reference

### `EditorState` and `EditorConfig`

```ts
interface EditorState {
  readonly state: State;
  readonly selection: Selection;
  readonly history: History;
  readonly renderTree: RenderNode;
  readonly layoutTree: LayoutBox;
  readonly containerWidth: number;
  readonly targetX: number | null;
  // Non-undoable VIEW state (never in History / Selection / Position).
  readonly caretPageHint?: number;            // which page a click landed on
  readonly caretAffinity?: "before" | "after"; // bidi dual-caret side (see Bidi cursor)
}

interface EditorConfig {
  readonly measurer: TextShaper | TextMeasurer;
  readonly componentRegistry: ComponentRegistry;
  readonly attrRegistry: AttrRegistry;
  readonly containerWidth: number;
  readonly pageConfig?: PageConfig;
  // Injected clock for undo-coalescing timing. Defaults to `Date.now`;
  // tests pass a controllable counter so the pause window is deterministic.
  readonly now?: () => number;
}
```

`targetX` semantics: when `MOVE_LINE` or `EXPAND_LINE` runs, the cursor
remembers the column-pixel of its position at the start of the vertical
motion sequence. Subsequent vertical moves prefer landing at that
column (subject to per-line content), so a series of ArrowDown +
ArrowUp returns to the original column. Any non-vertical action clears
`targetX` to `null`.

### `History` (selection-aware, Y.UndoManager-backed)

The editor delegates undo/redo entirely to `History` from
`state/history.ts`. `History` is Y.Doc-backed via `Y.UndoManager`. Undo-group
boundaries are owned by `beginEntry` / `breakCoalescing`, which the reducer
drives to coalesce typing runs into single undo units (see **Undo coalescing**
above); a single `commit` records one unit's selection meta but no longer
decides the boundary.

```ts
interface SelectionEntry {
  readonly before: Selection | null;
  readonly after: Selection | null;
}

interface UndoRedoResult {
  readonly state: State;
  readonly selection: Selection | null;
  // BlockIds the undo/redo's reversal mutated; threaded into the
  // editor's incremental render pipeline so it rebuilds only the
  // affected subtrees instead of the whole document.
  readonly dirtyIds: ReadonlySet<BlockId>;
}

class History {
  constructor(state: State);
  beginEntry(key: "insert" | "delete" | "command", now: number): void;
  breakCoalescing(): void;
  commit(opResult: OperationResult, selections: SelectionEntry): void;
  canUndo(): boolean;
  canRedo(): boolean;
  undo(): UndoRedoResult | null;
  redo(): UndoRedoResult | null;
}
```

**Contracts.**

- **Selection on `StackItem.meta`.** `History` stores each action's
  `SelectionEntry` on its `Y.UndoManager` `StackItem.meta` (written at
  `commit` onto the just-closed item; read at `undo`/`redo` from the
  popped item and re-welded onto the opposite stack's new top). Selection
  travels with the stack item, so it cannot index-desync from the Yjs
  stacks — there is no parallel selection array. See `1.1-state.md`
  (History reference) for the full mechanism.
- **No-op short-circuit.** `Y.UndoManager` skips empty groups, so
  callers MUST short-circuit BEFORE invoking `commit` when an
  operation was a no-op (`opResult.state === inputState`, equivalent
  to `opResult.dirtyIds.size === 0` per the state module's T7 identity
  contract). Action handlers enforce this with one
  `if (result.state === editor.state) return editor;` guard before any
  `commit`.
- **Capture timeout.** The wrapper constructs `Y.UndoManager` with
  `captureTimeout: Number.MAX_SAFE_INTEGER`. Yjs never auto-merges or
  auto-closes groups by its own clock; `History` owns every undo-group
  boundary explicitly via `beginEntry` / `breakCoalescing` (`commit` no
  longer calls `stopCapturing`). This lets a single action handler chain
  multiple state-module operations (e.g. `deleteRange` + `insertText`
  inside `PASTE`) and have them merge into one undo entry, while the
  reducer decides whether consecutive actions coalesce (see **Undo
  coalescing** below).
- **Meta-map exclusion (intentional).** The Y.Doc's meta `Y.Map` is not
  tracked by the `Y.UndoManager`. Today it holds only the immutable
  `rootId`; a future writer adding a new meta field must explicitly
  consider undoability and update the wrapper's tracked-types list if
  the field needs coverage.
- **Undo coalescing (time-based, Google-Docs parity).** A run of typing
  collapses into one undo unit. The reducer is the single chokepoint: it
  classifies each action with the pure, exhaustive `coalesceKeyOf`
  (`editor/coalesce-key.ts`) into
  `insert | delete | command | selection-break | inert`, then calls
  `history.beginEntry(key, now)` for committing actions or
  `history.breakCoalescing()` for selection jumps / undo / redo, BEFORE
  dispatching the handler. Consecutive same-kind coalescible edits
  (`insert` = `INSERT_TEXT`; `delete` = the `DELETE_*` family) within
  `UNDO_COALESCE_PAUSE_MS` merge into one unit; a pause, a kind switch
  (`insert ↔ delete`), any discrete command, or a selection jump breaks
  the group. The clock is injected via `EditorConfig.now` (defaults to
  `Date.now`) for deterministic tests. `SET_CONTAINER_WIDTH` is inert.
  The boundary decision runs before the per-handler no-op short-circuit
  (a no-op committing action still advances the boundary — accepted edge,
  policy kept in one place). See `1.1-state.md` (History reference) for
  the full mechanism.

### `EditorAction` discriminated union

`editor-action.ts` is the authoritative source; the union below is grouped
for readability (text editing, navigation, inline formatting, block
formatting, structure, history).

```ts
type EditorAction =
  // Text editing
  | { type: "INSERT_TEXT"; text: string }
  | { type: "INSERT_NODE"; node: BlockInit; position?: Position }
  | { type: "PASTE"; text: string }
  | { type: "DELETE_BACKWARD" }
  | { type: "DELETE_FORWARD" }
  | { type: "DELETE_WORD"; direction: "forward" | "backward" }
  | { type: "DELETE_LINE" }
  | { type: "SPLIT_NODE" }
  // Navigation (move) + selection extension (expand)
  | { type: "MOVE_CURSOR"; direction: "forward" | "backward" }
  | { type: "MOVE_WORD"; direction: "forward" | "backward" }
  | { type: "MOVE_LINE"; direction: "up" | "down" }
  | { type: "MOVE_LINE_BOUNDARY"; boundary: "start" | "end" }
  | { type: "MOVE_DOCUMENT_BOUNDARY"; boundary: "start" | "end" }
  | { type: "EXPAND_SELECTION"; direction: "forward" | "backward" }
  | { type: "EXPAND_WORD"; direction: "forward" | "backward" }
  | { type: "EXPAND_LINE"; direction: "up" | "down" }
  | { type: "EXPAND_LINE_BOUNDARY"; boundary: "start" | "end" }
  | { type: "EXPAND_DOCUMENT_BOUNDARY"; boundary: "start" | "end" }
  | { type: "SELECT_ALL" }
  | { type: "SET_SELECTION"; selection: Selection; caretPageHint?: number }
  // Inline (character) formatting — applied to the selection RANGE
  | { type: "TOGGLE_STYLE"; style: "bold" | "italic" | "underline" | "strikethrough" }
  | { type: "SET_LINK"; url: string | null }
  | { type: "SET_TEXT_COLOR"; color: string | null }
  | { type: "SET_HIGHLIGHT"; color: string | null }
  | { type: "SET_FONT_SIZE"; size: number | null }
  | { type: "SET_FONT_FAMILY"; family: string | null }
  | { type: "SET_TEXT_TRANSFORM"; value: TextTransform }
  | { type: "CLEAR_FORMATTING" }
  // Block / paragraph formatting — per-leaf-block attrs over the selection's leaves
  | { type: "SET_BLOCK_TYPE"; blockType: string; properties?: Record<string, unknown> }
  | { type: "TOGGLE_LIST"; listType: "ordered" | "unordered" }
  | { type: "SET_LIST_TYPE"; listType: "ordered" | "unordered" }
  | { type: "SET_LIST_RESTART"; value: number | null }
  | { type: "LIST_INDENT" }
  | { type: "LIST_OUTDENT" }
  | { type: "SET_TEXT_ALIGN"; align: TextAlign }
  | { type: "SET_LINE_SPACING"; spacing: number }
  | { type: "INDENT" }
  | { type: "OUTDENT" }
  | { type: "SET_PARAGRAPH_SPACING"; edge: "before" | "after"; value: number | null }
  // Structure — sections, page templates, footnotes
  | { type: "SECTION_BREAK" }
  | { type: "TOGGLE_SECTION_LANDSCAPE" }
  | { type: "INSERT_HEADER" }
  | { type: "INSERT_FOOTER" }
  | { type: "INSERT_FOOTNOTE" }
  | { type: "SET_FOOTNOTE_POLICY"; /* … */ }
  // Atomic-leaf blocks — image, horizontal line
  | { type: "INSERT_HORIZONTAL_LINE" }
  | { type: "INSERT_IMAGE"; src: string; width?: number; height?: number }
  | { type: "SET_IMAGE_SIZE"; blockId: BlockId; width: number; height: number }
  // Find & Replace (replace side; the find session lives in the host)
  | { type: "REPLACE_MATCH"; match: TextMatch; replacement: string }
  | { type: "REPLACE_ALL"; matches: TextMatch[]; replacement: string }
  // Layout / history
  | { type: "SET_CONTAINER_WIDTH"; width: number }
  | { type: "UNDO" }
  | { type: "REDO" };
```

**Two formatting handler shapes.** *Inline* formatting (`TOGGLE_STYLE`,
`SET_LINK`, `SET_TEXT_COLOR`, `SET_HIGHLIGHT`, `SET_FONT_SIZE`,
`SET_FONT_FAMILY`, `SET_TEXT_TRANSFORM`, `CLEAR_FORMATTING`) sets per-`TextItem`
attrs over the selection range via `applyAttrsToRange`; it no-ops on a collapsed
selection.
*Block* formatting (`SET_TEXT_ALIGN`, `SET_LINE_SPACING`, `INDENT`/`OUTDENT`,
`SET_PARAGRAPH_SPACING`) sets per-block attrs on the selection's **leaf** blocks
(collapsed → focus leaf; range → every `inlineContent !== null` block,
containers filtered out) via `mergeBlockAttrs`; the caret is preserved (a
block-geometry change, not a caret move). Both share the T7 identity contract
(no-op → same `editor` reference, no `commit`).

The read-side of these inline actions is the pure `getActiveFormatting(state,
selection)` engine query that hosts call to drive toolbar state: it reports each
inline attr's value across the selection, collapsing to a single value when
uniform or `"mixed"` when the selection spans differing values (and `null` when
unset). It includes a `textTransform: TextTransform | "mixed" | null` field
alongside the bold/italic/color/font fields.

**Block-attr → layout threading convention.** Block-level formatting attrs
(`textAlign`, `lineHeight`, `marginInlineStart` (indent), `marginBlockStart` /
`marginBlockEnd` (paragraph spacing)) do NOT reach layout through the generic
cascade attr-interpreter path — the inline-bearing-leaf components
(`paragraph`, `heading`, `list-item`) synthesize them onto the ElementBox
`style` from `view.attrs` via the `*FromAttrs` helpers in
`components/leaf-style-attrs.ts` (spread LAST so an explicit attr wins over the
component's default). An absent attr contributes nothing, so unformatted blocks
render byte-identically. This is the single mechanism every block-formatting
action above relies on.

### Per-action behavior

Conventions used in the table:
- **State**: what mutation the handler performs on the document.
- **Selection (after)**: where the caret / selection lands when the
  action completes. "preserved" means anchor / focus unchanged.
- **History**: whether the handler appends to `History` via `commit`.

| Action | State | Selection (after) | History |
|---|---|---|---|
| `INSERT_TEXT` | If selection is non-collapsed: replace range with text. Else: insert text at cursor. | cursor → end of inserted text | commit |
| `INSERT_NODE` | Insert `node` (a `BlockInit` subtree) at the document root as the last child of root. | preserved (the insert appends at the document end and does not shift existing block ids/positions, so the prior selection stays valid; the cursor is intentionally not teleported to the appended block) | commit |
| `PASTE` | If selection is non-collapsed: delete range. Then split text on `\n`; first line inserts at cursor, subsequent lines split the block + insert. | cursor → end of pasted | commit (one group) |
| `DELETE_BACKWARD` | If selection is non-collapsed: delete range. Else: delete one grapheme cluster before cursor (across block boundaries: merge prev block in). At a block boundary whose adjacent sibling is an atomic-leaf (image/horizontal-line), remove that object as a unit instead (`atomic-edits.ts` — atomic blocks carry no cursor positions, so the grapheme stepper skips them and the merge path would otherwise no-op). | cursor → at deletion point | commit |
| `DELETE_FORWARD` | Symmetric to backward (incl. atomic-leaf removal of the next sibling). | cursor → at deletion point | commit |
| `DELETE_WORD` | Delete one word in `direction` (within a block; cross-block is a no-op). | cursor → at deletion point | commit |
| `DELETE_LINE` | Delete from `lineStart` to cursor within the current line. | cursor → line start | commit |
| `SPLIT_NODE` | If selection is non-collapsed: delete range first. Then split the containing leaf block at cursor (Enter behavior). | cursor → start of new block | commit (one group across the delete + split) |
| `MOVE_CURSOR` | none | If selection was non-collapsed: collapse to start/end based on direction. Else: move one cluster. | no commit |
| `MOVE_WORD` | none | Move one word in `direction`; collapse. | no commit |
| `MOVE_LINE` | none | Move to next/prev visual line at column `targetX`; preserve `targetX`. | no commit |
| `MOVE_LINE_BOUNDARY` | none | Move to start/end of current visual line. | no commit |
| `MOVE_DOCUMENT_BOUNDARY` | none | Move to the first/last `Position` WITHIN the caret's selection context (resolves via `selectionContextOf`, like `SELECT_ALL`): main tree → document start/end; a footnote/embed or header/footer body → that body's start/end. Context-aware, so it cannot escape the caret's context (Ctrl+End in a footnote stays in the footnote). | no commit |
| `EXPAND_*` | none | Extend `focus` per the analogous `MOVE_*`; keep `anchor`. `EXPAND_DOCUMENT_BOUNDARY` is context-aware exactly like `MOVE_DOCUMENT_BOUNDARY`: the new `focus` is resolved WITHIN the caret's selection context, so the resulting span stays single-context (never cross-context) and is always iterable. | no commit |
| `SELECT_ALL` | none | anchor → start, focus → end of the caret's selection context (main tree, or the one footnote/embed/header/footer body the caret is in — `selectionContextOf`). | no commit |
| `SET_SELECTION` | none | Replace selection wholesale. Rejects a cross-context span (anchor and focus in different selection contexts — main tree vs a footnote/embed body vs a header/footer body) at the reducer chokepoint via `selectionContextOf`: dev-throw, production no-op (keeps the prior selection). It is the only arm that accepts an arbitrary externally-supplied span (the `MOVE_*`/`EXPAND_*`/`SELECT_ALL` arms are context-confined by construction), so it is the external chokepoint where the backstop lives. | no commit |
| `TOGGLE_STYLE` | If collapsed: no-op. Else: apply or remove the inline style across the selection range. | preserved | commit (when non-collapsed) |
| `SET_BLOCK_TYPE` | Change the cursor's containing leaf block's `type` (e.g. paragraph → heading). Refuses cross-kind shape changes. | preserved | commit |
| `TOGGLE_LIST` | Flat unified Google-Docs toggle. Turns the selection OFF only when EVERY eligible text-leaf is already a list-item of the requested type (→ paragraphs, clearing `listId`/`listLevel`/`listCounterOverride`); otherwise turns all ON — paragraphs AND other-type list-items become list-items of the requested type. Adjacent-join reuses an immediately-adjacent same-type list's `listId` (BEFORE neighbour wins), else mints a fresh `listId` via `newListId()` + writes its def via `setListType`. Multi-block selection → one list. No tree surgery (flat model). | preserved | commit |
| `SET_LIST_TYPE` | Change the type (ordered ⇄ unordered) of the list(s) the selection touches by rewriting the shared `ListDef` via `setListType` (never adds/removes membership). Lists already of that type are skipped. | preserved | commit |
| `SET_LIST_RESTART` | Set (number) or clear (`null`) the focus item's `listCounterOverride` attr via `setListRestart` ("restart numbering at N" / "continue previous"). | preserved | commit |
| `LIST_INDENT` / `LIST_OUTDENT` | Step the target list-item(s)' `listLevel` by ±1, clamped [0, 8]; level 0 clears the attr. Targets list-item leaves only (a non-list-item in the selection is skipped — plain-paragraph indent uses `INDENT`/`OUTDENT`). | preserved | commit |
| `SET_LINK` / `SET_TEXT_COLOR` / `SET_HIGHLIGHT` / `SET_FONT_SIZE` / `SET_FONT_FAMILY` | Inline value-attr (link / color / backgroundColor / fontSize / fontFamily) over the selection range; `null`/empty clears the attr. Collapsed → no-op. | preserved | commit (when non-collapsed) |
| `SET_TEXT_TRANSFORM` | Inline `textTransform` value-attr (`capitalize`/`uppercase`/`lowercase`) over the selection range. Because `"none"` is the property's initial value, the handler treats `value: "none"` as a removal sentinel — it REMOVES the attr rather than writing it. Collapsed → no-op. | preserved | commit (when non-collapsed) |
| `CLEAR_FORMATTING` | Clear every `INLINE_FORMAT_ATTR_KEYS` attr (which includes `textTransform`) over the range in one op (one undo step). Collapsed → no-op. | preserved | commit |
| `SET_TEXT_ALIGN` / `SET_LINE_SPACING` / `SET_PARAGRAPH_SPACING` | Set a per-leaf-block attr (`textAlign` / `lineHeight` / `marginBlockStart`\|`marginBlockEnd`) on the selection's leaf blocks; `null`/negative clears. | preserved | commit |
| `INDENT` / `OUTDENT` | Step each selected leaf block's `marginInlineStart` by ±48px (read-modify-write per block); outdent clamps at 0. SKIPS `list-item` leaves (I5): list nesting is `listLevel` via `LIST_INDENT`/`LIST_OUTDENT`, not `marginInlineStart` — though a list-item CAN still carry a user `marginInlineStart` that the BFC composes ON TOP of its level padding. | preserved | commit |
| `SECTION_BREAK` / `TOGGLE_SECTION_LANDSCAPE` / `INSERT_HEADER` / `INSERT_FOOTER` / `INSERT_FOOTNOTE` / `SET_FOOTNOTE_POLICY` | Structural: split a section / toggle a section's page size / attach a header\|footer template body / insert a footnote anchor + body / set the doc-wide footnote numbering policy. | varies (footnote: caret → body) | commit |
| `INSERT_HORIZONTAL_LINE` / `INSERT_IMAGE` | Insert an atomic-leaf block (`horizontal-line`, or `image` with `src` + optional `width`/`height`) immediately after the caret's focus block, plus a trailing empty paragraph so the doc stays editable past it; caret → start of the trailing paragraph. Main-tree only (no-op when the focus resolves outside the body, e.g. a header/footer). | caret → new trailing paragraph | commit |
| `INSERT_TABLE_ROW` | Insert a full row (one cell per column, each holding an empty paragraph) `above`\|`below` the caret's row, via `resolveTableContext` → `insertTableRow`. Span-gated: no-op when the caret is outside any table OR the table `hasSpans` (any real rowSpan/colSpan or ragged rows — deferred to P15b). | preserved (caret stays in place, per Google Docs) | commit |
| `DELETE_TABLE` | Delete the entire table the caret is in, via `resolveTableContext` → `deleteTableWithReplacement`. **Span-agnostic** (NOT gated on `hasSpans` — deleting a whole table is always safe, and Google Docs allows it). When the table is the body's sole child, removal would empty the body, so a fresh empty paragraph replaces it. Main-tree only (no-op when the caret is outside any table). | caret → surviving sibling (`nextSiblingId ?? prevSiblingId`), or the fresh replacement paragraph when the table was the sole child | commit |
| `SET_IMAGE_SIZE` | Merge `width`/`height` (px) onto the `image` block named by an explicit `blockId` (an image is an atomic-leaf with no cursor positions, so it can't be the selection focus — the browser-gated resize handle supplies the id). No-op when the target is missing / not an `image` / dims non-finite or ≤0 / dims unchanged. | preserved | commit |
| `REPLACE_MATCH` | Replace one find `TextMatch` via `replaceRange` (replacement takes the formatting at `match.start`). Classed `command` → its own undo step. The host recomputes matches after (offsets shifted). | caret → seam (`match.start + replacement.length`) | commit |
| `REPLACE_ALL` | Replace every `TextMatch` via `planReplaceMatches` + one `applyOperation` batch (ONE undo step for the whole replace-all). Empty matches → no-op. | caret → start of the first affected block's first replacement | commit |
| `SET_CONTAINER_WIDTH` | none | preserved | no commit (re-runs layout only) |
| `UNDO` / `REDO` | Restore prior state via `History`. | Restore prior selection (`before` on undo, `after` on redo). | history mutation only |

### List editing (flat model)

List membership and nesting are per-item attrs (`listId` / `listLevel`),
not tree structure — so list editing is attribute edits, never tree
surgery (see `1.1-state.md` for the flat model, `1.2-render.md` for how
markers are numbered). Beyond the dedicated list actions above, three
edit paths have list-aware special cases:

- **Enter on an EMPTY list-item exits the list** (`handleSplitNode`,
  Google-Docs behavior): a nested item (`listLevel > 0`) OUTDENTS one
  level (via `LIST_INDENT`'s helper); a top-level item un-lists to a
  paragraph. A non-empty list-item splits normally (the new block stays a
  list-item).
- **Backspace at the START of a list-item** (offset 0,
  `handleDeleteBackward`): a nested item outdents one level; a top-level
  item un-lists to a paragraph (it does NOT merge into the previous
  block).
- **Tab / Shift+Tab in a list-item** route to `LIST_INDENT` /
  `LIST_OUTDENT`. The DOM key-handler is context-sensitive: it takes an
  optional `KeyContext { inListItem? }` (the controller sets it when the
  caret's focus block is a `list-item`); outside a list-item, Tab stays
  unmapped. See `2-dom` (`key-handler`).

Shared helpers `listLevelOf` / `unlistBlock` (convert a list-item back to
a paragraph, clearing `listId`/`listLevel`/`listCounterOverride` while
keeping the block id + content so the caret stays put) live in
`editor/actions/list-edits.ts`.

### Reducer flow

```
function reduceEditor(editor, action, config) -> EditorState:
  // Open the undo boundary before any Y.Doc transaction runs.
  class = coalesceKeyOf(action)
  if class in ("insert", "delete", "command"):
    editor.history.beginEntry(class, (config.now ?? Date.now)())
  else if class == "selection-break":
    editor.history.breakCoalescing()
  // else "inert": no boundary change

  isVertical = (action.type == "MOVE_LINE" || action.type == "EXPAND_LINE")

  result = dispatch(action.type, editor, action, config)

  // Clear targetX on non-vertical actions
  if not isVertical and result.targetX !== null:
    result = { ...result, targetX: null }

  return result
```

Each state-mutating handler internally:

1. Computes the new `state` + `selection` by composing state-module
   primitives and cursor operations.
2. Short-circuits and returns `editor` unchanged when the operation was
   a no-op (`result.state === editor.state`).
3. Calls `editor.history.commit(opResult, { before: oldSelection,
   after: newSelection })`.
4. Calls `rebuildTrees(newEditor, oldEditor, config)`, which currently
   runs `render → layoutTree` on the full document. [partial — target:
   incremental rebuild that consumes `dirtyIds` and reuses unchanged
   render+layout subtrees by reference.]

Pure read-only handlers (`MOVE_CURSOR`, `EXPAND_SELECTION`,
`SELECT_ALL`, `SET_SELECTION`, etc.) skip both the `commit` and the
`rebuildTrees` calls — they only return a new `EditorState` with the
updated `selection` and (for line motions) `targetX`.

### Hit-test approach

Hit-test descends the layout tree once via `collectLineBoxes` (in
`cursor/line-flatten.ts`) to enumerate every `LineBox` with absolute
coordinates. Line identity is the `LineBox` reference itself —
float-Y fragility is structurally resolved. The target line is the
one whose vertical range contains the click `y`. Within the line,
`collectLineLeaves` walks the line's children to find the text-run
or inline-block leaf whose X range contains the click `x`. The
returned `Position` is
`(line.ownerBlockId, line.inlineOffsetStart + withinLineOffset + charOffset)`
where `withinLineOffset` is the sum of preceding leaves' state-
model offset contributions and `charOffset` is a binary search over
prefix widths in the target text-run.

Empty paragraphs are first-class: the LineBox carries
`ownerBlockId` and `inlineOffsetStart === inlineOffsetEnd === 0`,
so a click on the empty paragraph's line returns offset 0 of that
paragraph directly — no synthetic-strut machinery needed.

### Writing-mode-aware geometry

The geometry layer operates on the **active inline/block axes** rather than
hard-coding x as inline and y as block, so it is correct under every writing
mode. The boxes it reads are already-physical (the `vertical-rl` block-axis
mirror was baked in by the `physicalizeVertical` pass; see
[`1.4-layout/overview.md`](./1.4-layout/overview.md#logical-axis-discipline-and-the-vertical-rl-physicalize-pass)),
and each consumer picks the right physical coordinate via
`axisMapFor(writingMode, direction)`:

- **cursor-position** places the caret on the inline axis at the block-axis
  line band.
- **hit-test** picks the BODY line by block-axis band and the leaf within it
  by inline-axis position.
- **selection-geometry** projects each line-range interval to true physical
  rects via the line's axis map.
- **line-navigation** moves along the block axis while preserving the
  inline-axis goal coordinate (the writing-mode-general form of `targetX`).
- the **bidi cursor** (below) is generalized to the inline axis.

`LineLeaf` carries both physical axes (`absoluteX` / `absoluteY`, `width` /
`height`); `PixelPosition`'s `x` / `y` are inline-/block-semantic but
physically valued, so for `horizontal-tb` (inline == x, block == y) they are
byte-identical to the legacy fields.

`[partial]` The **slot-zone hit-test** is not yet axis-generalized:
`pickRegionByBand`'s classification of header / footer / footnote zones
still uses the `horizontal-tb` (vertical-band) path, so clicking a vertical
document's header/footer/footnote slot is not yet resolved correctly; only
the BODY hit-test is writing-mode-general. The caret still draws as a
vertical bar and glyphs still paint horizontally — the browser-gated paint
remainder (see [`2-dom/2.2-canvas-renderer.md`](../2-dom/2.2-canvas-renderer.md)
and [state-of-branch](../state-of-branch.md)).

### Bidi cursor

The cursor layer is bidi-aware: on a line the IFC reordered into visual
order (see [1.4-layout/1.4.2-ifc.md](./1.4-layout/1.4.2-ifc.md) "Bidi
handling"), caret X, click→offset, selection geometry, and visual-order
navigation all account for the LTR↔RTL run structure. The four geometry
concerns share one primitive so they round-trip against each other.

**`LineBidiView` (`cursor/line-bidi.ts`).** The single per-line object
that knows the VISUAL↔LOGICAL leaf correspondence. `buildLineBidiView(alb)`
collects the line's leaves in visual (post-reorder) order, EXCLUDES
synthetic runs that own no state positions (the empty-paragraph strut, the
synthetic hyphen — detected by `offsetLength === 0 && sourceStart ===
undefined`), then reconstructs LOGICAL order by sorting the surviving
leaves on `box.sourceStart` (a sort key only — never added to a state
offset; `text-transform` changes a run's length, never its position, so
source order equals state order). It accumulates each leaf's STATE span
(`logStart`/`logEnd`) in logical order starting from the line's
`inlineOffsetStart`, and tags each with its UAX #9 `level` (`box.bidiLevel
?? paragraphLevel`; even = LTR, odd = RTL). The result exposes
`visualLeaves` and `logicalLeaves` — the SAME `BidiViewLeaf` objects in two
orders — plus `paragraphDirection` and `isEmpty` (a strut-only line).

`caretXInLeaf(view-leaf, stateOffset, measurer)` and
`offsetInLeaf(view-leaf, localX, measurer)` are the direction-aware
intra-leaf converters and exact inverses. For a text-run they map state↔
display via `sourceDisplayLengths` and measure the display prefix; the
LTR placement is `absoluteX + measureWidth(prefix)` and the RTL placement
mirrors it (`absoluteX + width − measureWidth(prefix)`), so the logically-
earlier prefix sits at the run's RIGHT edge. Inline-blocks are atomic
(leading vs trailing edge / midpoint split). The same machinery generalizes
to the active inline axis: under a vertical writing mode the leaf's inline
extent runs along physical y, and the placements read the leaf's inline-axis
coordinate via `axisMapFor` (see "Writing-mode-aware geometry" above), so
bidi caret / hit-test / selection remain correct for vertical-RTL content.

**Caret affinity.** `EditorState.caretAffinity` (`"before" | "after"`)
disambiguates the dual caret at a direction boundary: one logical `offset`
has TWO visual positions at an LTR↔RTL boundary, and the affinity says
which leaf the caret sticks to — `"before"` draws at the trailing edge of
the leaf ENDING at the offset, `"after"`/undefined at the leading edge of
the leaf STARTING at it (inert on a uniform line, where both give the same
X). It is non-undoable VIEW state: NOT on `Selection` / `Span` / `Position`
/ `History` — it mirrors `caretPageHint`'s lifecycle (the OPPOSITE of
`targetX`'s central clear). It is SET by the actions that manage it and
RESET to `undefined` after any other action by the reducer's central reset.
`actionManagesCaretAffinity` is the single exemption list: `SET_SELECTION`
(seeds the hit side from a click), `MOVE_CURSOR` / `EXPAND_SELECTION`
(visual arrows carry the boundary-flip side), `MOVE_LINE_BOUNDARY` /
`EXPAND_LINE_BOUNDARY` (Home/End seed a direction-independent affinity).

**The four concerns, all bidi-aware.**

- **cursor-position** (`resolvePixelPosition`) — finds the owning logical
  leaf for `(offset, caretAffinity)` and returns the direction-aware caret
  X via `caretXInLeaf` (clamped to the leaf's box edges, mirroring the #338
  trailing-space clamp so caret and selection agree).
- **hit-test** (`resolvePositionFromPixel`) — after locating the visual
  leaf under the click X, calls `offsetInLeaf` (the RTL-aware inverse of
  `caretXInLeaf`, so click↔render round-trips) and returns `{ position,
  caretAffinity }`, seeding the affinity from the hit side.
- **selection-geometry** (`computeSelectionRects`) — a single logical range
  that crosses a direction boundary maps to ≥ 2 disjoint VISUAL rects.
  `selectionRectsForLineRange` walks the view's logical leaves, emits one
  interval per overlapped leaf (endpoints from `caretXInLeaf`, always
  `xLo ≤ xHi` so width is never negative on a reordered line), and
  coalesces ONLY physically-adjacent SAME-level intervals (never across a
  direction boundary). A pure-LTR or pure-RTL range yields one interval.
- **navigation** — `moveVisually(view, offset, caretAffinity, visualDir,
  step)` takes ArrowLeft/Right in VISUAL order: it resolves the owning run
  by level parity (visual-right = logical-forward in an LTR run,
  logical-backward in an RTL run), steps one grapheme inside the run, and
  at the run's visual edge CROSSES to the visually-adjacent run, flipping
  `caretAffinity` to the entered run — the dual-caret "first press flips,
  second advances" at a direction boundary. Running off the line's visual
  edge returns `{ exit }` and the handler moves to the adjacent line's
  visual edge. `MOVE_CURSOR` (collapsed) and `EXPAND_SELECTION` (extends
  the FOCUS visually, anchor fixed) both drive `moveVisually`. Home/End
  (`MOVE_LINE_BOUNDARY` / `EXPAND_LINE_BOUNDARY`) stay LOGICAL — Home →
  `inlineOffsetStart`, End → `inlineOffsetEnd` in BOTH directions — and
  seed a direction-independent affinity (Home → `"after"`, End →
  `"before"`) so the logical boundary RENDERS at the correct visual edge of
  an RTL line via the caret X, NOT via an offset swap.

`visual-motion.ts` supplies the move/expand handlers' shared
`resolveLineForPosition` (the `AbsoluteLineBox` owning the moving head,
virtual- and positioned-tree aware) and `buildBlockGraphemeStepper` (a
`GraphemeStepper` over the block's state-indexed text, each embed one
atomic U+FFFC unit) that `moveVisually` steps with.

The reorder geometry, glyph paint (a run's clusters paint right-to-left
when `bidiLevel` is odd), and this cursor layer are all built; the bidi
cursor work is unit-verified. `[partial]` Pending the P4 in-browser smoke:
the two `TODO(C.2.7 browser-confirm)` boundary cases (the left-going
dual-caret double-stop, and the cross-line visual edge when a line's
content direction differs from the paragraph base) and the exact RTL
Home/End semantic (the logical-Home convention is near-universal but its
Google-Docs RTL rendering shares C.2.3's browser-divergent class). These
are browser-confirm-pending refinements of built behavior, not gaps.
