# 1.6 — Text

The text subsystem owns everything about turning Unicode text into
positioned glyphs for layout and paint to consume: shaping, bidi,
grapheme clustering, line-break opportunities, hyphens, font metrics.
It cuts across the layout and paint phases — both consume the same
shaper output.

## The shaper interface

`core` defines a `TextShaper` interface but never instantiates one.
Hosts (or external packages) implement it; `dom` ships a canvas-based
default in [`2.4-canvas-shaper.md`](../2-dom/2.4-canvas-shaper.md).

The interface contract:

- **Input:** a string of Unicode text plus a `ComputedStyle` (font
  family/size/weight/style; possibly font-feature-settings,
  letter-spacing, word-spacing, language tag) plus optional shape
  options (e.g., available width for shaping, whether to enable
  hyphenation).

- **Output:** a `ShapedRun` containing positioned glyphs (each with an
  advance width), cluster boundaries (to map characters to glyphs and
  back), break opportunities (where the IFC may wrap), bidi levels per
  cluster, and font metrics (ascent, descent, line-height).

The interface lets the IFC pack tokens into lines, the painter draw
the glyphs at their positions, the cursor logic place the caret within
ligatures, and the hit-test logic translate pixel coordinates into
character offsets — all from one shaper pass per text run.

## Letter- and word-spacing (CSS Text 3 §8)

`letter-spacing` adds tracking after every typographic character unit;
`word-spacing` adds spacing to word-separator characters (U+0020, U+00A0).
The rule lives in one pure module, `layout/text-spacing.ts`
(`resolveSpacingPx` — `normal`→0, px→itself; `clusterSpacing(clusterText,
letterPx, wordPx)` — letter on every cluster, word on separators).

It is applied at the **two chokepoints that independently compute cluster
advances**, so layout, intrinsic sizing, and paint stay in lockstep (the
caret/glyph-drift class of bug otherwise — a single kerned whole-run draw vs
per-cluster summed advances):

1. **The shaper** (`TextShaper.shape`) bakes `clusterSpacing` into each
   returned cluster's `inlineAdvance` and the run aggregates
   (`minClusterInlineSize`, `unbreakableRunInlineSize`). The IFC (token
   widths + wrapping) and intrinsic sizing (min/max-content) read those
   advances, so both pick spacing up for free.
2. **The canvas renderer's per-cluster paint loop** adds the same
   `clusterSpacing` to each cumulative advance (it re-measures clusters
   independently), so painted glyph origins equal the layout advances.

`resolveSpacingPx("normal") === 0`, so the default editing path is inert and
byte-identical. The IFC additionally trims trailing tracking at each line's
end — see [`1.4.2-ifc.md`](1.4-layout/1.4.2-ifc.md).

## Text transform (CSS Text 4 §2.1)

`text-transform` (`none` | `capitalize` | `uppercase` | `lowercase`) is a
**display transform**: the rendered, measured, and painted text is transformed,
while the state text stays pristine (`uppercase` of `straße` paints `STRASSE`,
but the document still holds `straße`, and `getActiveFormatting` reports it
unchanged). The rule lives in one pure module, `layout/text-transform.ts`:

```ts
function transformRun(text: string, mode: TextTransform):
  { display: string; sourceDisplayLengths: readonly number[] };
```

- **`uppercase` / `lowercase`** apply JS default-locale case mapping, which is
  the one place a case mapping can grow or shrink the string (`ß` → `SS`).
- **`capitalize`** upper-cases the first cased character after each word
  boundary. The v1 word boundary is the run start plus any position following
  whitespace (a per-code-unit approximation), not the full UAX #29 word
  segmentation.

`transformRun` always returns the `display` string and a `sourceDisplayLengths`
array — one entry per source code unit giving the count of display code units it
expands to (so `ß` → `SS` yields `2` at that position, while a length-preserving
character yields `1`). The IFC carries this array onto a leaf **only when the
transform changed the run's length**; a length-preserving (1:1) transform leaves
the leaf without it, because the display string then maps offset-for-offset to
the source and the untransformed fast path is exact.

**The state↔display offset map.** Cursor consumers keep caret, hit-test, and
selection correct across length-changing case mappings by composing
`sourceDisplayLengths` with the existing `measureWidth(display.slice(...))` path
— never a separate measurement codepath, so there is no paint-vs-measure drift
(the class of bug that motivated keeping measurement and paint on one advance
source):

- **Cursor position** remaps a state offset `o` to a display index
  `d = sum(sourceDisplayLengths[0..o])` before measuring the display prefix.
- **Hit-test** reverse-maps a measured display offset back to the nearest state
  code-unit boundary (the cursor never lands inside a single source unit's
  expansion, e.g. between the two `S`s of an upper-cased `ß`).
- **Selection geometry** needs no transform-specific logic — it derives its
  edges from the same remapped cursor-position path.

When the leaf carries no `sourceDisplayLengths` (1:1 transform, or no
transform), these paths are byte-identical to the untransformed case.

**v1 limitations (target: full CSS Text 4).** The case mapping uses the JS
default locale, so locale-tailored mappings are not yet honored (Turkish
dotless-i `i`/`İ`, Greek final-sigma context, Lithuanian accent retention).
`capitalize` uses the per-code-unit post-whitespace boundary above rather than
UAX #29 word segmentation. The expansion model is per-code-unit, so a transform
that reshaped an astral-plane grapheme cluster would map at the code-unit level
rather than the cluster level. A transform that grows a word (e.g. `ß` → `SS`)
does not re-run hyphenation against the grown display text — the IFC clears that
token's hyphen opportunities.

## Unicode algorithm responsibilities

A correct text subsystem implements three Unicode algorithms; in this
engine the work is split between the shaper and the IFC:

- **UAX #29 — Grapheme cluster boundaries.** Defines what a single
  user-visible character is — a base codepoint plus combining marks,
  emoji ZWJ sequences, regional indicator pairs, etc. Used for cursor
  positioning (cursor never lands inside a grapheme cluster) and for
  line-break decisions (don't break inside a cluster). The shaper emits
  cluster boundaries; the IFC and cursor logic respect them.

- **UAX #14 — Line-break opportunities.** Defines where text may wrap:
  after spaces, after hyphens, between CJK ideographs, but not before a
  closing bracket or after an opening one, and never across `GL` glue
  (e.g. NBSP `U+00A0`). **Implemented** as a hand-rolled conformant rule
  engine in `layout/uax14/` (`lineBreakOpportunities(text, {cjBreakable})`
  returns the soft/mandatory break points; rules LB1–LB31 with the §8.2
  number tailoring; passes the full `LineBreakTest.txt` suite). The break
  property table is generated from vendored Unicode data and committed, so
  there is no runtime dependency. The shaper calls the classifier to fill
  its per-token break opportunities; the **IFC** runs the classifier once
  over the assembled inline source text and uses the result as its wrap
  authority (see `1.4.2-ifc.md`). `cjBreakable` selects the CSS
  `line-break` behavior for CJ small-kana (default CJ→NS, i.e.
  `line-break: normal` keeps kana together; flipping it to ID makes them
  breakable). CJK ideographs are class ID and break regardless of
  `cjBreakable`.

- **UAX #9 — Bidirectional algorithm.** Defines how mixed-direction
  text is reordered visually (Arabic/Hebrew with Latin runs, Arabic
  numerals in RTL contexts). The shaper assigns bidi levels per
  cluster; the IFC reorders clusters per line according to UAX #9 L1-L3
  rules. Uniform-direction lines reorder mechanically; mixed-direction
  lines apply the full algorithm.

## Hyphenation

Hyphenation extends UAX #14 with within-word break opportunities driven
by language-specific dictionaries (Knuth-Liang patterns or equivalent).
The shaper exposes hyphenation points per token when the language and
hyphens property request it; the IFC uses them as last-resort breaks
when a line would otherwise overflow.

## Font metrics

The shaper provides per-font-style ascent, descent, x-height, and
line-height values used by the IFC for baseline alignment and by the
painter for glyph positioning. Font fallback (when the requested font
doesn't have glyphs for some codepoints) is the shaper's responsibility
— the engine sees only the resolved metrics.

## Tokenization vs shaping

Two-level processing:

1. **Tokenization** (`text-tokenize`, in the layout module) partitions
   inline content into `Token`s — wrap-units with shared style and
   break-opportunity semantics. Each token comes from one render-node
   run.

2. **Shaping** (the shaper interface, called by the IFC) takes a token
   and produces glyph positions, cluster boundaries, and break
   opportunities for that token. The IFC pre-shapes tokens before
   packing into lines so wrap decisions have widths to work with.

## The legacy measurer

A simpler `TextMeasurer` interface exists in the codebase (width-only:
"how wide is this string in this style?"). It's a sunset path retained
for backwards compatibility while consumers migrate to `TextShaper`.
New code uses `TextShaper`; the engine internally adapts a measurer
to a degraded shaper when only a measurer is available.

## Where the work happens

| Concern | Owner |
|---|---|
| Glyph positioning, cluster boundaries, font metrics | shaper (host) |
| Token construction (wrap units) | `text-tokenize` (layout module) |
| Line-break classification (UAX #14) | `layout/uax14` classifier — called by both the shaper (per-token break opportunities) and the IFC (wrap authority over the assembled inline source) |
| Bidi levels per cluster (UAX #9) | shaper (uniform per-run; full algorithm not yet implemented — P4) |
| Bidi reorder per line | IFC (consumes shaper levels) |
| Cursor positioning within clusters | cursor module + geometry queries (consume shaper boundaries) |
| Hyphenation dictionaries | shaper |
| Hyphenation point selection | IFC (consumes shaper opportunities) |

## Reference

### `TextShaper` interface

```ts
interface TextShaper {
  shape(
    text: string,
    style: Readonly<ComputedStyle>,
    baseDirection: Direction,
  ): ShapedRun;

  measureFontMetrics(style: Readonly<ComputedStyle>): FontMetrics;
}
```

A single `TextShaper` instance is shared across all shape calls in an editor's lifetime. It must be stateless across calls (or maintain only internal caches that don't affect output).

### `ShapedRun`

```ts
interface ShapedRun {
  readonly text: string;
  readonly computedStyle: Readonly<ComputedStyle>;

  readonly clusters: readonly Cluster[];

  readonly ascent: number;
  readonly descent: number;
  readonly lineGap: number;

  readonly minClusterInlineSize: number;        // widest single cluster (paragraph min-content input)
  readonly unbreakableRunInlineSize: number;    // total run inline-size with no breaks (max-content sum input)

  readonly breakOpportunities: readonly BreakOpportunity[];
  readonly bidiLevel: number;                   // 0 = LTR, 1 = RTL, ... (UAX #9)
}
```

### `Cluster`

```ts
type GlyphId = number;

interface Cluster {
  readonly start: number;            // UTF-16 code-unit offset, inclusive
  readonly end:   number;            // UTF-16 code-unit offset, exclusive
  readonly inlineAdvance: number;    // px advance through this cluster
  readonly isLigature: boolean;      // multi-codepoint → one glyph
  readonly glyphs: readonly GlyphId[]; // opaque IDs passed to painter
}
```

A `Cluster` is a **UAX #29 extended grapheme cluster** — one user-visible
character: a base codepoint plus its combining marks, a surrogate-pair emoji, an
emoji ZWJ sequence, or a regional-indicator flag pair are each ONE cluster. The
cursor never lands inside a cluster. Grapheme segmentation runs through
`graphemeClusters` (`layout/graphemes.ts`, an `Intl.Segmenter`-backed walk), which
the mock shaper and `segmentClusters` (feeding the canvas shaper and the
per-cluster paint loop) share. (The legacy `measurerToShaper` adapter, used only
when a host supplies a bare `TextMeasurer` rather than a `TextShaper`, remains
per-code-unit — a `TextMeasurer` exposes only a total width, so per-grapheme
advances are not recoverable from it.)

`start`/`end` are **UTF-16 code-unit offsets that SPAN the grapheme**
(`end - start` is the grapheme's code-unit count, e.g. 2 for a surrogate-pair
emoji). Graphemes are a clustering concept layered over a code-unit address
space: **state offsets stay UTF-16 code units** — a `Cluster` does not introduce a
separate grapheme-ordinal address space. Cursor movement, selection, and deletion
are already grapheme-correct independently (the cursor module steps over whole
graphemes), so they consume cluster boundaries without any code-unit/grapheme
translation layer.

`inlineAdvance` is the cluster's contribution to the run's total inline-size, and
is **one base width per grapheme** — combining marks add 0 to the advance. Real
complex-script glyph metrics (HarfBuzz-quality positioning of marks, ligatures,
and contextual forms) are out of scope; the v1 advance approximation is
`Intl.Segmenter` grouping plus a per-cluster `measureText` (canvas backend) or
fixed mock width.

### `BreakOpportunity`

```ts
interface BreakOpportunity {
  readonly clusterIndex: number;     // code-unit offset; break is BEFORE this position
  readonly kind: "hard" | "soft" | "hyphen";
}
```

`clusterIndex` is a **UTF-16 code-unit offset**, not a grapheme ordinal — it
indexes the same code-unit address space as `Cluster.start`/`end` and state
offsets.

- `hard` — forced break (newline in `pre`/`pre-wrap`/`pre-line`, end of run).
- `soft` — UAX #14 wrap point, computed by the `layout/uax14` classifier (after a space, between CJK ideographs, etc.); never across `GL` glue such as NBSP.
- `hyphen` — within-word break point from a hyphenation dictionary; the IFC inserts a hyphen glyph at the line end if it splits here.

### `FontMetrics`

```ts
interface FontMetrics {
  readonly ascent: number;       // top of glyphs to baseline
  readonly descent: number;      // baseline to bottom of glyphs
  readonly lineGap: number;      // recommended spacing between lines
  readonly capHeight: number;    // for vertical-align: text-top
  readonly xHeight: number;      // for vertical-align: middle
}
```

Returned by `measureFontMetrics(style)` for the line-height calculation; also embedded in every `ShapedRun` for the run's specific font.

### Tokenization (`text-tokenize.ts`)

```ts
function tokenize(text: string, whiteSpace: WhiteSpace): string[];
```

Partitions a text string into wrap-units. Whitespace handling per `whiteSpace` mode:

| `whiteSpace` | Behavior |
|---|---|
| `normal`, `nowrap` | Trim text; collapse runs of whitespace to single space; alternate word / space tokens. |
| `pre`, `pre-wrap`, `break-spaces` | Preserve all whitespace; emit `LINE_BREAK` sentinel between newline-separated segments. `break-spaces` additionally emits each preserved space as its OWN token (not slurped into the preceding word), so spaces are distinct wrap units. |
| `pre-line` | Per-line: collapse whitespace within each line; insert `LINE_BREAK` between lines. |

The IFC consumes the resulting array, looking up each token's shaped width and break opportunities via the shaper.

**Trailing-space HANG + CLAMP (the editor's `break-spaces` body default).** Matching Google Docs, a trailing space at a soft-wrap boundary HANGS rather than wrapping: in the IFC greedy wrap loop a *space* unit never triggers its own wrap (only word / inline-block units wrap), so a lone trailing space stays at the line end and only the next *word* wraps. A hung space is then CLAMPED — its laid-out box `inlineOffset`/width are pinned to the line's content edge (the fit cursor still advances by the natural width, so a following word still wraps), and the caret resolver clamps within each leaf's own box — so for *any* number of trailing spaces no glyph and no caret is placed past the content edge (the property the reverted `pre-wrap` hang lacked). The per-space state offsets are unchanged (each space is still one character); only the physical x stops at the edge. This is an intentional word-processor deviation from literal CSS `break-spaces` (which wraps each space) — principle 7 over principle 6 for this editing-shape question.

### Implementation choices for the canvas backend

The default canvas-shaper is described in [`2.4-canvas-shaper.md`](../2-dom/2.4-canvas-shaper.md). Key implementation choices:

- **Glyph positioning + advance widths.** Browser canvas `measureText` and `fillText` — delegates to the browser's underlying shaper (HarfBuzz on Chrome / Firefox).
- **Cluster boundaries (UAX #29).** `Intl.Segmenter` with `granularity: "grapheme"` (via `graphemeClusters`) groups codepoints into extended grapheme clusters — base + combining marks, surrogate-pair emoji, ZWJ sequences, and regional-indicator flags. Each cluster's `inlineAdvance` is one per-cluster `measureText` (combining marks add 0); spanning grapheme metrics from a full shaper are out of scope for v1.
- **Bidi levels (UAX #9). [TARGET]** Target: hand-rolled L1-L3 per-cluster level assignment from script + paragraph base direction. Shipped v1 emits a single uniform level per shaped run, derived from the run's base direction — mixed-direction reordering within a run is not yet performed.
- **Break opportunities (UAX #14). [IMPLEMENTED]** `shape()` calls `toBreakOpportunities` — the canonical adapter (in `layout/text-shaper.ts`) over the `layout/uax14` classifier `lineBreakOpportunities`, a hand-rolled conformant rule engine on a committed line-break property table — for whitespace-, punctuation-, and CJK-aware breaks (mandatory→`hard`, soft→`soft`). All three shaper backends route through this one adapter so the kind-mapping can't drift. Hyphenation breaks remain a separate, not-yet-wired concern (see below).
- **Hyphenation.** Future plan integrates a hyphenation dictionary (Knuth-Liang patterns; e.g., the `hypher` library or hand-rolled). Pattern format: per-language tables loaded async; the shaper exposes them via `BreakOpportunity` of kind `"hyphen"` when `style.hyphens === "auto"` and the document declares a language.
- **Font fallback chain.** Browsers manage fallback automatically when the requested font lacks glyphs; the canvas shaper's `fillText` benefits from this transparently. Custom font fallback (for non-browser hosts) is a separate concern.

### Mock backend

`createMockShaper(charWidth, lineHeight)` returns a deterministic `TextShaper` for tests:
- Every cluster has the same `inlineAdvance`.
- Cluster boundaries are UAX #29 grapheme boundaries (via `graphemeClusters`), so a surrogate-pair emoji or a base+combining-mark sequence is one cluster with `charWidth` advance, not one per code unit.
- Break opportunities come from the real `layout/uax14` classifier (the same one the canvas shaper uses), so the mock wraps after spaces, between CJK ideographs, etc. — not a bespoke "every space" heuristic.
- Bidi level is always 0.
- Font metrics are derived from `charWidth` and `lineHeight`.

### Performance contracts

- `shape(text, style)` cold: O(L) where L is `text.length`.
- The shaper may cache per-`(text, style)` calls internally; downstream consumers (IFC) further cache via `IFCStateCache` so repeated paragraphs don't re-shape.
- `tokenize`: O(L).
