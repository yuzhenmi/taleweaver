# 1.9 — `decorations/` and position mapping (view-only overlays)

Decorations are **view-only** marks a host computes from document state and hands to a
backend controller: a mention highlight, a spelling/grammar squiggle, a search hit, ghost
text, a flagged paragraph. They are never stored in the document, the undo history, the
clipboard, or serialization. Core owns their *model* (types, block index, how they ride
through edits); each backend owns *drawing* and *pointer events*.

Decorations deliberately do **not** enter the render tree. Splitting `TextBox`es at
decoration edges would add wrap/shaping seams in `print`'s IFC (a decoration boundary
must never change line breaking or kerning), so backends draw them on top of their own
output instead (see the backend docs).

## Types (`decorations/decorations.ts`)

```ts
type Decoration = InlineDecoration | WidgetDecoration | BlockDecoration;

interface DecorationAttrs {
  style?: DecorationStyle;              // engine-drawn by EVERY backend
  class?: string;                       // DOM backends only
  attributes?: Record<string, string>;  // DOM backends only (engine-owned names refused)
}
interface DecorationStyle {
  backgroundColor?: string;
  underline?: { color?: string; style?: "solid" | "wavy" | "dotted" | "dashed" };
}
// every decoration: { id: string; data?: unknown } & DecorationAttrs
interface InlineDecoration { kind: "inline"; from: Position; to: Position; inclusiveStart?; inclusiveEnd? }
interface WidgetDecoration { kind: "widget"; at: Position; side?: -1 | 1; text?: string; toDom?(doc): Node }
interface BlockDecoration  { kind: "block"; blockId: BlockId }
```

`id` and `data` are host identity reported back on pointer events; the engine never
interprets them. A widget occupies **zero** offsets: the caret skips it and copy never
includes it. `side` places a widget after (`1`, default) or before (`-1`) its position — a
caret at the position sits after side `-1` widgets and before side `1` widgets — and is
its mapping assoc.

**Decorations over document marks.** A host mark (e.g. a `mention`, see
[`1.3-cascade.md`](./1.3-cascade.md) "Inline marks") is document content; its look comes
from the mark's `toStyle` / `toDom`. Hover / click behaviour is attached with
decorations: compute inline decorations from `getMarkRanges(state, type, registry)` (carrying the
mark's value in `data`) and pass them to the controller — the pointer events then report
the mark under the pointer on both backends.

## `DecorationSet`

`createDecorationSet(state, decorations)` validates each decoration against `state`
(unknown block, offset out of range, inverted/empty range, endpoints in different
selection contexts → dropped, so a stale host result never breaks the editor) and
indexes it per block: `forBlock(id) → { inline: InlineSegment[]; widgets; block }`, a
multi-block inline range contributing one `[start, end)` segment per leaf block.

- `mapDecorationSet(set, mapping, nextState)` carries a set through one transition.
  Inline edges map with assoc from `inclusiveStart`/`inclusiveEnd` (exclusive by
  default: typing at an edge does not extend); a range that collapses disappears; a
  widget whose position is unmappable disappears; a block decoration whose block was
  removed disappears. Only decorations indexed in the transition's dirty blocks
  (`mapping.dirty`) are re-mapped and re-indexed: the set's index is an overlay chain
  (each mapping layers its touched blocks over the previous set; flattened past a
  bounded depth), so a keystroke costs O(decorations in the edited blocks).
- `changedDecorationBlocks(a, b)` — blocks whose drawn decorations differ. Comparison is
  by VALUE (id, offsets, visual attrs; `data` excluded), so a host that rebuilds an
  equal set every change re-draws nothing. When `b` was mapped from `a` (or both are
  merges of such layers) only the mapping's touched blocks are compared.
- `mergeDecorationSets(sets)` — a read-only union drawn in order (later layers nest
  inside earlier ones).
- `patchDecorationSet(set, state, blocks, decorations)` — replace exactly the
  decorations drawn in `blocks` (an incremental per-block recompute, e.g. find matches
  re-found in the edited blocks); everything else is reused.
- `mapDecorations(list, mapping, next)` — map a plain decoration list (a host result
  computed against an older State) before indexing it.
- `decorationsAt(set, position)` — hit query for pointer handling.

## Layers (`decorations/decoration-layers.ts`)

`createDecorationLayers()` is the per-controller bookkeeping both backends share. Layers
draw bottom-to-top: suggestion highlights, host suggestion-group styling, comment
highlights, find highlights, host decorations. `advance(prev, next)` carries the host and find layers through each
transition by position mapping. Comment ranges are delimited by marker characters, so
they map exactly too (end edge inclusive: text typed before the end marker is inside the
comment); the comment layer is re-resolved from the document only when an edit adds,
removes or moves a marker. The suggestion layer is re-resolved when an edit touches a
tracked run (a document scan — see the `ponytail:` note; an incremental per-block index
is a tracked follow-up). A text-identical change (formatting, accepting/rejecting a
suggestion) maps as identity but still re-checks those two layers. `patchFind` redraws only the find highlights of given blocks (the
find session's incremental refresh). `merged` is what a
backend draws. `advance(prev, next, mapping?)` maps through `transitionMapping`, which
composes the `lastChange` chain back to `prev` (see "Batched transitions" below); only a
jump past the bounded chain maps as UNKNOWN (decorations dropped, never misplaced).

**Suggestion groups styled by the host.** `suggestionGroupDecorations(state,
styleOf)` returns an inline decoration over every live range of every open suggestion
group for which `styleOf(group)` gives a look (class / style / attributes — e.g. a
colour per `metadata.source`); `data` is the group. The built-in suggestion visuals
(author colour, insertion underline, deletion strike) remain the defaults underneath.
A host does NOT feed snapshots of it into the host layer (they would go stale on
accept / reject / undo): `DecorationLayers.setSuggestionStyles(state, styleOf | null)`
keeps a live layer, re-derived from the document on every transition that touches a
tracked run or the suggestion records (the records' side table surfaces the root as
dirty) and position-mapped otherwise. Each setter (`setComments`, `setSuggestions`,
`setSuggestionStyles`) re-derives ONLY its own layer, and `advance` re-derives each
layer only when its own trigger fires. Both controllers expose it as
`setSuggestionStyles(styleOf)` (React: the `suggestionStyles` prop).

**Built-in highlights are decorations.** `findHighlightDecorations`,
`commentHighlightDecorations`, `suggestionHighlightDecorations`
(`builtin-highlights.ts`) express find / comment / suggestion highlights as inline
decorations with ids `tw-find:*`, `tw-comment:*`, `tw-suggestion:*`, classes
`tw-find[-active]` etc. and the canonical fills — one drawing mechanism for everything.

## Position mapping (`state/position-mapping.ts`)

```ts
createPositionMapping(prev: State, next: State, dirtyIds, hint?, nextHint?): PositionMapping
interface PositionMapping {
  identity: boolean;
  dirty: ReadonlySet<BlockId> | null;   // the transition's dirty blocks (null = unknown)
  map(position, assoc?: -1 | 1): { position: Position | null; deleted: boolean };
  touches(from, to): boolean;   // did the transition change content inside [from, to]?
}
transitionMapping(prevEditor, nextEditor): PositionMapping   // decorations/ helper
```

The mapping is a **text diff over the transition's dirty leaf blocks**: their texts
(embeds as U+FFFC), read in document order from each state and joined with a
separator, are diffed: common prefix and common suffix, both stopping at the edit
hints — `hint`, a prev-coordinate position the edit touches (the prev selection start),
and `nextHint`, the same in next coordinates (the post-edit caret) — so an edit inside
repeated text resolves to the side it happened on ("aa|a" + "a" inserts at 2; Backspace
in "xo|o" deletes [1, 2); deleting " Berlin" from "in Berlin" with the caret elsewhere
keeps the first "n"). Hints are best-effort: actions that edit away from the caret
(replace-all, find-bar replace, foreign changes, suggestion accept/reject) leave hints
that only widen the diffed middle. The middle gets a bounded character-level Myers
diff; past the distance bound (many scattered edits, e.g. replace-all inside one long
paragraph) it is diffed again at WORD-token level, which needs far fewer edits; only if
that also exceeds the bound does it fall back to one replacement hunk. When the
transition kept the same leaf blocks in the same order (no split / merge / insert /
remove), each block is diffed on its own, so edits spread over many blocks are bounded
per block rather than in total; the joined cross-block diff is used only when text can
move between blocks.

Positions map through the hunks with ProseMirror's assoc semantics. Because the mapping
compares text rather than replaying operations it is uniform across every source of
change — typing, deletes, block split/merge (text moving to another block), paste,
undo/redo and foreign (collaborative) updates — and formatting-only edits are identity.
Yjs `RelativePosition` cannot follow content into a new block (a split/merge recreates
it), which this handles.

The PREV state's block text is read through `peekBlock` (cache-only; a superseded
State's Y.Doc has already been mutated, so a cold read would return new content). A
dirty block whose previous snapshot is not cached is left out of both diffed regions and
positions in it map to `{ position: null, deleted: true }` — conservative, never wrong
text. Local edits are always warm (the reducer reads the blocks it edits before
mutating them); a foreign change can hit a cold block. Two things keep the blocks that
matter warm: the reducer re-reads the selection's blocks after every action, and an
anchor re-reads its blocks on creation and after each remap — so the caret and every
anchored range map exactly even through a foreign change to an off-screen paragraph.

Cost: linear in the dirty leaf blocks' text (one paragraph per keystroke) plus a bounded
diff; computed only when something needs mapping.

**Batched transitions.** `EditorState.lastChange` is a bounded chain of the recent
document changes (`DocumentChange { from, dirtyIds, prior, depth }`, trimmed past
`MAX_CHANGE_CHAIN`), so `transitionMapping(prev, next)` walks back to the change made
from `prev.state` and diffs `prev.state` → `next.state` ONCE over the union of the
changes' dirty blocks — reading only the two endpoints (prev via the peek, next live),
never a superseded intermediate State — so a host that batches several dispatches before
handing the controller a state still maps every decoration. Only a
jump longer than the chain (or across a wholesale replacement) maps as unknown.

### Mapping log (`editor/mapping-log.ts`)

`createMappingLog(capacity)` keeps a controller's recent transitions (`reset(state)`,
`record(from, to, mapping)`); `mappingFrom(olderState)` composes every mapping since it
(`composeMappings`), or returns `null` once that State has aged out. Controllers use it
for `setDecorations(decorations, basedOn)`: a host result computed against an older
State is mapped through the edits made meanwhile, or dropped when unmappable.


## Anchors (`editor/anchors.ts`)

A host computing something asynchronously (a check, a suggestion service) anchors its
input and later reads where it is now. `createAnchorSet()` — one per controller — holds
live `Anchor { from, to, deleted, changed, disposed, dispose() }`:

- `create(state, from, to?, { inclusive?, assoc? })`: a range (edges map with assoc
  from = +1 / to = −1, so text typed at an edge stays outside; `inclusive` flips them)
  or a point (`assoc`, default +1).
- `createAt(log, current, version, from, to?, options)`: the positions refer to an OLDER
  version; mapped through the controller's `MappingLog` first. Null when the version has
  aged out or the content is already gone; the anchor starts `changed` when the range was
  edited since that version.
- `advance(prev, next, mapping)` — called by the controller with the transition's mapping
  (the same one the decoration layers use) — visits only the anchors indexed under the
  mapping's dirty blocks (every anchor on an unknown mapping). Each anchor is indexed
  under EVERY leaf block its span covers (computed with `iterateSpan` on creation and
  again only when an end moves to another block or the transition touched a block it is
  not indexed under — a block inserted / removed inside it), so an edit in a middle
  paragraph of a multi-block range reaches it while a keystroke elsewhere costs nothing:
  O(anchors in dirty blocks) per keystroke (counter `anchors.remapped`). `deleted` (sticky; the anchor leaves the set): an edge
  could not be mapped, a point lost the content on BOTH of its sides (deleting only the
  next character keeps it), or a non-empty range collapsed (all of its content removed).
  `changed` (sticky): when the mapping `touches` the range, its text is compared with the
  text at creation — formatting-only edits and type-then-delete do not count.

`mapPositionFrom(log, current, version, position, assoc)` maps a bare position from an
older version (`{ position, deleted }`, or null once aged out of the log's 512 transitions
or across a document replacement). Both controllers expose these as `version`,
`mapPosition(position, version, assoc?)` and `createAnchor(from, to?, { …, basedOn? })`.

## Foreign (collaborative) changes

Peers are separate Y.Docs synced by Yjs updates (the provider model; `getYDoc(state)`
gives a provider the Y.Doc). `subscribeRemoteChanges(state, cb, onIncompatible,
onCompatible?, { startHalted? })` reports
every transaction applied to the doc from outside (`!transaction.local`, i.e.
`Y.applyUpdate`) with its dirty blocks (a side-table-only change dirties the root); local
edits, undo / redo and suggestion resolution are local transactions and never reported. A
remote transaction carrying legacy inline storage goes to `onIncompatible(blockIds)`
instead, and the controller halts (1.5 "Incompatible documents"); the subscription then
reports nothing until a transaction — remote, or a local one (the host upgrading the
shared doc itself) — leaves the document compatible, which calls `onCompatible()` once. Every controller subscribes for that shape check, also one that
does not apply peer changes (`remoteChanges: "ignore"`). Selection rebasing
snaps every rebased endpoint to a grapheme-cluster boundary. Both controllers
subscribe to their document's Y.Doc and dispatch `APPLY_FOREIGN_CHANGE { dirtyIds }`
(digital to itself; print to its host, which owns the state) — synchronously from Yjs
`afterTransaction`, inside the provider's `Y.applyUpdate` call, so a host dispatch must
be re-entrancy-safe and must not forward updates from inside it (or must defer).
Exactly one controller per document observes remote changes (`remoteChanges:
"observe"`, the default); any other controller over the same document passes
`"ignore"`. Its reducer arm
(`editor/foreign-change.ts`) reconciles the state (`reconcileForeignChange`: fresh
snapshot of the dirty blocks, `lastDirtyIds`, `lastChange`) and REBASES the selection
through the transition mapping (endpoint order read cache-only from the superseded
State — never its live Y.Doc) — a collapsed caret with assoc −1 (a peer typing exactly at
the caret does not push it), a range keeping its content (from +1, to −1); an unmappable
endpoint goes to the nearest valid position (same block clamped → the previous surviving
sibling's end → the next one's start → document start); endpoints that end up in
different contexts collapse to the focus. The action is undo-inert (a peer's change is
never in the local undo history and never splits a local typing group). Then the usual
per-transition work runs: decorations, anchors, triggers and the mapping log advance;
the backend repaints / patches only the dirty blocks.
