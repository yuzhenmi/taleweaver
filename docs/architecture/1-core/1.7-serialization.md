# 1.7 — Document serialization

This module turns a document `State` into bytes (or text) and back. It is the
engine's **encode → wire** and **wire → decode** boundary; the host owns where
those bytes live (a database row, a file, a network frame). The engine does not
read or write storage — it only (de)serializes.

Serialization is pluggable: one `DocumentSerializer` per wire format, looked up
in a `SerializerRegistry` by a stable format id. The default built-in is a
**lossless binary** serializer backed by Yjs's native update format; a
human-friendly, hand-authorable **`taleweaver-json`** serializer ships alongside
it (host-registered, not default-registered — see below).

### Fidelity tiers

The engine ships three serializers at three fidelity tiers — pick the one whose
trade-off the use-case wants (see also the **clipboard fragment helpers** below for
the clipboard-specific encode/decode paths that feed the `PASTE` action):

- **`taleweaver-binary`** — *lossless-CRDT.* Captures the whole `Y.Doc`
  (every block tree, every side-table, the meta map, CRDT update structure).
  The interchange / save format; the only one that round-trips tables and
  preserves Yjs identity.
- **`taleweaver-json`** — *lossless-document-model-EXCEPT-tables.* A readable,
  hand-authorable nested-tree JSON over the full document model (all three block
  trees + every side-table), id-optional for authoring. Tables THROW (the binary
  serializer is the lossless escape; JSON table round-trip is roadmapped).
- **`taleweaver-html`** — *semantic + interop.* A Google-Docs-complete prose +
  list **+ table** subset for authoring/seeding and clipboard interop. Mints fresh
  ids (not id-preserving); drops comments/suggestions. Lives in `core`'s
  `state/serialize/` alongside the json/binary peers. ENCODE is pure; DECODE
  parses through an INJECTED `HtmlParser` over the DOM-free `HtmlNode` interface
  (a browser host supplies a `DOMParser`-backed adapter), so core references no
  DOM type. Table decode builds a nested `table → table-row → table-cell`
  `ContainerBlockNode` subtree (the inverse of the encoder): `<thead>`/`<tbody>`/
  `<tfoot>` flatten into the row sequence, a LEADING `<thead>` sets `headerRowCount`,
  `<colgroup>` `%` widths become `columnWidths`, `colspan`/`rowspan` become per-cell
  attrs, and mixed inline+block cell content is recovered (bare text wrapped in
  paragraphs). The `HtmlNode` seam exposes the two inline-style props decode reads —
  `textAlign` and `width` (for `<col>`). Round-tripping pasted HTML to real table
  blocks is the engine half; wiring a rich-clipboard paste path that feeds it is a
  separate (browser-gated) concern.

## Why it lives inside `state/`

The serializer consumes and produces `State`, and the binary serializer needs the
raw underlying `Y.Doc`, which lives behind the module-private `STATE_INTERNAL`
symbol (see [`1.1-state.md`](./1.1-state.md) and `state/state-internal.ts`). That
symbol is deliberately NOT re-exported from the `state/` barrel — the whole Yjs
encapsulation depends on it. Every legitimate consumer
(`build-state-from-blocks.ts`, `list-defs.ts`, `initial-state.ts`) reaches the
`Y.Doc` by a relative sibling import of `state-internal`. The serialize module
does the same: it lives at `state/serialize/` and imports
`STATE_INTERNAL` by sibling path. A `serialize/` directory OUTSIDE `state/` could
not legally reach the doc. The serialize barrel's public surface is re-exported
through `state/index.ts` (and onward through the core barrel); `getMetaRootId`
(the meta-map read the binary decoder uses) stays state-private.

## The `DocumentSerializer` contract

```ts
type SerializedDocument = Uint8Array | string;

interface DocumentSerializer<TWire extends SerializedDocument = SerializedDocument> {
  readonly format: string;                 // stable format id; the registry key
  encode(state: State): TWire;
  decode(source: TWire): State;
}
```

`encode` / `decode` are INVERSES for round-trippable formats — the binary
serializer is exactly lossless. `SerializedDocument` is `Uint8Array | string`:
binary for the Yjs-native format, text for a future human-friendly format.

Dependencies a serializer needs (e.g. an `IdAllocator` for a future structured
text decoder) are injected at CONSTRUCTION — a factory closing over them — NOT
passed per call. That keeps the interface a clean two-method contract and keeps
per-call sites (the engine dispatch below) dependency-free.

## The registry

`SerializerRegistry` mirrors the component and attribute registries: a small
interface over a `Map`, keyed by `serializer.format`, with two factories.

```ts
interface SerializerRegistry {
  register(serializer: DocumentSerializer): void;
  get(format: string): DocumentSerializer | undefined;
  has(format: string): boolean;
}

createSerializerRegistry(): SerializerRegistry          // empty — tests isolate behavior
createDefaultSerializerRegistry(): SerializerRegistry   // pre-registers the binary serializer
```

`register` stores by the serializer's own `format`. A
`DocumentSerializer<Uint8Array>` is assignable to the registry's
default-generic `DocumentSerializer`, so the binary serializer registers without
ceremony.

## Engine-level dispatch

Two pure functions look up the serializer for a `format` and delegate. They are
the engine entry points the host calls.

```ts
serializeDocument(state: State, format: string, registry: SerializerRegistry): SerializedDocument
deserializeDocument(source: SerializedDocument, format: string, registry: SerializerRegistry): State
```

When `format` is not registered, both throw `UnknownSerializerFormatError`
(carrying the offending `format`). A serializer's `decode` may additionally throw
`MalformedDocumentError` for structurally-invalid wire data.

## The v1 Yjs-binary serializer

`createBinaryDocumentSerializer()` returns the `DocumentSerializer<Uint8Array>`
registered under `BINARY_FORMAT` (`"taleweaver-binary"`).

State is Yjs-native, so the round-trip is a thin shell over Yjs's update codec:

- **encode**: `Y.encodeStateAsUpdate(doc)` captures the ENTIRE `Y.Doc` — all
  three block trees (`blocks` / `embedContents` / `templateContents`), the
  `listDefs` config side-table, the `comments` side-table, and the `meta` map
  (which carries the immutable `rootId`) — into one `Uint8Array`. Because comment
  threads live in the `comments` map AND each comment's range is delimited by
  `comment-start` / `comment-end` marker embeds in inline content, capturing the
  whole `Y.Doc` round-trips comments AND their anchors losslessly with no
  comment-specific serializer code.
- **decode**: `Y.applyUpdate(freshDoc, update)` rebuilds that doc exactly, then
  the decoder reads `rootId` via `getMetaRootId(doc)` and calls
  `createState({ rootId, doc })`. `createState` is idempotent on already-seeded
  meta, and the freshly-decoded `State` correctly starts with an EMPTY snapshot
  cache — the cache is a derived read-side structure over the `Y.Doc`, not part
  of the serialized document.

`getMetaRootId` returns `undefined` when the decoded doc carries no (valid)
`rootId` — e.g. a bare `Y.Doc` that never seeded one. The decoder turns that into
a `MalformedDocumentError`, the one structural-validity check it owns. (Raw
garbage bytes are a different failure: `Y.applyUpdate` may throw a Yjs-internal
error before the rootId check is even reached.)

The **v1** update codec (`encodeStateAsUpdate` / `applyUpdate`) is used, not v2 —
v1 is the interchange unit Yjs's own ecosystem (the `y-*` bindings) treats as
stable.

### Round-trip guarantee + format stability

`decode(encode(state))` reconstructs a `State` structurally equal to the input
across every block in all three trees (each block's `type`, `attrs`,
parent/sibling/child links, and `inlineContent` — text items with attrs, embed
items with `embedType` + `properties`, including the `comment-start` /
`comment-end` marker embeds), the `listDefs`, the `comments` thread records, and
`rootId`. A round-tripped comment's range re-resolves to the same live (non-orphaned)
span because its markers travel with the content. The per-State snapshot cache is
intentionally NOT preserved (it is derived).

`BINARY_FORMAT` is a STABLE id. A future format change ships a NEW id; old bytes
are never reinterpreted under a different meaning. This is what lets a stored
document name its format and decode unambiguously years later.

## The `taleweaver-json` serializer

`createJsonDocumentSerializer({ allocator, blockKindResolver })` returns the
`DocumentSerializer<string>` registered under `JSON_FORMAT` (`"taleweaver-json"`)
— a readable, hand-authorable JSON document format that is lossless for the whole
document model EXCEPT tables.

### Kind-driven nested-tree schema

The wire form is a NESTED tree (`JsonNode`), not the flat id-keyed block records
State stores. Parent / sibling / child pointers are DERIVED from nesting + array
order on decode (never stored). Which payload a node carries is decided by the
block's KIND — resolved through the injected `blockKindResolver` (typically the
component registry):

- **container** → a `children: JsonNode[]` array (ALWAYS present, even `[]`); no
  `content`.
- **inline-bearing-leaf** → a `content: JsonInlineItem[]` array (ALWAYS present,
  even `[]`); no `children`.
- **atomic-leaf** → NEITHER `content` NOR `children`.

This kind-driven split is the ONLY thing that distinguishes an empty paragraph
(`inlineContent: { items: [] }`) from an empty container or an atomic leaf (both
`inlineContent: null`). On decode the block's `inlineContent` is reconstructed
PURELY from its KIND — never from the presence of the `content` key — so the
distinction survives a round-trip. A `JsonInlineItem` is either a styled text run
(`{ text, attrs? }`) or an embed marker (`{ embed, attrs?, props? }`).

### Id-optional authoring path

`JsonNode.id` is OPTIONAL: present → preserved verbatim (the lossless,
id-preserving round-trip); absent → MINTED via the injected `IdAllocator` on
decode (the hand-authoring path — a human writes a tree with no ids and the
decoder assigns them while deriving the links). Decoding the same id-less JSON
twice yields distinct ids but identical structure.

### Lossless EXCEPT tables

Tables carry grid / span geometry the flat JSON tree cannot represent
losslessly. A `table` / `table-row` / `table-cell` block THROWS on encode (a
clear error pointing at the binary serializer) and a table-typed node THROWS
`MalformedDocumentError` on decode. The match is an EXACT type-set, NOT a prefix:
`table-of-contents` is an atomic leaf, not a table, and round-trips. The binary
serializer is the lossless escape for table-bearing documents; a JSON table
round-trip is roadmapped.

### Side-tables + embed / template body trees

The top-level `JsonDocument` envelope carries `format` + `version` + `root`, plus
optional top-level keys (omitted when empty): `embedContents` / `templateContents`
(each a FOREST of nested-tree roots — footnote / header / footer bodies) and the
three side-tables `listDefs` / `comments` / `suggestions` (each an id-keyed
record map). Comment / suggestion records are written as BARE records: the
host-derived `range` / `orphaned` fields are STRIPPED on encode (a comment's range
re-resolves from its round-tripped `comment-start` / `comment-end` marker embeds;
a suggestion's range re-resolves from its id-tagged inline items), and on decode
each record is built from its VALIDATED named fields only (id taken from the map
key) — a stray `range` / `orphaned` / `id` in hand-authored JSON cannot ride
along.

### Ingress validation

Decode is an INGRESS surface for hand-authored JSON, so it validates field by
field and throws `MalformedDocumentError` on any mismatch rather than crashing
raw or accepting a corrupt record: a malformed envelope (wrong `format`/`version`,
missing `root`); a structurally-invalid node (non-string `type`, table type,
non-array `children`/`content`); a malformed `listDefs` level (non-array `levels`,
invalid `style`/`restart`, missing `start`); a malformed `comments` record
(non-string `author`/`body`, non-number `createdAt`, non-boolean `resolved`,
non-array `replies`, a malformed reply); a malformed `suggestions` record (a
`kind` outside the `insertion`/`deletion`/`formatting` union, missing `author`,
non-object `proposedAttrs`).

### Host-registration rationale

This serializer is HOST-registered, NOT default-registered (it is absent from
`createDefaultSerializerRegistry`). Its `decode` needs a `blockKindResolver` (to
classify each block type's KIND) and an `IdAllocator` (to mint ids for id-less
nodes). The block-kind classifier lives in the COMPONENT registry, which sits
ABOVE `state` in the layering; default-registering this serializer inside the
state-module registry would invert that `components → state` dependency. The host
constructs it with its own resolver + allocator and registers it explicitly.

### Public types

`JsonNode` / `JsonInlineItem` / `JsonDocument` (the wire schema),
`createJsonDocumentSerializer` (the factory), and `JSON_FORMAT` (the stable
format id). `JSON_FORMAT` is a STABLE id on the same terms as `BINARY_FORMAT`: a
future schema change ships a new id rather than reinterpreting old JSON.

## Clipboard fragment helpers

These live in `core/state/serialize/` alongside the document serializers and are the
encode/decode half of the clipboard pipeline (the other half — `extractFragment` /
`insertFragment` — lives in `state/ops/`; see
[`1.5-editor.md`](./1.5-editor.md#clipboard-and-paste)).

### `base64.ts` — runtime-agnostic codec

`bytesToBase64(bytes: Uint8Array): string` and
`base64ToBytes(b64: string): Uint8Array | null`.

Hand-rolled over the standard base64 alphabet on `Uint8Array` (3-byte → 4-char
groups with `=` padding); does NOT use `btoa`/`atob` (DOM-only) or `Buffer`
(Node-only), so it runs in any JS runtime — browser, Node, worker. `base64ToBytes`
returns `null` on malformed input (wrong alphabet character, misplaced padding) and
never throws. Used by `encodeFragmentClip` / `decodeFragmentClip` below.

### `fragment-clip.ts` — lossless clipboard flavor

```ts
const TALEWEAVER_CLIP_MIME = "application/x-taleweaver-clip";

encodeFragmentClip(fragment: State): string    // binary-serialize → base64
decodeFragmentClip(clip: string): State | null // base64 → binary-deserialize; null on malformed
```

`TALEWEAVER_CLIP_MIME` is the private clipboard MIME type written by `copy`/`cut`
and read back by `paste`. Within the same browser session, Chromium and Firefox
round-trip custom MIME types via `clipboardData.setData/getData`, so this flavor is
the primary internal-clipboard path.

`encodeFragmentClip` calls `createBinaryDocumentSerializer().encode(fragment)` then
`bytesToBase64`. `decodeFragmentClip` calls `base64ToBytes` (returns `null` on
malformed input → fall through to the next flavor) then
`createBinaryDocumentSerializer().decode`. Because the fragment is a full `State`
assembled by `extractFragment` (see [`1.5-editor.md`](./1.5-editor.md#clipboard-and-paste)),
the binary encode captures the whole Y.Doc — blocks + embedContents + listDefs +
suggestions — so footnotes, images, list identity, and pending suggestion state all
round-trip losslessly in DIRECT-mode paste.

### `html-decode.ts` — HTML whitespace collapsing

`decodeHtml` applies CSS `white-space: normal` semantics to text-node data during
the `accumulateNode` text-node accumulation phase: runs of ASCII whitespace
(space/tab/newline/CR/FF) are collapsed to a single space; whitespace-only text
nodes that sit between block-level elements are dropped; `<br>` (hard-break embed)
and explicit tab embeds are preserved. This is a correctness requirement for
cross-app paste — Word, Google Docs, and web HTML carry inter-tag newlines and
indentation that would otherwise land as literal whitespace runs. The `decodeHtml`
signature is unchanged; the collapsing is an internal behavior change only.

## Editor-level open / save surface

The engine dispatch above operates on a bare `State`. The editor layer wraps it
with `exportDocument` / `loadDocument` (in `editor/document-io.ts`, re-exported
from the core barrel) — the convenient "save the current document" / "open a
document" operations a host actually calls. See
[`1.5-editor.md`](./1.5-editor.md#document-load--save) for the full contract; in
brief:

```ts
exportDocument(editor: EditorState, format: string, registry: SerializerRegistry): SerializedDocument
loadDocument(source: SerializedDocument, format: string, registry: SerializerRegistry, config: EditorConfig): EditorState
```

`exportDocument` is a thin pass-through to `serializeDocument(editor.state, …)`.
`loadDocument` is the editor-level "open document": it `deserializeDocument`s the
bytes, derives a valid initial caret (`initialSelectionForState`), and builds a
FRESH `EditorState` (a fresh `History` bound to the loaded `State` + a full
render/cascade/layout) via `createEditorStateFromState`. Both surface the
serializer's `UnknownSerializerFormatError` (unregistered format) and, for load,
`MalformedDocumentError` (invalid wire data). Editor-session view state beyond
the caret (scroll position, etc.) is NOT part of this surface — that is the
named follow-up below.

## Host-owns-persistence boundary

The engine's responsibility ends at `Uint8Array` / `string`. Saving, loading,
chunking, compression, and transport are the host's. This keeps the engine
runtime-agnostic (no filesystem, no network) and lets different hosts (a desktop
shell, a server, a browser app) make their own storage choices over the same
wire format.

## Named follow-ups (future, not degraded splits)

- The **editor-level export/import wrapper** has shipped as `exportDocument` /
  `loadDocument` (see the "Editor-level open / save surface" section above and
  [`1.5-editor.md`](./1.5-editor.md#document-load--save)). `loadDocument` already
  derives a valid initial caret; pairing the wire document with the REST of
  editor-session view state (scroll position, selection beyond the initial caret)
  for a complete save/restore remains a future addition.
- A **human-friendly HTML serializer** has SHIPPED — the `taleweaver-html`
  `DocumentSerializer<string>`, a readable AUTHORING/seeding format over a
  Google-Docs-complete prose + list + table subset. It lives in `core`'s
  `state/serialize/` (the third peer of json/binary). ENCODE is a pure `State` →
  HTML-string walk; DECODE parses HTML through an INJECTED `HtmlParser` over the
  DOM-free `HtmlNode` interface (`state/serialize/html-node.ts`) and lowers the
  parsed tree to a declarative `BlockNode` tree via the core
  `buildDocumentFromTree` primitive — so core references no DOM type and stays
  headless. A browser host supplies the `DOMParser`-backed adapter
  (`browserHtmlParser`, in `@taleweaver/print`). Round-trip fidelity is SEMANTIC,
  not id-preserving (this format mints fresh ids; the binary serializer above is
  the lossless, id-preserving path).
  The human-friendly `taleweaver-html` serializer DROPS comments + their markers
  (it is an authoring format); the binary AND `taleweaver-json` serializers
  round-trip them.
- A **diff-friendly, hand-authorable JSON serializer** has SHIPPED — the
  `taleweaver-json` `DocumentSerializer<string>` (see "The `taleweaver-json`
  serializer" above): a kind-driven nested-tree JSON, id-optional for authoring,
  lossless over the full document model EXCEPT tables (which throw — the binary
  serializer is the lossless escape; a JSON table round-trip remains a future
  addition).
- **v2 / migration**: when the document model changes shape, a new format id plus
  a decode path that upgrades old bytes — never an in-place reinterpretation of
  the v1 id.

## Relationship to collaborative editing

The binary serializer uses the SAME Yjs update primitives a future collab sync
transport will use (per [CLAUDE.md](../../../CLAUDE.md), the state model is built
on Yjs primitives from the start). Serialization (whole-doc snapshot) and collab
(incremental update exchange) are distinct concerns, but both ride
`encodeStateAsUpdate` / `applyUpdate`, so the binary format and collab transport
share a foundation rather than diverging.
