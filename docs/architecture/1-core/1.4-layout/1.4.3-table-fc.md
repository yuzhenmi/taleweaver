# 1.4.3 — Table Formatting Context (Table FC)

The Table FC lays out elements with `display: table`. It owns column-
width resolution, row-height computation, anonymous row/cell synthesis,
and the table's border-collapse behavior.

## Responsibilities

- **Column-width resolution (auto-layout).** The default CSS table
  algorithm. For each column, gather the min-content and max-content of
  every cell in that column. Resolve column widths by distributing the
  table's available inline-size: each column gets at least its
  min-content, more up to its max-content if there's spare, with
  proportional distribution when content overflows.

- **Anonymous row/cell synthesis.** When a `display: table` element
  contains direct children that aren't `display: table-row` (e.g., bare
  `<td>`-equivalent cells, or text content), the Table FC synthesizes
  anonymous rows around them, and synthesizes anonymous cells for
  non-cell content within rows. This matches the CSS spec's "missing
  parent" rules for table boxes.

- **Row-height computation.** For each row, lay out each cell against
  its resolved column width; the row's height is the max cell height.
  Cells with `vertical-align` (top, middle, bottom, baseline) position
  their content within the row's height.

- **Cell layout.** Each cell establishes a new BFC and lays out its
  contents via the BFC algorithm.

- **Border-collapse.** When `border-collapse: collapse`, adjacent cells
  share borders rather than each drawing their own; the Table FC
  resolves which cell's border wins per CSS Tables 3 (heaviest, then
  most specific).

- **Per-render-node reuse.** Like other formatting contexts, the Table
  FC checks the layout-box cache before laying out and reuses unchanged
  table subtrees by reference.

## Inputs and outputs

The entry function takes the `display: table` element's render node, a
block offset and inline offset where layout starts, and a
`LayoutContext`. It returns a `TableBox` containing `TableRowBox` and
`TableCellBox` children.

## What's not yet implemented

The current auto-layout column-width algorithm walks cells with a
sequential `colIdx++`, which doesn't correctly handle:

- **`colspan > 1` cells.** Should advance the index by the span count
  and contribute their intrinsic sizes split across the spanned columns
  per CSS Tables 3 §17.5.2.

- **`rowspan > 1` cells.** Should not be re-counted in subsequent rows
  occupied by the same cell.

The schema for cells doesn't yet have `rowSpan` / `colSpan` properties.
Both come together as a single feature.

Other deferred behavior:

- Repeating header rows when a table fragments across pages
  (pagination work).
- Fixed-layout (`table-layout: fixed`) — the alternate algorithm where
  column widths come from the table's first row or explicit column
  sizing rather than from cell content.

## Reference

### Entry point

```ts
function layoutTable(
  node: ElementBox,           // display: "table"
  inlineOffset: number,
  blockOffset:  number,
  ctx: LayoutContext,
  shaper: TextShaper,
): TableBox;
```

### Algorithm

```
function layoutTable(node, inlineOffset, blockOffset, ctx, shaper):
  cs = node.computedStyle
  usedStyle = computeUsedStyle(cs, ctx.containingInlineSize, ...)

  // 1. Synthesize anonymous rows for direct non-row children
  rowGroups = []
  inlineRunBuffer = []
  for child in node.children:
    if child.computedStyle.display == "table-row":
      flush inlineRunBuffer to anonymous-row
      rowGroups.push({ kind: "row", node: child })
    else:
      inlineRunBuffer.push(child)
  flush inlineRunBuffer to anonymous-row

  // 2. Synthesize anonymous cells per row
  rows = []
  for rowGroup in rowGroups:
    cells = []
    for cellChild in row.node.children:
      if cellChild.computedStyle.display == "table-cell":
        cells.push(cellChild)
      else:
        cells.push(synthesizeAnonymousCell(cellChild, rowGroup))
    rows.push({ node: rowGroup.node, cells })

  // 3. Compute column count: max cells across rows
  columnCount = max(row.cells.length for row in rows)

  // 4. Per-cell intrinsic sizing
  perColumnMins = [0] * columnCount
  perColumnMaxs = [0] * columnCount
  for row in rows:
    for c, cell in enumerate(row.cells):
      intrinsic = computeIntrinsicSizes(cell, shaper, ctx.intrinsicCache)
      perColumnMins[c] = max(perColumnMins[c], intrinsic.minContent)
      perColumnMaxs[c] = max(perColumnMaxs[c], intrinsic.maxContent)

  // 5. Distribute available width
  totalMin = sum(perColumnMins)
  totalMax = sum(perColumnMaxs)
  available = ctx.containingInlineSize - usedStyle.paddingInlineStart - usedStyle.paddingInlineEnd

  if totalMax <= available:
    // Each column gets max-content; spare distributes proportionally to max-content
    columnWidths = perColumnMaxs.map(m => m * (available / totalMax))     // when totalMax > 0
  else if totalMin <= available:
    // Distribute by interpolating between min and max
    spare = available - totalMin
    span = totalMax - totalMin
    columnWidths = perColumnMins.map((mn, i) => mn + spare * ((perColumnMaxs[i] - mn) / span))
  else:
    // Overflow: each column at min-content; table overflows
    columnWidths = perColumnMins

  // 6. Lay out each row
  rowBoxes = []
  rowBlockOffset = usedStyle.paddingBlockStart
  for row in rows:
    cellBoxes = []
    cellInlineOffset = usedStyle.paddingInlineStart
    rowHeight = 0
    for c, cell in enumerate(row.cells):
      cellCtx = makeChildContext(ctx, row.node.computedStyle, columnWidths[c], "indefinite")
      cellBox = layoutBlock(cell, cellInlineOffset, 0, cellCtx, shaper)  // fresh BFC per cell
      cellBoxes.push(cellBox)
      rowHeight = max(rowHeight, cellBox.blockSize)
      cellInlineOffset += columnWidths[c]
    // Apply vertical-align per cell within rowHeight (top / middle / bottom / baseline)
    rowBox = createTableRowBox(row.node.key, paddingInlineStart, rowBlockOffset,
                               sum(columnWidths), rowHeight, ...)
    rowBoxes.push(rowBox)
    rowBlockOffset += rowHeight

  // 7. Border-collapse adjustments (when border-collapse: collapse)
  if cs.borderCollapse == "collapse":
    apply per-pair border resolution: heaviest wins; tied → most specific
    adjust cell positions to share borders

  return createTableBox(node.key, inlineOffset, blockOffset,
                        sum(columnWidths) + paddingInlineStart + paddingInlineEnd,
                        rowBlockOffset + paddingBlockEnd,
                        ctx.writingMode, ctx.direction, cs, usedStyle,
                        rowBoxes, columnWidths, ctx.containingInlineSize)
```

### Column-width distribution math

Three cases on the relationship between available width and aggregate column intrinsics:

- **Slack** (`totalMax ≤ available`): each column expands to its max-content; the residual spreads proportionally to `maxContent` (so wider columns get more of the slack).
- **Constrained** (`totalMin ≤ available < totalMax`): each column gets at least its min-content; the spare (`available - totalMin`) is distributed proportionally to each column's growth range (`max - min`).
- **Overflow** (`available < totalMin`): each column at its min-content. The table's actual width exceeds the available width — caller (the BFC) decides whether to clip or scroll based on the parent's `overflow`.

### Anonymous synthesis rules

CSS Tables 3 §17:

- A `display: table` parent's child that is not `table-row` or `table-row-group` gets wrapped in an anonymous `table-row`.
- A `table-row` parent's child that is not `table-cell` gets wrapped in an anonymous `table-cell`.
- An anonymous row's computedStyle inherits from the `table` parent; layout-relevant fields like margin/padding/border are zero.
- An anonymous cell's computedStyle inherits from its row; like above, layout-relevant fields are zero.

### Rowspan / colspan target algorithm

Cells gain two schema fields: `rowSpan: number` (default 1) and `colSpan: number` (default 1) on `table-cell` `StateNode.properties`. The Table FC consumes them as follows.

#### Column-width computation with colspan

For a cell with `colSpan === 1`, the cell contributes its intrinsic min/max-content to its column directly (the algorithm in the section above).

For a cell with `colSpan > 1`, distributing its intrinsic across the spanned columns follows CSS Tables 3 §17.5.2:

```
function distributeIntrinsicAcrossSpan(cell, startCol, span, perColumnMins, perColumnMaxs):
  spanMin = cell.intrinsic.minContent
  spanMax = cell.intrinsic.maxContent

  // The spanned columns already have per-column mins/maxs from 1-cell cells.
  currentSpanMin = sum(perColumnMins[startCol..startCol+span])
  currentSpanMax = sum(perColumnMaxs[startCol..startCol+span])

  // If the cell's intrinsic exceeds the columns' aggregates, distribute the excess
  if spanMin > currentSpanMin:
    excessMin = spanMin - currentSpanMin
    // Distribute proportionally to existing per-column min (or evenly if all zero)
    for c in startCol..startCol+span:
      share = (perColumnMins[c] / currentSpanMin) * excessMin   // when currentSpanMin > 0
      perColumnMins[c] += share

  if spanMax > currentSpanMax:
    excessMax = spanMax - currentSpanMax
    for c in startCol..startCol+span:
      share = (perColumnMaxs[c] / currentSpanMax) * excessMax
      perColumnMaxs[c] += share
```

This pass runs after the 1-cell sweep, so the multi-cell distribution doesn't shrink columns that 1-cell cells already established as wider.

#### Row-height computation with rowspan

A cell with `rowSpan > 1` is laid out once but participates in multiple rows. Track an "occupancy grid" while walking rows:

```
function layoutTableBody(rows, columnWidths):
  occupied = 2D array of booleans, indexed by [rowIdx][colIdx], all false
  rowBoxes = []

  for rowIdx, row in enumerate(rows):
    cellBoxes = []
    colIdx = 0
    for cell in row.cells:
      // Skip columns occupied by a rowspan from above
      while occupied[rowIdx][colIdx]: colIdx += 1

      // Layout cell at (colIdx, rowIdx) with width sum(columnWidths[colIdx..colIdx+cell.colSpan])
      cellBox = layoutBlock(cell, ...)
      cellBoxes.push(cellBox)

      // Mark cells covered by this cell's rowspan/colspan as occupied
      for r in 0..cell.rowSpan:
        for c in 0..cell.colSpan:
          occupied[rowIdx + r][colIdx + c] = true

      colIdx += cell.colSpan

    rowBoxes.push(createTableRowBox(...cellBoxes))

  // Resolve row heights: a rowspan cell's height splits across its rows
  // (a cell with rowSpan=2 contributes max(its blockSize / 2) to each row, OR
  // distributes proportionally to per-row max-of-non-spanning-cells, per CSS Tables 3 §17.5.3)
  resolveRowHeights(rowBoxes, occupied)
  return rowBoxes
```

Row-height resolution: each row's height is `max` over its non-spanning cells. For spanning cells, after the row heights settle, if the cell's blockSize exceeds the sum of its spanned-row heights, redistribute the excess proportionally back to the spanned rows.

### Cross-page row repetition

When a table fragments across pages (target architecture; pagination owns this — see [`1.5-pagination.md`](../1.5-pagination.md)), `<thead>`-equivalent rows repeat at the top of each page-portion of the table:

1. The Table FC produces a `TableBox` containing all rows in document order plus a `headerRowCount: number` field indicating how many leading rows are header rows. (Convention: rows whose `display: table-row` element has a `properties.isHeader === true` flag, or rows nested inside a `display: table-header-group` element.)
2. The fragmenter recognizes `TableBox` as a fragmentable container. When fragmenting, it splits the body rows at row boundaries and prepends the header rows to each fragment.
3. The header-row layout boxes are reused-by-reference across page-portions when their content is identical (which is the common case — the header doesn't change per page). Each page's `TableBox` carries a `children` array starting with the (shared) header rows followed by that page's body rows.
4. `break-inside: avoid` on a row prevents intra-row splitting (current architecture; future enhancement could split tall cells with content like nested paragraphs).

Repeating footers (`<tfoot>`) follow the symmetric pattern at the table's end.

### Fixed-layout (`table-layout: fixed`)

The alternate algorithm where column widths come from the table's first row or explicit column sizing rather than from cell content. Deferred. Schema would add a `tableLayout: "auto" | "fixed"` field on `Style`. With `fixed`:

1. The first row's cells determine column widths via their explicit `inlineSize` values; cells without explicit `inlineSize` divide the remaining space equally.
2. Subsequent rows inherit those widths regardless of their cell content (overflow is the cell's responsibility).

This algorithm enables faster table layout because no full intrinsic-sizing pass is needed.

### Performance contracts

- `layoutTable` cold: O(R × C × cell-cost) where R = rows, C = columns, cell-cost depends on cell content.
- `layoutTable` cache hit (when render node is layout-equivalent): O(1).
