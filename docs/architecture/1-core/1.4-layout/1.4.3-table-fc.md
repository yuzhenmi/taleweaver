# 1.4.3 — Table Formatting Context (Table FC)

The Table FC lays out elements with `display: table`. It owns the
occupancy-grid model, column-width resolution, row-height computation
(including `rowSpan`/`colSpan`), anonymous row/cell synthesis, and
fragmentation of tables — and spanning cells — across pages.

## Responsibilities

- **Occupancy grid (CSS Tables 3 §17.5).** Before geometry, every cell
  is assigned a `(gridRow, gridCol)` origin plus its `rowSpan`/`colSpan`
  rectangle by scanning rows top-to-bottom, cells left-to-right: each
  cell takes the first column free at its row (skipping columns still
  consumed by a cell spanning down from an earlier row), then claims its
  `colSpan × rowSpan` rectangle. The result is the column count and a
  rectangular `occupancy[row][col] → owning cell id | null` map. Both the
  intrinsic-size pre-pass and the geometry pass build the SAME grid, so
  the column structure they assume agrees. The assignment core
  (`assignTableGrid`) lives in the shared `table-grid-core` module and is
  reused by the state layer's span-aware table-editing ops (see
  [`1.1-state.md`](../1.1-state.md)) — both build a byte-identical grid from
  the same cell-span values, so an edit reasons in the exact grid coordinates
  layout will lay the table out in, and preserves the rectangular-occupancy
  invariant this FC depends on (a well-formed spanned table has no `null`
  slots).

- **Column-width resolution (auto-layout, §17.4).** For each column,
  gather the min/max-content of every cell. `colSpan === 1` cells
  contribute to their single column; `colSpan > 1` cells distribute their
  intrinsic across the spanned columns (span-1 columns established first,
  then spanning cells distribute any shortfall narrowest-column-first,
  proportional to current width). Column widths then resolve by
  distributing the table's available inline-size: each column gets at
  least its min-content, more up to max-content if there is spare, with
  proportional distribution when content overflows.
  `metadata.columnWidths` (explicit fractions) bypasses auto-layout.

- **Row-height computation with `rowSpan` (§17.5.3).** Base row heights
  come from the cells that span exactly one row (max over them, honoring
  an explicit row block-size). A `rowSpan > 1` cell whose interior is
  taller than the rows it spans distributes the deficit across those rows
  (proportional to current height; evenly when all equal/zero). Heights
  only grow, so the fixpoint converges within the spanning-cell count.
  Each cell's block-size is the SUM of the rows it spans.

- **Anonymous row/cell synthesis.** A `display: table` child that is not
  `table-row` is wrapped in an anonymous `table-row`; a `table-row` child
  that is not `table-cell` is wrapped in an anonymous `table-cell`. This
  matches the CSS spec's "missing parent" rules. Anonymous boxes inherit
  the parent's computed style with layout-relevant fields (margin/
  padding/border) zeroed; anonymous cells never span.

- **Cell layout.** Each cell establishes a new BFC and lays out its
  contents via `layoutBlock` at its summed column width.

- **Fragmentation (incl. spanning cells).** When a page break falls
  between rows the table splits at row boundaries; when it falls INSIDE a
  `rowSpan > 1` cell's spanned region the cell's interior is fragmented
  and continued on the next page. See [Fragmentation](#fragmentation).

- **Per-render-node reuse.** Like other formatting contexts, the Table FC
  reuses unchanged table subtrees by reference via the layout-box cache.

### Status of divergences from this target

- **`border-collapse: collapse`** `[missing]` — every cell currently
  draws its own borders; the heaviest-wins/most-specific collapse
  resolution is not implemented.
- **Repeating `<thead>`/`<tfoot>` rows across page fragments**
  `[missing]` — needs a `table-header-group` schema addition.
- **`table-layout: fixed`** `[missing]` — only the auto algorithm exists.

## Inputs and outputs

`layoutTable` takes the `display: table` element's render node, the inline
and block offsets where layout starts, a `LayoutContext`, a `TextShaper`,
and an optional `FragmentationContext`. It returns
`LayoutResult<TableBox>` — `{ box, breakToken }`.

The `TableBox` carries its `TableRowBox` → `TableCellBox` children plus
the grid metadata downstream consumers (hit-test, selection, paint) read:

- `columnPxWidths: number[]` — resolved column widths.
- `columnCount: number`.
- `occupancy: (BlockId | null)[][]` — the reverse map a point/selection
  uses to find the merged cell owning a grid slot (a spanning cell's box
  lives only in its first row's children; lower rows' slots resolve here).
- `cellBoxById: Map<BlockId, TableCellBox>` — O(1) occupancy-id → box.

Each `TableCellBox` carries its `{ gridRow, gridCol, rowSpan, colSpan }`.

## Reference

### Entry point

```ts
function layoutTable(
  node: ElementBox,           // display: "table"
  inlineOffset: number,
  blockOffset:  number,
  ctx: LayoutContext,
  shaper: TextShaper,
  fragmentation?: FragmentationContext,
): LayoutResult<TableBox>;
```

### Geometry algorithm

After anonymous synthesis and grid assignment, geometry runs as four
passes over the cells (grouped by their starting row), then a
fragmentation fit-check:

```
function layoutTable(node, inlineOffset, blockOffset, ctx, shaper, fragmentation):
  rows = groupTableRows(node)                       // + anonymous-row synthesis
  grid = assignTableGrid(rows.map(groupRowCells))   // §17.5 occupancy
  columnPxWidths =
      explicit metadata.columnWidths * tableInlineSize
      OR auto-layout via distributeColumnIntrinsics (§17.4, colSpan-aware)
  sumCols(from, to) = Σ columnPxWidths[from..to)

  startBodyRow = fragmentation?.resumeFrom.resumeAtRow ?? 0

  // Pass A — lay every cell interior (BFC, no fragmentation) at its summed
  // inline-size sumCols(gridCol, gridCol+colSpan); group by STARTING row.
  for rowIdx in [startBodyRow, rows.length):
    for cell in row: laidByRow[rowIdx].push({ interior, placement, ... })

  // Resume preamble — re-attach still-spanning cells from an earlier fragment
  // (see Fragmentation ▸ Resuming spanning cells).

  // Pass B — base row heights from rowSpan==1 cells (+ explicit row size).
  // Pass C — §17.5.3: distribute each rowSpan>1 cell's height deficit across
  //          its spanned rows; iterate to fixpoint (bounded by spanning count).
  // Pass D — cumulative block offsets; each cell's block-size = Σ spanned rows.

  // E.1 — fragmentation fit-check (see below) OR return the full table.
```

### Column-width distribution math

Three cases on available width vs. aggregate column intrinsics:

- **Slack** (`totalMax ≤ available`): each column expands to max-content;
  residual spreads proportionally to `maxContent`.
- **Constrained** (`totalMin ≤ available < totalMax`): each column gets
  its min-content; the spare (`available − totalMin`) distributes
  proportionally to each column's growth range (`max − min`).
- **Overflow** (`available < totalMin`): each column at min-content; the
  table overflows and the parent BFC decides clip/scroll.

`colSpan > 1` cells distribute through `distributeColumnIntrinsics`: span-1
cells set the per-column base, then each spanning cell that exceeds its
columns' aggregate distributes the shortfall narrowest-column-first
(proportional to current max, evenly when all zero), so a wide spanning
cell never shrinks a column a span-1 cell already widened.

### Anonymous synthesis rules

CSS Tables 3 §17:

- A `display: table` child that is not `table-row`/`table-row-group` is
  wrapped in an anonymous `table-row`.
- A `table-row` child that is not `table-cell` is wrapped in an anonymous
  `table-cell`.
- Anonymous boxes inherit the parent's computed style; layout-relevant
  fields (margin/padding/border) are zero. Anonymous cells never span.

## Fragmentation

`layoutTable` accepts `fragmentation?: FragmentationContext` and returns
`LayoutResult<TableBox>`. Pagination geometry — see
[`1.5-pagination.md`](../1.5-pagination.md).

### Row-level fit + break

The fit-check walks the placed row boxes accumulating block-axis size and
stops at the first row that overflows `availableBlockSize`:

- **No rows fit** → `{ box: null, breakToken: { type: "table",
  resumeAtRow: startBodyRow } }` (the parent pushes the whole table down).
- **Partial fit** → the placed-rows prefix + `{ type: "table",
  resumeAtRow: startBodyRow + placedRowCount }`.
- **All fit** → the full `TableBox`, `breakToken: null`.

`resumeAtRow` indexes into the table BODY. Resuming skips body rows
`0..resumeAtRow−1` and emits the suffix.

### Spanning cells across the break

When the break row falls inside a `rowSpan > 1` cell's span (the cell
originates in the placed rows but its rectangle reaches past the break):

1. **Emit.** The cell's interior is re-laid under a `FragmentationContext`
   sized to the placed spanned-rows height; its box is trimmed to that
   height (so it no longer overflows the trimmed page); and a
   `SpanningCellContinuation` is appended to the `TableBreakToken`'s
   `spanningCells`, recording the cell's grid placement and its interior
   `BreakToken`. The interior token is `null` for the "empty spanned tail"
   case (content fit the placed rows but the merged box still spans rows
   made tall by other cells) — the continuation is still emitted so the
   resume keeps those columns occupied.

2. **Resuming spanning cells.** On the next fragment, the resume preamble
   reads `resumeFrom.spanningCells`. For each continuation it locates the
   originating cell, lays its REMAINING interior (resuming from the
   continuation's interior token), and re-attaches it as a cell clamped to
   `[resumeAtRow, gridRow + rowSpan)` for this fragment — folded into the
   normal Pass B/C/D so it sizes and positions like any spanning cell.
   The continuation carries the cell's ORIGINAL origin/span, so a cell
   spanning three-plus pages re-breaks correctly down the chain.

   Column routing needs no rebuild: `assignTableGrid` runs over the whole
   table on every fragment, so the post-break rows are already assigned
   around the still-occupied columns.

`breakTokensEqual` compares table tokens by `resumeAtRow` AND their
`spanningCells` list, so an incremental page-reuse gate never reuses a
fragment whose spanning-cell continuations changed.

### Atomicity

A single row is atomic (no intra-row split other than via a spanning
cell's interior fragmentation described above). `break-inside: avoid`
handling and `<thead>`/`<tfoot>` repetition are future work.

## Deferred algorithms

### Repeating `<thead>`/`<tfoot>` across fragments `[missing]`

`<thead>`-equivalent rows should repeat at the top of each page-portion
(and `<tfoot>` at the bottom). Needs a `table-header-group` /
`table-footer-group` schema addition so the fragmenter can recognize and
re-prepend header rows; header layout boxes would be reused by reference
across page-portions. `resumeAtRow` already indexes the body excluding any
future header rows.

### Fixed-layout (`table-layout: fixed`) `[missing]`

The alternate algorithm where column widths come from the first row or
explicit column sizing rather than cell content: the first row's cells
(or explicit `inlineSize`) fix the columns, subsequent rows inherit them
regardless of content. Faster (no full intrinsic-sizing pass). Would add a
`tableLayout: "auto" | "fixed"` style field.

### `border-collapse: collapse` `[missing]`

Adjacent cells would share borders rather than each drawing their own,
with per-pair resolution (heaviest wins; tied → most specific) per CSS
Tables 3, and cell positions adjusted to share the collapsed border.

## Performance contracts

- `layoutTable` cold: O(R × C × cell-cost), R = rows, C = columns.
- `layoutTable` cache hit (layout-equivalent render node): O(1).
- A spanning cell crossing a break is laid an extra time per fragment it
  crosses (natural-height measure + the per-fragment trimmed lay); this is
  bounded by the number of spanning cells that actually straddle breaks.
