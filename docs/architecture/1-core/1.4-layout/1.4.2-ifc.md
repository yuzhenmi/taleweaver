# 1.4.2 — Inline Formatting Context (IFC)

The IFC lays out a paragraph (or any anonymous inline run) into lines.
It walks the inline content, tokenizes it into wrap-units, packs tokens
into lines respecting the available inline-size at each block offset,
applies bidi reorder per line, and emits a sequence of `LineBox`es.

## Responsibilities

- **Tokenization.** Walk the inline content (text runs, inline elements,
  inline-blocks, line-breaks) and produce a flat sequence of `Token`s.
  Each token is a contiguous unit with shared style. Tokens carry their
  text, advance widths per cluster, break opportunities (whitespace
  boundaries, hyphenation points), bidi level, and back-references to
  their containing inline ancestors.

- **Line wrapping.** Greedy line-fit: accumulate tokens into the current
  line until the next token would overflow available inline-size, then
  break. The available inline-size at each block offset comes from the
  BFC's float environment (floats may narrow some lines).

- **Below-min-content handling.** When the available inline-size is
  smaller than even the next token's minimum (a single character /
  cluster), the IFC pushes the line below the next float bottom rather
  than overflowing.

- **Hyphen splitting.** When a token has hyphenation opportunities and
  the line would otherwise overflow, the IFC splits the token at a
  hyphen and emits the prefix on the current line with a hyphen glyph,
  carrying the suffix to the next line.

- **Cluster-level bidi reorder.** Once a line's tokens are placed in
  logical order, the IFC reorders them visually per the Unicode Bidi
  Algorithm. Within a uniform-direction line the reorder is mechanical;
  mixed-direction lines apply UAX #9 rules to produce the correct visual
  order.

- **Inline-block sizing.** When an inline child has `display:
  inline-block`, the IFC consults intrinsic sizes for shrink-to-fit
  resolution, lays out the inline-block's interior via a fresh BFC, and
  then participates in line packing as a single atomic unit.

- **Baseline alignment.** Each line's baseline is the dominant baseline
  of its tokens; subscript/superscript inline children offset their
  glyphs from that baseline.

- **Per-paragraph reuse.** The `IFCStateCache` keys cached wrap state
  by paragraph render-node. When the paragraph is unchanged, its
  cached `LineBox`es return without re-tokenizing or re-wrapping.

## Inputs and outputs

The IFC's entry takes:

- An anonymous element box (or a paragraph render node) carrying the
  inline children.
- A starting inline offset (within the parent's content area).
- A starting block offset.
- A `LayoutContext` with the float environment, intrinsic-sizes cache,
  and shaper.

It returns a sequence of `LineBox`es, each with positioned children
(`TextRunBox`, `InlineBox`, inline-`BlockBox` for inline-blocks,
markers for line-break indicators).

## Tokenization details

Token construction has stable identity: each token's `id` is derived
from its source (the originating render node's key plus an offset
within that render node's text). Same identity across passes lets
incremental wrap (when wired) detect which prefix is unchanged and
resume from there. The current implementation re-tokenizes each
wrap pass but the IDs are present and ready to consume.

## Bidi handling

The shaper produces tokens with bidi levels. The IFC's reorder pass
runs per line: it groups consecutive same-level tokens into runs, then
reverses runs whose level is higher than the line's base level (an
even/odd interleaving from UAX #9). Mixed-direction text within a single
shaped run requires per-cluster level information from the shaper; the
IFC's reorder logic handles uniform-direction runs today and is
extensible to per-cluster runs once the shaper provides them.

## Convergence (incremental wrap)

The `wrap-incremental` module implements a convergence-detection
algorithm: when re-wrapping after an edit, walk forward from the change
point and compare each line's break to the prior pass; once two
consecutive lines break at the same offset, the suffix is unchanged and
the prior pass's lines reuse from that point. The algorithm exists and
is tested but not yet wired into the main wrap loop because hyphen
splitting complicates the contiguous-token-range invariant convergence
needs. Wiring it would let typing in a long paragraph touch only the
edit-affected lines instead of re-wrapping the whole paragraph.
