# 1.4.2 — Inline Formatting Context (IFC)

The IFC lays out a paragraph (or any anonymous inline run) into lines.
It walks the inline content, tokenizes it into wrap-units, packs tokens
into lines respecting the available inline-size at each block offset,
applies bidi reorder per line, and emits a sequence of `LineBox`es.

## Responsibilities

- **Tokenization.** Walk the inline content (text runs, inline elements,
  inline-blocks, line-breaks) and produce a flat sequence of `Token`s.
  Each token is a contiguous unit with shared style. Tokens carry their
  text, advance widths per cluster, break opportunities (whitespace
  boundaries, hyphenation points), bidi level, and back-references to
  their containing inline ancestors.

- **`text-transform` display transform.** When a token's `ComputedStyle`
  carries a non-`none` `textTransform`, `collectInlineTokens` runs the token's
  text through the pure `transformRun` rule (`layout/text-transform.ts`) and
  re-shapes the *display* text — overriding the token's `text`, `width`, and
  `clusterWidths` — so wrap decisions, measurement, and paint all see the
  transformed glyphs while the state text stays pristine. The state text and the
  display text are kept reconcilable by a per-state-code-unit `sourceDisplayLengths`
  map (see [`1.6-text.md`](../1.6-text.md)); only length-changing transforms
  (e.g. `uppercase` of `ß` → `SS`) carry it. Each leaf `TextRunBox` concatenates
  its tokens' contributions into one `sourceDisplayLengths` so the cursor layer
  can map state↔display offsets.

- **Line wrapping.** Greedy line-fit: accumulate tokens into the current
  line until the next token would overflow available inline-size, then
  break. The available inline-size at each block offset comes from the
  BFC's float environment (floats may narrow some lines).

- **Below-min-content handling.** When the available inline-size is
  smaller than even the next token's minimum (a single character /
  cluster), the IFC pushes the line below the next float bottom rather
  than overflowing.

- **Hyphen splitting.** When a token has hyphenation opportunities and
  the line would otherwise overflow, the IFC splits the token at a
  hyphen and emits the prefix on the current line with a hyphen glyph,
  carrying the suffix to the next line.

- **Cluster-level bidi reorder.** Once a line's tokens are placed in
  logical order, the IFC reorders them visually per the Unicode Bidi
  Algorithm. Within a uniform-direction line the reorder is mechanical;
  mixed-direction lines apply UAX #9 rules to produce the correct visual
  order.

- **Inline-block sizing.** When an inline child has `display:
  inline-block`, the IFC consults intrinsic sizes for shrink-to-fit
  resolution, lays out the inline-block's interior via a fresh BFC, and
  then participates in line packing as a single atomic unit.

- **Baseline alignment.** Each line's baseline is the dominant baseline
  of its tokens; subscript/superscript inline children offset their
  glyphs from that baseline.

- **Text alignment (`text-align`).** After a line's content width is
  known, the IFC applies the block's `textAlign`: `start`/`end`/`center`
  add a logical inline offset to the line (gap = available − content,
  resolved physical via `logicalToPhysical`; trailing whitespace is
  excluded from the content width so it doesn't shift the line). `justify`
  instead distributes the gap across the line's interior inter-word spaces
  (widening each), leaving the LAST line of the paragraph and any
  hard-break-terminated line `start`-aligned. Because every cursor/paint
  consumer reads the laid-out `box.x`, alignment flows to caret, hit-test,
  and selection for free.

- **Trailing-space hang + clamp.** A trailing space at a soft-wrap
  boundary hangs (a space unit never wraps alone; only words wrap) and its
  box is clamped to the line content edge, keeping glyphs and the caret
  on-page for any number of trailing spaces. See
  [`1.6-text.md`](../1.6-text.md) for the full behavior.

- **Trailing letter-spacing trim (CSS Text 3 §8.1).** The trailing tracking
  of the last RETAINED typographic unit on a line is removed, so a line's
  content box does not end with hanging tracking. `trailingLetterSpacingOf`
  walks the line's wrap units from the end, skips the hung trailing space(s)
  (so the trimmed glyph is the word before the space, not the space itself —
  it composes with the trailing-space hang above, no double-subtract), and
  returns the last retained unit's `letterSpacing`. Two effects: it is
  subtracted from `contentWidth` (so alignment + the justify gap exclude it),
  and the last NON-space text-run leaf is rebuilt with `inlineSize − trim`
  (so the end-of-line caret + last selection rect sit at the trimmed edge).
  The narrow case of the last glyph nested inside an `InlineBox` at the wrap
  point is deferred (alignment stays correct; only the nested caret-edge —
  see #434). Under `letter-spacing: normal` the trim is 0 (inert).

- **Per-paragraph reuse.** The `IFCStateCache` keys cached wrap state
  by paragraph render-node, the containing inline-size, and the block's
  `textAlign` + `direction` (so an alignment/direction change with
  unchanged content + width re-lays the lines rather than returning stale
  aligned ones). When all match, the cached `LineBox`es return without
  re-tokenizing or re-wrapping.

## Inputs and outputs

The IFC's entry takes:

- An anonymous element box (or a paragraph render node) carrying the
  inline children.
- A starting inline offset (within the parent's content area).
- A starting block offset.
- A `LayoutContext` with the float environment, intrinsic-sizes cache,
  and shaper.

It returns a sequence of `LineBox`es, each with positioned children
(`TextRunBox`, `InlineBox`, inline-`BlockBox` for inline-blocks,
markers for line-break indicators).

## Tokenization details

Token construction has stable identity: each token's `id` is derived
from its source (the originating render node's key plus an offset
within that render node's text). Same identity across passes lets
incremental wrap (when wired) detect which prefix is unchanged and
resume from there. The current implementation re-tokenizes each
wrap pass but the IDs are present and ready to consume.

### `text-transform` per-token transform

`collectInlineTokens` applies `textTransform` per non-whitespace token when the
token's `ComputedStyle.textTransform !== "none"`. For each such token it shapes
the *display* string returned by `transformRun(token.text, mode)` and overrides
the token's `text` / `width` / `clusterWidths` with the display shaping. When the
transform changes length (`uppercase` of `ß` → `SS`), the token records a
`sourceDisplayLengths` array (one entry per source code unit, giving the count of
display code units it expands to) and clears `hyphenBreaks` (the dictionary
positions no longer index the changed display text — a grown word does not
auto-hyphenate). Equal-length (1:1) transforms omit `sourceDisplayLengths`; the
display string is byte-compatible offset-wise.

`buildLineChildrenForAncestorLevel` concatenates the per-token
`sourceDisplayLengths` of the runs that compose a leaf into the leaf's
`TextRunBox.sourceDisplayLengths`. The concatenation preserves the invariant that
the array length equals the leaf's state `offsetLength` (one entry per source
code unit), with collapsed-whitespace code units contributing **zero** entries
(they occupy no display position). A leaf assembled entirely from 1:1 or
untransformed tokens omits the array. The cursor layer consumes it to map
state↔display offsets (see [`1.6-text.md`](../1.6-text.md)).

Intrinsic sizing applies the same transform: `intrinsic-sizes-pass` shapes the
transformed display text (not the source text) when computing min-content /
max-content, so inline-block and shrink-to-fit widths reflect the rendered
glyphs — keeping wrap, intrinsic sizing, and paint in lockstep on the display
string.

## Bidi handling

The shaper produces tokens with bidi levels. The IFC's reorder pass
runs per line: it groups consecutive same-level tokens into runs, then
reverses runs whose level is higher than the line's base level (an
even/odd interleaving from UAX #9). Mixed-direction text within a single
shaped run requires per-cluster level information from the shaper; the
IFC's reorder logic handles uniform-direction runs today and is
extensible to per-cluster runs once the shaper provides them.

## Convergence (incremental wrap)

The `wrap-incremental` module implements a convergence-detection
algorithm: when re-wrapping after an edit, walk forward from the change
point and compare each line's break to the prior pass; once two
consecutive lines break at the same offset, the suffix is unchanged and
the prior pass's lines reuse from that point. Wiring it would let typing
in a long paragraph touch only the edit-affected lines instead of
re-wrapping the whole paragraph.

The algorithm exists and is tested but is **not yet wired** into the main
wrap loop — it is foundation-built-ahead, scoped to P18 ("Cascade +
layout incremental polish"). The IFC today does **all-or-nothing** reuse
(`findChangePoint`): identical tokens reuse the whole paragraph, any
change re-wraps it; the paragraph cache already delivers the dominant win
(every un-edited paragraph is reused each keystroke). `rewrapIncremental`
adds only the marginal PARTIAL reuse within the single edited paragraph.
A correct wire-in must first resolve four integration hazards the module
does not yet address (a naive wire-in would ship a degraded, incorrect
partial-reuse):

1. **Tail vertical-repositioning** — reused tail lines are returned by
   reference with their baked-in `y`; an edit that adds/removes a head
   line shifts the tail, so the tail's block-offset geometry must be
   re-stamped (the detector matches token boundaries, not `y`).
2. **Float-environment gate** — convergence checks only
   `availableInlineSize`, not the float intrusion profile at the tail's
   new block offset; reused tail widths could be wrong under floats
   (the virtualized-layout design already falls floats back to the legacy
   full path for the same reason).
3. **Bidi-context gate** — the per-line reorder pass depends on
   paragraph-level base direction; reuse must confirm the bidi context is
   unchanged.
4. **Fragmentation interaction** — the wrap cache is bypassed under active
   fragmentation; partial reuse must respect `IFCBreakToken` boundaries.

Hyphenated splitting additionally complicates the contiguous-token-range
invariant the detector relies on.

### `Token` schema

```ts
interface Token {
  readonly id: string;                              // stable: `${sourceKey}:${offset}`
  readonly text: string;                            // tokenizer-emitted run; whitespace tokens have isSpace=true
  readonly width: number;                           // shaped advance in px
  readonly isSpace: boolean;
  readonly isLineBreak: boolean;                    // true for tokens emitting forced breaks (whiteSpace pre/pre-wrap newlines)
  readonly style: ComputedStyle;                    // for vertical-align baseline and line-height
  readonly inlineBlock?: ElementBox;                // present when the token represents an inline-block child
  readonly inlineAncestors: readonly ElementBox[];  // ancestor inline elements (for fragmentEdge resolution)
  readonly inlineAncestorStyles: readonly ComputedStyle[];
  readonly hyphenBreaks?: readonly number[];        // code-unit offsets where token may hyphenate
  readonly clusterWidths?: readonly number[];       // per-code-unit advance, attributed to the grapheme's first unit
  readonly bidiLevel: number;                       // from shaper
}
```

A token's `id` is derived deterministically from its source so that token equality can be checked across passes without re-tokenizing.

**`clusterWidths` is a per-code-unit array, grapheme-attributed.** Because a
shaper `Cluster` is a UAX #29 grapheme cluster (see [`1.6-text.md`](../1.6-text.md))
that may span multiple UTF-16 code units, the IFC attributes each grapheme's
**full `inlineAdvance` to its FIRST code unit** and **0 to every interior unit**
(`clusters.find(c => c.start === offset)?.inlineAdvance ?? 0`). A combining mark —
an interior code unit of its base's grapheme — therefore contributes 0 width.
A prefix-sum over `clusterWidths` (used by the hyphen-split fit search) still
totals each grapheme's full advance exactly, because the per-grapheme width sits
entirely at the grapheme's first offset. Consistent with this, `hyphenBreaks` and
`BreakOpportunity.clusterIndex` are **code-unit offsets**, not grapheme ordinals —
they index the same UTF-16 address space as state offsets and `Cluster.start`/`end`.

### Wrap algorithm (greedy)

```
function layoutInlineContent(paragraph, inlineOffset, blockOffset, ctx, shaper):
  // Cache hit?
  cacheEntry = ctx.ifcStateCache.get(paragraph.key)
  if cacheEntry exists && cacheEntry.renderNode === paragraph
       && cacheEntry.containingInlineSize == ctx.containingInlineSize:
    return cacheEntry.lines

  tokens = collectTokens(paragraph, shaper, ctx)
  lines = []
  i = 0
  currentBlockOffset = blockOffset

  while i < tokens.length:
    // Available width at this y, accounting for floats
    occupied = ctx.floatEnv.availableInlineSizeAt(currentBlockOffset, ctx.containingInlineSize)
    availableInlineSize = ctx.containingInlineSize - occupied.inlineStartSize - occupied.inlineEndSize

    // Try to pack tokens greedily
    line = packLine(tokens, i, availableInlineSize, ctx)

    if line.tokenCount == 0 && availableInlineSize < tokens[i].minClusterWidth:
      // Below-min-content: no progress possible at this offset
      currentBlockOffset = ctx.floatEnv.nextFloatBottomBelow(currentBlockOffset)
      continue

    if line needs hyphen split:
      line = splitTokenAtHyphen(tokens, i, availableInlineSize, line.partialToken)

    bidi reorder per UAX #9 levels
    apply text-align (start / end / center / justify)
    emit LineBox (and contained TextRunBox / InlineBox / inline-BlockBox / MarkerBox children)
    lines.push(LineBox)
    i += line.tokenCount
    currentBlockOffset += LineBox.height

  ctx.ifcStateCache.set(paragraph.key, { renderNode: paragraph, lines, containingInlineSize: ctx.containingInlineSize })
  return lines
```

### Wrap-with-justify interaction

When `text-align: justify`, after greedy packing produces a line:

- If the line is the last line of the paragraph OR ends in a forced break: don't justify (left-align in LTR, right-align in RTL).
- Otherwise: distribute the remaining space across the line's space tokens. Each space's `width` is enlarged by `extra / numSpaces`. If there are no space tokens (one big word that filled the line), the line stays as packed.

`letterSpacing` and `wordSpacing` are honored as additional advances per cluster / per space; they apply pre-justify, so justify distributes the residual after letter/word spacing.

### Bidi reorder (UAX #9 line-end)

The shaper assigns a `bidiLevel` per cluster (consumed via tokens; uniform-direction tokens emit a single level). Within a line:

1. Determine the line's base level from the paragraph's `direction` (`ltr` → 0, `rtl` → 1).
2. Find the highest bidi level among the line's clusters. Call it `maxLevel`.
3. From `level = maxLevel` down to `(baseLevel + 1)`:
   - Reverse every contiguous run of clusters whose level is ≥ `level`.
4. The result is the visual order.

The IFC's reorder operates on the line's children (TextRunBox / InlineBox / etc.) by treating reference-equal-style runs as atomic. Uniform-direction tokens reorder mechanically as whole units. The mixed-direction case has its own algorithm:

### Mixed-direction reorder (target algorithm)

When a single shaped run contains clusters at multiple bidi levels (e.g., Arabic `كتاب` embedded in English `read the كتاب book` — the Arabic clusters are level 1 in an LTR base direction, the English clusters are level 0), the run's `TextRunBox` cannot be treated as atomic. The reorder pass operates on the cluster level instead:

```
function reorderLineMixedDirection(line, baseLevel):
  // Flatten line children into a cluster array, preserving back-references
  clusters = []
  for child in line.children:
    if child has uniform bidi level:
      clusters.push({ source: child, range: full child, level: child.bidiLevel })
    else:  // mixed-level shaped run
      for clusterIdx in 0..child.shapedRun.clusters.length:
        clusters.push({ source: child, range: clusterIdx, level: child.shapedRun.clusters[clusterIdx].level })

  // Apply UAX #9 L1 (reset trailing whitespace to base level) and L2 (level-based reverse)
  applyL1(clusters, baseLevel)            // trailing/segment-separator whitespace gets baseLevel
  maxLevel = max(c.level for c in clusters)
  for level from maxLevel down to (baseLevel + 1):
    for run of consecutive clusters where level >= level:
      reverse the run in place

  // Re-emit boxes from the reordered cluster sequence:
  // - Adjacent clusters from the same source TextRunBox at the same level merge into one TextRunBox fragment.
  // - Adjacent clusters at different levels (e.g., source contains both Arabic and Latin) emit separate TextRunBox fragments
  //   each with their own visual-order text content.
  emit reorderedChildren by walking the cluster array and grouping
  adjust each child's inlineOffset so visual-x positions align with the reordered sequence

  return line with reorderedChildren
```

UAX #9 rules at this level:
- **L1.** Whitespace at the end of a line (and at segment separators) resets to the paragraph's base level. So a trailing space in `"hello "` (Latin in RTL paragraph) renders at the start of the line, not the end.
- **L2.** Level-based reverse — the algorithm above.
- **L3.** Combining marks reorder with their base. Per UAX #29 they're already in the same cluster, so the cluster-level reorder honors L3 implicitly.

Per-cluster bidi levels come from the shaper. The canvas shaper currently emits one level per shaped run; supporting mixed-direction within a run requires the shaper to expose per-cluster levels through `Cluster` (a `level: number` field). Once exposed, the IFC's reorder uses the algorithm above.

### Hyphen split

When `availableInlineSize` would not fit the next token AND the current line is empty AND the token has `hyphenBreaks`:

1. Find the largest hyphen offset `h` in `hyphenBreaks` such that the prefix (code units `0..h`) plus the hyphen glyph fits in `availableInlineSize`, summing `clusterWidths` (each grapheme's full advance sits at its first code unit, so the prefix-sum totals correctly).
2. Emit a fragment of the token covering code units `0..h` followed by a hyphen glyph (advance from font metrics).
3. The remainder (code units `h..end`) becomes the head of the next line, with its style and ancestors preserved. Because hyphen offsets are UAX #29 break opportunities, a split never falls inside a grapheme cluster.

When the token has no hyphen opportunity that fits, the token is placed on the current line anyway (overflow) — CSS spec behavior for un-hyphenateable overflow.

### Inline-block sizing

When a token's `inlineBlock` is set:

1. If `cs.inlineSize` is a number, use it directly.
2. Else (`auto`), call `computeIntrinsicSizes(child, shaper, ctx.intrinsicCache)` and use `intrinsic.maxContent` (current implementation; CSS-spec shrink-to-fit would be `min(maxContent, max(minContent, available))` — see state-of-branch F3J.1).
3. Lay out the inline-block via `layoutBlock(child, 0, 0, makeRootContext(cs, finalInlineSize), shaper)` — a fresh BFC root.
4. The result's `width` becomes the token's effective width for line packing.

### Baseline alignment

Each line's baseline is the dominant baseline among its tokens. Tokens with `verticalAlign`:
- `baseline` (default): glyph baseline aligns with line baseline.
- `top` / `bottom`: glyph top / bottom aligns with line top / bottom.
- `middle`: glyph midpoint aligns with line midpoint.
- `sub` / `super` (target architecture): glyph baseline shifts by a fraction of font-size.

The line's `height` is `max(ascent) + max(descent)` across its tokens after vertical-align adjustments.

### IFC paragraph cache

```ts
interface IFCState {
  readonly tokens: readonly Token[];        // identity check (via findChangePoint)
  readonly lines: readonly LineBox[];
  readonly availableInlineSize: number;     // invariant
  readonly textAlign: TextAlign;            // lines bake in their alignment offset
  readonly direction: Direction;            // lines bake in visual (bidi) order
  readonly textIndent: number;              // first line bakes in the indent
}

interface IFCStateCache {
  get(paragraphKey: string): IFCState | undefined;
  set(paragraphKey: string, state: IFCState): void;
  invalidate(paragraphKey: string): void;
  clear(): void;
}
```

The cache is keyed by `paragraph.key`. Hit requires ALL of: `availableInlineSize`, `textAlign`, `direction`, and `textIndent` unchanged AND `findChangePoint(cached.tokens, tokens) === -1` (tokens identical). The alignment / direction / indent gates are load-bearing because each cached line bakes in its aligned position, visual bidi order, and (first line) indent offset — an attribute-only change with identical tokens must still re-lay. Miss: re-tokenize and re-wrap, then store. The cache is bypassed entirely when fragmentation is active (a cached box holds all lines, not a partial fragment), and `invalidate`d / `clear`ed when the layout context is reset (typically on container-width change).

### Performance contracts

- `layoutInlineContent` cold (no cache): O(T) where T = token count.
- `layoutInlineContent` cache hit: O(1).
- Convergence-detection wrap (when wired): O(D + suffix-prefix) where D is the change region.

## Fragmentation

`layoutInlineContent` accepts `fragmentation?: FragmentationContext` and returns `LayoutResult<BlockBox> { box, breakToken }`.

The wrap pass produces all lines first (line layout is deterministic given content + width). When fragmentation is active, the IFC walks the lines (or a suffix of them, if resuming) accumulating block-axis used size, and applies the split-point search:

1. **Fit-loop.** Find the largest `k` such that `sum(lineHeights[0..k])` fits in `availableBlockSize`.

2. **Orphans constraint.** Require `k >= orphans` (default 2 per CSS Fragmentation L4). If not, push whole paragraph (return `box: null + IFCBreakToken { resumeAtLine: 0 }`).

3. **Widows constraint.** Back off `k` until `lines.length - k >= widows` (default 2). If the back-off violates orphans, push whole paragraph.

4. **Hyphen-pair constraint** (CSS Fragmentation L4 §5). If `lines[k-1]` ends with a hyphenation continuation onto `lines[k]`, back off `k`. Re-check orphans after back-off.

5. **Resume.** When `fragmentation.resumeFrom.type === "ifc"`, IFC re-runs line layout from line 0 (deterministic) and emits lines starting at `resumeAtLine`. The constraints above apply to the suffix, not the full set.

Caches are bypassed when fragmentation is active (the cache stores full all-lines results; partial outputs must not poison it).
