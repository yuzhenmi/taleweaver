# 1.5 — Pagination

Pagination splits the document into a sequence of output pages. The
paginated path is VIRTUALIZED into two passes: a cheap MEASURE pass that
computes where pages break (run every keystroke), and an on-demand POSITION
pass that materializes one `PageBox` at a time. Both honor the CSS
Fragmentation Module Level 4 rules: whole-block-fits-on-page first, then
within-block fragmentation at line boundaries, with widows/orphans and
`break-*` properties constraining where breaks may occur.

## Where pagination sits

Pagination is part of the layout module — code lives under
`packages/core/src/layout/` alongside the formatting contexts. A cheap
measure pass computes the page boundaries (the `PagePlan`) from cached
per-block fragmentation metadata — allocation-free, run every keystroke in
the reducer — and a separate on-demand `getPage(i)` positions ONE page at a
time by driving the BFC's fragmentation-aware child-placement loop
(`layoutBlock` with a `FragmentationContext`) over that page's content range.
Pages the viewport never requests are never positioned. Floats / `clear`
documents fall back to the legacy eager full-positioned path (`paginateRoot`).

## Inputs

Pagination activates when the editor's `EditorConfig` carries
pagination settings:

- `pageInlineSize` / `pageBlockSize` — the page's logical inline-size and
  block-size.
- `pageMargins` — the page's content-area margins (`blockStart` / `blockEnd` /
  `inlineStart` / `inlineEnd`). The content area is the page minus margins;
  headers and footers occupy the top and bottom margins respectively.
- `pageGap` — the visual gap between successive pages when rendered to
  a screen.

When these are absent, the engine produces a single `BlockBox` with no
page wrapping (the non-paginated mode used during composition or
testing).

## Output

A `PageBox` is a layout-box variant whose children are the content
that fits on one page (some `BlockBox`es, some partial `BlockBox`es
fragmented at line boundaries), plus the laid-out header/footer/footnote
slots.

A paginated document root is a `VirtualLayoutTree` (discriminated from a
plain `LayoutBox` by `type: "virtual-root"`): it holds the `PagePlan` (the
page boundaries from the measure pass) and a memoizing `getPage(i)` /
`getPages(from, to)` that positions pages on demand — pages the viewport
never requests are never positioned. A non-paginated document (no page
config), or a floats/`clear` document via the legacy fallback, produces a
fully-positioned `LayoutBox` instead. Pages render vertically with `pageGap`
between them.

Each materialized `PageBox` carries:

- The page's logical position in the document (page index, page break
  before/after rules that produced this page).
- Header and footer slots, each holding the section's header/footer
  template body laid into the margin band (or `null` if none).
- Footnote slot for any footnotes that landed on this page.

## Fragmentation rules

The fragmenter walks the document's flow content top-down:

1. **Whole-block placement.** Try to fit each block on the current
   page. If it fits, place it and advance the block offset.

2. **`break-before` / `break-after`.** If a block has `break-before:
   page` (or `column`/`region`), force a page break before it; finish
   the current page at the previous block's end. Same for `break-after`
   on the previous block.

3. **Block doesn't fit and `break-inside: avoid`.** Push the block to
   the next page, even if that leaves whitespace at the bottom of the
   current page.

4. **Block doesn't fit and is fragmentable.** Find the line within the
   block where the page break should fall:
   - Honor widows/orphans: at least N lines on each side of the break.
   - Avoid breaks inside word-broken regions (don't split a hyphenated
     word across pages).
   - Lines emit a `LineBox` for the prefix on the current page; the
     suffix starts a new partial `BlockBox` on the next page.

5. **Footnotes.** When inline content contains a footnote reference
   (`float: footnote` per CSS Generated Content for Paged Media), the
   footnote body floats to the bottom of the page that contains its
   reference. Pagination reserves the footnote's height in the current
   page's available size before fitting the next line.

6. **Repeating header rows in tables.** When a table fragments across
   pages, its `thead` rows repeat at the top of each page-portion of
   the table.

## Page templates

Each page carries running content drawn from the owning section:

- **Running headers and footers.** Header/footer template BODIES (block subtrees in
  `templateContents`) are cascaded and laid into each page's header/footer slot;
  per-page text like page numbers comes from layout-dependent **page-fields** (see
  Reference), NOT CSS `target-counter()`. Association + growing-slot behaviour are in
  the "Headers and footers (page templates)" Reference subsection.
- **First / left / right page variants** (cover page, mirrored book spreads) are not
  yet built.

## Layout-dependent values (page numbers, totals)

Per-page running values — page numbers, the document total — follow the
WORD-PROCESSOR model, not CSS `target-counter()` / generated content (which
are out of scope; see the "Generated content" note under Reference). A
`page-field` inline embed renders a page-agnostic placeholder, and its value
is bound LATE during the per-page materialize, with a bounded width-convergence
loop closing the value→header-wrap→page-count feedback. See "Layout-dependent
fields (page-fields)" under Reference for the full pipeline.

## Why pagination is a distinct doc

Pagination cuts across the BFC (where blocks stack), the IFC (where
lines emit), the Table FC (where row repetition happens), and the
render layer (where header/footer bodies + page-fields slot in). Documenting it
separately lets the per-formatting-context docs stay focused on the
within-page algorithms while pagination owns the fragmentation rules
that span them.

## Reference

### Types

```ts
interface PageBox extends LayoutBoxBase {
  readonly type: "page";
  readonly children: readonly LayoutBox[];
  readonly pageIndex: number;            // 0-based
  readonly headerSlot: BlockBox | null;  // the section's header template body, laid into the top margin band
  readonly footerSlot: BlockBox | null;  // the section's footer body, laid into the bottom margin band
  readonly footnoteSlot: BlockBox | null;
  readonly effectiveTopInset: number;    // page-local top of the body content area: = margin on plain
  readonly effectiveBottomInset: number; // pages, > margin on a #328 growing-slot page (header/footer taller than its margin)
}

interface PageConfig {
  readonly pageInlineSize: number;       // logical inline-size
  readonly pageBlockSize:  number;       // logical block-size
  readonly pageMargins: {
    readonly inlineStart: number;
    readonly inlineEnd:   number;
    readonly blockStart:  number;
    readonly blockEnd:    number;
  };
  readonly pageGap: number;              // visual gap between pages on screen
}
```

There is NO `PageTemplate` / `PageContext` type. Headers and footers are real
template BODIES (block subtrees in the state's `templateContents` tree), NOT
render-function callbacks; per-page running values like page numbers come from
**page-fields** (see "Layout-dependent fields" below), not a `pageContext`. Each
section associates its header/footer body and any per-section page geometry on its
`SectionBoundary` (`headerBlockId` / `footerBlockId` / per-section `pageConfig?`
override — see `section-plan.ts`); the implicit leading section reads the doc-root
box's `headerBlockId` / `footerBlockId` metadata. First/left/right-page template
VARIANTS (cover page, mirrored spreads) are not yet built.

### Pagination passes (measure + position)

The paginated path is virtualized into two passes (both under
`packages/core/src/layout/`); `dispatch.layoutTree` selects them and returns a
`LayoutBox | VirtualLayoutTree`.

**1. Measure pass — every keystroke (`buildVirtualPaginatedTree` / `measurePass`).**
`buildVirtualPaginatedTree` first builds per-block fragmentation metadata
(`buildBlockFitMetas`, cached by cascaded-node ref so an unchanged block costs
nothing), then `measurePass` computes the `PagePlan` — the sequence of page
boundaries — via an allocation-free fit-core over those metas (threaded with the
section plan, header/footer slot insets, and footnote reservations). It computes
WHERE pages break, NOT where boxes sit, so it is cheap enough to run on every
keystroke; the prior plan is carried forward so unchanged pages are reused.
`buildVirtualPaginatedTree` also runs `resolveFootnotes` (the footnote layout pass)
and a bounded §4.4 width-convergence loop (for page-field widths) over these same
CHEAP measure passes — never `getPage` — before handing the plan to
`makeVirtualLayoutTree`; see `### Footnotes` and `### Layout-dependent fields`.

**2. Position pass — on demand (`makeVirtualLayoutTree` / `getPage(i)`).**
`makeVirtualLayoutTree` returns the `VirtualLayoutTree`. `getPage(i)` materializes
a positioned `PageBox` for page `i` by running `layoutBlock` over that page's
content range (the plan entry's `resumeInto` break token + `stopBeforeIndex` cap),
then laying its header/footer/footnote slots; results are memoized per index.
Pages the caller never requests are never positioned — calling only `getPage(19)`
on a 20-page document positions one page, not twenty. Invariant: `getPage(i)` is
deep-equal to the page `i` the legacy `paginateRoot` would position.

**Legacy fallback — floats / `clear` (`paginateRoot`).**
`measurePassUnsupported(cascadedRoot)` returns true when any descendant uses
`float: inline-start|inline-end` or `clear` (non-local break decisions the fit-core
measure pass does not model in v1). Such documents take the legacy eager
coordinator `paginateRoot`, which drives `layoutBlock` one page at a time —
resuming each page from the prior page's `BreakToken` until layout completes — and
returns a fully-positioned page tree (`LayoutBox`, not a `VirtualLayoutTree`):

```
function paginateRoot(root, ctx, shaper, pageConfig):
  pages = []; resumeFrom = null; pageIndex = 0
  contentBlockSize = pageBlockSize - margins.blockStart - margins.blockEnd
  do:
    { box, breakToken } = layoutBlock(root, ctx, shaper,
      { availableBlockSize: contentBlockSize, pageIndex, resumeFrom })
    box = physicalizeVertical(box, pageBlockSize)   // map logical→physical for vertical writing modes
    pages.push(makePageBox(pageIndex, box.children, geometry))
    resumeFrom = breakToken; pageIndex += 1
  while resumeFrom is not null
  return wrapPagesAsRoot(pages)
```

The break-aware behavior — honoring `break-before`/`break-after`/`break-inside`,
widows/orphans constraints, the overflow rule, and margin truncation across breaks
— lives inside each formatting context (both passes share it; `layoutBlock` accepts
a `FragmentationContext` and may stop early, returning `{ box, breakToken }`). See
[`1.4.1-bfc.md`](1.4-layout/1.4.1-bfc.md),
[`1.4.2-ifc.md`](1.4-layout/1.4.2-ifc.md), and
[`1.4.3-table-fc.md`](1.4-layout/1.4.3-table-fc.md) for the per-FC fragmentation
rules. The `BreakToken` types are defined in
`packages/core/src/layout/fragmentation.ts`.

### Footnotes

Inline content with `float: footnote` (a CSS Generated Content for Paged Media value) reserves block-axis space at the bottom of the current page. The fragmenter's `availableForFlow` shrinks by `footnoteSlot.blockSize` when footnotes accumulate; this can force earlier content to push to the next page.

### Layout-dependent fields (page-fields)

Page-number / page-count fields display values that only exist AFTER pagination — the
self page index, or the document's total page count. They follow the word-processor model
(NOT CSS `target-counter()` / `counter()`, which are out of scope — see "Generated content"
below): a `page-field` inline embed renders a page-AGNOSTIC placeholder at render time
(`1.2-render.md`), and the value is bound LATE, per page, at materialize. Two stages, in
`virtual-producer.ts` (the layout build) then at `getPage` (materialize):

1. **Collect (once, before the loop): `collectPageFields(cascadedTemplateContents, rootChildren)
   → FieldSpec[]`** — a pure walk over the cascaded render trees finds every `page-field` atom,
   keyed by its stable render key (`${blockId}/inline/${i}`), carrying `fieldKind` / `numberStyle`
   / `computedStyle` / `host` (`"template"` for header/footer, `"main"` collected but unconsumed —
   main-body page-fields are out of scope).
2. **§4.4 width-convergence loop: `runFieldConvergence`** (`field-convergence.ts`). THE feedback:
   a wide value (`"of 100"`) can wrap a header to an extra line → taller slot → shorter body → more
   pages → different value. A bounded grow-only iterate-to-fixpoint (mirrors the FN-6 footnote
   convergence) whose body re-runs only the CHEAP measure passes (never `getPage`):
   1. **`patchFieldWidths(templates, grownWidths)`** (`patch-field-widths.ts`) — spine-clones the
      cascaded template bodies, overriding each overflowing TEMPLATE field's placeholder
      `inlineSize` to the grown reservation so the slot reserves room for the wide value.
   2. `computeSlotInsets` + `measurePass` + `resolveFootnotes` — re-derive the header/footer slot
      height + re-paginate against the grown placeholder.
   3. `resolvePageFields(plan, fieldSpecs, measurer) → { globalFieldValues, maxValueWidthByKey }` —
      `page-count` resolves once from `plan.entries.length` (same value every page); `page-number`
      is per-page. `maxValueWidthByKey` (each field's widest value width) is the overflow signal:
      grow any field whose width exceeds its reservation and iterate, bounded at
      `MAX_FIELD_CONVERGENCE_ITERATIONS` with a 2-cycle pin-to-larger. The common case (every value
      ≤ the reserved placeholder width, < 100 pages) is a single body pass then break —
      byte-identical to a no-field build.
3. **Substitute (at materialize / `getPage`, AFTER the loop): `substitutePageFields(body,
   pageIndex, globalFieldValues)`** — a spine-clone that replaces each placeholder's text with its
   per-page value (`page-number` = `pageIndex + 1`; `page-count` = `globalFieldValues`),
   identity-preserving elsewhere (the FN-6.2b late-binding precedent). The page fingerprint folds
   the per-page value strings so a value change (the doc grew a page) busts the carry-forward while
   an unchanged page reuses. This runs per materialized page and does NOT feed back into the loop.

### Generated content

CSS generated content — `counter()` / `counters()` / `target-counter()`, `::before` / `::after` /
`::marker` pseudo-elements, the `content:` property — is **OUT of scope** (discarded 2026-06-06;
this engine follows the word-processor model, not CSS, for these capabilities). The capabilities they
would serve are modeled the Google-Docs way: **list numbering** via the render-time numbering service
(`1.2-render.md`); **cross-references** via reference fields; **per-page page numbers** via the
layout-dependent page-fields above. There is no generated-content / `::marker` styling surface.

### Headers and footers (page templates)

A header/footer is a real template BODY — a block subtree (container root with
paragraphs) living in the state's `templateContents` tree — NOT a render-function
callback. It is rendered (`RenderOutput.templateContents`), cascaded
(`cascadedTemplateContents`), and laid into each page's `headerSlot` / `footerSlot`
by the per-page materialize (`makeVirtualLayoutTree` / `materializePage`'s
`layoutSlot`). The SAME body renders into every page that the owning section spans;
per-page running values (page numbers) come from page-fields substituted at
materialize (see "Layout-dependent fields"), not from re-rendering the body per page.

Association + per-section geometry live on the `SectionBoundary` (`section-plan.ts`):

- `headerBlockId` / `footerBlockId` — the `templateContents` body ids for this
  section's header / footer slot. The implicit leading section reads them from the
  doc-root box's `headerBlockId` / `footerBlockId` metadata.
- `pageConfig?` — a per-section page-geometry override (e.g. a landscape section),
  resolved over the doc-wide `PageConfig`. Absent ⇒ the doc-wide config.

**Growing slot (#328/#329).** `computeSlotInsets` lays each section's header/footer
body at the section's effective content inline-size and takes its NATURAL (uncapped)
height, then `max`es against the raw page margin: a header taller than its margin
band PUSHES the body content down (the footer pushes it up) — content-shrinking, like
Google Docs. The growth is capped (#329) so a header/footer taller than the page can
never drive the body content area ≤ 0.

First/left/right-page template VARIANTS (cover page, mirrored book spreads) are not
yet built.

### Performance contracts

- **Measure pass (every keystroke):** allocation-free fit-core over cached per-block
  metas. Carry-forward reuses unchanged page entries from the prior plan, so a
  localized edit re-fits only from the affected page onward (the earlier pages reuse
  by reference) — the target is O(1)-at-end for an edit that doesn't shift earlier
  page counts. This is the pass the virtualized split makes cheap enough to run in
  the reducer on every keystroke.
- **Position pass (`getPage`):** O(content on that page) per requested page, memoized
  per index. Viewport-bounded — the controller positions only the visible pages (plus
  the cursor's page), so a 200-page document positions a handful of pages, not 200.
- **Legacy `paginateRoot` fallback (floats / `clear`):** O(N + P × header/footer-cost)
  cold, where N is content size and P is page count — it positions every page eagerly.
  This is why floats/`clear` documents are the slow path and the only remaining
  non-virtualized carve-out.
