# 1.0 — `styles/`

The styles module is the type vocabulary. Every other module in the
engine imports from here; nothing here imports from anywhere else in
core. `styles/` defines the three forms of style that flow through the
pipeline (declared → computed → used), the shared primitives
(`Length`, `Color`, `Display`, `WritingMode`, etc.), the inheritance
metadata (`PROPERTY_META`), and the initial-value table
(`INITIAL_COMPUTED_STYLE`). It also owns the logical↔physical axis
arithmetic that LayoutBox factories invoke.

## Submodules

- **`style.ts`** — declared `Style` (all-optional partial) and the
  enumerations referenced by it (`Display`, `BorderStyle`, `FontWeight`,
  `FontStyle`, `WhiteSpace`, `VerticalAlign`, `Float`, `Clear`,
  `BreakBefore`/`After`/`Inside`, `ListStyleType`, `ListStylePosition`,
  `BoxSizing`).

- **`computed-style.ts`** — `ComputedStyle` (all-required, post-cascade).

- **`used-style.ts`** — `UsedStyle` (all-required, fully numeric, post-layout).

- **`length.ts`** — `Length`, `LengthOrAuto`, `ComputedLength`,
  `ComputedLengthOrAuto`, `UsedLength`, `UsedLengthOrAuto`,
  `IntrinsicSizingKeyword`, plus `LogicalRect` and `PhysicalRect` for
  the axis arithmetic.

- **`color.ts`** — `Color = string` (CSS color string; validation
  deferred to consumers).

- **`writing-mode.ts`** — `WritingMode`, `Direction`, the exhaustiveness
  guard `assertNeverWritingMode`, the axis-mapping arithmetic
  `logicalToPhysical` / `physicalToLogical`, and the consumer-facing axis
  selector `axisMapFor`.

- **`property-meta.ts`** — `PROPERTY_META` (per-property inheritance
  flag) and `INITIAL_COMPUTED_STYLE` (the canonical initial-value
  record).

### `PROPERTY_META`

Closed mapping; one entry per `Style` key. The `inherits` flag drives `composeComputed`'s decision to inherit from parent vs. take initial.

```ts
const PROPERTY_META: Record<keyof Style, { inherits: boolean }> = { /* ... */ };
```

The full inheritance table appears in [`1.3-cascade.md`](1.3-cascade.md#property_meta--inheritance-flags).

### `logicalToPhysical` — full mapping for all writing modes

`LayoutBox` factories accept logical-axis args (`inlineOffset`, `blockOffset`, `inlineSize`, `blockSize`) and call `logicalToPhysical` to derive the physical-axis fields (`x`, `y`, `width`, `height`). It handles all three writing modes via a switch over the `WritingMode` union whose `default` arm calls `assertNeverWritingMode` — so a future 4th mode is a compile error at every call site, and an out-of-union value (reachable only via a cast) throws at runtime.

```ts
function logicalToPhysical(
  logical: LogicalRect,
  writingMode: WritingMode,
  direction: Direction,
  containingInlineSize: number,
  containingBlockSize?: number | "indefinite",  // vertical-rl block-axis mirror only
): PhysicalRect;
```

`containingInlineSize` is required for inline-axis mirroring (RTL in any mode). `containingBlockSize` is consulted ONLY by `vertical-rl`, for its block-axis (physical x) mirror; it is optional because the box factory does not have the containing block-size at construction time (an auto-size block's block extent is the OUTPUT of laying out its children). When it is omitted or `"indefinite"`, `vertical-rl` returns the un-mirrored pending x (`x = blockOffset`); the post-layout `physicalizeVertical` pass corrects it once the containing block-size is resolved (see [`1.4-layout/overview.md`](1.4-layout/overview.md#logical-axis-discipline-and-the-vertical-rl-physicalize-pass)).

The mapping by `(writingMode, direction)`:

#### `horizontal-tb` (default)

The block axis runs top-to-bottom; the inline axis runs left-to-right (LTR) or right-to-left (RTL).

| Direction | `x` | `y` | `width` | `height` |
|---|---|---|---|---|
| `ltr` | `inlineOffset` | `blockOffset` | `inlineSize` | `blockSize` |
| `rtl` | `containingInlineSize − inlineOffset − inlineSize` | `blockOffset` | `inlineSize` | `blockSize` |

In LTR the mapping is identity. In RTL the inline-start edge is on the right; physical x is mirrored against the containing block's inline-size.

#### `vertical-rl`

The block axis runs right-to-left; the inline axis runs top-to-bottom (LTR) or bottom-to-top (RTL). Common for traditional Chinese, Japanese, Mongolian.

| Direction | `x` | `y` | `width` | `height` |
|---|---|---|---|---|
| `ltr` | `containingBlockSize − blockOffset − blockSize` | `inlineOffset` | `blockSize` | `inlineSize` |
| `rtl` | `containingBlockSize − blockOffset − blockSize` | `containingInlineSize − inlineOffset − inlineSize` | `blockSize` | `inlineSize` |

The block axis maps to physical x (mirrored: blocks stack right-to-left). The inline axis maps to physical y. Logical width and height swap when crossing into physical: a box that's `inlineSize=100, blockSize=200` has physical `width=200, height=100`.

Because `containingBlockSize` is indefinite at box-factory time for an auto-size block, the `vertical-rl` block-axis mirror is deferred: the factory stores the un-mirrored pending x, and the post-layout `physicalizeVertical` pass bakes in the mirror once every container's `blockSize` is resolved. The painter must rotate glyph rendering 90° clockwise so that a horizontal-script run paints downward along the inline axis `[missing]`.

#### `vertical-lr`

The block axis runs left-to-right; the inline axis runs top-to-bottom (LTR) or bottom-to-top (RTL).

| Direction | `x` | `y` | `width` | `height` |
|---|---|---|---|---|
| `ltr` | `blockOffset` | `inlineOffset` | `blockSize` | `inlineSize` |
| `rtl` | `blockOffset` | `containingInlineSize − inlineOffset − inlineSize` | `blockSize` | `inlineSize` |

Symmetric to `vertical-rl` but blocks stack left-to-right.

#### Painter integration `[missing]`

For non-`horizontal-tb` modes the painter must apply a ±90° rotation to text runs so a horizontal-script run paints along the inline axis. This is the browser-gated remainder of vertical writing-mode support — the box geometry, axis arithmetic, and editing geometry are in place, but the renderer still paints glyphs horizontally and the caret as a vertical bar. Target:

- `vertical-rl`: rotate +90° (clockwise) about the run's start point. Latin glyphs end up rotated; CJK glyphs would be drawn upright by `text-orientation: upright` (a future property).
- `vertical-lr`: rotate +90° likewise; the difference vs. `vertical-rl` is purely in the block-axis direction.

`text-orientation` (CSS Writing Modes 3) selects whether non-CJK glyphs are upright or sideways within vertical writing modes — a future schema addition (see [state-of-branch](../state-of-branch.md)).

### Borders, paddings, and the writing-mode swap

The logical border/padding fields (`borderBlockStartWidth`, `paddingInlineEnd`, etc.) keep their logical semantics through cascade and layout. The painter maps them to physical sides using `logicalToPhysical` semantics:

| Logical side | `horizontal-tb LTR` | `horizontal-tb RTL` | `vertical-rl` | `vertical-lr` |
|---|---|---|---|---|
| block-start | top | top | right | left |
| block-end | bottom | bottom | left | right |
| inline-start | left | right | top (LTR) / bottom (RTL) | top (LTR) / bottom (RTL) |
| inline-end | right | left | bottom (LTR) / top (RTL) | bottom (LTR) / top (RTL) |

A helper in `dom/canvas-renderer.ts` (`physicalBorderSides`) materializes this mapping for paint via an exhaustive switch over the `WritingMode` union (see [`2-dom/2.2-canvas-renderer.md`](../2-dom/2.2-canvas-renderer.md)).

### `physicalToLogical`

The exact inverse of `logicalToPhysical` for every `(writingMode, direction)` combo — the physical→logical mapping available to any consumer that needs to map a physical point/rect back to the logical axes. (The current hit-test path derives logical coordinates via `axisMapFor` directly rather than calling this.) For `vertical-rl` the `containingBlockSize` arg must match the form that produced the physical rect: supply it to invert the mirror, omit it to invert the un-mirrored (pending) form.

```ts
function physicalToLogical(
  physical: PhysicalRect,
  writingMode: WritingMode,
  direction: Direction,
  containingInlineSize: number,
  containingBlockSize?: number | "indefinite",
): LogicalRect;
```

### `axisMapFor`

The consumer-facing axis selector: which physical axis each logical axis maps to, plus whether the inline axis is reversed. Layout and cursor code call it to pick the right physical coordinate without re-deriving the full mapping table.

```ts
interface AxisMap {
  readonly inline: "x" | "y";       // physical axis the logical inline axis maps to
  readonly block:  "x" | "y";       // physical axis the logical block axis maps to
  readonly inlineReversed: boolean; // true iff direction is rtl (inline-start at the far end)
}

function axisMapFor(writingMode: WritingMode, direction: Direction): AxisMap;
```

`horizontal-tb` maps inline→x, block→y; both vertical modes map inline→y, block→x. `inlineReversed` is `true` iff `direction === "rtl"`.

### Performance contracts

- All primitives are simple types; no allocation costs at the type level.
- `logicalToPhysical` / `physicalToLogical` / `axisMapFor`: O(1).
- `INITIAL_COMPUTED_STYLE` is a single shared frozen reference — cascade reuses it across calls without allocation.
