# 1.8 — Accessibility

The engine paints its document onto a `<canvas>`, which is opaque to
assistive technology: a screen reader sees one image, not text, headings,
lists, or tables. The accessibility module closes that gap by producing a
pure, geometry-free **semantic projection** of the document — an
`AccessibilityNode` tree that a host materializes into a hidden DOM mirror
(see "The core/host split" below).

`buildAccessibilityTree(state, options?)` is the whole core surface. It is a
**read-side projection**, a sibling of `getOutline` and `extractText`: it
reads `State` and returns a tree, with **no layout, no canvas, and no
geometry dependency**. It never mutates state and never touches the render
or layout passes — accessibility is derived from the document model alone,
so it is correct independent of what is currently laid out or on screen.

## The `AccessibilityNode` shape

The projection is a tree of `AccessibilityNode`s. The interface is
**role-discriminated**: which optional fields are meaningful depends on
`role`. It carries typed fields only — there is no stringly-typed property
bag, so a consumer reads `node.level` or `run.link` directly rather than
parsing an untyped map.

```ts
interface AccessibilityNode {
  readonly role: AccessibilityRole;
  readonly sourceBlockId: BlockId | null;   // null for synthetic nodes (lists)
  readonly name?: string;                    // accessible name (img alt, landmark label)
  readonly level?: number;                   // heading level, list-item nesting depth
  readonly listOrdered?: boolean;            // synthetic list: ordered vs unordered
  readonly listOrdinal?: number;             // ordered listitem: resolved number (start/restart) → <li value>
  readonly text?: readonly AccessibilityTextRun[];  // text-bearing leaves
  readonly children: readonly AccessibilityNode[];
}
```

`sourceBlockId` ties each node back to the block it projects (so a host can
map a screen-reader cursor back to a document position); it is `null` only
for **synthetic** nodes that have no single backing block — the grouping
`list` nodes the projection invents around runs of `list-item` blocks.

### Text runs and the literal-offset contract

A text-bearing leaf (`paragraph`, `heading`, `list-item`) carries its inline
content as a sequence of `AccessibilityTextRun`s:

```ts
interface AccessibilityTextRun {
  readonly text: string;                     // DISPLAY text (view-projected, embed-serialized)
  readonly sourceOffsetStart: number;        // LITERAL block offset, inclusive
  readonly sourceOffsetEnd: number;          // LITERAL block offset, exclusive
  readonly emphasis?: readonly ("bold" | "italic" | "underline" | "strikethrough")[];
  readonly link?: string;
  readonly suggestion?: "insertion" | "deletion";
  readonly inComment?: boolean;
  readonly noteref?: BlockId;                // footnote-anchor → its body block id
  readonly fieldKind?: "page-number" | "page-count" | "cross-ref-page";  // page-valued field
  readonly fieldKey?: string;                // render key `${blockId}/inline/${i}` for late value binding
  readonly imageAlt?: string;                // inline-image embed → its alt text (standalone run, empty `text`)
}
```

Inline content is split into runs by **link + emphasis + suggestion +
comment-membership**: adjacent items merge into one run iff all four match,
so a run is the maximal span of uniformly-styled, uniformly-provenanced text.

`text` is the **display** projection — the text after the requested
suggestion view and the caption embed serializer are applied.
`sourceOffsetStart`/`sourceOffsetEnd` are **literal block offsets** in the
editor's `Position` offset domain: a text item contributes one offset per
UTF-16 code unit, and **an embed contributes exactly one offset regardless
of how many display characters it serializes to**. The two are therefore
NOT interchangeable — an inline image occupies one literal offset but
serializes to zero display characters, so a run's `text.length` can be
smaller than `sourceOffsetEnd - sourceOffsetStart`. Every literal offset in
the block is covered by exactly one run (or consumed by a view-projected-away
item — see "suggestionView contract"). Carrying literal offsets is what lets
a host map a screen-reader selection inside a run back to an exact document
`Position`.

A `footnote-anchor` embed always flushes the open run and emits its own
standalone run with `noteref` set to the footnote body block id and empty
`text` — so a screen reader announces a reference point, and the host can
jump to the corresponding `doc-footnote` node.

An **inline-image** embed (the in-line image — see
[`1.2-render.md`](./1.2-render.md#inline-images-in-line-image-embeds)) flushes
the open run the same way and emits its own standalone run carrying `imageAlt`
(the embed's `alt`) with empty `text` — so a screen reader announces an image
with its alt text rather than dropping it into surrounding prose. The host
materializes such a run as a child-less `<span role="img" aria-label>` (see
"The core/host split"). An absent `alt` yields `aria-label=""`, deliberate
parity with the block-image path. Like every embed, it consumes exactly one
literal offset and zero display characters.

### Page-valued fields

A page-number / page-count field, and a cross-reference rendered in "page"
mode, display a value that only exists AFTER pagination assigns pages — so the
geometry-free projection cannot know the number. Each such field flushes the
open run and emits its OWN standalone run carrying `fieldKind`
(`"page-number"` / `"page-count"` / `"cross-ref-page"`) and `fieldKey` — the
field atom's render key `${blockId}/inline/${i}`, produced by the shared
`inlineRenderKey` helper (`render/inline-render-key.ts`) so the key matches the
layout side exactly — with a `""` placeholder `text` (the run is
geometry-free; it carries no resolved number). The host's materialization layer
resolves the run's display text LATE against the layout-resolved field values
(see [`2-print/2.11-dom-mirror-host.md`](../2-print/2.11-dom-mirror-host.md)),
keyed by `fieldKey`. `page-count` and `cross-ref-page` values come from the
layout tree's `globalFieldValues` map; `page-number` is per-page and has no
global value, so its run stays at the `""` placeholder. The TOC navigation
landmark carries no field runs — its synthesized entry-line page numbers are
layout-derived and not projected (see "Role mapping").

## Role mapping

Every block type maps to one ARIA-aligned role:

| Block type | Role | Notes |
|---|---|---|
| `document` | `document` | the root |
| `paragraph` | `paragraph` | text runs |
| `heading` | `heading` | `level` 1–6 (out-of-range coerces to 1) |
| `list-item` | `listitem` | grouped under synthetic `list` nodes (below) |
| `table` | `table` | |
| `table-row` | `row` | built by the dedicated table-subtree walk (descended from `table`), not the top-level block dispatch |
| `table-cell` | `cell` / `columnheader` | `columnheader` for cells in the first `headerRowCount` rows (pinned-header semantics); built by the table-subtree walk, not the top-level dispatch |
| `image` | `img` | `name` from the `alt` attr |
| `horizontal-line` | `separator` | |
| `table-of-contents` | `navigation` | a landmark; entry links are layout-derived and not projected |
| `footnote-body` | `doc-footnote` | a footnote landmark |
| `template-body` | `banner` / `contentinfo` | header → `banner`, footer → `contentinfo`, classified by reverse-lookup (below) |
| `section` | *(flattened)* | layout-transparent (`display:contents`) → accessibility-transparent: NO node; its children splice inline |

**Synthetic list grouping.** The document model is a flat Google-Docs list
model — a `list-item` is a leaf carrying `listId` + `listLevel` attrs, with
no `list` container block. The projection reconstructs the ARIA `list` →
`listitem` structure: a contiguous run of `list-item` siblings is grouped
into synthetic `list` node(s) (`sourceBlockId: null`), broken into separate
lists at each `listId` change, and nested by `listLevel` (a deeper item
becomes a child `list` of the preceding shallower `listitem`).
`listOrdered` is resolved from the list definition (`classifyListDef`),
defaulting to unordered when the def is absent. Each ORDERED `listitem` also
carries `listOrdinal` — its resolved number from the numbering engine
(`collectListEvents` → `computeCounters`, the same single source of truth the
render/HTML paths use), start-at / restart applied — so the dom-mirror host can
emit `<li value=N>` and an AT announces the true number rather than a bare
`<ol>`'s 1,2,3…. A flattened `section` acts as a list-grouping boundary — items
inside it are grouped independently and do not merge with outer items.

**Inline embeds** within a text run are handled by provenance rather than
producing nodes: a `footnote-anchor` becomes a `noteref` run (above);
`comment-start` / `comment-end` markers bracket a region whose runs carry
`inComment: true`; the suggestion attrs (`insertionSuggestionId` /
`deletionSuggestionId`) tag a run's `suggestion` as `"insertion"` /
`"deletion"`. A page-valued field (a page-number / page-count field, or a
cross-reference in "page" mode) flushes the open run and emits its own standalone
field run (see "Page-valued fields" above) — its value is bound late at the dom
boundary, not serialized here. An `inline-image` embed flushes the open run and
emits its own standalone `imageAlt` run (host-materialized as
`<span role="img" aria-label>` — see "Text runs" above). Any other embed serializes into the surrounding
run's display `text` via the caption embed serializer (a tab → `"\t"`, a hard
break → `"\n"`, a text-mode cross-reference → its resolved text), consuming its
one literal offset.

## Reading order

**Document order is reading order.** The projection walks the three document
trees in a fixed sequence, appended as trailing children of the root
`document` node:

1. the **main body** (the main blocks tree), then
2. **footnote bodies** (the `embedContents` tree → `doc-footnote` nodes), then
3. **header/footer template bodies** (the `templateContents` tree →
   `banner` / `contentinfo` nodes).

Main-body content comes first (it is the document); footnotes follow as
document-content landmarks; page furniture (headers/footers) comes last. A
`BlockResolver` abstracts the per-tree block lookup so the same recursive
builders walk the main tree and the body subtrees uniformly — the main tree
resolves through the main-blocks lookup, while embed/template body subtrees
(whose blocks live in their own `Y.Map`) resolve through the
all-trees lookup.

A `template-body` is classified `banner` vs `contentinfo` by **reverse
lookup**: the projection scans for the section block that links to the body
via its `headerBlockId` (→ `banner`) or `footerBlockId` (→ `contentinfo`)
attr.

## suggestionView contract

`BuildAccessibilityTreeOptions.suggestionView` selects which change-tracking
projection to read, defaulting to `"suggesting"` (every tracked edit is
visible, attributed). Under `"final"` a deletion is projected away and an
insertion is accepted; under `"original"` the inverse. An item that the
requested view projects away **contributes no run, but still consumes its
literal offset span** — so the surviving runs keep their original literal
offsets and never shift. This keeps `sourceOffset*` a stable address into the
block regardless of which view a host is presenting.

## The core/host split

The accessibility surface is deliberately split across two layers:

- **Core (this module) — present.** The pure semantic projection:
  `buildAccessibilityTree` and the `AccessibilityNode` vocabulary. Geometry-
  free, derived from `State` alone.

- **The structural DOM mirror builder — present.** `buildDomMirror`
  (`packages/print`, see [`2-print/2.10-dom-mirror.md`](../2-print/2.10-dom-mirror.md))
  transforms the `AccessibilityNode` tree into a detached, visually-offscreen
  but screen-reader-visible DOM subtree that mirrors the document semantics
  (a real `<h2>`, `<ul><li>`, `<table>`, `role="doc-footnote"`, etc.). It is a
  pure builder — no mounting, no controller coupling — and stamps each run's
  literal `sourceOffset*` onto the run wrapper as the hook the sync layer uses
  to translate between a DOM range and a document `Position`.

- **The mirror materialization layer — present.** `createDomMirrorHost`
  (`packages/print`, see [`2-print/2.11-dom-mirror-host.md`](../2-print/2.11-dom-mirror-host.md))
  mounts the hidden, screen-reader-visible, focusable mirror into the live
  document, owns incremental keyed reconciliation on each paint (including
  page-valued field resolution upstream of the diff — see "Page-valued fields"),
  wires the controlled-contenteditable input / IME / clipboard host, and keeps
  the browser `Selection` in the mirror synchronized with the engine's
  caret/selection (via the run `sourceOffset*` hooks). It ships behind the
  default-off `accessibilityMirror` flag; flipping the default ON is gated on the
  user's in-browser screen-reader / IME smoke.

- **The PDF tagged-structure consumer — present.** The same `AccessibilityNode`
  projection also feeds the PDF emitter: `exportToPdf` maps it (via
  `mapAccessibilityTree` in `packages/pdf`) into a `PdfStructureNode` tree that
  `emitPdf` turns into a `/StructTreeRoot` + marked content, so exported PDFs are
  tagged/accessible. This is the second consumer of the projection (the DOM mirror
  is the first) — the geometry-free semantic tree is the single source of truth for
  both the live screen-reader mirror and the exported-document structure. See
  [`2-print/../5-pdf/overview.md`](../5-pdf/overview.md) "Tagged-PDF accessibility" and
  the `state-of-branch.md` Tagged-PDF entry.

## Exhaustiveness invariant

Every registered block type **must** map to a role. The role switch ends in
a runtime guard that **throws** on an unmapped block type — a missing node is
an invisible accessibility regression (a heading or list that simply vanishes
from a screen reader), and a loud throw at projection time surfaces it
immediately. The guard is a *runtime* contract rather than a compile-time
`never` because `block.type` is an open `string` by design (third-party
components register arbitrary type strings at runtime, like the render
component registry and the editor action pipeline) — so a closed-union
`never` check cannot cover it. Adding a new block type to the engine
therefore requires adding its role to this switch in the same change.
