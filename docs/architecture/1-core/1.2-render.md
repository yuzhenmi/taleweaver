# 1.2 — `render/` and `components/`

The render layer translates a `StateNode` tree into a `RenderNode` tree
of layout-relevant elements. It bridges the *semantic* document model
(what the user typed) and the *layout-ready* representation (what to
draw, with declared styles). The translation is component-driven: each
node type registers a render function in the component registry; the
render walker dispatches per node.

## Two coupled modules

`components/` and `render/` are separate directories but coupled
responsibilities: `components/` defines the plugin surface (what render
functions can register), `render/` defines the data the registry
produces and the walker that drives it.

## What a render tree looks like

A `RenderNode` is one of:

- **`ElementBox`** — a layout-relevant element with a key, declared
  style, optional metadata (image src, list-marker text, table
  structure), and children.
- **`TextBox`** — a leaf carrying text content with declared style.

After cascade (the next pass), each render node carries a
`ComputedStyle` in addition to its declared `style`. The cascade pass
writes into the existing render tree by producing new frozen nodes;
unchanged subtrees keep their references.

Render nodes are keyed for stable identity across rebuilds. Keys flow
from state-node `id`s; anonymous boxes (those introduced by render
functions for layout-time grouping like list markers) use composite
keys derived from their parent.

## Submodules

### `components/`

- **`component-definition`** — the `ComponentDefinition` type:
  `{ type: string, render: (state, children) => RenderNode }`. A
  component is just a typed render function.

- **`component-registry`** — `ComponentRegistry` with `register`, `get`,
  `has`. Exposes `createRegistry(components[])` for downstream consumers
  to assemble their set.

- **Built-in components** — `document`, `paragraph`, `heading`, `text`,
  `span`, `list`, `list-item`, `table`, `table-row`, `table-cell`,
  `image`, `horizontal-line`. Each is a render function that maps state
  → RenderNode. Built-ins ship as a default set (`defaultComponents`)
  that consumers extend.

- **`factories`** — convenience constructors for state nodes that match
  built-in components (`createParagraph`, `createHeading`, etc.).

### `render/`

- **`render-node-v2`** — the `RenderNode` types (`ElementBox`,
  `TextBox`) and their factory functions. Frozen at construction.

- **`render`** — `renderTree(state, registry)` and
  `renderTreeIncremental(state, oldState, oldRender, registry)`.
  - `renderTree` walks the state bottom-up, dispatching each node
    through the registry.
  - `renderTreeIncremental` adds a structural-sharing short-circuit:
    when `state === oldState` at any level, the corresponding
    `oldRender` subtree returns by reference, preserving identity for
    downstream cascade and layout reuse.

- **`render-node`** (legacy) — an older render-node shape retained for
  backwards compatibility during migration. Sunset path.

## How modules connect

The reducer in `editor/` calls `renderTreeIncremental(newState,
oldState, oldRender, registry)` after every state mutation. The walker
descends the new state tree:

- For each state node, it looks up the component via the registry.
- It recursively renders children first (bottom-up), passing the
  rendered children into the parent's render function.
- The render function returns a `RenderNode` for that subtree.
- If `state === oldState` at the current node, the walker returns the
  prior render node directly without invoking the component — preserving
  reference equality on unchanged subtrees.

The output is the input to the cascade pass.

## Why this layer exists

Components let the engine accept new document primitives without
modification. A consumer adding charts registers a `chart` component;
the engine treats it as another `RenderNode` (typically an `ElementBox`
with chart metadata) and lays it out as an inline-block or block
element. The render layer is where the unbounded user-visible vocabulary
of state-node types collapses into the bounded vocabulary of layout
primitives.
