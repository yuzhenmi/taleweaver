# 1.2 — `render/` and `components/`

The render layer translates a Y.Doc-backed `State` (block tree) into a
`RenderNode` tree of layout-relevant elements. It bridges the *semantic*
document model (what the user typed, stored as blocks + inline items)
and the *layout-ready* representation (what to draw, with declared
styles). Component-driven: each block type registers a render function;
the render walker dispatches per block.

The render module's runtime shape follows the push-model decisions
captured in `docs/superpowers/specs/phase-5-plus/decisions.md`
(decisions B, F, G): renderer owns traversal, components receive
already-rendered children, registries are constructor-injected, and
`text` / `span` are not registered component types (the renderer
expands inline items directly).

## Two coupled modules

`render/` and `components/` are separate directories but coupled
responsibilities. `components/` defines the plugin surface (what render
functions can register, and what shape they declare). `render/` defines
the data they consume (`BlockView` / `RenderContext`), the data they
produce (`RenderNode`), and the walker that drives the dispatch.

## What a render tree looks like

A `RenderNode` is a discriminated union:

- **`ElementBox`** — a layout-relevant element with a stable `key`,
  declared `style`, optional `metadata` (image src, embed properties,
  list-marker text, etc.), an optional `computedStyle` (populated by
  the cascade pass, NOT by render), and children.
- **`TextBox`** — a leaf carrying `text` content with declared `style`
  and optional `computedStyle`, plus an optional `link?: string` — the raw
  hyperlink URL passed through from the inline item's `link` attr (parallel to
  the cascade's visual link styling), threaded onward to the layout text run for
  export consumers (PDF `/Link`).

Keys flow from state-`BlockId`s; inline items keyed under their leaf
block (`${blockId}/inline/${i}`) so the keys are stable across rebuilds
of the same block.

## The render / cascade boundary

After `render()` produces the RenderNode tree, `cascadePass(root)`
(from `cascade/cascade-pass.ts`) walks every node and populates
`RenderNode.computedStyle` for the layout pass to consume. The two
modules share the field but each owns a different write side:

- **`render/`** sets `BlockView.computedStyle` (for the component's own
  use — components read it during `def.render(view, ctx, children)`).
  This is a per-block resolution.
- **`cascade/`** sets `RenderNode.computedStyle` on every RenderNode
  produced by render (block-level and inline-level). This is the
  canonical field layout reads.

The two passes run different stages of the same cascade pipeline:

- **`render-core.ts`'s `composeBlockStyle`** runs the FULL pipeline:
  `AttrRegistry.applyAll → composeComputed → flattenLengths`. It
  translates the block's open-schema `attrs` into a declarable
  `Partial<Style>` (via `applyAll`), composes against parent + initial
  to a `ComputedStyle`, and flattens em/rem lengths. The result is
  attached to `BlockView.computedStyle`. The translated declarable
  style is then stored on the RenderNode the component returns
  (as `RenderNode.style`).
- **`cascadePass`** runs only `composeComputed → flattenLengths`. By
  the time cascade sees a RenderNode, `applyAll` has already happened
  in render — `node.style` is already a translated `Style`, not the
  open-schema `attrs`. So cascade re-composes against parent and
  re-flattens, producing the final `RenderNode.computedStyle` for
  every node in the tree.

The two share the `composeComputed → flattenLengths` tail; render
includes the `applyAll` head because it has the original `attrs`.
Their results agree on the field they both touch (`computedStyle`).

## Submodules

### `components/`

- **`component-definition`** — the discriminated union
  `ComponentDefinition = ContainerComponentDefinition | LeafComponentDefinition`.
  Container components carry `kind: "container"` and receive
  `childRenderNodes`; leaf components carry `kind: "leaf"` plus a
  `leafShape: "inline-bearing" | "atomic"` (the kind-taxonomy field
  consumed by state via `BlockKindResolver`; see `1.1-state.md`).
- **`component-registry`** — `ComponentRegistry` with `register`, `get`,
  `has`, and `getBlockKind` (implementing `BlockKindResolver`).
  Constructor-injectable per Decision F.
- **Built-in components** — `document`, `section`, `paragraph`, `heading`,
  `list-item`, `table`, `table-row`, `table-cell`, `image`,
  `horizontal-line`, `footnote-body` (container for footnote body subtrees),
  `template-body` (container for header/footer body subtrees), and
  `table-of-contents` (atomic leaf that synthesizes entry lines from the
  document outline); `text` and `span` are deleted (no state-node types for
  them), and there is NO `list` container (the flat list model — a `list-item`
  is a leaf carrying `listId`/`listLevel` attrs; see `1.1-state.md`).
  `createDefaultComponentRegistry()` returns a registry pre-populated
  with all of them. `section` is a container that renders `display: contents`
  (CSS Display 3 §3.2): it generates NO box, so its body blocks lay out as if
  direct children of the document root — a section is a pagination-level
  grouping, transparent to the BFC/IFC. (Per-section page break + page geometry
  are a paginator concern, layered on `type === "section"` — not yet wired.)

### `render/`

- **`render-node`** — the `RenderNode` types (`ElementBox`, `TextBox`)
  and their factories (`createElementBox`, `createTextBox`). Factories
  freeze their output.
- **`block-view`** — the `BlockView` push-model types:
  `BlockViewBase`, `ContainerBlockView`, `LeafBlockView`, plus the
  `RenderContext` (read-only `State` + the per-cycle `footnoteNumber`
  lookup — the single cross-block seam).
- **`render-core`** — the shared push-model walker primitives: the
  per-block render body (`renderBlockBody`), the style composition
  (`composeBlockStyle`), and the inline-item expansion
  (`expandInlineItems`). This is the leaf of the render dependency graph —
  it imports neither `render` nor `render-incremental`, and both depend on
  it. `renderBlockBody` is parameterized over a `recurse` callback so the
  full path and the incremental path share one walk body without one
  importing the other. When a run carries change-tracking suggestion-id
  attrs, `expandInlineItems` resolves the suggestion visuals via
  `resolveSuggestionStyle`: insertion → author-color + underline, deletion →
  author-color + line-through, formatting → its `proposedAttrs` composited as
  a preview plus an author-color underline indicator. The author color comes
  from `authorColorOf` (deterministic per author); the fast path returns the
  base style unchanged for plain runs. A suggested paragraph BREAK (the
  `block-split-suggestion` / `block-join-suggestion` embeds) renders as a
  VISIBLE pilcrow (¶) wrapped in a single inline-block atom — split underlined
  (insertion-flavored), join struck (deletion-flavored), tinted by the owning
  record's author color — preserving the embed's one-token / one-offset
  invariant while making the mark visible (the comment-range markers keep the
  separate zero-width inline-block atom). All of the above is the
  `"suggesting"` view; a `RenderContext.suggestionView` of `"final"` / `"original"`
  (the change-tracking preview projection) instead PROJECTS the document as it
  would read once accepted / rejected: `expandInlineItems` drops the resolved-away
  items via `itemVisibleInView` (final → deletion runs + join breaks; original →
  insertion runs + split breaks), SUPPRESSES the suggestion decoration on the
  survivors, renders a surviving break embed as a zero-width atom (no pilcrow),
  and — in `"final"` only — applies a formatting proposal's `proposedAttrs` FOR
  REAL. (Block-boundary MERGE of an accepted-join / rejected-split is a separate
  future concern; in this view the blocks stay structurally distinct.)
- **`render`** — the full-render entry and the top-down recursion wrapper.
  Public entry `render(state, componentRegistry, attrRegistry,
  options?): RenderOutput`; owns the full-path recursion wrapper
  (`renderBlock`, which threads `renderBlockBody`'s `recurse` back into
  itself) and the `RenderOutput` / `RenderOptions` type exports. Depends on
  `render-core` for the walk body and on `render-incremental` for the
  incremental dispatch branch of `render()`.
- **`render-incremental`** — the incremental cache/invalidation engine.
  Owns the opt-in incremental rebuild path (`renderIncremental`,
  `renderBlockIncremental`) and the invalidated-set closure expansion
  (`computeInvalidatedBlocks`, `addAncestorsToInvalidated`,
  `addDescendantsToInvalidated`) plus the `prevByKey` index build
  (`indexRenderNodesByKey`). Depends on `render-core` for the walk body;
  the only thing it pulls from `render` is the `RenderOutput` TYPE
  (`import type`, erased at runtime). The runtime dependency graph is a
  clean DAG: `render-core` ← `render-incremental` ← `render`, and
  `render-core` ← `render` — no back-edge into `render`.
- **`render-footnotes`** — the footnote-numbering glue between the
  `footnotes/` module and the render walk: `makeRenderContext` (binds the
  per-cycle `footnoteNumber`), `effectiveRenderPolicy`,
  `footnoteAnchorsUnchanged` / `blockHasFootnoteAnchor` / `blockIsSection`
  (the FN-8 reuse predicates), and `EMPTY_FOOTNOTE_NUMBERS`. Imports render
  types via `import type` only, so no runtime cycle forms.
- **`resolve-cross-reference`** — the pure resolver for a cross-reference
  field: `resolveCrossReference(state, numbering, { targetId, refMode }, view)`
  returns the displayed string (`view` defaults to `"suggesting"`; `"text"` mode
  honors it, `"number"` mode is view-independent). `"number"` → `numbering.get(targetId).formatted`
  (the resolver's ONLY check is map presence; a target absent from the per-cycle
  numbering map — deleted, unregistered, or not a numbered list-item — yields the
  broken-ref text). `"text"` → the target block's full text via `getBlock` +
  `extractText` over its inline content (a missing or non-inline-bearing target
  → broken-ref). `getBlock` reads the MAIN body tree only, so `"text"` targets
  the body; `"number"` targets are body-scoped because the numbering map is built
  from the body tree. `BROKEN_CROSS_REFERENCE_TEXT` is the broken-ref string.
  (Structural target validation — wrong-kind, etc. — is the EDITOR handler's job,
  not the resolver's; see `1.5-editor.md`.)
- **`collect-cross-references`** — the cross-reference index + reuse predicate:
  `buildCrossReferenceIndex(state)` produces the `targetId → host blockIds`
  reverse index (main-tree doc-order scan, mirroring `collectFootnoteAnchors`;
  returns the shared empty `EMPTY_CROSS_REFERENCE_INDEX` for a ref-free doc),
  and `blockHasCrossReference(block)` is the incremental reuse-gate probe
  (mirrors `blockHasFootnoteAnchor`).

## How render works

```
render(state, componentRegistry, attrRegistry):
  1. Walk the main block tree top-down from state.rootId:
     a. For each block: compose its ComputedStyle via the cascade
        pipeline (attrRegistry.applyAll → composeComputed → flattenLengths).
     b. Build a BlockView (container or leaf) carrying that ComputedStyle.
     c. Container blocks: recursively render each child first; pass the
        resulting RenderNodes as `childRenderNodes` to the component.
     d. Leaf blocks: expand inlineContent.items into RenderNodes
        (TextBoxes for TextItems, ElementBoxes for EmbedItems); pass
        them as `inlineRenderNodes` to the component. A `cross-reference`
        EmbedItem expands to a one-token inline-block atom carrying the
        resolved string (`resolveCrossReference` — see below).
     e. Dispatch to componentRegistry.get(block.type).render(view, ctx, ...).
  2. Walk the embed-contents tree (footnote bodies, etc.) the same way,
     producing one RenderNode per embed-content subtree ROOT.
  3. Walk the template-contents tree (header/footer bodies) the same way,
     producing one RenderNode per template-content subtree ROOT.
  4. Return { root, embedContents, templateContents, footnoteAnchors,
     footnoteNumbers, listCounters, crossReferenceIndex } (see the
     RenderOutput reference below).
```

The pseudocode above is the **full-walk core**: the `render()` entry in
`render.ts` driving the per-block walk body (`renderBlockBody`) in
`render-core.ts`. When `render` is handed the incremental triple (`prev` /
`prevState` / `dirtyIds`), it delegates to the `render-incremental` engine,
which drives the SAME walk body and reuses
unchanged RenderNode subtrees by reference and only re-runs this walk on
the invalidated set (see "Incremental rebuild" below).

Cycle detection: a `Set<BlockId>` tracks the visit chain during
main-tree recursion. Re-entry of an already-visited block throws.
(Embed- and template-content subtrees use a fresh visited set per
subtree — they're independent walks in a separate id-namespace.)

The atomic-leaf strut: when a leaf block's `inlineContent.items` is
empty (e.g., an empty paragraph), the renderer emits a sentinel empty
TextBox so the IFC dispatch fires downstream and produces a strut line.
Atomic-leaf components (image, horizontal-line) ignore
`inlineRenderNodes` by convention.

## How modules connect

`render` consumes:
- `State` (read via `getBlock`, the embed/template subtree-root iterators
  `getEmbedContentIds`/`getTemplateContentIds`, and `getEmbedContent`/
  `getTemplateContent` — no `Y.Doc` exposure; the state module's
  `STATE_INTERNAL` symbol is not in scope here). The `*ContentIds` iterators
  yield the cached subtree ROOTS in O(roots), so consuming them per render
  does not tie the per-keystroke pipeline's O(D) cost to body size.
- `ComponentRegistry` (dispatch per block type).
- `AttrRegistry` (translate open-schema `attrs` to declarable `Style`).

`render` produces a `RenderOutput`, consumed by `cascade/cascadePass`
which populates `computedStyle` on every RenderNode, then by `layout/`
which dispatches per formatting context (BFC / IFC / Table FC).

## Reference

### `RenderNode`

```ts
type RenderNode = ElementBox | TextBox;

interface ElementBox {
  readonly type: "element";
  readonly key: string;
  readonly style: Readonly<Style>;
  readonly computedStyle?: Readonly<ComputedStyle>;   // populated by cascade
  readonly metadata?: Readonly<LayoutBoxMetadata>;
  readonly children: readonly RenderNode[];
}

interface TextBox {
  readonly type: "text";
  readonly key: string;
  readonly style: Readonly<Style>;
  readonly computedStyle?: Readonly<ComputedStyle>;   // populated by cascade
  readonly text: string;
  readonly link?: string;   // raw hyperlink URL (from the inline `link` attr); threaded to layout for export (PDF /Link)
}
```

`metadata` carries layout-relevant per-element data the layout pass
consumes verbatim. It is the typed `LayoutBoxMetadata` struct (defined in
the render layer, `render/layout-metadata.ts`, and shared with the
layout-layer `BlockBox` — see [`2.2-layout/overview.md`](../2-print/2.2-layout/overview.md#layoutboxmetadata)),
NOT an untyped `Record<string, unknown>` bag: known-shape keys (`image`,
`horizontalLine`, `columnWidths`, `headerRowCount`, `blockType`,
`embedType`) are strongly typed, while attrs-/embed-properties-derived
values (page geometry,
header/footer/content ids) stay `unknown` and are coerced at their read
boundaries. (Note: marker text — a list bullet, or a footnote body's
leading number — is NOT metadata; it is the `markerText` **Style**
property on the element's `computedStyle`, which the BFC reads to emit a
generated, offset-excluded `MarkerBox`.)

### `BlockView`

```ts
interface BlockViewBase {
  readonly id: BlockId;
  readonly type: string;
  readonly attrs: ReadonlyAttrs;
  readonly computedStyle: ComputedStyle;     // pre-resolved by renderer
}

interface ContainerBlockView extends BlockViewBase {
  readonly kind: "container";
}

interface LeafBlockView extends BlockViewBase {
  readonly kind: "leaf";
  readonly inlineContent: InlineContent;
}

type BlockView = ContainerBlockView | LeafBlockView;
```

### `RenderContext`

```ts
interface RenderContext {
  readonly state: State;
  // The formatted footnote number (e.g. "1") for a footnote BODY whose root id
  // is contentBlockId, or undefined if not a footnote body in this cycle's
  // numbering map. The footnote-body component reads this to set its generated
  // markerText (the leading "1" in the slot), sourced from the same per-cycle
  // footnoteNumbers map the call marker reads, so the two always agree.
  footnoteNumber(contentBlockId: BlockId): string | undefined;
  // The computed list marker for a block, from the render-time numbering
  // service. `scopeKey` is the block's `listId`; the result is the
  // `{ value, formatted }` CounterValue, or undefined when the block is
  // not numbered this cycle (or when the context omits the field — legacy
  // stub contexts). The list-item component bakes this into style.markerText.
  counterValue?(scopeKey: string, blockId: BlockId): CounterValue | undefined;
}
```

`RenderContext` carries the read-only `State`, the per-cycle
`footnoteNumber` lookup, and the per-cycle `counterValue` numbering lookup;
it keeps `BlockView` focused on "this block's own data" while leaving the
seams for cross-block lookups. Cross-block footnote lookups flow through
`footnoteNumber` + the `embedContents` map; list-marker numbers flow through
`counterValue` (bound to the per-cycle `listCounters` map by
`makeRenderContext(state, footnoteNumbers, listCounters)`).

### Component dispatch

```ts
interface ContainerComponentDefinition {
  readonly type: string;
  readonly kind: "container";
  render(
    view: ContainerBlockView,
    context: RenderContext,
    childRenderNodes: ReadonlyArray<RenderNode>,
  ): RenderNode;
}

interface LeafComponentDefinition {
  readonly type: string;
  readonly kind: "leaf";
  readonly leafShape: "inline-bearing" | "atomic";
  render(
    view: LeafBlockView,
    context: RenderContext,
    inlineRenderNodes: ReadonlyArray<RenderNode>,
  ): RenderNode;
}

type ComponentDefinition =
  | ContainerComponentDefinition
  | LeafComponentDefinition;
```

A component MUST return a `RenderNode` whose `key` is stable across
calls for the same block. The convention is `key === block.id` for
1:1 mappings; components that emit multiple render nodes per block
compose keys deterministically (`${block.id}/${suffix}`).

`leafShape` is consumed by the state module via `BlockKindResolver` for
cross-kind-transition refusal in `setBlockType`. The render dispatch
itself only narrows on `kind` ("container" vs "leaf").

### Image wrap (component-set seam)

An image carries a `wrap` attr holding the Google-Docs **physical** text-wrap
enum: `"left"` / `"right"` (wrap text around the image floated to that physical
side) or `"break"` (no wrap — the image breaks the text flow, sitting in the
block stream as a full-width-row sibling). `"break"` is the default and is stored
as ABSENCE of the attr, so a never-wrapped image is byte-identical to an
explicit `"break"`.

The `image` component MAPS that physical enum to the engine's **logical** `Float`
and bakes it onto the ElementBox `style` at render time, via `imageWrapFloat(wrap,
direction)` in `components/leaf-style-attrs.ts`. The mapping resolves against the
cascaded writing `direction` so a "wrap left" stays PHYSICALLY left under RTL:
`"left"` → `inline-start` (LTR) / `inline-end` (RTL); `"right"` → `inline-end`
(LTR) / `inline-start` (RTL); `"break"`/absent → no `float` key. The `float` is
spread onto `style` ONLY when defined, so a non-wrapped image's box style is
unchanged.

This is a **component-set seam**, not a cascade attr-interpreter (the same
mechanism the block-formatting `*FromAttrs` helpers use — see `1.5-editor.md`
"Block-attr → layout threading convention"). A generic cascade interpreter would
no-op here: `cascadePass` re-derives `computedStyle` from `node.style`, and the
render-time `view.computedStyle` carrying the resolved `direction` is not threaded
onto the box style — so the component reads `view.attrs.wrap` + `view.computedStyle.direction`
and writes the resolved `float` directly. Once on the box, the existing CSS-9.5
BFC float placement + IFC line-narrowing wrap the following paragraph's text
around the floated image with no image-specific layout code (the image is a
document-root float sibling under the same BFC float environment the following
paragraph inherits). See `2.2-layout/2.2.1-bfc.md` (float placement) and
`2.2-layout/2.2.2-ifc.md` (line narrowing).

### Inline images (in-line image embeds)

An **inline image** is the Google-Docs "In line" positioning: an image that
flows IN LINE with the surrounding text (occupying one cursor stop, sitting on
the text baseline) rather than breaking the flow or floating beside it (the
block-image / wrap-left / wrap-right cases above). It is NOT a block — it is an
inline `EmbedItem` (`embedType: INLINE_IMAGE_EMBED_TYPE === "inline-image"`,
`properties: { src, width, height, alt }`) inside a leaf block's `inlineContent`,
sharing the one-token / one-offset embed contract the footnote anchor,
cross-reference, page-field, tab, and hard-break embeds all rely on.

**Render form (Option B — reuse the block-image paint).** `expandInlineItems`
renders the inline-image embed as an OUTER `display: inline-block` ElementBox
carrying `metadata.replacedInline: true`, wrapping ONE INNER child-less
`display: block` ElementBox that carries `metadata.image: { src, width, height }`
plus an explicit numeric `blockSize` / `inlineSize`. The inner block is exactly
the shape the atomic-leaf `image` component produces, so the existing
BLOCK-image paint runs for it for free via `paintContainerChildren` recursion —
on canvas AND in the PDF exporter — with zero new paint code. The outer
inline-block makes it an IFC atom (one token, one offset); the inner block is
the drawable. `display: inline-block` (outer) / `display: block` (inner) are
load-bearing for the atom + paint, not attr-overridable.

The outer box's `replacedInline` flag rides the layout pipeline so the IFC sits
the image on the text baseline as a CSS *replaced* inline-block (bottom margin
edge on the baseline, CSS2 §10.8.1) rather than the `*0.8` content-baseline used
for text-bearing inline-blocks — see [`2.2-layout/2.2.2-ifc.md`](../2-print/2.2-layout/2.2.2-ifc.md)
"Replaced inline-block baseline".

**Intrinsic width.** The inner image block is child-less, so it would otherwise
report zero min/max-content and the shrink-to-fit outer inline-block would
collapse to nothing. The intrinsic-sizes pass short-circuits a block-level box
with a DEFINITE numeric `inlineSize` to contribute that size as both min- and
max-content (CSS Sizing 3 §5.1) — so the inner image block reports its declared
width and the wrapping inline-block shrink-to-fits to the image. See
[`2.2-layout/overview.md`](../2-print/2.2-layout/overview.md#intrinsic-sizing).

**A11y / HTML / editing.** The inline image projects an `imageAlt` accessibility
run (see [`1.8-accessibility.md`](./1.8-accessibility.md)), exports as an inline
`<img>` (see `html-encode`), and is inserted by `INSERT_INLINE_IMAGE` (the
`insertInlineImage` Layer-3 op; see `1.5-editor.md`).

### Render entry point

```ts
function render(
  state: State,
  componentRegistry: ComponentRegistry,
  attrRegistry: AttrRegistry,
  options?: RenderOptions,   // opt-in incremental: { prev, prevState, dirtyIds,
                             // footnoteNumbersOverride, suggestionView? } — see "Incremental rebuild"
): RenderOutput;

interface RenderOutput {
  readonly root: RenderNode;
  readonly embedContents: ReadonlyMap<BlockId, RenderNode>;     // footnote bodies
  readonly templateContents: ReadonlyMap<BlockId, RenderNode>;  // header/footer bodies (C.2a)
  // FN-8: cached so the next incremental cycle can reuse them and skip the
  // O(N_blocks) anchor walk + renumber diff when no anchor changed.
  readonly footnoteAnchors: readonly FootnoteAnchorRef[];
  readonly footnoteNumbers: ReadonlyMap<BlockId, FootnoteNumber>; // keyed by contentBlockId
  // Per-cycle list-marker numbers (blockId → CounterValue) from the
  // numbering service. Cached so the next incremental cycle can diff against
  // it (listCounterRenumberedBlocks) to expand the invalidated set. Empty
  // when the doc has no lists.
  readonly listCounters: ReadonlyMap<BlockId, CounterValue>;
  // Cross-reference target → host blockIds reverse index. Cached so the next
  // incremental cycle can REUSE it (rebuilt only when a dirty block gained /
  // lost / retargeted a ref — an internal per-cycle check in render-incremental)
  // and EXPAND the invalidated set: a target whose value changed (edited /
  // deleted / renumbered) forces every host referencing it to re-render. Empty
  // when the doc has no references.
  readonly crossReferenceIndex: ReadonlyMap<BlockId, ReadonlyArray<BlockId>>;
  // The document-outline signature: the ordered heading list (id, level, display
  // text) a live `table-of-contents` block derives its entry lines from, plus the
  // set of TOC anchor block ids. Cached so the next incremental cycle can REUSE it
  // O(1) when no heading changed, and EXPAND the invalidated set when it did — a
  // heading edit re-derives every TOC even though the TOC blocks are not in
  // `dirtyIds`. Empty when the doc has no headings / TOCs.
  readonly outlineSignature: OutlineSignature;
  // The SuggestionView the output was rendered under ("suggesting" | "final" |
  // "original"). Cached so the incremental path can detect a view switch and fall
  // back to a full rebuild when the view changes.
  readonly suggestionView: SuggestionView;
}
```

`render` throws on:
- A block whose `type` is not registered.
- A child id that does not resolve to a block.
- A cycle in the main block tree's traversal.

### Incremental rebuild

The state module produces `dirtyIds: Set<BlockId>` at every Layer-3
operation — the **raw mutated set**, exactly the blocks whose own Y.Doc
data changed (see `1.1-state.md`). `render` consumes that raw set and is
responsible for the closure expansion below. When `RenderOptions` carries
the full triple — the previous `RenderOutput` (`prev`), the previous
`State` (`prevState`), and `dirtyIds` — `render` rebuilds only the
invalidated blocks and reuses every other RenderNode by reference.

Invalidated set = `dirtyIds ∪ ancestors(dirtyIds) ∪ descendants(dirtyIds)`
(this is the **closure-expanded set**, computed by render, NOT what state
emits):

- `dirtyIds`: blocks whose own attrs / content changed (the raw set state
  passes in).
- `ancestors`: their `children` arrays now point at fresh child
  RenderNodes, so the parent RenderNode must be rebuilt to capture the
  new references.
- `descendants`: a dirty block's attrs may change the inherited context
  its descendants compose against, so they re-render too.

There is no separate stateful `RenderCache` object: the previous
`RenderOutput` *is* the cache, threaded in as `RenderOptions.prev`. When
any of `prev` / `prevState` / `dirtyIds` is absent, `render` falls back to
a full O(N) walk (the initial render, and full rebuilds such as a
container-width change). The editor's `rebuildTrees` threads the full
triple on every mutating action — and likewise drives
`cascadePassIncremental` and `layoutTreeIncremental` — so the
per-keystroke pipeline's WALK is O(D), not O(N) (modulo the O(N) `prevByKey`
index rebuild noted under Performance contracts below).

**Cross-cutting invalidation expansions.** Beyond the structural closure
(`ancestors ∪ descendants`), the incremental path widens the invalidated set
for the four derived-value subsystems whose displayed value can change in a
block that is NOT itself in `dirtyIds`:

- **Footnote renumber:** inserting/deleting/moving an anchor renumbers
  downstream markers + body slots; the per-anchor diff vs `prev.footnoteNumbers`
  adds the changed hosts + body roots.
- **List renumber:** `listCounterRenumberedBlocks(listCounters,
  prev.listCounters)` adds every list-item whose number changed.
- **Cross-reference target change:** a target's value changes when it is edited
  or deleted (`targetId ∈ dirtyIds`) or renumbered (`targetId ∈` the list-
  renumber set); the `crossReferenceIndex` then maps each such target to its
  host blocks, which are added to the invalidated set so they re-resolve.
  The index itself is reused from `prev` unless a dirty block added / removed /
  retargeted a reference (an internal reuse-gate check, by analogy to
  `footnoteAnchorsUnchanged` but private to `render-incremental`).
- **Outline change (table of contents):** a live `table-of-contents` block derives
  its entry lines from the document outline (other blocks' headings) — so a heading
  edit / insert / delete / re-level / reorder changes a TOC whose own block is not in
  `dirtyIds`. The reuse-gate (`outlineMightHaveChanged`) is cheap: it fires only when
  a dirty block is/was a heading. When it fires AND the recomputed `outlineSignature`
  differs from `prev.outlineSignature`, every TOC anchor (from `tocAnchorIds`) is
  added to the invalidated set so its render-core branch re-derives. A non-heading
  edit reuses `prev.outlineSignature` by reference and never walks the outline — the
  TOC RenderNode is reused by ref (O(1)).

### Numbering (list markers) — the render-time numbering service

There is NO CSS generated-content or counters layer (`::before` /
`::after` / `::marker`, `counter()`, `counters()`, `target-counter()`).
Following the Google-Docs model (CLAUDE.md: list numbering is a
list-property model, not CSS counters), list markers are produced by a
dedicated render-time numbering SERVICE (`packages/core/src/numbering/`)
and baked onto the list-item element by its component. The service is
render-time only — it has no layout dependency. (Layout-dependent
numbering, e.g. footnote-restart-per-page, is computed in the layout
pass, not here.)

**The numbering engine (`numbering/`).**

- `computeCounters(events, defs): Map<BlockId, CounterValue>` — a pure
  engine. `CounterEvent { blockId, scopeKey, level, breakBefore, override? }`
  is one numbering event in document order; `CounterValue { value, formatted }`
  is the computed number. Per-scope state is a stack of running counters
  indexed by level: entering a level resets all deeper levels (CSS-list-like);
  `breakBefore` restarts the scope's chain (a fresh consecutive run); `override`
  forces a value and the sequence continues from it. Configuration is a
  `CounterDefs` (`scopeKey → CounterDef { levels: CounterLevelDef[] }`, where
  `CounterLevelDef = { style, start, restart }` and
  `CounterRestart = "always" | "never" | "after-break"`).
- `collectListEvents(state): CounterEvent[]` — walks the BODY tree in
  document order (`iterateBlocksInDocumentOrder`) and emits one event per
  `list-item`, keyed by its `listId` (the `scopeKey`), with `level` from
  `listLevel`, `override` from `listCounterOverride`, and `breakBefore` true
  when the immediately-preceding document-order block is NOT a same-`listId`
  list-item (so two distinct lists never share a running counter).
- `listCounterRenumberedBlocks(next, prev): Set<BlockId>` — diffs two
  counter maps; the set of blocks whose computed number changed (or
  appeared/disappeared). Used by the incremental render path.

Lists are the FIRST consumer of this general service; footnotes and
custom components are intended future consumers (the service generalizes
the existing per-consumer counter logic).

**Render wiring (full path).** The full render computes
`docHasLists(state) ? computeCounters(collectListEvents(state), getListDefsForState(state)) : EMPTY`
once per cycle and exposes it through `RenderContext.counterValue` (see
the reference below). The `docHasLists` guard early-exits so a doc with no
lists pays nothing. The `list-item` component reads
`ctx.counterValue?.(listId, view.id)` and bakes the result into
`style.markerText` — `"<formatted>."` for an ordered marker, the bullet
glyph (•/○/▪) as-is for an unordered one — which the BFC then reads to emit
the marker box (no counting happens in layout; see `2.2-layout/2.2.1-bfc.md`).
The per-cycle map is cached on `RenderOutput.listCounters`.

**Render wiring (incremental path).** The incremental render recomputes
the counter map the same way, then expands the invalidated set with
`listCounterRenumberedBlocks(next, prev.listCounters)` (plus ancestors) so
that inserting/reordering/retyping one item re-renders every item whose
number shifted — not just the edited block.

### Cross-references (reference fields)

A cross-reference is the Google-Docs **reference field** (NOT CSS
`target-counter()`): an inline `EmbedItem` (`embedType: "cross-reference"`,
`properties: { targetId, refMode }`) that DISPLAYS a value owned by another
block — the target's number or text — and auto-updates when the target
changes. It is a POINTER: it owns no body block (unlike a footnote anchor's
`contentBlockId`), so the embed-cascade scanners ignore it. A dangling target
is a legal state. `refMode` is `"number" | "text" | "page"` against MAIN-tree
targets. `"number"`/`"text"` resolve at RENDER time (the target's number or
text). `"page"` is LAYOUT-DEPENDENT (the target's page index is unknown at
render): it renders a PLACEHOLDER inline-block atom (one cursor stop,
reserved-glyph width) carrying `metadata: { embedType, refMode: "page", targetId,
numberStyle }`, and is bound LATE at materialize via the layout-dependent field
seam (`collectPageFields` / `resolvePageFields` / `substituteLayoutFields`, shared
with page-number/count fields) — the target's page number is substituted once
pagination is known, with the field-width convergence loop covering the case
where the ref's digit count shifts pagination. heading-number / bibliography /
caption references are future work.

- **Resolution (render-time).** `resolveCrossReference(state, numbering, props, view)`
  (`resolve-cross-reference.ts`) returns the displayed string: `"number"` →
  the target's formatted counter from the same per-cycle `numbering` map the
  list markers use (broken-ref when the target is absent from the map — deleted,
  unregistered, or not a numbered list-item); `"text"` → the target block's full
  text via `getBlock` + `extractText` (broken-ref when the target is missing or
  non-inline-bearing). The resolver itself does no structural kind-check — that
  is the editor handler's job; here a wrong-kind target simply produces the
  broken-ref string `BROKEN_CROSS_REFERENCE_TEXT`. `"text"` mode honors the render
  pass's `SuggestionView` (`expandInlineItems` threads its `view`): a `"final"` /
  `"original"` preview resolves the caption against the SAME projection the target
  renders under, so the reference text never goes stale relative to the previewed
  document (`"number"` mode is view-independent — counters are already view-correct
  in the `numbering` map). The `"text"` extraction uses a cross-reference-display
  serializer (NOT the clipboard `builtinEmbedSerializer`): a hard-break / tab in
  the target collapses to a single space and every embed (footnote anchors, nested
  refs, images, markers) contributes nothing, so the inline caption is clean text
  rather than leaking `\n` / `\t` / U+FFFC.
- **Render form (the atom).** `expandInlineItems` renders the field as ONE
  inline-block element box wrapping the resolved string — exactly one IFC token,
  matching the state model's 1-unit offset for an EmbedItem. A bare text box
  would tokenize the resolved string into N tokens and drift the per-line offset
  accumulator, corrupting cursor/hit-test downstream (the same 1-token invariant
  the footnote marker relies on). `display: inline-block` is locked (not
  attr-overridable) because the atomicity is load-bearing. The atom also carries
  the field's `targetId` onto its `metadata` (all ref modes), threaded to the
  laid-out `InlineBlockBox.targetId` so the PDF exporter can emit an internal
  `/GoTo` destination link to the target's page (see `5-pdf/overview.md`).
- **Incremental.** `buildCrossReferenceIndex` (`collect-cross-references.ts`)
  produces the `targetId → host blockIds` reverse index, cached on
  `RenderOutput.crossReferenceIndex`. The incremental path reuses it unless a
  dirty block touched a reference (`crossReferenceIndexUnchanged`), then expands
  the invalidated set with every host whose target changed value — see the
  cross-cutting invalidation expansions under "Incremental rebuild".
- **Editing.** `INSERT_CROSS_REFERENCE { targetId, refMode }` (handler
  `editor/actions/insert-cross-reference-action.ts`) splices the field at the
  caret and structurally validates the target (the Layer-3 op trusts it):
  main-body caret only, main-tree target, ordered-list-item for `"number"`,
  inline-bearing for `"text"`; an invalid target is a silent no-op. See
  `1.5-editor.md`.

### Page-fields (layout-dependent fields)

A page-field is the Google-Docs **page-number / page-count** running-content field:
an inline `EmbedItem` (`embedType: "page-field"`, `properties: { fieldKind, numberStyle }`,
`fieldKind: "page-number" | "page-count"`) whose displayed value depends on PAGINATED
layout — the self page index, or the document's total page count. Like a cross-reference
it is a POINTER that owns no body (the embed-cascade scanners ignore it).

The crucial difference from a cross-reference: a cross-reference resolves at RENDER time
(its value lives in the per-cycle numbering map, which render has). A page-field's value
lives in the paginated layout, which does NOT exist at render time — so render cannot
produce the final value. Instead:

- **Render form (the placeholder atom).** `expandInlineItems` renders the field as ONE
  inline-block element box — exactly one IFC token / one offset (the same 1-token
  invariant the cross-reference and footnote marker rely on) — wrapping a page-AGNOSTIC
  placeholder of `PAGE_FIELD_RESERVED_GLYPHS` reserved zero-glyphs, and
  carrying `metadata: { embedType, fieldKind, numberStyle }` so the layout pass can find
  and value-bind it. The placeholder is identical on every page; `display: inline-block`
  is locked (atomicity is load-bearing).
- **Late value binding.** The real value is substituted at MATERIALIZE, per page, from the
  paginated layout (`substituteLayoutFields`; `page-number` = page index + 1, `page-count` =
  the document total). The placeholder's reserved width also feeds the §4.4 width-
  convergence loop so a wide value (`"of 100"`) that would wrap a header reserves room.
  This is the FN-6.2b late-binding precedent; see `2.3-pagination.md` for the resolution
  pass, substitution, and convergence.
- **Editing.** `INSERT_PAGE_NUMBER` / `INSERT_PAGE_COUNT` (handler
  `editor/actions/insert-page-field-action.ts`) splices the field at the caret in a
  HEADER/FOOTER context only (main-body and footnote-body page-fields are out of scope —
  it diverges from the cross-reference handler's main-body-only gate). See `1.5-editor.md`.

### Performance contracts

- `render` (full path — initial render, or no `dirtyIds`): O(N) where N
  is the state-tree size.
- `render` (incremental path — full `prev`/`prevState`/`dirtyIds` triple):
  the WALK is O(D) where D is the invalidated set (dirty blocks + ancestors +
  descendants); unchanged subtrees flow through by reference. **Caveat
  (known limitation):** before the walk, the `prev`→RenderNode key index
  (`prevByKey`) is rebuilt by indexing the entire previous render tree — the
  main root plus every embed/template body — which is O(N) in render-node
  count per cycle. So the true per-cycle cost has an O(N) index-build component
  on top of the O(D) walk. This is masked by layout today; if render ever shows
  up in a keystroke profile, persist the key→node index on `RenderOutput` and
  patch only the invalidated subtrees instead of rebuilding it.
- Render-tree reference equality: a stable input block snapshot
  (`getBlock(state, id) === getBlock(prev, id)`) outside the invalidated
  set produces a reference-equal RenderNode subtree — the property the
  downstream `cascadePassIncremental` and `layoutTreeIncremental` reuse
  passes depend on.
