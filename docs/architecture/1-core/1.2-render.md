# 1.2 — `render/` and `components/`

The render layer translates a `StateNode` tree into a `RenderNode` tree
of layout-relevant elements. It bridges the *semantic* document model
(what the user typed) and the *layout-ready* representation (what to
draw, with declared styles). The translation is component-driven: each
node type registers a render function in the component registry; the
render walker dispatches per node.

## Two coupled modules

`components/` and `render/` are separate directories but coupled
responsibilities: `components/` defines the plugin surface (what render
functions can register), `render/` defines the data the registry
produces and the walker that drives it.

## What a render tree looks like

A `RenderNode` is one of:

- **`ElementBox`** — a layout-relevant element with a key, declared
  style, optional metadata (image src, list-marker text, table
  structure), and children.
- **`TextBox`** — a leaf carrying text content with declared style.

After cascade (the next pass), each render node carries a
`ComputedStyle` in addition to its declared `style`. The cascade pass
writes into the existing render tree by producing new frozen nodes;
unchanged subtrees keep their references.

Render nodes are keyed for stable identity across rebuilds. Keys flow
from state-node `id`s; anonymous boxes (those introduced by render
functions for layout-time grouping like list markers) use composite
keys derived from their parent.

## Submodules

### `components/`

- **`component-definition`** — the `ComponentDefinition` type:
  `{ type: string, render: (state, children) => RenderNode }`. A
  component is just a typed render function.

- **`component-registry`** — `ComponentRegistry` with `register`, `get`,
  `has`. Exposes `createRegistry(components[])` for downstream consumers
  to assemble their set.

- **Built-in components** — `document`, `paragraph`, `heading`, `text`,
  `span`, `list`, `list-item`, `table`, `table-row`, `table-cell`,
  `image`, `horizontal-line`. Each is a render function that maps state
  → RenderNode. Built-ins ship as a default set (`defaultComponents`)
  that consumers extend.

- **`factories`** — convenience constructors for state nodes that match
  built-in components (`createParagraph`, `createHeading`, etc.).

### `render/`

- **`render-node-v2`** — the `RenderNode` types (`ElementBox`,
  `TextBox`) and their factory functions. Frozen at construction.

- **`render`** — `renderTree(state, registry)` and
  `renderTreeIncremental(state, oldState, oldRender, registry)`.
  - `renderTree` walks the state bottom-up, dispatching each node
    through the registry.
  - `renderTreeIncremental` adds a structural-sharing short-circuit:
    when `state === oldState` at any level, the corresponding
    `oldRender` subtree returns by reference, preserving identity for
    downstream cascade and layout reuse.

- **`render-node`** (legacy) — an older render-node shape retained for
  backwards compatibility during migration. Sunset path.

## How modules connect

The reducer in `editor/` calls `renderTreeIncremental(newState,
oldState, oldRender, registry)` after every state mutation. The walker
descends the new state tree:

- For each state node, it looks up the component via the registry.
- It recursively renders children first (bottom-up), passing the
  rendered children into the parent's render function.
- The render function returns a `RenderNode` for that subtree.
- If `state === oldState` at the current node, the walker returns the
  prior render node directly without invoking the component — preserving
  reference equality on unchanged subtrees.

The output is the input to the cascade pass.

## Why this layer exists

Components let the engine accept new document primitives without
modification. A consumer adding charts registers a `chart` component;
the engine treats it as another `RenderNode` (typically an `ElementBox`
with chart metadata) and lays it out as an inline-block or block
element. The render layer is where the unbounded user-visible vocabulary
of state-node types collapses into the bounded vocabulary of layout
primitives.

## Reference

### `RenderNode`

```ts
type RenderNode = ElementBox | TextBox;

interface ElementBox {
  readonly type: "element";
  readonly key: string;
  readonly style: Readonly<Style>;
  readonly computedStyle?: Readonly<ComputedStyle>; // populated by cascade
  readonly metadata?: Readonly<Record<string, unknown>>;
  readonly children: readonly RenderNode[];
}

interface TextBox {
  readonly type: "text";
  readonly key: string;
  readonly style: Readonly<Style>;
  readonly computedStyle?: Readonly<ComputedStyle>; // populated by cascade
  readonly text: string;
}
```

`metadata` carries layout-relevant per-element data the cascade and layout
passes consume verbatim — examples: `{ src }` for images, `{ markerText }` for list markers, `{ columnWidths }` for tables once auto-layout produces them.

### Factory contract

```ts
function createElementBox(
  key: string,
  style: Style,
  children: readonly RenderNode[],
  metadata?: Record<string, unknown>,
): ElementBox;

function createTextBox(
  key: string,
  style: Style,
  text: string,
): TextBox;
```

Both factories `Object.freeze` their output and freeze nested objects (`style`, `metadata`, `children`). `style` is shallow-copied (`Object.freeze({ ...style })`), so two calls with the same style object produce different style references — the cascade pass's structural-equality fallback compensates by reusing prior `ComputedStyle` references when value-equal.

### Component contract

```ts
type ComponentRenderFn = (state: StateNode, children: readonly RenderNode[]) => RenderNode;

interface ComponentDefinition {
  readonly type: string;       // matches StateNode.type
  readonly render: ComponentRenderFn;
}

class ComponentRegistry {
  register(def: ComponentDefinition): void;
  has(type: string): boolean;
  get(type: string): ComponentDefinition | undefined;
}

function createRegistry(components: readonly ComponentDefinition[]): ComponentRegistry;

const defaultComponents: readonly ComponentDefinition[];
```

A component MUST return a `RenderNode` whose `key` is stable across calls for the same `state` reference. The convention is `key === state.id` for one-to-one mappings; components that emit multiple render nodes per state node (rare) compose keys deterministically (`${state.id}/${suffix}`).

### Render pass

```ts
function renderTree(state: StateNode, registry: ComponentRegistry): RenderNode;

function renderTreeIncremental(
  state: StateNode,
  oldState: StateNode | null,
  oldRender: RenderNode | null,
  registry: ComponentRegistry,
): RenderNode;
```

`renderTree` walks the state bottom-up: for each node, it recursively renders children first, then dispatches the node itself through the registry. It throws on unknown `state.type`.

`renderTreeIncremental` adds a structural-sharing short-circuit: when `state === oldState`, the corresponding `oldRender` subtree returns by reference unchanged. Otherwise it walks children with positional matching against `oldState.children` and `oldRender.children` (per-index pairing) and recurses. The short-circuit is the load-bearing optimization for downstream cascade and layout reuse.

### Generated content and counters

CSS-spec generated content (`::before`, `::after`, `::marker`, `content:` values, `counter()`, `counters()`, `target-counter()`) integrates into the engine through anonymous render-node synthesis during the render walk. The render walker maintains a counter state map alongside the walk and emits anonymous render nodes around real elements where pseudo-elements apply.

#### Pseudo-element synthesis

The render walker, after a component's render function produces its `RenderNode`, post-processes the output to inject `::before` / `::after` / `::marker` content when the computed style declares them.

Because the cascade hasn't run yet at render time, pseudo-element resolution actually happens during the **cascade pass**, which has the resolved `content:` values available. The cascade pass's child walk emits anonymous render nodes:

```
function cascadeNodeWithPseudoElements(newNode, oldNode, oldCascaded, parentComputed, oldParentComputed):
  // Cascade this node normally
  cascaded = cascadeNodeIncremental(newNode, oldNode, oldCascaded, parentComputed, oldParentComputed)

  // Inject pseudo-elements based on cascaded.computedStyle
  // (For element nodes only — text nodes have no pseudo-elements.)
  if cascaded.type == "element":
    children = []
    if cs.beforeContent != null:
      children.push(synthesizePseudoElement(cascaded.key + "::before", cs.beforeContent, cs))
    children.push(...cascaded.children)
    if cs.afterContent != null:
      children.push(synthesizePseudoElement(cascaded.key + "::after", cs.afterContent, cs))
    return frozen { ...cascaded, children }
  return cascaded

function synthesizePseudoElement(key, content, parentCs):
  // content is one of:
  //   - { kind: "string", value: string }                  → emits a TextBox carrying that string
  //   - { kind: "counter", name, style }                   → emits a TextBox with the counter's current formatted value
  //   - { kind: "counters", name, separator, style }       → emits a TextBox with all enclosing scope values joined
  //   - { kind: "target-counter", target, name, style }    → deferred until pagination resolves; emits a placeholder
  //   - { kind: "attr", name }                             → emits a TextBox with the parent state node's attribute value
  //   - { kind: "concat", parts }                          → multiple of the above concatenated
  // Returns a TextBox or ElementBox-with-children.
```

`Style` schema gains: `beforeContent?: ContentValue`, `afterContent?: ContentValue`, plus the `ContentValue` discriminated union.

#### Counter scoping

Counter state is a map from counter name to a stack of values. The cascade walk maintains the stack:

- **`counter-reset: name [initial?]`** — push a fresh counter value (default 0) onto the stack at this node.
- **`counter-increment: name [delta?]`** — increment the topmost value (default delta 1) of the named counter at this node.
- **`counter(name)`** — read the topmost current value, formatted per `style` (decimal, lower-roman, etc.).
- **`counters(name, separator)`** — read all values on the stack, joined by `separator`. Used for nested-list numbering: `1.2.3`.

The cascade walk runs as a top-down recursion that threads the counter map through. On entering a node:
1. Apply `counter-reset` (push values).
2. Apply `counter-increment` (mutate top values).
3. Resolve `content:` references for `::before` (which may consult counter values).
4. Recurse into children with the updated counter state.
5. Resolve `::after` content (which sees state after children).
6. On exit, pop any values pushed by step 1.

Stack semantics match CSS Lists 3: `counter-reset` creates a new scope; nested `counter-reset`s shadow outer scopes; `counters()` walks the entire stack from outer to inner.

#### `target-counter()` two-pass resolution

`target-counter(href, name)` reads the value of a counter at the resolution point of an internal link's target — typically `page` for "see page 42" cross-references. The target's page index isn't known until pagination completes, so resolution happens in two passes:

1. **First pass (regular cascade + layout + pagination).** `target-counter` references emit a placeholder text in the `::before` / `::after` content (e.g., `"??"`). Pagination produces `PageBox`es; each `PageBox` carries its `pageIndex` and a list of element keys it contains.
2. **Resolution pass.** Walk the placeholders, look up each target's `pageIndex` from the page map, and substitute the resolved value back. Re-cascade and re-layout only the affected pseudo-elements.

For documents without `target-counter` references, the second pass is skipped — the engine detects this and avoids the cost.

### Performance contracts

- `renderTree`: O(N) where N is the state-tree size.
- `renderTreeIncremental`: O(D) where D is the size of the dirty subtrees. Unchanged subtrees flow through by reference.
- Render-tree reference equality: when `state === oldState` at any node, the render output for that node and its subtree is reference-equal across passes.
- Counter walk: O(N) per cascade pass. Counter resolution is constant-time per `counter()` reference.
