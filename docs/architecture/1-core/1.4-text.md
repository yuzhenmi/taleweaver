# 1.4 — Text

The text subsystem owns everything about turning Unicode text into
positioned glyphs for layout and paint to consume: shaping, bidi,
grapheme clustering, line-break opportunities, hyphens, font metrics.
It cuts across the layout and paint phases — both consume the same
shaper output.

## The shaper interface

`core` defines a `TextShaper` interface but never instantiates one.
Hosts (or external packages) implement it; `print` ships a canvas-based
default in [`2.7-canvas-shaper.md`](../2-print/2.7-canvas-shaper.md).

The interface contract:

- **Input:** a string of Unicode text plus a `ComputedStyle` (font
  family/size/weight/style; possibly font-feature-settings,
  letter-spacing, word-spacing, language tag) plus optional shape
  options (e.g., available width for shaping, whether to enable
  hyphenation).

- **Output:** a `ShapedRun` containing positioned glyphs (each with an
  advance width), cluster boundaries (to map characters to glyphs and
  back), break opportunities (where the IFC may wrap), bidi levels per
  cluster, and font metrics (ascent, descent, line-height).

The interface lets the IFC pack tokens into lines, the painter draw
the glyphs at their positions, the cursor logic place the caret within
ligatures, and the hit-test logic translate pixel coordinates into
character offsets — all from one shaper pass per text run.

## Letter- and word-spacing (CSS Text 3 §8)

`letter-spacing` adds tracking after every typographic character unit;
`word-spacing` adds spacing to word-separator characters (U+0020, U+00A0).
The rule lives in one pure module, `layout/text-spacing.ts`
(`resolveSpacingPx` — `normal`→0, px→itself; `clusterSpacing(clusterText,
letterPx, wordPx)` — letter on every cluster, word on separators).

It is applied at the **two chokepoints that independently compute cluster
advances**, so layout, intrinsic sizing, and paint stay in lockstep (the
caret/glyph-drift class of bug otherwise — a single kerned whole-run draw vs
per-cluster summed advances):

1. **The shaper** (`TextShaper.shape`) bakes `clusterSpacing` into each
   returned cluster's `inlineAdvance` and the run aggregates
   (`minClusterInlineSize`, `unbreakableRunInlineSize`). The IFC (token
   widths + wrapping) and intrinsic sizing (min/max-content) read those
   advances, so both pick spacing up for free.
2. **The canvas renderer's per-cluster paint loop** adds the same
   `clusterSpacing` to each cumulative advance (it re-measures clusters
   independently), so painted glyph origins equal the layout advances.

`resolveSpacingPx("normal") === 0`, so the default editing path is inert and
byte-identical. The IFC additionally trims trailing tracking at each line's
end — see [`2.2.2-ifc.md`](../2-print/2.2-layout/2.2.2-ifc.md).

## Text transform (CSS Text 4 §2.1)

`text-transform` (`none` | `capitalize` | `uppercase` | `lowercase`) is a
**display transform**: the rendered, measured, and painted text is transformed,
while the state text stays pristine (`uppercase` of `straße` paints `STRASSE`,
but the document still holds `straße`, and `getActiveFormatting` reports it
unchanged). The rule lives in one pure module, `layout/text-transform.ts`:

```ts
function transformRun(text: string, mode: TextTransform):
  { display: string; sourceDisplayLengths: readonly number[] };
```

- **`uppercase` / `lowercase`** apply JS default-locale case mapping, which is
  the one place a case mapping can grow or shrink the string (`ß` → `SS`).
- **`capitalize`** upper-cases the first cased character after each word
  boundary. The v1 word boundary is the run start plus any position following
  whitespace (a per-code-unit approximation), not the full UAX #29 word
  segmentation.

`transformRun` always returns the `display` string and a `sourceDisplayLengths`
array — one entry per source code unit giving the count of display code units it
expands to (so `ß` → `SS` yields `2` at that position, while a length-preserving
character yields `1`). The IFC carries this array onto a leaf **only when the
transform changed the run's length**; a length-preserving (1:1) transform leaves
the leaf without it, because the display string then maps offset-for-offset to
the source and the untransformed fast path is exact.

**The state↔display offset map.** Cursor consumers keep caret, hit-test, and
selection correct across length-changing case mappings by composing
`sourceDisplayLengths` with the existing `measureWidth(display.slice(...))` path
— never a separate measurement codepath, so there is no paint-vs-measure drift
(the class of bug that motivated keeping measurement and paint on one advance
source):

- **Cursor position** remaps a state offset `o` to a display index
  `d = sum(sourceDisplayLengths[0..o])` before measuring the display prefix.
- **Hit-test** reverse-maps a measured display offset back to the nearest state
  code-unit boundary (the cursor never lands inside a single source unit's
  expansion, e.g. between the two `S`s of an upper-cased `ß`).
- **Selection geometry** needs no transform-specific logic — it derives its
  edges from the same remapped cursor-position path.

When the leaf carries no `sourceDisplayLengths` (1:1 transform, or no
transform), these paths are byte-identical to the untransformed case.

**v1 limitations (target: full CSS Text 4).** The case mapping uses the JS
default locale, so locale-tailored mappings are not yet honored (Turkish
dotless-i `i`/`İ`, Greek final-sigma context, Lithuanian accent retention).
`capitalize` uses the per-code-unit post-whitespace boundary above rather than
UAX #29 word segmentation. The expansion model is per-code-unit, so a transform
that reshaped an astral-plane grapheme cluster would map at the code-unit level
rather than the cluster level. A transform that grows a word (e.g. `ß` → `SS`)
does not re-run hyphenation against the grown display text — the IFC clears that
token's hyphen opportunities.

## Unicode algorithm responsibilities

A correct text subsystem implements three Unicode algorithms; in this
engine the work is split between the shaper and the IFC:

- **UAX #29 — Grapheme cluster boundaries.** Defines what a single
  user-visible character is — a base codepoint plus combining marks,
  emoji ZWJ sequences, regional indicator pairs, etc. Used for cursor
  positioning (cursor never lands inside a grapheme cluster) and for
  line-break decisions (don't break inside a cluster). The shaper emits
  cluster boundaries; the IFC and cursor logic respect them.

- **UAX #14 — Line-break opportunities.** Defines where text may wrap:
  after spaces, after hyphens, between CJK ideographs, but not before a
  closing bracket or after an opening one, and never across `GL` glue
  (e.g. NBSP `U+00A0`). **Implemented** as a hand-rolled conformant rule
  engine in `layout/uax14/` (`lineBreakOpportunities(text, {cjBreakable})`
  returns the soft/mandatory break points; rules LB1–LB31 with the §8.2
  number tailoring; passes the full `LineBreakTest.txt` suite). The break
  property table is generated from vendored Unicode data and committed, so
  there is no runtime dependency. The shaper calls the classifier to fill
  its per-token break opportunities; the **IFC** runs the classifier once
  over the assembled inline source text and uses the result as its wrap
  authority (see `2.2.2-ifc.md`). `cjBreakable` selects the CSS
  `line-break` behavior for CJ small-kana (default CJ→NS, i.e.
  `line-break: normal` keeps kana together; flipping it to ID makes them
  breakable). CJK ideographs are class ID and break regardless of
  `cjBreakable`.

- **UAX #9 — Bidirectional algorithm.** Defines how mixed-direction
  text is reordered visually (Arabic/Hebrew with Latin runs, Arabic
  numerals in RTL contexts). The full Unicode Bidirectional Algorithm
  lives in `layout/uax9/` as a self-contained engine **[IMPLEMENTED]**:
  `resolveBidiLevels(text, base)` runs P2/P3 (paragraph level) → X1–X10
  (explicit embeddings/overrides/isolates) → W1–W7 → N0–N2 → I1/I2 to
  produce a per-codepoint level array, and `reorderVisual(levels, types,
  paragraphLevel, lineStart, lineEnd)` applies L1/L2 to produce the
  visual-order permutation for a line. It is conformant against the
  official Unicode `BidiTest.txt` + `BidiCharacterTest.txt` oracles at
  100%, with zero runtime dependencies (a committed generated bidi-class
  table mirrors the `uax14` pattern). The engine is now integrated end to
  end (browser smoke pending). Paragraph resolution (P4-B):
  `@taleweaver/print` `layout/ifc-bidi.ts` — `resolveParagraphBidi(source, base)`
  runs the engine over a whole paragraph's assembled source and exposes
  `bidiLevelAtSourceOffset(pb, utf16Offset)` (astral-safe UTF-16↔codepoint
  mapping) so layout code can query a character's level by source offset.
  Bidi is resolved per PARAGRAPH (not per shaped run — a run's levels depend
  on surrounding runs), so the seam is the IFC's assembled paragraph source,
  NOT the per-run shaper. Per-line reorder (P4-C.1): the private function
  `reorderLineForBidi` inside `@taleweaver/print` `layout/ifc.ts` calls
  the per-line primitive `reorderLineLeaves` (in
  `print/src/layout/ifc-bidi-reorder.ts`) to segment each line by post-L1 level
  and reorder the segments (L2) into physical/visual box geometry, each run
  carrying its `bidiLevel`. Glyph paint (P4-C.1 T7) reverses an odd-`bidiLevel` run's
  cluster placement. RTL cursor/hit-test/selection/navigation (P4-C.2) is
  built on the `bidiLevel` runs (see `1.5-editor.md` "Bidi cursor"). All
  unit-verified; the remaining open item for the bidi feature is the
  in-browser smoke validation.

## Hyphenation

The `hyphens` property (`none | manual | auto`; cascaded, inherits, default
`manual`) controls within-word breaking.

**`manual` (and the `none` half) — [IMPLEMENTED].** A U+00AD SOFT HYPHEN is an
author-supplied hyphenation opportunity. The engine honors it end-to-end:
- **Zero-advance.** U+00AD is a Unicode `Cf` format char — it renders nothing and
  contributes ZERO inline advance unless it is the chosen line-end break. All
  shapers (mock + canvas) give its cluster `inlineAdvance: 0` (the shaper is the
  single source of truth for advances), so a word measures identically with or
  without embedded soft hyphens, in both used-size and intrinsic-size paths.
- **Producer.** At the IFC token-collection site, when `cs.hyphens !== "none"`, a
  `hyphenBreaks` entry `ci+1` is synthesized for each U+00AD at token-relative
  index `ci` (the mock/canvas shapers classify U+00AD as UAX #14 class `BA` →
  `kind:"soft"`, never `kind:"hyphen"`, so the producer synthesizes the
  opportunity). The wrap loop's `tryHyphenSplit` finds the widest fitting position,
  shapes a `"-"` glyph, splits the token, and stamps `endsWithHyphenContinuation` on
  the prefix line.
- **`none` suppression.** The glyph-less UAX #14 soft break a U+00AD suggests is
  suppressed UNCONDITIONALLY in `annotateLineBreaks` (it is never the correct
  rendering — `none` → no break; `manual`/`auto` → a glyph-bearing hyphen break
  instead). `intrinsic-sizes-pass.ts` separately filters the post-U+00AD break from
  min-content under `none`.
- **Fragmentation.** A page break must not fall between the two lines of a
  hyphenated word — the D.4 hyphen-pair back-off in `fit-core.ts` (driven by
  `LineBox.endsWithHyphenContinuation`) moves the break a line earlier.

**`auto` (dictionary hyphenation) — [IMPLEMENTED].** Automatic break-point
discovery is complete end-to-end: (1) the `language` cascade property + `lang` attr
interpreter (inherited string, default `""`) — a block-level `lang` attr is
synthesized onto the ElementBox `style` by the block components (`langFromAttrs`,
`components/leaf-style-attrs.ts`) so it reaches the layout cascade's `cs.language`,
and because `language` inherits, a document-root `lang` cascades to every body run;
(2) the injected `Hyphenator`
capability — the interface + a mock in core (`layout/hyphenator.ts`), wired as
optional `LayoutConfig.hyphenator` and threaded to every text-tokenization site;
(3) the `hyphenateLimitChars` cascaded property (inherited `readonly [number,
number, number]`, default `[5, 2, 2]` = `min-word min-before min-after`); (4) the
**auto producer arm** at the IFC token-collection site — gated on `cs.hyphens ===
"auto"` + non-empty `cs.language` + an injected `hyphenator`, it asks
`hyphenator.hyphenate(part, cs.language)` for suffix-start break indices over the
display word, keeps only those passing `cs.hyphenateLimitChars`, and merges them
(dedup + sort) with the soft-hyphen and shaper `kind:"hyphen"` breaks into the
token's `hyphenBreaks` (so `tryHyphenSplit` + the synthetic `"-"` glyph + the
hyphen-pair fragmentation constraint all apply origin-agnostically; text-transform
grow/shrink tokens clear the breaks by the same rule as soft hyphens); and (5) the
**concrete Liang hyphenator algorithm + per-language pattern data**. The algorithm
ships in `@taleweaver/print` (`createLiangHyphenator(languages)`: a pure Knuth-Liang
trie matcher with an LRU word memo and the U+00AD soft-hyphen contract); the
per-language pattern data ships one package per language
(`@taleweaver/hyphenation-en-us`, …), each exporting a single `PatternSet` (the
`PatternSet` data type lives in core, next to the `Hyphenator` interface). The host
composes the languages it needs — `createLiangHyphenator({ en: EN_US_PATTERN_SET })`
— and injects the result via `LayoutConfig.hyphenator`. The measure-pass
`_metaCache` keys on the `hyphenator` instance (alongside the shaper) so swapping it
correctly invalidates pagination.

**Adding a language is DATA, not code:** publish another `@taleweaver/hyphenation-<lang>`
data package exporting that language's `PatternSet`, and pass it into
`createLiangHyphenator` keyed by its language prefix — no core or algorithm change.
The example app authors `lang="en"` + `hyphens="auto"` on its justified prose
(wiring `@taleweaver/hyphenation-en-us`) to exercise the full path. When NO
hyphenator is configured (or none covers the content language), `hyphens: auto`
falls back to `manual` (honors
soft hyphens only) — exactly what a CSS UA does when no hyphenation resource exists
for the content language, so the unconfigured case is *correct* `auto` behavior,
not a degraded build.

**Named follow-ups:** RTL hyphen-glyph placement (the synthetic `"-"` is appended
with no `bidiLevel`, so on an RTL line it lands at the inline-end instead of
inline-start — LTR is correct); and the cache-key gap where `tokensEqual`/
`findChangePoint` do not compare `hyphenBreaks` (unreachable in the manual feature —
no `hyphens`-toggle editor path — but required by `auto` or P18 partial re-wrap).

## Overflow-wrap (CSS Text 3 §5.1)

The `overflowWrap` property (`normal | break-word | anywhere`; cascaded, inherits,
initial `normal`) controls the LAST-RESORT within-word break.

**`break-word` — [IMPLEMENTED].** A word with NO real break opportunity (no UAX #14
soft break, no authored hyphen) that exceeds the line is broken at a
GRAPHEME-CLUSTER boundary rather than overflowing. The IFC's `tryEmergencyBreak`
(a 2-tuple sibling of `trySoftSplit`, no glyph) finds the widest fitting prefix by
prefix-summing `clusterWidths`, with the **≥1-grapheme progress guarantee** (CSS
§5.1: place at least one grapheme even if it overflows — guarantees the wrap loop
terminates). It is the THIRD, last-resort attempt in the wrap loop: **soft →
hyphen → emergency**, so a real break always wins. Wired at both split sites
(alone-on-line after `tryHyphenSplit`; shared-line only in the `breakableBefore ===
false` NBSP-glued branch — when the word can move to a fresh line it does so first,
matching browsers). The gate suppresses ONLY `normal` (the initial — byte-identical
to the prior overflow behavior); `break-word` AND `anywhere` both emergency-break
(see below). Skips text-transform grow tokens (`sourceDisplayLengths` set), mirroring
the hyphen path. An emergency break is an ordinary token split with contiguous source
offsets (NO inserted char), so caret/click/selection across it resolve correctly
(behavior-tested).

**Editor body default = `break-word`** (Google-Docs parity, principle 7 over the CSS
`normal` initial — mirrors the `white-space: break-spaces` body default): set on the
document / footnote-body / template-body component styles (the cascade ROOTS), so a
long unbreakable string in the body breaks to fit the page rather than running off
it. The `normal` STYLE initial is unchanged, so an explicitly-overridden block gets
CSS-correct overflow.

**`anywhere` — [IMPLEMENTED].** Its USED-layout break is IDENTICAL to `break-word`
(same `tryEmergencyBreak` path — that is why the gate accepts both). The DIFFERENCE
is intrinsic sizing: `anywhere` makes the within-word break point COUNT for
**min-content**, so a shrink-to-fit / inline-block box (e.g. a table cell holding a
long URL) can narrow to ONE grapheme. `intrinsic-sizes-pass.ts` `computeTextContribution`
sets `minContent = run.minClusterInlineSize` (widest single cluster) under `anywhere`
instead of the widest unbreakable segment. `max-content` (the longest unbreakable RUN,
a used-layout concept) is unaffected by either value.

**`break-word` leaves min-content unchanged** per CSS — only `anywhere` collapses it —
so a `break-word` shrink-to-fit box still sizes to its widest word.

**Named follow-ups:** `word-break: normal | break-all | keep-all` (a separate
CJK-typography property; `keep-all` also inverts the IFC's `cjBreakable: true`);
emergency-breaking text-transform grow tokens via `sourceDisplayLengths`; a
`SET_OVERFLOW_WRAP` editor action (the property is a body default, not a
user-toggled inline format in v1).

## Tab stops

Tab stops are modeled the **Google-Docs / word-processor way — a paragraph stop list,
NOT CSS `tab-size`** (CSS Text 4 §6 has no real stops; principle 7 governs the
feature, principle 6 only the layout mechanics). A paragraph carries a `tabStops`
block-attr — an ordered list of `{ position /* px from inline-start */, alignment:
"left" | "center" | "right" | "decimal" | "content-edge", leader: "none" | "dot" | "dash" | "line" }`
— resolved onto `ComputedStyle.tabStops` by a cascade attr-interpreter and synthesized
onto the layout cascade via the component-set convention (`leaf-style-attrs.ts`, like
`textAlign`/`lineHeight`). A scalar `defaultTabStop` (px, default 48 = 0.5in,
inherits) fills the gaps. `defaultTabStop` and `tabStops` are both cascaded/used-style
fields; the former CSS `tabSize` reservation was removed.

**A tab is the `"tab"` inline EMBED** (atomic, one cursor offset), flowing through the
inline-block pipeline — the same machinery footnote-anchors and inline images use. The
generic embed render emits it as a `display:inline-block` box; the IFC RECOGNIZES it
(`Token.isTab`/`WrapUnit.isTab`) and carries a typed `InlineBlockBox.inlineMeta =
{ embedType:"tab"; leader }`. Because it is an embed, caret/click/selection/bidi reuse
the existing inline-block leaf path with no tab-specific cursor code.

**Position-dependent advance — resolve-at-assembly, freeze-geometry.** A tab's advance
depends on the running pen position, so it is resolved in the IFC wrap loop at the
overflow-check seam (where the pen `x = currentWidth` is known) — each tab is resolved
as it is reached, the only token whose width is not intrinsic.
`nextStop(x, tabStops, defaultTabStop, contentEdge)` returns the nearest stop AHEAD of `x`
by a min-scan over each stop's EFFECTIVE position (`content-edge → contentEdge` = the
line's content width, else the stop's `position`); the nearest-ahead scan does not rely on
the stop list's sort order. With no stop ahead it returns the next default-grid multiple.
The advance is
then frozen onto a fixed-width inline-block box (the unit is cloned with both
`totalWidth` and `tokens[0].width` set), so all downstream geometry stays
position-independent. For intrinsic-sizing queries (`min-content` / `max-content`),
where no pen position exists, a tab contributes `defaultTabStop` as a conservative
representative advance (`intrinsic-sizes-pass.ts`). Alignments:
- **left / default-grid:** advance to the stop position.
- **right / center / decimal / content-edge:** a bounded look-ahead measures the post-tab
  segment (peeking the following wrap units by index, bounded by the next tab / line break /
  remaining line budget — only the on-line head). right → segment ends at the stop;
  center → segment centered on the stop; decimal → the first `.` (U+002E; v1 separator)
  aligns on the stop, with a right-alignment fallback when there is no separator;
  **content-edge** → right-aligns the segment to the line's content edge (the stop's
  effective position is `lineInlineSize`, so its own `position` field is ignored) — used by
  generated flush-right layouts such as the Table-of-Contents entry's page number. All
  clamp to `max(0, min(advance, lineRemaining))` — an overflowing aligned tab collapses
  to zero advance (the pen does not move; content continues from it).

**Cache.** The IFC paragraph cache (`IFCState`) gates on `tabStops`/`defaultTabStop`, so
a stop-list change with an identical token stream still reflows; a `hasTab` flag bypasses
the incremental fast path for tab-containing paragraphs (a tab's frozen width is
position-dependent, not token-equality-stable).

**Editing.** Pressing **Tab** inserts a `"tab"` embed (`INSERT_TAB`, a bodyless atomic
embed insert) — EXCEPT while the caret is in a list-item block (at any offset), where
Tab / Shift+Tab adjust the list nesting (`LIST_INDENT`/`LIST_OUTDENT`); each Tab is a discrete undo step
(`"command"` coalescing). `SET_TAB_STOPS` sets a paragraph's stop list via
`mergeBlockAttrs` (preserving other attrs).

**Justify + RTL.** A line containing a tab is NOT justify-stretched (`justifyUnits`
returns it unchanged — the tab advances already position content to the stops, matching
Google Docs). The advance is computed in logical-inline coordinates and projected
logical→physical by the inline-block axis map, so RTL tabs advance toward the inline-end.

**Leaders** paint in the canvas renderer's inline-block branch when `inlineMeta.leader
!= "none"`: dots/dashes/a baseline rule across the tab's advance in the text color.

**Named follow-ups:** ruler UI for setting/dragging stops; `word-break`-style bar tabs;
a locale-configurable decimal separator; per-tab-segment justification; editing tab
stops on a paragraph inside an embed/template body (the `SET_TAB_STOPS` handler is
main-tree-only in v1).

## Font metrics

The shaper provides per-font-style ascent, descent, x-height, and
line-height values used by the IFC for baseline alignment and by the
painter for glyph positioning. Font fallback (when the requested font
doesn't have glyphs for some codepoints) is the shaper's responsibility
— the engine sees only the resolved metrics.

## Tokenization vs shaping

Two-level processing:

1. **Tokenization** (`text-tokenize`, in the layout module) partitions
   inline content into `Token`s — wrap-units with shared style and
   break-opportunity semantics. Each token comes from one render-node
   run.

2. **Shaping** (the shaper interface, called by the IFC) takes a token
   and produces glyph positions, cluster boundaries, and break
   opportunities for that token. The IFC pre-shapes tokens before
   packing into lines so wrap decisions have widths to work with.

## The legacy measurer

A simpler `TextMeasurer` interface exists in the codebase (width-only:
"how wide is this string in this style?"). It's a sunset path retained
for backwards compatibility while consumers migrate to `TextShaper`.
New code uses `TextShaper`; the engine internally adapts a measurer
to a degraded shaper when only a measurer is available.

## Reference

### `TextShaper` interface

```ts
interface TextShaper {
  shape(
    text: string,
    style: Readonly<ComputedStyle>,
    baseDirection: Direction,
  ): ShapedRun;

  measureFontMetrics(style: Readonly<ComputedStyle>): FontMetrics;
}
```

A single `TextShaper` instance is shared across all shape calls in an editor's lifetime. It must be stateless across calls (or maintain only internal caches that don't affect output).

### `ShapedRun`

```ts
interface ShapedRun {
  readonly text: string;
  readonly computedStyle: Readonly<ComputedStyle>;

  readonly clusters: readonly Cluster[];

  readonly ascent: number;
  readonly descent: number;
  readonly lineGap: number;

  readonly minClusterInlineSize: number;        // widest single cluster (paragraph min-content input)
  readonly unbreakableRunInlineSize: number;    // total run inline-size with no breaks (max-content sum input)

  readonly breakOpportunities: readonly BreakOpportunity[];
  readonly bidiLevel: number;                   // 0 = LTR, 1 = RTL, ... (UAX #9)
}
```

### `Cluster`

```ts
type GlyphId = number;

interface Cluster {
  readonly start: number;            // UTF-16 code-unit offset, inclusive
  readonly end:   number;            // UTF-16 code-unit offset, exclusive
  readonly inlineAdvance: number;    // px advance through this cluster
  readonly isLigature: boolean;      // multi-codepoint → one glyph
  readonly glyphs: readonly GlyphId[]; // opaque IDs passed to painter
}
```

A `Cluster` is a **UAX #29 extended grapheme cluster** — one user-visible
character: a base codepoint plus its combining marks, a surrogate-pair emoji, an
emoji ZWJ sequence, or a regional-indicator flag pair are each ONE cluster. The
cursor never lands inside a cluster. Grapheme segmentation runs through
`graphemeClusters` (`layout/graphemes.ts`, an `Intl.Segmenter`-backed walk), which
the mock shaper and `segmentClusters` (feeding the canvas shaper and the
per-cluster paint loop) share. (The legacy `measurerToShaper` adapter, used only
when a host supplies a bare `TextMeasurer` rather than a `TextShaper`, remains
per-code-unit — a `TextMeasurer` exposes only a total width, so per-grapheme
advances are not recoverable from it.)

`start`/`end` are **UTF-16 code-unit offsets that SPAN the grapheme**
(`end - start` is the grapheme's code-unit count, e.g. 2 for a surrogate-pair
emoji). Graphemes are a clustering concept layered over a code-unit address
space: **state offsets stay UTF-16 code units** — a `Cluster` does not introduce a
separate grapheme-ordinal address space. Cursor movement, selection, and deletion
are already grapheme-correct independently (the cursor module steps over whole
graphemes), so they consume cluster boundaries without any code-unit/grapheme
translation layer.

`inlineAdvance` is the cluster's contribution to the run's total inline-size, and
is **one base width per grapheme** — combining marks add 0 to the advance. Real
complex-script glyph metrics (HarfBuzz-quality positioning of marks, ligatures,
and contextual forms) are out of scope; the v1 advance approximation is
`Intl.Segmenter` grouping plus a per-cluster `measureText` (canvas backend) or
fixed mock width.

### `BreakOpportunity`

```ts
interface BreakOpportunity {
  readonly clusterIndex: number;     // code-unit offset; break is BEFORE this position
  readonly kind: "hard" | "soft" | "hyphen";
}
```

`clusterIndex` is a **UTF-16 code-unit offset**, not a grapheme ordinal — it
indexes the same code-unit address space as `Cluster.start`/`end` and state
offsets.

- `hard` — forced break (newline in `pre`/`pre-wrap`/`pre-line`, end of run).
- `soft` — UAX #14 wrap point, computed by the `layout/uax14` classifier (after a space, between CJK ideographs, etc.); never across `GL` glue such as NBSP.
- `hyphen` — within-word break point where the IFC inserts a hyphen glyph at the line end if it splits here. Produced two ways: a shaper MAY report it from a hyphenation dictionary (`hyphens: auto` — future), and the IFC synthesizes it from authored U+00AD SOFT HYPHENs under `hyphens: manual`/`auto` (the engine's mock/canvas shapers classify U+00AD as `kind:"soft"`, so the manual path does not rely on the shaper emitting `kind:"hyphen"`).

### `FontMetrics`

```ts
interface FontMetrics {
  readonly ascent: number;       // top of glyphs to baseline
  readonly descent: number;      // baseline to bottom of glyphs
  readonly lineGap: number;      // recommended spacing between lines
  readonly capHeight: number;    // for vertical-align: text-top
  readonly xHeight: number;      // for vertical-align: middle
}
```

Returned by `measureFontMetrics(style)` for the line-height calculation; also embedded in every `ShapedRun` for the run's specific font.

### Tokenization (`text-tokenize.ts`)

```ts
function tokenize(text: string, whiteSpace: WhiteSpace): string[];
```

Partitions a text string into wrap-units. Whitespace handling per `whiteSpace` mode:

| `whiteSpace` | Behavior |
|---|---|
| `normal`, `nowrap` | Trim text; collapse runs of whitespace to single space; alternate word / space tokens. |
| `pre`, `pre-wrap`, `break-spaces` | Preserve all whitespace; emit `LINE_BREAK` sentinel between newline-separated segments. `break-spaces` additionally emits each preserved space as its OWN token (not slurped into the preceding word), so spaces are distinct wrap units. |
| `pre-line` | Per-line: collapse whitespace within each line; insert `LINE_BREAK` between lines. |

The IFC consumes the resulting array, looking up each token's shaped width and break opportunities via the shaper.

**Hard-break embed (`<br>`) — a forced break that is NOT a newline character.** A `<br>` decodes to an inline EMBED (`embedType` `HARD_BREAK_EMBED_TYPE`): a zero-width, child-less inline-block whose presence the IFC recognizes via the box's `metadata.embedType` — the same metadata hook the `"tab"` embed uses, requiring no `<br>`-specific token type. On that recognition the IFC emits an `isLineBreak` token (width 0, one source unit = one cursor stop), structurally identical to the `LINE_BREAK` sentinel a `\n` produces in `pre`/`pre-wrap`/`pre-line` — so the text before and after the embed land on two visual lines without splitting the block (distinct from a paragraph boundary, which IS a block split). A **terminal** forced break (a hard break or `\n` with no content after it) opens an empty trailing line that the caret-after-the-break attaches to; this is the same mechanism that gives `pre-line` text ending in `"A\n"` its visible empty final line.

**Trailing-space HANG + CLAMP (the editor's `break-spaces` body default).** Matching Google Docs, a trailing space at a soft-wrap boundary HANGS rather than wrapping: in the IFC greedy wrap loop a *space* unit never triggers its own wrap (only word / inline-block units wrap), so a lone trailing space stays at the line end and only the next *word* wraps. A hung space is then CLAMPED — its laid-out box `inlineOffset`/width are pinned to the line's content edge (the fit cursor still advances by the natural width, so a following word still wraps), and the caret resolver clamps within each leaf's own box — so for *any* number of trailing spaces no glyph and no caret is placed past the content edge (the property the reverted `pre-wrap` hang lacked). The per-space state offsets are unchanged (each space is still one character); only the physical x stops at the edge. This is an intentional word-processor deviation from literal CSS `break-spaces` (which wraps each space) — principle 7 over principle 6 for this editing-shape question.

### Implementation choices for the canvas backend

The default canvas-shaper is described in [`2.7-canvas-shaper.md`](../2-print/2.7-canvas-shaper.md). Key implementation choices:

- **Glyph positioning + advance widths.** Browser canvas `measureText` and `fillText` — delegates to the browser's underlying shaper (HarfBuzz on Chrome / Firefox).
- **Cluster boundaries (UAX #29).** `Intl.Segmenter` with `granularity: "grapheme"` (via `graphemeClusters`) groups codepoints into extended grapheme clusters — base + combining marks, surrogate-pair emoji, ZWJ sequences, and regional-indicator flags. Each cluster's `inlineAdvance` is one per-cluster `measureText` (combining marks add 0); spanning grapheme metrics from a full shaper are out of scope for v1.
- **Bidi levels (UAX #9). [PARTIAL]** The full algorithm engine ships in `layout/uax9/` (`resolveBidiLevels` + `reorderVisual`, 100% conformant — see "Unicode algorithm responsibilities" above), but the shaper backend does NOT yet call it: `shape()` still emits a single uniform level per shaped run, derived from the run's base direction. Threading `resolveBidiLevels` into per-cluster level assignment (and `reorderVisual` into the IFC's per-line reorder) is P4-B/P4-C.
- **Break opportunities (UAX #14). [IMPLEMENTED]** `shape()` calls `toBreakOpportunities` — the canonical adapter (in `layout/text-shaper.ts`) over the `layout/uax14` classifier `lineBreakOpportunities`, a hand-rolled conformant rule engine on a committed line-break property table — for whitespace-, punctuation-, and CJK-aware breaks (mandatory→`hard`, soft→`soft`). All three shaper backends route through this one adapter so the kind-mapping can't drift. Manual hyphenation (authored U+00AD) is wired in the IFC, not the shaper (see Hyphenation below); dictionary `auto` hyphenation is the injected `Hyphenator` (Liang algorithm in `@taleweaver/print`, pattern data in `@taleweaver/hyphenation-<lang>`), also IFC-side.
- **Hyphenation.** Manual hyphenation (`hyphens: manual`, authored U+00AD soft hyphens) is IMPLEMENTED end-to-end via the IFC producer + `tryHyphenSplit` — see the [Hyphenation](#hyphenation) section. Dictionary-driven `auto` hyphenation is IMPLEMENTED: the injected `Hyphenator` capability (`LayoutConfig.hyphenator`; interface + mock in `layout/hyphenator.ts`), the `language` + `hyphenateLimitChars` cascade properties, the IFC auto producer arm that calls the hyphenator under `style.hyphens === "auto"` + a declared language, and the concrete Liang hyphenator algorithm (`createLiangHyphenator(languages)`) in `@taleweaver/print` fed per-language `PatternSet` data from `@taleweaver/hyphenation-<lang>` packages (`en-us` shipped), injected by the host — NOT exposed via the shaper (the `BreakOpportunity` `kind:"hyphen"` is a legacy/optional channel the IFC also merges, but the auto path does not depend on it). The canvas shaper already zero-advances U+00AD so the manual path measures correctly.
- **Font fallback chain.** Browsers manage fallback automatically when the requested font lacks glyphs; the canvas shaper's `fillText` benefits from this transparently. Custom font fallback (for non-browser hosts) is a separate concern.

### Mock backend

`createMockShaper(charWidth, lineHeight)` returns a deterministic `TextShaper` for tests:
- Every cluster has the same `inlineAdvance`.
- Cluster boundaries are UAX #29 grapheme boundaries (via `graphemeClusters`), so a surrogate-pair emoji or a base+combining-mark sequence is one cluster with `charWidth` advance, not one per code unit.
- Break opportunities come from the real `layout/uax14` classifier (the same one the canvas shaper uses), so the mock wraps after spaces, between CJK ideographs, etc. — not a bespoke "every space" heuristic.
- Bidi level is always 0.
- Font metrics are derived from `charWidth` and `lineHeight`.

### Performance contracts

- `shape(text, style)` cold: O(L) where L is `text.length`.
- The shaper may cache per-`(text, style)` calls internally; downstream consumers (IFC) further cache via `IFCStateCache` so repeated paragraphs don't re-shape.
- `tokenize`: O(L).
