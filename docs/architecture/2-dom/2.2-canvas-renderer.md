# 2.2 — `canvas-renderer`

The canvas renderer paints a `LayoutBox` tree onto a `<canvas>`. It is
the only module in `dom` that calls drawing APIs directly. It has two
entry points (`paintCanvas` for single-canvas, `paintPage` for
per-page) that share most of the same paint logic.

## Inputs

Both entry points take:

- A `CanvasRenderingContext2D` to draw into.
- The `LayoutBox` to paint (the document root for `paintCanvas`, a
  page box for `paintPage`).
- Selection rectangles (pre-computed by `core`'s
  `computeSelectionRects`).
- Cursor position + cursor state (`active` / `inactive` / `hidden`).
- Visible viewport bounds (top, bottom in canvas pixels) for
  viewport culling.
- An optional `ImageCache` for async-loaded image resources.
- An optional `PaintCache` for incremental paint.

`paintCanvas` additionally takes the canvas's logical width and height
for full-clear fallbacks. `paintPage` infers those from the page box.

## Output

The list of dirty rectangles painted in this pass. The host can ignore
the return value or use it for diagnostics; the canvas itself is
mutated as a side effect.

## Paint algorithm

Two paths, selected by whether a `PaintCache` was supplied.

### Incremental path (cache supplied)

1. **Walk for dirty.** Call `walkAndDetectChanges` to compare each
   layout box's paint-input hash against the cached one and accumulate
   the rectangles of boxes whose hashes differ. The walk's first action
   is a root short-circuit: if the layout tree's root is reference-equal
   to the previously walked one, the walk returns immediately with no
   dirty regions and no per-box hashing.

2. **Skip if nothing dirty.** If the dirty list is empty, return without
   touching the canvas. This is the fast path for cursor moves where
   layout didn't change.

3. **Clear dirty regions only.** For each dirty rect, `ctx.clearRect`.

4. **Repaint the entire tree on top.** Walk the layout tree top-down
   and call `paintBox` per box, with viewport culling: each box's
   `paintBox` early-returns if the box lies entirely outside the
   visible viewport. The repaint is full because per-box compositing
   isn't yet implemented; clearing only dirty rects but repainting all
   visible boxes preserves correctness when a child's repaint would
   otherwise overlap a parent's stale background.

5. **Paint cursor.** Draw the caret rectangle if the cursor state is
   `active` or `inactive`; skip when `hidden`.

### Non-incremental path (no cache)

1. Clear the entire canvas.
2. Paint selection rectangles.
3. Paint the layout tree (with viewport culling).
4. Paint cursor.

This is the fallback when a host doesn't supply a cache. Used by
unit tests and in degraded modes.

## Per-box drawing

`paintBox` dispatches on `box.type`:

- **`text-run`** — set font, fill style; draw the text content at the
  box's baseline via `fillText`. The font string is built from the
  computed-style font fields once per box and cached via a `lastFont`
  optimization to avoid redundant assignments.

- **`block` / `line` / `inline`** — draw background (if any), then
  borders (each side independently using the used-style border-width),
  then recurse into children.

- **`marker`** — draw the marker text (bullet, digit, or roman) at the
  marker's position using the line's font.

- **`table`, `table-row`, `table-cell`** — draw cell backgrounds and
  borders (border-collapse logic compresses adjacent borders),
  then recurse.

- **`page` (if pagination is active)** — draw page background, page
  margins, then recurse. Headers and footers are children of the page
  box and paint via the normal path.

- **Images** — text-run boxes carrying image metadata draw via
  `drawImage` once the underlying image has finished loading (the
  image-cache module signals when it's ready and triggers re-paint).

## Viewport culling

`paintBox` early-returns when `absY + box.height < visibleTop` or
`absY > visibleBottom`. The bounds are passed in by the controller. The
culling propagates: skipping a parent skips its entire subtree. For
multi-page documents, only visible pages paint.

## Why the renderer is in `dom`

Drawing depends on canvas APIs. `core` doesn't know about canvases.
Putting the renderer in `dom` lets `core` stay platform-agnostic — a
non-browser host (Node.js for PDF rendering, native for desktop) can
implement its own renderer against the same `LayoutBox` tree without
touching anything in `core`.
