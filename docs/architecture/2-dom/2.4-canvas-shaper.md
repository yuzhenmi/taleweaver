# 2.4 — `canvas-shaper`

The canvas shaper is the default `TextShaper` implementation that ships
with `dom`. It produces shaped runs for the engine's IFC and painter by
delegating glyph rendering and metrics to the browser's canvas API,
supplemented with the engine's own Unicode-algorithm code for cluster
boundaries, bidi levels, and break opportunities.

## Construction

`createCanvasShaper(canvas) → TextShaper`. The host instantiates one
shaper per editor and passes it as `EditorConfig.measurer`. The shaper
holds a reference to a canvas's 2D rendering context — used internally
to call `measureText` and to read font metrics.

A single shaper instance can serve many shape calls; it has no
per-string state.

## What it does

For each `shape(text, computedStyle, options)` call, the shaper:

1. **Resolves the font.** Builds the canvas font string from the
   computed-style font fields (`fontStyle fontWeight fontSize fontFamily`)
   and assigns it to the context.

2. **Measures glyph advances.** Calls `measureText(text)` on the
   context. The browser's underlying text shaper (HarfBuzz on Chrome
   / Firefox, CoreText on WebKit) does the heavy lifting — handling
   ligatures, kerning, contextual forms, and font-feature-settings
   honored by the OS.

3. **Computes cluster boundaries (UAX #29).** Walks the input string
   to identify grapheme clusters — base codepoints with combining
   marks, emoji ZWJ sequences, regional indicator pairs. Each cluster
   maps to one cursor stop and is treated as atomic for line-break
   decisions.

4. **Computes bidi levels (UAX #9).** Determines the bidi level per
   cluster from the script and the surrounding context's base
   direction. Outputs uniform-direction runs as a single level; mixed-
   direction runs (Hebrew embedded in English, Arabic in Latin) get
   per-cluster levels for the IFC's reorder pass.

5. **Computes break opportunities (UAX #14).** Walks the text and
   identifies positions where line wrap may occur — after spaces,
   after hyphens, before/after CJK characters, etc. Hyphenation
   opportunities (within-word breaks) come from a per-language
   dictionary when the `hyphens` style + the document language
   request them.

6. **Reads font metrics.** Ascent, descent, x-height, line-height —
   read from the `TextMetrics` object the canvas returns. Used by the
   IFC for baseline alignment.

The output is a `ShapedRun` containing positioned glyphs (with
advances), cluster boundaries, bidi levels, break opportunities, and
font metrics — the engine's IFC and painter both consume from this
single representation.

## What it doesn't do

The canvas shaper does not implement a HarfBuzz integration in
JavaScript. It relies on the browser's native shaper for the actual
glyph positioning. This means:

- **Latin and most European scripts** render correctly because the
  browser handles them well via canvas.
- **Arabic, Hebrew** render correctly because the browser shapes them
  for `fillText`; the shaper's bidi work makes them flow correctly in
  multi-script lines.
- **Indic, complex emoji ZWJ sequences** may render imperfectly at
  cluster boundaries that the canvas's shape grouping doesn't expose
  cleanly. A future plan can ship a `@taleweaver/shaper-harfbuzz`
  package that bundles HarfBuzz-WASM for cases where canvas falls
  short; the engine consumes either backend through the same
  `TextShaper` interface without modification.

## Hyphenation dictionaries

Hyphenation is language-dependent and dictionary-driven. The shaper
loads a dictionary (e.g., Knuth-Liang patterns) per declared document
language and generates within-word break opportunities for each word
when the `hyphens` style requests them. Loading is async; until the
dictionary lands the shaper falls back to no-hyphenation.

## Font fallback

When a glyph isn't available in the requested font, the browser's
canvas falls back to a configured font chain. The shaper sees the
final advance widths post-fallback and exposes them; the engine
doesn't need to know about the fallback chain itself.

## Why this is the default

A canvas shaper is the cheapest path to a working engine in a browser:
no WASM bundle, no font fetching, no integration work. It's good enough
for the dominant document use cases (Latin and CJK with Hebrew/Arabic
supported via the browser's bidi-capable shaper) and gives the engine
correct cluster, bidi, and break behavior even when the underlying
glyph shaper is opaque.

When richer shaping is needed, the same engine accepts a different
implementation — the contract is the `TextShaper` interface, not the
canvas-specific implementation.
