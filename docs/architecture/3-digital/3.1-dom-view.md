# 3.1 — `dom-view` (read-only DOM viewer)

The read-only DOM viewer renders a document `State` into real DOM elements that
the **browser** flows to any width. It is the seed of the dual-mode engine's
DIGITAL-view brick: where the print/PDF backend computes pixel geometry itself
(pages, fragmentation, footnote slots), the digital view hands the browser a
styled element tree and lets the browser's own layout engine reflow it
continuously to the container width.

Both modes are fed by the **same styled tree** — the `render()` →
`cascadePass()` output the print layout engine also consumes — so the viewer
proves the load-bearing **styled-tree → DOM** seam without re-deriving the
document's logical shape or its cascade.

## Why it lives in `digital`, not `core`

`core` is platform-agnostic and must not depend on DOM APIs. The viewer creates
real `Element`/`Text` nodes through a `Document`, so it lives in
`packages/digital`, where a `Document` is available (the browser at runtime;
jsdom under the test env). The pipeline's upstream halves — `render()` and
`cascadePass()` — are pure `core` functions the viewer imports; `digital`'s
contribution is the node-walk that materializes the styled tree into DOM.
`digital` imports `core` only — it pulls in none of `print`'s geometric layout
engine.

## Public surface

```ts
export function renderDocumentToDom(
  state: State,
  componentRegistry: ComponentRegistry,
  attrRegistry: AttrRegistry,
  doc: Document,
  options?: RenderDocumentToDomOptions,
): HTMLElement;

export function renderNodeToDom(node: RenderNode, doc: Document, stamp?: boolean): Node | null;

export function computedStyleToInlineStyle(cs: ComputedStyle): string;

export interface RenderDocumentToDomOptions {
  readonly suggestionView?: SuggestionView;
  readonly stampBlockIds?: boolean; // the digital controller passes true → data-block-id on every block element
}
```

## Pipeline

`renderDocumentToDom` runs three stages:

1. `render(state, componentRegistry, attrRegistry, …)` produces the styled tree
   (pre-cascade `RenderNode`s).
2. `cascadePass(root)` resolves and populates `computedStyle` on every node.
3. `renderNodeToDom(root, doc)` recursively walks the cascaded tree, emitting one
   DOM node per styled node.

It returns the root `HTMLElement`. The document root component is `display:block`,
so the walk yields a single `<div>`; the entry point wraps any fragment/null edge
case so the `HTMLElement` return contract always holds.

## Node → DOM mapping

`renderNodeToDom` dispatches on node type. An `ElementBox` maps to a tag by
**first-match** on its metadata flags, then — when no flag matches — on the
cascaded `computedStyle.display` (always the cascaded value, never the pre-cascade
`style.display`):

- `headingLevel` → `<h1>`…`<h6>`
- `horizontalLine` → `<hr>`
- `image` → `<img src width height alt>` (alt defaults to `""`)
- `blockType: "section"` or `display: contents` → **unwrap** (emit children into a
  fragment; the box has no tag of its own)
- otherwise by `display`: `list-item` → `<li>`, `table` → `<table>`,
  `table-row` → `<tr>`, `table-cell` → `<td>`, `inline`/`inline-block` →
  `<span>` (inline-block also gets an explicit `display:inline-block`), `none` →
  skip (returns `null`), generic block/flow-root/fallback → `<div>`.

A `TextBox` maps to an HTML-escaped text node (created via `createTextNode`, so
the browser escapes it) wrapped inside-out by inline-markup tags it carries:
optional style `<span>`, then `<s>` (line-through), `<u>` (underline), `<em>`
(italic), `<strong>` (bold), and finally a `<a href>` when the run carries a link
whose URL passes the export-safe scheme filter (`isExportSafeLinkUrl`) — an
unsafe-scheme link drops the `<a>` but keeps the text.

## Empty-line filler

A line-hosting block with no inline content (an empty paragraph/heading/list-item
— the blank line left by pressing Enter) gets **no line box** from the browser →
zero height → the blank line is invisible and the caret cannot land in it. So
`fillEmptyLineHost` gives an empty line-hosting block (`display`
`block`/`flow-root`/`list-item`/`table-cell`) a marked filler `<br
data-tw-empty-line>`. Emptiness is decided by **content**, not child-node count:
an empty paragraph renders as a `<div>` holding an empty styled `<span>` (it
carries the cascaded `white-space` etc.), which still has no line box — so the
block is filled when it has no text **and** no replaced/embed content, and
`replaceChildren` drops the empty styled span so the block holds exactly the
filler. A block that hosts a **nested block** (a `[data-block-id]` child — e.g. a
table-cell wrapping an empty paragraph) is excluded, so its real block children
are never wiped (the empty leaf paragraph inside gets the filler instead);
structural containers (`table`/`table-row`) and inline boxes are excluded by
`display`. This is the digital analog of the paginated path's empty-line strut,
and the same trailing-`<br>` trick contenteditable editors (ProseMirror/Lexical)
use. The selection bridge measures the filler as **zero** content units and pins
the caret BEFORE it (`offset 0`), so content offsets are unaffected and the caret
never lands on a phantom second line
([`3.2-digital-controller.md`](./3.2-digital-controller.md)).

## Styling

`computedStyleToInlineStyle(cs)` maps a node's cascaded `ComputedStyle` to an
inline `style=""` declaration string, emitting **only** properties that differ
from `INITIAL_COMPUTED_STYLE` (writing-mode, direction, color, background, font,
text-decoration, alignment, line-height, white-space, text-indent, letter/word
spacing, text-transform, `list-style-type`, and the box-model). The keyword
`list-style-type` forms map to the matching CSS keyword; the custom `{ content }`
marker maps to a CSS `<string>` value (escaped). Logical box-model sides
(`marginInlineStart`, `paddingBlockEnd`, the four logical border edges, …) map to
**physical** CSS sides (`top`/`right`/`bottom`/`left`) via `resolveLogicalSides`,
so RTL and vertical-writing-mode documents render correctly when the browser
flows them. `applyStyle` writes the declaration onto the element (merging with any
display hint already set).

## Lists

Consecutive `display:list-item` sibling nodes that carry `list` metadata
(`level`, `listId`, `ordered`) group into nested `<ul>`/`<ol>` via a level-stack,
mirroring the string-based `encodeListRun` in the HTML serializer. A new list
container opens when the `listId` changes or the nesting `level` increases (so two
adjacent but distinct lists stay separate, and deeper levels nest inside the last
`<li>` of the shallower level). Any non-list child ends an open list run. Each
`<li>` carries the list-item's own cascaded block style (text-align, line-height,
the structural indent gutter via `padding-inline-start`, writing-mode, paragraph
spacing, inherited color) — applied like every other element box.

**The marker is engine-owned, not browser-native.** The digital view does NOT lean
on the browser's `<ol>`/`<ul>` native marker (which a host stylesheet's
`list-style: none` would silently kill, and whose `list-style-position` + the
browser's own `<ul>` padding double up with the engine indent and hang the marker
OUTSIDE the content boundary). Instead the `<ul>`/`<ol>` reset their native list
furniture (`margin: 0; padding: 0; list-style: none`) and each `<li>` renders the
engine's resolved `markerText` — the SAME cascaded `computedStyle.markerText` the
paginated BFC reads, a bullet glyph or a formatted number (`"1."`/`"v."`) that
already encodes the document's format AND ordinal (start/restart/continue) — as an
explicit `<span data-tw-marker contenteditable="false">` positioned absolutely in
the gutter (`inset-inline-start: 0`). The marker is generated content with ZERO
cursor stops: the selection bridge treats `data-tw-marker` exactly like the
empty-line filler (`measure` returns 0, every offset walk skips it), so it never
shifts content offsets. This unifies digital list rendering with print (both
markerText-driven) and is robust to host CSS. A non-contiguous level jump (e.g.
level 0 then level 2)
clamps to the deepest currently-open level so the deeper list nests under the last
open item rather than escaping to the root (graceful degradation for malformed
input).

## `suggestionView` option

The viewer forwards `options.suggestionView` to `render()`, letting a consumer
choose the tracked-changes view (`"suggesting"`, the default) or the clean view
(`"final"`). This is the same `SuggestionView` axis the rest of the engine uses;
the viewer does not add change-tracking logic of its own.

## Out of scope

These are deliberate boundaries — print/page apparatus or separate features, NOT
reduced-MVP cuts of the viewer:

- **Pagination / page breaks / multi-column fragmentation** — the browser flows
  the content continuously; there are no engine-computed pages in this view.
- **Headers / footers** — page apparatus, not body content.
- **Footnote BODIES** — the anchor superscript still renders inline (it is part of
  the body's inline content); the collected bodies belong to the paginated view.
- **The accessibility tree** — the existing `dom-mirror` owns the AT projection.

The interactive `contenteditable` editing controller — input adaptation, DOM
reconciliation, and browser-`Selection` ↔ `Position` bridging — is implemented
in the `editor-digital/` sub-package of `@taleweaver/digital` and documented in
[`3.2-digital-controller.md`](./3.2-digital-controller.md). It is a separate
module from this read-only viewer.

### Documented limitation: `display` is not emitted

`computedStyleToInlineStyle` does NOT emit a `display` declaration — tag choice
carries display intent instead. A consequence: a node whose cascaded display is
`flow-root` renders as a `<div>`, which is HTML-default `block`, dropping the
BFC-establishing hint. This is acceptable for a flowing read-only view (this scope
has no floats or `clear`), and is recorded here as a known gap rather than a
silent one.
