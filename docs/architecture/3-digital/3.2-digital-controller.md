# 3.2 — `editor-digital` (the interactive contenteditable controller)

Where [`3.1-dom-view.md`](3.1-dom-view.md) is the **read-only** DOM viewer,
`editor-digital/` is the **interactive editing backend**: a `contenteditable`
controller that drives the same `core` document and keeps a live DOM in sync with
it. It is the digital peer of `print`'s canvas editor controller — same `core`
brain, same `EditorAction` editing model, but the **browser** owns caret geometry
and flow instead of an in-engine layout pass.

## `createDigitalController`

```ts
function createDigitalController(options: DigitalControllerOptions): DigitalController

interface DigitalControllerOptions {
  readonly container: HTMLElement;            // the contenteditable host
  readonly componentRegistry: ComponentRegistry;
  readonly attrRegistry: AttrRegistry;
  readonly containerWidth?: number;
  readonly pageConfig?: PageConfig;
  readonly doc?: Document;                    // for tests / multi-document hosts
  readonly initialDocument?: State;              // seed (else an empty document)
  readonly onChange?: (state: EditorState) => void;  // change notification
  readonly extensions?: EditorExtensions;     // host commands / keymap / input rules / triggers
  readonly onIncompatibleDocument?: (report: IncompatibleDocumentReport) => void; // HALTED (see below)
  readonly onDocumentCompatible?: () => void;  // while halted, the document was upgraded (by a peer or this host)
}

interface DigitalController {
  readonly editorState: EditorState;          // always-current (getter)
  readonly halted: boolean;                   // halted on incompatible (legacy) document storage
  dispatch(action: EditorAction): void;
  replaceDocument(state: State): void;        // show another document (fresh history, caret at start); resumes a halted controller
  runCommand(command: string | Command): boolean; // host command by name or value
  readonly version: State;                    // current document version (opaque)
  mapPosition(position: Position, version: State, assoc?: Assoc): MappedPosition | null;
  createAnchor(from: Position, to?: Position, options?: AnchorOptions & { basedOn?: State }): Anchor | null;
  propose(proposal: Proposal, options?: { basedOn?: State }): Promise<ProposeResult>; // host proposal → one suggestion group; resolves at once with the reducer's verdict ("controller destroyed" after destroy)
  setSuggestionStyles(styleOf: SuggestionGroupStyle | null): void; // live per-group suggestion styling (1.9)
  suggestionRects(suggestionId: SuggestionId): DOMRect[]; // a suggestion's non-empty text client rects (none inside a glyph) + each of its ¶ glyph rects, once
  focus(): void;
  destroy(): void;
}
```

The controller holds the `EditorState` internally. Every transition — whether a
host's programmatic `dispatch` or a user gesture — funnels through one private
`dispatch(action)`:

    editorState = reduceEditor(editorState, action)
    reconciler.reconcile(prev, editorState, isComposing)   // update the DOM
    if (editorState !== prev) onChange?.(editorState)        // notify the host

`onChange` lets a host (e.g. a React toolbar) mirror the controller's state and
re-render on input-driven edits the host can't otherwise observe; it fires only
on a real transition. Hosts must NOT call `dispatch` re-entrantly from inside
`onChange` (it is not re-entrant).

**Document replacement.** `replaceDocument(document)` swaps in another document (or a
fresh Document over the same Y.Doc): a fresh `EditorState` (fresh `History` — the old one
is destroyed — and the caret at the document start), the mapping log restarted (older
versions no longer map), anchors advanced through an unknown transition, EVERY
decoration layer and the find session dropped (the host sets them again), the
remote-change subscription re-created afresh (even on the same Y.Doc), a full DOM
rebuild, and one `onChange`.

**HALTED.** A peer update carrying legacy inline storage (1.5 "Incompatible
documents") halts the controller — every controller subscribes for this shape check,
including one with `remoteChanges: "ignore"` (which only does not apply peer changes):
`halted` turns true, `onIncompatibleDocument({ legacyBlocks })` is called once per halt
(and again, while still halted, when legacy storage returns after `onDocumentCompatible`
was reported),
`contenteditable` is switched off, an in-flight IME composition is abandoned (the
reconciler's `restore()` re-materializes the DOM from the last RENDERED tree — no
document read — dropping the composed text; a later `compositionend` is dropped the
same way), input (beforeinput, keys, selection changes, composition commits, paste) and
every further remote change are ignored, and the last good render stays. Every member
has a defined result without touching the Y.Doc: `dispatch` → ignored; `editorState` /
`version` / `decorations` → the last good values; `mapPosition` / `createAnchor` →
null; `propose` → `{ ok: false, reason: "halted" }`; `runCommand` → false; `findStart`
/ `findNext` / `findPrev` / `findStatus` / `replaceActive` / `replaceAll` → the empty
status; `findClose` → no-op; `setDecorations` / `set*Highlights` / `clear*Highlights` /
`setSuggestionStyles` → no-ops; copy / cut → an empty clipboard; `focus` / `destroy`
work. While halted the subscription re-checks the known legacy blocks plus the touched
ones on every transaction (local ones included) and calls `onDocumentCompatible()` once
the document is upgraded (by an upgraded peer or by this host). Exit:
`replaceDocument` with a Document over the upgraded document — a fresh Document over the same
Y.Doc (`createDocument({ rootId, doc, resolver })`) or another document. Every `replaceDocument`,
halted or not, checks the Document for legacy storage first (O(blocks); legacy storage can
land between `createDocument` and the call): a Document whose document holds legacy storage
the watch never saw (not halted yet, another document, or a local write after
`onDocumentCompatible`) is refused — the current editor is kept, the controller halts
(or, already halted, reports again if the host was told "compatible") and watches that
document halted (its upgrade is reported). The new `EditorState` is built before the old `History` is destroyed, so a
failing build leaves the editor intact.

## Input adaptation — native events → `EditorAction`

The controller makes the `container` `contenteditable` and wires native events,
mapping each to a geometry-free `EditorAction` the shared `core` reducer consumes.
It `preventDefault()`s **only the gestures it handles** so the ENGINE owns those
document edits, not the browser's default contenteditable mutation — an inputType
that maps to no action (e.g. `insertTranspose`, `formatJustify*`) falls through to
native handling rather than becoming a silently-cancelled no-op:

- **`beforeinput`** → `mapBeforeInput(e, { selection, domToPosition })` — maps the
  event's `getTargetRanges()` (via the selection bridge) + `inputType` to an
  insert / delete `EditorAction` (with an internal `dataTransfer` fallback for the
  `insertText` case where `e.data` is null — Safari dictation). `insertParagraph`
  (Enter) → `SPLIT_NODE`; `insertLineBreak` (Shift+Enter) → `INSERT_LINE_BREAK`, a soft
  break inside the paragraph, as print's Shift+Enter binding. `preventDefault()`
  fires inside the `action !== null` branch only. The `insertFromPaste` inputType
  is a special case: the controller `preventDefault()`s it (to suppress the native
  mutation) but does **not** dispatch — the `paste` ClipboardEvent handler is the
  single paste source, so mapping here too would insert the text twice.
  `insertFromDrop` (which has no ClipboardEvent peer) is still mapped to `PASTE`.
  The `replace` inputs (`insertReplacementText`, e.g. autocorrect) are a two-step:
  the mapped action deletes the replaced range, then the controller dispatches a
  follow-on `INSERT_TEXT` of `replacementInsertText(e)` (the exported helper that
  returns `e.data`, falling back to `dataTransfer["text/plain"]` when `e.data` is
  null).
- **`keydown`** → first the HOST keymap (`runKeyBinding(extensions, e, modConvention,
  …)`, skipped while composing — the IME owns Enter etc.): a command that runs, or an
  unbound (`null`) key, preventDefaults and stops (the keymap is compiled at creation, so
  a malformed binding throws then). Escape is claimed only when `escapeWouldChange`
  (object selection / active trigger), else it reaches the page. Then `mapDigitalKey(e, { mac,
  inListItem })` — a THIN direct-key map:
  the NON-navigation chords digital dispatches (bold/italic/undo/…) plus a few
  direct keys (`Escape` → `ESCAPE`). **Tab is context-sensitive** (Google Docs,
  mirroring `print`'s `mapKeyEvent`): the controller reads `editorState` to set
  `inListItem` (focus block is a `list-item`). In a list-item, Tab / Shift+Tab nest
  / un-nest the list (`LIST_INDENT` / `LIST_OUTDENT`); outside one, Tab inserts a
  tab (`INSERT_TAB`) and Shift+Tab is a no-op (Google Docs has no body-text
  reverse-tab). It returns `null` for every nav key (arrows / Home / End / PageUp /
  PageDown), every plain printable key, and Backspace / Delete / Enter — the
  **browser** owns caret movement and `beforeinput` owns insertion/deletion. It
  deliberately does NOT reuse `print`'s `mapKeyEvent` (which returns a geometric
  `NavIntent` and transitively imports layout — that would break the
  `digital ↛ print` boundary).
- **`selectionchange`** → read the DOM selection through the bridge and dispatch
  `SET_SELECTION`, guarded by `selectionsEqual` so a no-op DOM-selection echo does
  not re-enter the reducer.
- **`compositionstart` / `compositionend`** — IME composition: hold reconciliation
  during composition, commit the composed text on end (guarding against a null
  `CompositionEvent.data`, which a cancelled composition can deliver). Typed and
  committed text is dispatched as `INSERT_TEXT { userInput: true }` (beforeinput
  `insertText`, replacement text, composition commits), so host input rules and
  triggers fire on it — and only after composition ends.
- **Collaboration** — the controller subscribes to its document's Y.Doc
  (`subscribeRemoteChanges`) and applies every peer update synchronously as
  `APPLY_FOREIGN_CHANGE` (selection rebased; decorations, anchors, triggers and the
  mapping log advanced; only the dirty blocks re-rendered), re-subscribing whenever the
  document's Y.Doc changes. The dispatch runs synchronously from Yjs `afterTransaction`
  (inside the provider's `Y.applyUpdate`), so an `onChange` handler must not forward
  updates to the provider from inside it (or must defer). `remoteChanges: "observe" |
  "ignore"` (default observe): exactly one controller per document observes. While an
  IME composition is active the DOM selection is never written (the reconciler skips
  `positionToDom`); `compositionend` re-projects the rebased selection. Anchors / versions: see
  [`1-core/1.9-decorations.md`](../1-core/1.9-decorations.md) "Anchors".
- **`copy` / `cut` / `paste`** — rich clipboard via the same three-flavor pipeline
  as the print controller (`extractFragment(document, selection)`, so
  `copy: "drop"` marks never leave the editor): `copy`/`cut` write `text/plain` (`extractText`),
  `text/html` (`encodeHtml`), and `TALEWEAVER_CLIP_MIME` (`encodeFragmentClip`) in
  the synchronous `ClipboardEvent` handler; `paste` reads all three flavors and
  dispatches `PASTE { text?, html?, clip? }`. The format-priority policy (clip →
  html → text) runs inside `handlePaste` in core. `browserHtmlParser` from
  `digital/src/editor-digital/html-parser.ts` is injected into
  `EditorConfig.htmlParser` (digital ships its own DOM-adapter file — symmetric in
  function to `@taleweaver/print`'s `html-parser.ts` — so `digital` does not import
  `print`). The `paste` ClipboardEvent handler remains the **single** paste source;
  the follow-on `beforeinput(insertFromPaste)` is suppressed so a paste dispatches
  exactly once.
  **Paste without formatting (Ctrl/Cmd+Shift+V):** a `keydown` handler calls
  `navigator.clipboard.readText()` asynchronously and dispatches `PASTE { text }` —
  core's `handlePaste` falls straight to the plain-text line path. Graceful no-op on
  unavailable secure context or denied permission.

## The reconciler — `EditorState` diff → DOM mutations

`createDigitalReconciler(componentRegistry, attrRegistry, doc)` owns the DOM:

```ts
interface DigitalReconciler {
  mount(container: HTMLElement, initial: EditorState, decorations?: DecorationSet): void;
  reconcile(prev: EditorState | null, next: EditorState, isComposing: boolean, decorations?: DecorationSet): void;
  getBridge(): DigitalSelectionBridge | null;   // the SINGLE bridge it owns (null before mount)
  hasPending(): boolean;                        // DOM left stale under an IME composition
  destroy(): void;
}
```

`mount` materializes the whole styled tree into DOM (`render()` → `cascadePass()` →
the viewer's styled-tree walk, `data-block-id` stamped per block, decorations drawn) and
records what it rendered (`Document`, `RenderOutput`, cascaded root, decoration set). It
maintains `blockElMap`, the authoritative `BlockId → HTMLElement` index the bridge uses.

`reconcile` is **incremental** whenever `next.lastDirtyIds` is set: `render()` runs with
`{ prev, prevDocument, dirtyIds }` and `cascadePassIncremental` reuses unchanged styled
subtrees by reference. The reconciler then walks the previous and next cascaded trees
together, descending only into nodes whose identity changed (or that lead to a block
whose decorations changed — `changedDecorationBlocks` — or that an IME deferral left
stale). Each container's children are grouped into **DOM units** — a block's element; a
run of list-items as ONE top-level `<ul>/<ol>` (split where a level-0 item belongs to a
different list, exactly as the viewer groups them); an unwrapped section /
`display:contents` box contributes its children's units — and patched by key:

- a changed **leaf** block is re-rendered through `renderBlockToDom` and swapped in;
- a changed **container** keeps its element when its own shell (display, metadata,
  inline CSS) is unchanged and recurses; otherwise it is re-rendered;
- a list run with the same item keys and list structure patches changed `<li>`s in
  place (carrying nested sub-lists over); a structurally changed run is re-rendered;
- new units are rendered and inserted, removed units detached, and the container's unit
  elements put in order. Old unit elements are resolved before any patching so a key
  re-registered by a re-render (paragraph → list-item) never hides the stale element.

When a changed container keeps the same child keys and every changed child is a plain
block or a list-item whose list placement is unchanged, the children are patched in
place without grouping units. Cost per keystroke is therefore one reference comparison
per child of each container on the changed path — for the document root that is
O(top-level blocks), pointer compares only — plus the changed blocks' DOM. Selection-only transitions do no
DOM work; a state change without a dirty set (document replaced) does a full rebuild.
The incremental result is DOM-identical to a full render (a randomized equivalence test
over edits, lists, tables, undo/redo and decoration churn enforces this).

**IME guard.** A unit containing the block under an active composition is never
rebuilt. A deferred leaf/list-item is re-rendered on the next cycle that is not blocked
by a composition; when the conflict is STRUCTURAL (a removed unit, a restructured list
run around the composed block) the whole parent container is rebuilt instead (the root
via a full rebuild), so no stale element survives. The controller redraws on
`compositionend` when only deferred work is pending.

## Decorations

The controller owns a core `DecorationLayers` (see `1-core/1.9-decorations.md`):
`setDecorations(decorations, basedOn?)` replaces the host layer (`basedOn` = the Document
the host computed them against; mapped through later edits via the controller's
`MappingLog`, dropped if unmappable); `setFindHighlights` /
`setCommentHighlights` / `setSuggestionHighlights` (+ `clear*`) set the built-in layers
(same API as the print controller). Every dispatch advances the layers through the
transition (host, find and comment layers mapped by position mapping; comments re-resolved
only when a marker is added/removed, suggestions when an edit touches a tracked run) and
the reconciler draws `layers.merged`; `controller.decorations` exposes the mapped host
layer. Drawing (`dom-view/decorate-dom.ts`, applied to each stamped block as it is
rendered):

- **inline** → each covered text node — and each covered inline embed, whole (one offset
  unit) — is wrapped in `<span data-tw-deco="id">` carrying
  the class, host attributes (engine-owned names — `data-tw-*`, `data-block-id`,
  `data-inline-embed`, `contenteditable`, `class`, `style`, `on*` — are refused) and the
  engine visual as CSS (`background-color`, `text-decoration-*`);
- **widget** → `<span data-tw-widget="<side>" data-tw-deco contenteditable="false">`
  holding the host's `toDom(doc)` node or `text`, placed right after the text unit ending
  at its offset (inside that run's formatting spans, OUTSIDE any decoration wrappers);
  widgets at one offset are ordered side `-1` then `1`. Zero offsets for the bridge; the
  bridge puts a caret at the offset after side `-1` widgets, and the controller hops the
  DOM caret over widgets on the inline-axis arrows so no keypress is dead. Host visuals go
  through the CSSOM (`style.setProperty`) and attribute names are validated, so a
  decoration can neither inject declarations nor throw mid-render;
- **block** → class / attributes / background applied to the block element and its ids
  listed in `data-tw-block-deco` (updated in place for containers).

**Find / replace.** `findStart(query, options)` / `findNext` / `findPrev` / `findClose`
/ `findStatus` / `replaceActive` / `replaceAll` — the same contract as the print
controller, driven by core's geometry-free `createFindSession` (find from the caret,
wrap, re-find in the edited blocks after every edit while open — redrawing only those
blocks' highlights via `patchFind`, ids `tw-find:<block>:<offset>` — and replace via
`REPLACE_MATCH` / `REPLACE_ALL`).
Matches draw as find-highlight decorations; the active one is scrolled into view with the
browser's `scrollIntoView`. The caret never moves. Find highlights are ONE layer:
`setFindHighlights` / `clearFindHighlights` write it directly, `findStart` takes it over
(the session re-finds into it after every edit while open), and `findClose` clears it.

**Pointer events** (`decoration-pointer.ts`, enabled by `onDecorationPointer`): delegated
`mouseover` / `mouseleave` / `click` on the container resolve every decoration between
the event target and the container — inline wrappers, widgets, and the block decorations
of the target's block and its ancestor blocks (overlaps all report) — and emit `enter` /
`leave` / `click` with the live decoration (looked up through its block), the hovered
fragment's rect, and every fragment's client rects. A hovered decoration the host
removes reports `leave` with its last-known snapshot.

## The selection bridge — DOM ⟷ core `Position`

`createDigitalSelectionBridge(root, win, blockElementLookup?)` is the coordinate
translator between the browser's `Selection`/`Range` and core's `{ blockId, offset }`
positions:

```ts
interface DigitalSelectionBridge {
  readonly root: HTMLElement;
  domToPosition(node: Node, nodeOffset: number, edge?: "start" | "end"): Position | null;  // DOM point → core
  readDomSelection(): Span | null;                                  // live selection → core Span
  positionToDom(selection: Selection): void;                        // core selection → DOM
}
```

**Object blocks in a range** (rule, image, TOC, table — a range covers one whole; see
1-core 1.1-state "span-iteration"): `positionToDom` maps an object endpoint `(obj, 0)`
to just BEFORE the object's element at the range start and just AFTER it at the range
end, so the native highlight covers it. `domToPosition` takes the endpoint's `edge`: a
point on an object maps to `(obj, 0)`; a point between blocks maps to the first block
at or after it as a range start, the last block before it as a range end (never a
container position). A native drag into a table cell arrives as an ordinary
`SET_SELECTION`; core lifts it to the table and the DOM is re-projected.

It resolves the enclosing `data-block-id` element and measures UTF-16 units within
it (a `Text` node contributes its length, an inline embed `[data-inline-embed]`
contributes 1, generated content — list markers `[data-tw-marker]`, decoration
widgets `[data-tw-widget]`, END anchors `[data-tw-generated]` — contributes 0, a
container is the sum; a point inside a ¶ anchor maps to `(block, len)`), so the digital
offset model matches core's UTF-16 offsets exactly. A structural marker (bookmark /
comment) is never a caret stop: `domToPosition` normalizes every point through
core's `caretAfterMarkers` against the rendered state, so a point just before markers
stands after them, as print's hit-test does. On `selectionchange` a collapsed caret after
a ¶ anchor is normalized to before it (`normalizeCaret`). Because the browser still gives
each marker embed and END anchor a caret stop, the inline-axis arrows — for the focus
element's computed `writing-mode`, ArrowLeft / ArrowRight when horizontal, ArrowUp /
ArrowDown when vertical (ArrowRight / ArrowDown forward; `direction: rtl` reverses it) — and their Shift forms (a plain arrow over a range is left
to the browser; block-axis keys never hop) first move the DOM caret past
them in the direction of travel (`hopMarkers`, from the model focus): backward to before
the markers on its left (core `caretBeforeMarkers`), forward to after them, or past the
¶'s END anchors when the focus is at the ¶'s end — so the native move advances one real
character or leaves the ¶, never a dead press. Then the widget hop runs.

**Selected ¶ (`selected-paragraphs.ts`).** Every ¶ the selection covers — start ≤
`(P, len)` and end ≥ `(N, 0)`, i.e. the text blocks from the start's block up to, not
including, the end's — is drawn selected at P's END anchor (3.1), because the browser's
native `::selection` does not paint block ends uniformly. The covered set is H(anchor
block) XOR H(focus block) (H(b) = every text block from b on), so a selection change
toggles exactly the blocks between the old and new anchor and between the old and new
focus, walked from the old endpoint in both directions until the new one: O(changed
blocks) per selection change — extending a 100-page selection by one line touches one ¶.
A walk that would cancel out over a long distance (a far click) is cut off after
2·|selected| + 2·|changed blocks| + 64 steps and replaced by a reset (clear what is drawn,
draw the new covered set). A document change of known extent — `EditorState.lastChange`
made from the Document last synced, a local edit or a peer's — does the same endpoint walks
(skipping its changed blocks), then re-judges only the changed blocks: walking back from
each to the nearest unchanged (or already judged) text block q, a changed text block is
covered iff q is, flipped once per endpoint passed. Each block is walked once, so a peer's
keystroke or Enter inside a 100-page selection costs O(changed blocks), never the
selection. A previous endpoint whose block the change removed is not walked from: its
position maps to the deletion's seam, so the blocks between it and the new endpoint are
the removed ones, and the new endpoint's block is re-judged with the changed blocks — a
peer deleting the anchor's paragraph also costs O(changed blocks). Only a change of
unknown extent, or anchor and focus in different selection contexts re-derive the covered set (a
model walk over the selection); either way only blocks whose state differs are touched. The reconciler reports every
(re)mounted block element (`onBlockMounted`), and a re-rendered selected block gets its
indicator again.

**One bridge per controller.** The reconciler creates the bridge on `mount` and the
controller reuses it via `reconciler.getBridge()` for its `domToPosition` /
`readDomSelection` needs — there is no second bridge. The reconciler threads its
`blockElMap` into the bridge as the optional `blockElementLookup`, so `positionToDom`
resolves `blockId → element` through an O(1) map lookup (keeping the per-keystroke
selection re-projection O(1)) instead of an O(n) `[data-block-id]` scan of `root`.
A standalone bridge built with no lookup falls back to that scan.

## Boundary: `digital ↛ print`

The whole module imports `core` only — never `print`. Caret geometry, hit-testing,
and line navigation are the **browser's** job in digital mode (the user clicks and
arrows through real DOM); the controller never computes a positioned box. The key
mapper's refusal to reuse print's `NavIntent` mapper is the load-bearing
expression of that boundary: digital ships no layout engine
([`overview.md`](overview.md)).
