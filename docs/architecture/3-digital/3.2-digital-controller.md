# 3.2 — `editor-digital` (the interactive contenteditable controller)

Where [`3.1-dom-view.md`](3.1-dom-view.md) is the **read-only** DOM viewer,
`editor-digital/` is the **interactive editing backend**: a `contenteditable`
controller that drives the same `core` document and keeps a live DOM in sync with
it. It is the digital peer of `print`'s canvas editor controller — same `core`
brain, same `EditorAction` editing model, but the **browser** owns caret geometry
and flow instead of an in-engine layout pass.

## `createDigitalController`

```ts
function createDigitalController(options: DigitalControllerOptions): DigitalController

interface DigitalControllerOptions {
  readonly container: HTMLElement;            // the contenteditable host
  readonly componentRegistry: ComponentRegistry;
  readonly attrRegistry: AttrRegistry;
  readonly containerWidth?: number;
  readonly pageConfig?: PageConfig;
  readonly doc?: Document;                    // for tests / multi-document hosts
  readonly initialState?: State;              // seed (else an empty document)
  readonly onChange?: (state: EditorState) => void;  // change notification
}

interface DigitalController {
  readonly editorState: EditorState;          // always-current (getter)
  dispatch(action: EditorAction): void;
  focus(): void;
  destroy(): void;
}
```

The controller holds the `EditorState` internally. Every transition — whether a
host's programmatic `dispatch` or a user gesture — funnels through one private
`dispatch(action)`:

    editorState = reduceEditor(editorState, action, config)
    reconciler.reconcile(prev, editorState, isComposing)   // update the DOM
    if (editorState !== prev) onChange?.(editorState)        // notify the host

`onChange` lets a host (e.g. a React toolbar) mirror the controller's state and
re-render on input-driven edits the host can't otherwise observe; it fires only
on a real transition. Hosts must NOT call `dispatch` re-entrantly from inside
`onChange` (it is not re-entrant).

## Input adaptation — native events → `EditorAction`

The controller makes the `container` `contenteditable` and wires native events,
mapping each to a geometry-free `EditorAction` the shared `core` reducer consumes.
It `preventDefault()`s **only the gestures it handles** so the ENGINE owns those
document edits, not the browser's default contenteditable mutation — an inputType
that maps to no action (e.g. `insertTranspose`, `formatJustify*`) falls through to
native handling rather than becoming a silently-cancelled no-op:

- **`beforeinput`** → `mapBeforeInput(e, { selection, domToPosition })` — maps the
  event's `getTargetRanges()` (via the selection bridge) + `inputType` to an
  insert / delete `EditorAction` (with an internal `dataTransfer` fallback for the
  `insertText` case where `e.data` is null — Safari dictation). `preventDefault()`
  fires inside the `action !== null` branch only. The `insertFromPaste` inputType
  is a special case: the controller `preventDefault()`s it (to suppress the native
  mutation) but does **not** dispatch — the `paste` ClipboardEvent handler is the
  single paste source, so mapping here too would insert the text twice.
  `insertFromDrop` (which has no ClipboardEvent peer) is still mapped to `PASTE`.
  The `replace` inputs (`insertReplacementText`, e.g. autocorrect) are a two-step:
  the mapped action deletes the replaced range, then the controller dispatches a
  follow-on `INSERT_TEXT` of `replacementInsertText(e)` (the exported helper that
  returns `e.data`, falling back to `dataTransfer["text/plain"]` when `e.data` is
  null).
- **`keydown`** → `mapDigitalKey(e, { mac, inListItem })` — a THIN direct-key map:
  the NON-navigation chords digital dispatches (bold/italic/undo/…) plus a few
  direct keys (`Escape` → `ESCAPE`). **Tab is context-sensitive** (Google Docs,
  mirroring `print`'s `mapKeyEvent`): the controller reads `editorState` to set
  `inListItem` (focus block is a `list-item`). In a list-item, Tab / Shift+Tab nest
  / un-nest the list (`LIST_INDENT` / `LIST_OUTDENT`); outside one, Tab inserts a
  tab (`INSERT_TAB`) and Shift+Tab is a no-op (Google Docs has no body-text
  reverse-tab). It returns `null` for every nav key (arrows / Home / End / PageUp /
  PageDown), every plain printable key, and Backspace / Delete / Enter — the
  **browser** owns caret movement and `beforeinput` owns insertion/deletion. It
  deliberately does NOT reuse `print`'s `mapKeyEvent` (which returns a geometric
  `NavIntent` and transitively imports layout — that would break the
  `digital ↛ print` boundary).
- **`selectionchange`** → read the DOM selection through the bridge and dispatch
  `SET_SELECTION`, guarded by `selectionsEqual` so a no-op DOM-selection echo does
  not re-enter the reducer.
- **`compositionstart` / `compositionend`** — IME composition: hold reconciliation
  during composition, commit the composed text on end (guarding against a null
  `CompositionEvent.data`, which a cancelled composition can deliver).
- **`copy` / `cut` / `paste`** — rich clipboard via the same three-flavor pipeline
  as the print controller: `copy`/`cut` write `text/plain` (`extractText`),
  `text/html` (`encodeHtml`), and `TALEWEAVER_CLIP_MIME` (`encodeFragmentClip`) in
  the synchronous `ClipboardEvent` handler; `paste` reads all three flavors and
  dispatches `PASTE { text?, html?, clip? }`. The format-priority policy (clip →
  html → text) runs inside `handlePaste` in core. `browserHtmlParser` from
  `digital/src/editor-digital/html-parser.ts` is injected into
  `EditorConfig.htmlParser` (digital ships its own DOM-adapter file — symmetric in
  function to `@taleweaver/print`'s `html-parser.ts` — so `digital` does not import
  `print`). The `paste` ClipboardEvent handler remains the **single** paste source;
  the follow-on `beforeinput(insertFromPaste)` is suppressed so a paste dispatches
  exactly once.
  **Paste without formatting (Ctrl/Cmd+Shift+V):** a `keydown` handler calls
  `navigator.clipboard.readText()` asynchronously and dispatches `PASTE { text }` —
  core's `handlePaste` falls straight to the plain-text line path. Graceful no-op on
  unavailable secure context or denied permission.

## The reconciler — `EditorState` diff → DOM mutations

`createDigitalReconciler(componentRegistry, attrRegistry, doc)` owns the DOM:

```ts
interface DigitalReconciler {
  mount(container: HTMLElement, initial: EditorState): void;
  reconcile(prev: EditorState | null, next: EditorState, isComposing: boolean): void;
  getBridge(): DigitalSelectionBridge | null;   // the SINGLE bridge it owns (null before mount)
  destroy(): void;
}
```

`mount` materializes the initial styled tree into DOM (the same
`render()` → `cascadePass()` → styled-tree walk the read-only viewer uses, with
`data-block-id` stamped per block) and projects the initial selection into the DOM.
It also maintains `blockElMap`, an authoritative `BlockId → HTMLElement` index kept
in lockstep with the live DOM across reconciles.
`reconcile(prev, next, isComposing)` diffs the two
`EditorState`s and applies the minimal DOM mutations for the changed blocks
(indexed by `BlockId`), then re-projects the editor selection back into the live
DOM. For each dirty block it: **replaces** its element when the block exists on
both sides (the common typing case, O(dirty)); **collects** NEW blocks (no dirty
ancestor to re-render them) for insertion; and **detaches** the old element when
the block was REMOVED and no dirty ancestor will drop it. The collected new blocks
are then placed at a **fixpoint** — repeatedly sweeping the pending set and
inserting any whose anchor (`parentId` + `prevSiblingId`) is now live in
`blockElMap`, until none remain (falling back to a full rebuild if an anchor never
resolves). The fixpoint orders a RUN of consecutive new siblings (a multi-line
paste) correctly regardless of dirty-set iteration order: the run's head anchors on
an existing block, each subsequent block on the just-placed one. The insert/detach
paths matter because a mid-document split (Enter), merge (Backspace), or pasted run
only dirties the parent when the FIRST/LAST child changes — a structural change
between two existing siblings leaves the parent clean, so the new block(s) reach the
DOM only through these positional inserts (without them they land in state but never
the DOM). A new/removed block that DOES have a dirty ancestor is realized by that
ancestor's wholesale replace instead. During IME composition it defers DOM rewrites
so it does not fight the browser's composition.

## The selection bridge — DOM ⟷ core `Position`

`createDigitalSelectionBridge(root, win, blockElementLookup?)` is the coordinate
translator between the browser's `Selection`/`Range` and core's `{ blockId, offset }`
positions:

```ts
interface DigitalSelectionBridge {
  readonly root: HTMLElement;
  domToPosition(node: Node, nodeOffset: number): Position | null;  // DOM point → core
  readDomSelection(): Span | null;                                  // live selection → core Span
  positionToDom(selection: Selection): void;                        // core selection → DOM
}
```

It resolves the enclosing `data-block-id` element and measures UTF-16 units within
it (a `Text` node contributes its length, an inline embed `[data-inline-embed]`
contributes 1, a container is the sum), so the digital offset model matches core's
UTF-16 offsets exactly.

**One bridge per controller.** The reconciler creates the bridge on `mount` and the
controller reuses it via `reconciler.getBridge()` for its `domToPosition` /
`readDomSelection` needs — there is no second bridge. The reconciler threads its
`blockElMap` into the bridge as the optional `blockElementLookup`, so `positionToDom`
resolves `blockId → element` through an O(1) map lookup (keeping the per-keystroke
selection re-projection O(1)) instead of an O(n) `[data-block-id]` scan of `root`.
A standalone bridge built with no lookup falls back to that scan.

## Boundary: `digital ↛ print`

The whole module imports `core` only — never `print`. Caret geometry, hit-testing,
and line navigation are the **browser's** job in digital mode (the user clicks and
arrows through real DOM); the controller never computes a positioned box. The key
mapper's refusal to reuse print's `NavIntent` mapper is the load-bearing
expression of that boundary: digital ships no layout engine
([`overview.md`](overview.md)).
