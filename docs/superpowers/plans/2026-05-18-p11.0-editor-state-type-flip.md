# P11.0 — EditorState Type Flip + Document-Construction Migration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Flip `EditorState.state` from legacy `StateNode` to new `State` (Y.Doc-backed). Introduce dual representation per Decision D: both `state: State` and `stateLegacy: StateNode` carried on `EditorState`, with `stateLegacy` canonical during the parallel window and `state` rebuilt from it via `rebuildStateFromLegacy` after each legacy action. Wrap `EditorState.history` with the Y.UndoManager-backed `History` (decision C/D point 9), delegating to `historyLegacy` during parallel. Provide a `legacy-position-bridge.ts` with the four conversion helpers. Editor still wires the legacy renderer + cursor pipeline; cutover comes at P11.4.

**Architecture:**
- `EditorState` gains: `state: State`, `stateLegacy: StateNode`, `historyLegacy: EditorHistory`, while `history: History` switches from legacy snapshot-based to the wrapper class shipped at `state/history.ts`.
- After every legacy action handler runs (mutates `stateLegacy`), the reducer calls `rebuildStateFromLegacy(stateLegacy): State` to refresh `state`. BlockIds are path-derived via `pathToBlockId` (already shipped in `state/path-to-block-id.ts`) so selection paths translate directly to BlockIds. `state` is throwaway and rebuilt each action; renderer continues to consume `stateLegacy` for now.
- `editor/legacy-position-bridge.ts` provides `legacyPositionToNew`, `newPositionToLegacy`, `legacySelectionToNew`, `newSelectionToLegacy`. Used by P11.x handlers as they migrate.
- Selection field on `EditorState` stays legacy `Position`-by-path until P11.3 migrates it.

**Tech Stack:** TypeScript, Vitest, existing Y.Doc-backed state types + the History wrapper class (both already shipped).

```typescript
import type { StateNode } from "../state/state-node-legacy";
import { createState, type State } from "../state/state";
import { runTransaction, getBlocksMap } from "../state/yjs-doc";
import { buildYBlock } from "../state/y-block";
import { pathToBlockId } from "../state/path-to-block-id";
import type { InlineContent, InlineItem, TextItem } from "../state/inline-content";
import type { BlockId } from "../state/block-id";

export function rebuildStateFromLegacy(legacy: StateNode): State {
  const rootId = pathToBlockId([]);
  const state = createState({ rootId });
  runTransaction(state.doc, () => {
    const yBlocks = getBlocksMap(state.doc);
    walk(legacy, [], null, null, null, yBlocks);
  });
  return state;
}

// Helper: walk a StateNode at the given `path` with parent/prev/next
// context. Container nodes recurse into children. Leaf-of-tree nodes
// (paragraph, heading, etc.) collect inline content from their text/span
// children. text and span nodes are leaf inline contributors (not
// blocks).
function walk(
  node: StateNode,
  path: readonly number[],
  parentId: BlockId | null,
  prevSiblingId: BlockId | null,
  nextSiblingId: BlockId | null,
  yBlocks: Y.Map<Y.Map<unknown>>,
): void {
  // ... determine block kind (container/leaf) by inspecting children types
  // ... if container: recurse, wire up firstChild/lastChild/sibling links
  // ... if inline-bearing leaf (paragraph/heading): collect inline content
  //     from text/span descendants
  // ... set the block via yBlocks.set(blockId, buildYBlock({...}))
}
```

The key logic decisions:
- A StateNode is "container" if its children are blocks (paragraphs, lists, etc.). It maps to a Container block with `inlineContent: null`.
- A StateNode is "inline-bearing leaf" if its children are text/span (the legacy model uses text/span StateNodes inside paragraph/heading). It maps to a Leaf block with populated `inlineContent.items` collected by walking text/span descendants.
- text/span StateNodes themselves do NOT become blocks — they're collapsed into the parent leaf's inline content.

Read `packages/core/src/state/state-node-legacy.ts` and the legacy factory helpers in `state/create-node-legacy.ts` for the StateNode shape (especially `type` field values and `properties` shape for text content / span styles).

For inline collection: iterate the inline-bearing leaf's children. Each text StateNode becomes a `TextItem` with `text: node.properties.content`, `attrs: {}` (or accumulated span attrs if wrapped). Each span StateNode contributes its style attrs to its inner text children's attrs. Use `mergeAdjacentTextItems` from `state/inline-content.ts` after collection to normalize.
