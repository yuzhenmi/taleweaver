# P11.0 — EditorState type flip + document-construction migration

**Subject:** Flip `EditorState.state` field from `StateNode` to the new `State` type. Migrate document-construction (`createEmptyDocument`, `createInitialEditorState`). Keep the existing render call alive via a bridge so the old render pipeline still runs. Do NOT touch `EditorState.selection` (still legacy Position-by-path; selection migration is P11.3) and do NOT migrate any action handlers (those are P11.1+).

**Reference:** Strategy doc Decision 4 + round-1/round-4 fixes; master spec migration step 10b prereq.

## Goal

Action handlers in P11.1+ require `EditorState.state` to already be the new `State` type. P11.0 lands that prerequisite type flip in one focused phase before family-by-family handler migration begins. After P11.0, `EditorState.state` holds the Yjs-backed `State` (per decision C) and any caller using `editorState.state` gets the new type.

The render call in `createInitialEditorState` continues to operate during P11.0 — either by a bridge that converts new `State` → legacy `StateNode` for render input, or by P11.0 carrying both representations during the editor's transition window. Render-pipeline rewiring is the responsibility of P11.1+ (per-handler) or defers to P12 (layout/styles cleanup).

History collapse (decision C) is bundled into P11.0: `EditorState.history: EditorHistory` flips to `History` (the Yjs UndoManager wrapper). Legacy `Change`-based history is retired. Action handlers in P11.1+ call `pushHistoryEntry` directly.

## Dependencies

P4 (Layer 3 ops) — needed for `createEmptyDocument` to produce a `State`. ONLY P4. P11.0 does NOT need P9 (no action handlers calling cursor ops yet) or P7/P8 (no render rewire).

## Key technical considerations

1. **`createEmptyDocument`.** Legacy version returns `StateNode`. New version (`createEmptyDocumentNew` or whatever from `new-initial-state.ts`) returns `State`. P11.0 routes through the new version. May need to export it from index.ts.

2. **`Change` and history.** Legacy `Change` wraps StateNode. Two paths:
   - (a) Migrate `Change` to wrap `State` in P11.0 (touches editor-state.ts, change.ts, history.ts, all undo/redo handlers).
   - (b) Defer `Change` migration to P11.x action family migrations (each handler migrates its own change-creation).
   - Probably (a) for atomicity — flip `EditorState.state` AND `EditorState.history` consistently. But this risks scope creep. Plan decides.

3. **Selection field NOT touched.** Per round-4 strategy fix: `EditorState.selection` stays on legacy `Position`-by-path. Action handlers in P11.1/P11.2 will read selection (legacy type) and produce new `State` mutations. The cursor module continues to handle selection via legacy types until P11.3 selection action family migrates it.

4. **TypeScript will catch every mismatch.** Once `EditorState.state` flips, every consumer that uses `editorState.state` needs updating. That's a LOT of consumers — but most can be temporarily satisfied by passing through to legacy code via the bridge. The plan should expect 20-30+ TypeScript errors when the flip happens, and methodically resolve them.

5. **Test pass criterion.** After P11.0, the editor still functions end-to-end (open document, see something rendered). Action handlers still work via legacy paths. Selection still works via legacy paths. Only the `EditorState.state` field's type and document-construction has changed.

## Risks and patterns to apply

- **TypeScript scoping discipline.** When flipping a load-bearing type, do it in a tight commit so the breakage window is minimal. Resolve all errors in one focused effort. Don't batch unrelated changes.
- **Browser smoke critical.** Pixels could break in many ways during this flip. Smoke-test before declaring done.
- **Implementer escalation:** if any consumer of `editorState.state` requires a substantive migration that's not "use the bridge to convert to legacy" — STOP and escalate. Substantive migration belongs to P11.x.
