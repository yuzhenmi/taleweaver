# P11.1 — Editor: inline-text action family

**Subject:** Migrate inline-text action handlers (typing characters, deleting characters, formatting toggles) to use the new `State` and Layer 3 operations. Also depends on P9 cursor types — these handlers call cursor-ops helpers like `moveByCharacter`.

**Reference:** Master spec migration step 10b (split into action families per strategy doc Decision 4).

## Goal

The simplest action family to migrate first. Each handler reads the current `EditorState`, derives an action target from `selection`, calls a Layer 3 op (insertText, deleteRange, applyAttrsToRange, replaceRange) to produce a new state + dirtyIds, and updates `EditorState`.

After P11.1, `insertText`, `deleteBackward`, `deleteForward`, `deleteWord`, `deleteLine`, and `toggleStyle` all use new state + Layer 3 ops.

## Dependencies

- P11.0 (EditorState.state is new `State`).
- P9 (`cursor/cursor-ops.ts` migration) — these handlers call `moveByCharacter`, `moveByWord`, etc.

## Files involved

**Modified (in P11.1):**
- `actions/insert-text.ts` — call Layer 3 `insertText` instead of legacy `transformations.insertText`. Cursor advances via `moveByCharacter`.
- `actions/delete-backward.ts` — call `deleteRange` for collapsed-selection-backspace (deletes 1 char left of cursor); for non-collapsed selection, `deleteRange` over the selection.
- `actions/delete-forward.ts` — similar.
- `actions/delete-word.ts` — `moveByWord` to find boundary, then `deleteRange`.
- `actions/delete-line.ts` — `moveByLine` to find line boundaries, then `deleteRange`. (NOTE: `moveByLine` is P10, not P9. So P11.1 may need to use legacy line-navigation OR depend on P10. Decide in plan.)
- `actions/toggle-style.ts` — `applyAttrsToRange` over selection.
- `actions/paste.ts` — `clonePastedSubtree` + insertion via `insertBlock` (and possibly `replaceRange`).
- `actions/helpers.ts` — review and migrate any helpers used by the above.
- Their `.test.ts` files.

**Untouched in P11.1:**
- Other action families.
- Selection still operates on legacy `Position`-by-path (per P11.0 decision).

## Parallel-window contract (Decision D)

Every migrated handler in this phase MUST follow the contract defined in `decisions.md` decision D points 6, 9, 10. Concretely:

1. Read `selection: LegacySelection` from `EditorState`; convert to `NewSelection` via `legacySelectionToNew(state, selection)`.
2. Run Layer 3 op on `state`, producing new `state'` and new `NewSelection'`.
3. The wrapper computes `stateLegacy' = downgradeToStateNode(state')` and re-projects selection via `newSelectionToLegacy(stateLegacy', NewSelection')`.
4. Push history entry via the `History` wrapper (which routes to `historyLegacy` during parallel by constructing a `Change` from pre/post `stateLegacy` snapshots).
5. Ship a paired equivalence test: same action via legacy handler + via migrated handler against an equivalent starting state; assert resulting `stateLegacy` trees are structurally equal AND selections agree.

The wrapper hides the downgrade-and-reproject sequence from handler code; handler is responsible only for producing `state'` + `NewSelection'`. The paired tests are deleted in the cutover commit at the end of P11.4.

## Key technical considerations

1. **Selection conversion at the handler boundary.** Legacy `Selection` is `Span<LegacyPosition>`. New `Selection` is `Span<NewPosition>`. Handlers convert legacy → new on entry via `legacySelectionToNew` (per the parallel-window contract above); the wrapper handles the return trip. Helpers (`legacyPositionToNew`, `newPositionToLegacy`, `legacySelectionToNew`, `newSelectionToLegacy`) all live in `editor/legacy-position-bridge.ts` and are deleted at cutover.

2. **Dirty-ids consumption.** Layer 3 ops return `dirtyIds: Set<BlockId>`. The editor previously ran a post-hoc dirty-tree comparison (legacy `dirty.ts`). Now it can use `dirtyIds` directly to decide which RenderNodes to invalidate. P11.1's handlers should expose `dirtyIds` to the editor's render-decision logic.

3. **Cursor advancement after `insertText`.** After typing "hello", the cursor moves from position@offset to position@offset+5. Easy to compute. Selection needs to update too — the new `Selection` (still legacy type until P11.3) gets the new cursor position. Conversion at the boundary again.

4. **`deleteLine` line navigation.** Depends on P10 for `moveByLine`. If P10 isn't yet integrated, fallback to legacy `editor/line-navigation.ts` for now (which still works because selection is legacy). When P10 lands, this handler updates.

5. **`paste`** uses `clonePastedSubtree` → produces fresh blocks → caller (action handler) inserts them. The insertion involves `insertBlock` for each cloned block, OR a hypothetical "spliceBlocks" helper. Plan picks the mechanism. Paste is one of the most complex P11.1 handlers.

6. **`toggleStyle`** is `applyAttrsToRange` with an attrs delta. Caller computes whether to toggle on or off based on whether the entire selection currently has the attr. Helper: `selectionAllHaveAttr(state, span, key): boolean`.

## Risks and patterns to apply

- **Browser smoke after each handler migration.** Type characters, backspace, delete, word-delete, undo, paste — verify each works.
- **Test parity.** Each migrated handler needs at least the test coverage its legacy predecessor had. Likely many tests are already in `*.test.ts` files; their fixtures need migration to new types.
- **Math-typo defense.** Per Phase 4 lesson — implementer re-verifies any computed text in tests.
- **Implementer escalation:** if a handler requires functionality not yet provided by Layer 3 ops, STOP and escalate. Don't add unauthorized helpers to the state module.
