# P11.3 — Editor: selection action family

**Subject:** Migrate selection action handlers (cursor movement, hit-testing-driven selection, selection extension) and finally flip `EditorState.selection` field type from legacy `Position`-by-path to new `Position`.

**Reference:** Master spec migration step 10b (action family per Decision 4); also covers spec step 10c partial.

## Goal

After P11.3, the editor's selection field uses the new `Position` type. All cursor-movement and selection-extension handlers operate on new types. The editor's hit-test pipeline (P10) is wired in. Layout-coupled selection rendering (selection-geometry) is consumed.

This is the phase that finally retires legacy `Selection` / legacy `Position`-by-path from the editor.

## Dependencies

- P10 (cursor hit-test + selection-geometry on new types).
- P11.2 (block-structure actions migrated; selection field still legacy).

## Parallel-window contract (Decision D)

P11.3 is the phase that flips `EditorState.selection` from `LegacyPosition` (path-based) to the new `Position` (`{blockId, offset}`). After P11.3:
- Migrated handlers can read selection directly as `NewPosition`; the `legacyPositionToNew` step on entry is gone.
- The wrapper still needs to maintain `stateLegacy` (rebuilds AND downgrades) until cutover, and STILL must populate selection in the form the legacy renderer expects. Two paths:
  - (a) Renderer-cutover happens in the same phase as selection-cutover (P11.3 also cuts over the renderer to consume `state`). Then `EditorState.selection: NewPosition` is read directly by both handlers and renderer.
  - (b) Renderer stays on legacy until cutover. Then `EditorState.selection: NewPosition` is converted to legacy on every render via `newPositionToLegacy(stateLegacy, selection)` and the renderer reads the conversion.
- Recommendation: **path (b)** — keep selection cutover separable from renderer cutover. Selection conversion at the render boundary is a small per-render cost; renderer cutover stays as the closing task of P11.4. P11.3's per-phase plan picks this concretely.

Existing migrated handlers (from P11.1 / P11.2) need a sweep: remove their `legacyPositionToNew` calls (selection is now native new). Paired equivalence tests stay until cutover.

## Key technical considerations

1. **The bridge becomes obsolete.** Once `EditorState.selection` is new, action handlers no longer convert from legacy → new on entry. Search for the bridge utility name and verify no consumers; delete the legacy → new direction. The reverse (`newPositionToLegacy`) stays alive until cutover for renderer consumption per path (b) above.

2. **Layout coupling for `moveByLine` etc.** P10 introduced `cursor/line-navigation-v2.ts` that takes layout-tree input. P11.3 wires the editor handlers to this. Editor must have the layout tree available at action-handler time (it does — `EditorState` already holds the layout artifacts).

3. **Hit-test integration.** UI clicks call `editor/hit-test-v2.ts` to convert (x, y) → Position. P11.3 ensures the editor's input pipeline calls the new hit-test (probably in `react/use-editor.ts` or wherever pointer events are handled).

4. **Selection geometry consumption.** The editor uses selection-geometry to paint highlights. P11.3 wires the new geometry — though "wiring" is mostly type changes (the consumer reads RenderNodes from the layout tree, which is the same shape).

5. **`set-selection` semantics.** Direct selection-set: `set-selection.ts` accepts a `Selection` (now new-type) and writes it to EditorState. Validate that the selection is in-context (per spec lines 254-258 — same selection context for anchor and focus).

## Open questions

2. **Multi-cursor / multi-selection support.** Not in current `EditorState` (single Selection). Out of scope for P11.3 unless something has changed.
